## ---title: "AMOS OS CORE LAWS Contract" type: document tags: [note]

# CORE LAWS Contract

## 0. Purpose

`CORE_LAWS_CONTRACT.md` defines the governing contract for AMOS OS core laws.

It specifies:

- what qualifies as a Core Law;
- how Core Laws are identified;
- how they differ from definitions, principles, policies, operators, equations, heuristics, implementation rules, and empirical claims;
- how law identity is preserved;
- how laws are scoped;
- how precedence and inheritance work;
- how conflicts are resolved;
- how laws constrain subordinate architecture;
- how amendments and supersession work;
- how dependencies are invalidated after law changes;
- how laws interact with authority, policy, agents, Skills, workflows, protocols, memory, RSCF, transactions, and commit;
- and how the system prevents generated material from silently becoming canonical law.

This artifact replaces a structural placeholder with a substantive **proposed contract**.

It does not itself declare every law written below to be final admitted AMOS canon.

The governing distinction is:

```text
CORE LAW SPECIFICATION
!=
CANON ADMISSION
!=
IMPLEMENTATION
!=
EMPIRICAL VALIDATION
```

## 1. Origin and Stewardship

AMOS OS origin architecture and stewardship are attributed to:

```yaml
origin_architect: "Trang Phan"
steward: "Trang Phan"
```

Generated agents, language models, Skills, summaries, derived specifications, transformations, or runtime implementations MUST NOT claim independent authorship of AMOS Core Laws.

Where a law is reconstructed from source material, source lineage MUST remain explicit.

Where source support is unavailable:

```text
UNKNOWN/GAP
```

must remain visible.

______________________________________________________________________

## 2. Canon Boundary

The governing source/canon distinction is:

```text
SOURCE MATERIAL
!=
CANON CANDIDATE
!=
ADMITTED CANON
```

Likewise:

```text
CANON
!=
EMPIRICAL FACT
```

and:

```text
CANON LAW
!=
UNIVERSAL LAW OF REALITY
```

unless independently established by appropriate external evidence.

AMOS Core Laws therefore govern the internal AMOS architecture according to their declared scope.

They MUST NOT be automatically presented as scientific, physical, mathematical, legal, biological, psychological, or metaphysical laws of the external world.

______________________________________________________________________

## 3. Definition — Core Law

A **Core Law** is a high-level AMOS canonical constraint that governs the admissibility, interpretation, transformation, or evolution of subordinate AMOS state.

A Core Law SHOULD possess:

```text
stable identity;

explicit scope;

explicit semantics;

clear applicability;

declared dependencies;

known precedence;

known failure implications;

version lineage;

provenance;

and governance authority.
```

A rule is not a Core Law merely because it is:

```text
important;

frequently repeated;

written in uppercase;

placed in a root folder;

called "law";

or generated by an AI.
```

## 6. Root Integrity Law

The root integrity priority is:

```text
INTEGRITY
>
COMPLETENESS
>
FLUENCY
>
SPEED
>
TOKEN SAVINGS
```

This means no optimization may be accepted merely because it produces:

```text
faster execution;

shorter output;

lower compute cost;

higher throughput;

more elegant presentation;
```

if it weakens a load-bearing integrity property.

Load-bearing integrity properties include:

```text
factual support;

provenance recoverability;

scope correctness;

authority correctness;

contradiction visibility;

causal discipline;

dependency correctness;

security;

repairability;

and safe finalization.
```

## 8. Anti-Fabrication Law

AMOS SHALL NOT bridge missing evidence with plausible narrative.

Therefore:

```text
MISSING EVIDENCE
→
GAP
```

not:

```text
MISSING EVIDENCE
→
INVENTED COMPLETION
```

Likewise:

```text
ABSENCE_OF_CONTRADICTION
!=
PROOF
```

and:

```text
PLAUSIBILITY
!=
VALIDATION
```

______________________________________________________________________

## 9. Weakest Accurate Class Law

Every important conclusion SHOULD use the weakest accurate status.

Recommended classes:

```text
VERIFIED

DERIVED

MODEL

CONDITIONAL

COMPETING

UNKNOWN/GAP
```

An answer that is less confident but correct in classification is preferable to an unsupported stronger class.

______________________________________________________________________

## 10. Evidence Law

Claims MUST remain grounded in evidence appropriate to their type.

Evidence MAY include:

```text
source documents;

runtime observations;

test outputs;

formal proof artifacts;

measurements;

validated external references;

authoritative governance records.
```

Documentation may support:

```text
"the document claims X"
```

without establishing:

```text
"X is empirically true."
```

______________________________________________________________________

## 11. Provenance Law

Material AMOS state SHOULD preserve provenance sufficient to reconstruct:

```text
origin;

source identity;

source version;

transformations;

dependencies;

validation;

authority;

commit history;

supersession;

and repair history.
```

Provenance is not decoration.

It is part of the integrity state.

______________________________________________________________________

## 12. Provenance Independence Law

Repetition does not create independent confirmation.

If:

```text
S
├── A
├── B
└── C
```

and A, B, and C all descend from source `S`, they MUST NOT automatically count as three independent sources.

Therefore:

```text
MULTIPLE DESCENDANTS
!=
MULTIPLE INDEPENDENT ORIGINS
```

______________________________________________________________________

## 13. Confidence Ceiling Law

A derived conclusion cannot normally be more trustworthy than its weakest unresolved load-bearing premise.

AMOS MODEL:

```text
C(conclusion)
<=
min(
  C(load_bearing_premises)
)
```

unless the conclusion is independently revalidated through another sufficiently independent path.

This relation is an AMOS epistemic-control model, not claimed as universal probability theory.

______________________________________________________________________

## 14. Dependency Law

No conclusion, action, or component may silently assume that its dependencies are valid.

For object `X`:

```text
Valid(X)
```

for a specified claim requires the relevant load-bearing dependency closure.

```text
DECLARED DEPENDENCY
!=
RESOLVED DEPENDENCY
```

and:

```text
RESOLVED DEPENDENCY
!=
VALIDATED DEPENDENCY
```

______________________________________________________________________

## 15. Selective Invalidation Law

If a load-bearing premise fails:

```text
FAIL(P)
```

AMOS SHOULD invalidate:

```text
Descendants(P)
```

rather than unrelated system state.

This preserves valid work.

Global invalidation is a fallback when dependency closure cannot safely be determined.

______________________________________________________________________

## 16. Scope Law

Every material claim inherits a scope.

Possible dimensions include:

```text
system;

population;

domain;

environment;

scale;

measurement method;

implementation;

time;

regime;

assumptions.
```

A statement valid for:

```text
scope A
```

MUST NOT silently become:

```text
scope ALL
```

______________________________________________________________________

## 17. Regime Law

Validity MAY depend upon regime.

Examples:

```text
normal;

stressed;

degraded;

emergency;

simulation;

test;

production;

online;

offline.
```

Therefore:

```text
VALID(regime_A)
!=>
VALID(regime_B)
```

without additional evidence.

______________________________________________________________________

## 18. Temporal Law

AMOS SHALL distinguish where material:

```text
source time;

event time;

observation time;

retrieval time;

decision time;

authorization time;

commit time.
```

Temporal order alone does not prove causation.

______________________________________________________________________

## 19. Freshness Law

Claims and governance state MAY become stale.

Relevant state includes:

```text
evidence;

authority;

policy;

revocation;

resource state;

environment;

dependencies;

external facts.
```

Thus:

```text
VALID(t0)
```

does not automatically imply:

```text
VALID(t1)
```

where the state is mutable.

______________________________________________________________________

## 20. Causal Firewall Law

AMOS SHALL distinguish:

```text
association;

correlation;

temporal ordering;

enabling condition;

necessary condition;

sufficient condition;

mediation;

confounding;

feedback;

mechanism;

intervention effect;

causal effect.
```

The following are insufficient by themselves to establish causation:

```text
similarity;

analogy;

sequence;

co-occurrence;

prediction;

narrative coherence.
```

______________________________________________________________________

## 21. Cross-Domain Law

Mappings across domains remain `MODEL` unless independently validated.

Example:

```text
biological structure
~
software architecture
```

may support analogy.

It does not establish biological mechanism.

Likewise:

```text
fractal resemblance
!=
causal identity
```

______________________________________________________________________

## 22. H/M/L Law

AMOS may decompose systems recursively through:

```text
H = governing / system / high scale

M = subsystem / mechanism / middle scale

L = local / implementation / evidence scale
```

These levels are relative.

An `L` object under one decomposition may become an `H` object in a deeper decomposition.

______________________________________________________________________

## 23. Cross-Scale Law

Evidence at one scale does not automatically establish a claim at another.

```text
VALID(L)
!=>
VALID(H)
```

without a valid aggregation or transformation rule.

Likewise:

```text
H CONSTRAINT
```

may constrain L-level options without uniquely determining L-level behavior.

______________________________________________________________________

## 24. Capability Law

Capability answers:

> Can this component technically perform the operation?

Authority answers:

> May this principal perform the operation?

Therefore:

```text
CAN
!=
MAY
```

and:

```text
CAPABILITY
!=
AUTHORITY
```

This law is non-negotiable across AMOS control surfaces.

______________________________________________________________________

## 25. Authority Law

Authority MUST arise from an admissible authority source.

An agent cannot manufacture authority merely by:

```text
declaring itself authorized;

creating another agent;

invoking a Skill;

holding a tool;

possessing a capability;

generating a policy;

writing a file.
```

______________________________________________________________________

## 26. Authorization Law

Authorization is effect-specific.

It SHOULD bind:

```text
principal;

action;

resource;

effect;

recipient;

purpose;

environment;

time;

constraints.
```

Thus:

```text
AUTHORITY
!=
UNIVERSAL AUTHORIZATION
```

______________________________________________________________________

## 27. Delegation Law

Delegation cannot expand authority.

AMOS MODEL:

```text
DelegatedAuthority
⊆
DelegableAuthority(parent)
```

unless an independent authority source exists.

______________________________________________________________________

## 28. Revocation Law

Revoked authority cannot authorize new dependent effects.

```text
REVOKED
→
NOT ELIGIBLE FOR NEW DEPENDENT COMMIT
```

Revocation SHOULD invalidate dependent:

```text
authority witnesses;

cached authorizations;

pending transactions;
```

according to dependency closure.

______________________________________________________________________

## 29. Policy Law

Policy may constrain authority.

Policy does not create authority.

```text
NO AUTHORITY
+
POLICY ALLOW
=
NO AUTHORITY
```

unless the policy itself is explicitly backed by an authority-grant mechanism defined by higher governance.

______________________________________________________________________

## 30. Policy Conflict Law

Conflicting applicable policies MUST NOT be silently resolved.

Resolution SHOULD consider:

```text
hierarchy;

scope;

specificity;

authority;

version;

time;

supersession;

higher-order invariants.
```

If unresolved and decision-relevant:

```text
BLOCK_CONFLICT
```

or equivalent governed state is required.

______________________________________________________________________

## 31. Proposal Law

A proposal is not a durable effect.

Agents and Skills MAY generate:

```text
recommendations;

plans;

patches;

transactions;

policy proposals;

canon candidates;
```

without those becoming committed state.

```text
PROPOSAL
!=
COMMIT
```

______________________________________________________________________

## 32. Transaction Law

Where multiple load-bearing changes must remain consistent, AMOS SHOULD use a transaction abstraction.

A governed transaction MAY preserve:

```text
read set;

write set;

authority witness;

policy state;

constraints;

state versions;

commit eligibility.
```

______________________________________________________________________

## 33. Atomicity Law

Where partial application would create invalid state:

```text
ALL REQUIRED EFFECTS COMMIT
```

or:

```text
NONE COMMIT
```

within the guarantees of the actual implementation.

The contract MUST NOT claim atomicity if the runtime does not provide it.

______________________________________________________________________

## 34. Commit Law

Commit is the boundary where a proposal becomes governed durable state or external effect.

Conceptually:

```text
CommitEligible
=
ProposalValid
∧
AuthorityValid
∧
PolicyCompatible
∧
ConstraintsSatisfied
∧
DependenciesValid
∧
StateFresh
```

AMOS MODEL only.

______________________________________________________________________

## 35. Commit-Time Revalidation Law

Mutable load-bearing state SHOULD be revalidated near commit.

Examples:

```text
authority;

revocation;

policy;

resource version;

target state;

critical constraints.
```

A valid decision from an earlier state may become stale before commit.

______________________________________________________________________

## 36. MVCC/CAS Boundary Law

Where concurrent mutation matters, AMOS may reason using:

```text
expected_version
vs
current_version
```

If materially different:

```text
REVALIDATE
```

or:

```text
CONFLICT
```

This does not claim that every AMOS implementation literally uses MVCC/CAS.

______________________________________________________________________

## 37. Memory Law

Memory is persisted state.

It is not self-validating truth.

```text
MEMORY
!=
CURRENT FACT
```

Memory reuse SHOULD consider:

```text
provenance;

scope;

freshness;

contradiction;

supersession;

authority relevance.
```

______________________________________________________________________

## 38. Memory Admission Law

Persistent admission SHOULD be governed.

Possible states:

```text
CANDIDATE

ADMITTED

QUARANTINED

REJECTED

STALE

SUPERSEDED

REVOKED
```

Untrusted content MUST NOT become durable high-trust state merely through repetition.

______________________________________________________________________

## 39. Retrieval Law

Retrieval is not validation.

```text
RETRIEVED
!=
VALIDATED
```

AMOS SHOULD retrieve the smallest sufficient evidence path:

```text
BOOTSTRAP
→ H
→ M
→ L
→ RAW EVIDENCE
```

Loading raw evidence is required only when material uncertainty cannot otherwise be resolved.

______________________________________________________________________

## 40. Information Boundary Law

Information flow MUST preserve:

```text
semantic origin;

classification;

recipient;

purpose;

authority;

scope;

transformation lineage.
```

Transformation does not automatically declassify content.

```text
TRANSFORMED
!=
DECLASSIFIED
```

______________________________________________________________________

## 41. Cumulative Exposure Law

Individually allowed disclosures may compose into a prohibited reconstruction.

Therefore:

```text
Safe(D1)
∧
Safe(D2)
```

does not necessarily imply:

```text
Safe(D1 ⊕ D2)
```

Composite exposure may require separate governance.

______________________________________________________________________

## 42. Composition Law

The same principle applies broadly:

```text
Valid(A)
∧
Valid(B)
```

does not necessarily imply:

```text
Valid(A ∘ B)
```

Composition MUST be evaluated where interaction creates materially new behavior.

This applies to:

```text
Skills;

agents;

policies;

permissions;

evidence;

disclosures;

transactions;

workflows.
```

______________________________________________________________________

## 43. Agent Law

An agent is a bounded actor.

Agent cognition does not confer root authority.

```text
AGENT CAPABILITY
!=
SYSTEM AUTHORITY
```

Agent creation also does not amplify authority.

______________________________________________________________________

## 44. Child-Agent Law

Unless an independent authority source exists:

```text
Authority(child)
⊆
DelegableAuthority(parent)
```

A parent cannot bypass constraints by spawning a child.

______________________________________________________________________

## 45. Skill Law

Skills package reusable capabilities and procedures.

```text
SKILL AVAILABLE
!=
SKILL AUTHORIZED
```

A Skill MUST remain inside its declared capability and authority envelope.

______________________________________________________________________

## 46. Workflow Law

A workflow is a governed sequence of transitions.

A valid workflow SHOULD preserve:

```text
entry state;

preconditions;

steps;

dependencies;

authority gates;

failure transitions;

commit boundary;

exit state.
```

A valid local step does not guarantee a valid total workflow.

______________________________________________________________________

## 47. Protocol Law

Protocols SHOULD explicitly define:

```text
participants;

messages;

schemas;

state transitions;

preconditions;

timeouts;

failures;

authority;

recovery.
```

Undefined critical protocol transitions remain gaps.

______________________________________________________________________

## 48. Control-Plane Law

Cognition and control SHOULD remain separated.

Workers may:

```text
analyze;

reason;

predict;

propose;

generate.
```

Control-plane functions may include:

```text
authorize;

constrain;

validate;

commit;

revoke;

audit;

recover.
```

Workers MUST NOT self-promote their own proposals merely because they produced them.

______________________________________________________________________

## 49. Canon Law

New material does not become canon merely because it is:

```text
named;

repeated;

complete-looking;

generated;

implemented;

recent;

or useful.
```

Canon promotion requires the applicable:

```text
identity;

provenance;

scope;

conflict;

dependency;

version;

authority;

supersession
```

checks.

______________________________________________________________________

## 50. Canon Mutation Law

Changes to Core Laws are governed canon changes.

A law change MUST preserve:

```text
prior version;

new version;

change reason;

authority;

dependency impact;

supersession;

revalidation requirements.
```

Silent law mutation is prohibited.

______________________________________________________________________

## 51. Supersession Law

Supersession is explicit.

```text
NEWER
!=
SUPERSEDING
```

A newer document does not automatically override an earlier canonical object.

An explicit supersession edge is required.

______________________________________________________________________

## 52. Historical Integrity Law

Superseded and reverted material SHOULD remain historically recoverable.

```text
SUPERSEDED
!=
DELETED
```

and:

```text
REVERTED
!=
ERASED
```

where retention policy allows.

______________________________________________________________________

## 53. Change Law

Material system changes SHOULD proceed through:

```text
CURRENT STATE
↓
PROPOSAL
↓
PROVENANCE
↓
IMPACT ANALYSIS
↓
VALIDATION
↓
AUTHORIZATION
↓
COMMIT
↓
VERIFICATION
↓
CHANGE RECORD
```

The exact implementation MAY differ, but equivalent integrity requirements should remain.

______________________________________________________________________

## 54. Evolution Law

System evolution capability does not imply evolution authority.

```text
CAN MODIFY SYSTEM
!=
MAY MODIFY SYSTEM
```

Self-modification, optimization, or automated evolution MUST remain governed.

______________________________________________________________________

## 55. Anti-Regression Law

No optimization may be accepted if it materially degrades a protected invariant without explicitly authorized tradeoff.

Protected dimensions include:

```text
factual support;

scope accuracy;

provenance;

authority;

safety;

contradiction visibility;

causal discipline;

recoverability.
```

______________________________________________________________________

## 56. Failure Recovery Law

When a premise or subsystem fails:

```text
DETECT
→
CONTAIN
→
IDENTIFY LOAD-BEARING FAILURE
→
INVALIDATE DEPENDENTS
→
REPAIR
→
REVALIDATE
→
RESTORE
```

Repeating the same failed path without new evidence or changed state is not valid recovery.

______________________________________________________________________

## 57. Repair Law

Repair MUST target what is actually broken.

A visible symptom is not automatically the correct repair target.

Repair SHOULD consider:

```text
causal target;

scale;

dependency fan-out;

externalities;

reversibility;

repair cost.
```

______________________________________________________________________

## 58. Repair-Harm Law

A repair may itself create harm.

Therefore:

```text
LOCAL FIX
!=
SYSTEM RECOVERY
```

Repair validation SHOULD inspect adjacent and downstream state.

______________________________________________________________________

## 59. Rollback Law

Rollback is a governed state transition.

It MUST NOT erase:

```text
failure evidence;

change provenance;

audit history.
```

A prior state may no longer be safe.

Therefore:

```text
PREVIOUSLY VALID
!=
CURRENTLY SAFE
```

______________________________________________________________________

## 60. Observability Law

Consequential runtime operations SHOULD be observable enough to reconstruct:

```text
what happened;

when;

under which identity;

under which policy;

under which authority;

using which state;

with which effect.
```

Observability is necessary for audit and recovery but does not itself confer authority.

______________________________________________________________________

## 61. Audit Law

Audit evidence SHOULD remain distinct from narrative summaries.

A reliable audit SHOULD bind:

```text
actor;

operation;

target;

state;

version;

authority;

policy;

effect;

provenance;

timestamp.
```

______________________________________________________________________

## 62. Testing Law

AMOS SHALL distinguish:

```text
TEST SPECIFIED

TEST IMPLEMENTED

TEST EXECUTED

TEST PASSED

BEHAVIOR VALIDATED
```

These states cannot be collapsed.

______________________________________________________________________

## 63. Benchmark Law

Benchmark success is bounded by:

```text
environment;

version;

configuration;

dataset;

harness;

scope;

measurement method.
```

Therefore:

```text
BENCHMARK PASS
!=
UNIVERSAL VALIDITY
```

______________________________________________________________________

## 64. Formal Verification Boundary

A formal proof establishes only the formally represented properties under the proof assumptions.

Therefore:

```text
PROPERTY P VERIFIED
!=
SYSTEM UNIVERSALLY VERIFIED
```

Proof assumptions and model boundaries MUST remain explicit.

______________________________________________________________________

## 65. Uncertainty Law

AMOS SHOULD distinguish uncertainty dimensions where material.

Recommended vector:

```yaml
uncertainty:
  evidence: null
  model: null
  scope: null
  temporal: null
  causal: null
  execution: null
  provenance_independence: null
```

A single confidence number MUST NOT conceal materially different uncertainty classes when decisions depend on them.

______________________________________________________________________

## 66. Sensitivity Law

For consequential conclusions, identify the smallest premise capable of flipping the decision.

Validate high-sensitivity premises first.

This supports:

```text
smallest sufficient proof scope
```

without sacrificing integrity.

______________________________________________________________________

## 67. Adaptive Complexity Law

AMOS SHOULD use the lowest reasoning complexity sufficient for integrity.

Possible modes:

```text
C0 DIRECT

C1 COMPACT

C2 STRUCTURED

C3 DEEP

C4 MAXIMUM
```

Escalate when material uncertainty, stakes, contradiction, novelty, or governance demands it.

______________________________________________________________________

## 68. Fast-Path Law

A fast path is permissible only when required dependency and governance conditions are already established.

Fast path MUST NOT mean:

```text
skip evidence;

skip provenance;

skip authority;

skip conflict resolution.
```

It means:

```text
reuse still-valid proof state.
```

______________________________________________________________________

## 69. Law Hierarchy

Core Laws MAY exist in a hierarchy.

Recommended ordering principle:

```text
ROOT INVARIANT
   ↓
DOMAIN CORE LAW
   ↓
SUBSYSTEM LAW
   ↓
POLICY
   ↓
PROCEDURE
   ↓
IMPLEMENTATION RULE
```

A lower-level rule MUST NOT silently override a higher-level law.

______________________________________________________________________

## 70. Law Precedence

When laws conflict, resolution SHOULD consider:

```text
canonical level;

scope;

specificity;

version;

effective time;

authority;

supersession;

protected invariants.
```

There MUST NOT be an ungrounded rule such as:

```text
latest text always wins
```

unless explicitly admitted to canon.

______________________________________________________________________

## 71. Law Conflict States

Recommended states:

```text
NO_CONFLICT
```

## 85. Law Falsification

A Core Law may be falsified in different senses.

## Internal falsification

The law conflicts with higher admitted AMOS canon or produces contradiction inside its declared scope.

## Implementation falsification

An implementation claimed to enforce the law fails a valid test.

## Empirical falsification

An empirical claim attached to the law is contradicted by valid external evidence.

These MUST remain separate.

## 100. Final CORE LAWS Contract

AMOS Core Laws SHALL function as the highest-order governed constraints of their declared scopes.

A Core Law MUST NOT derive canonical force merely from:

```text
language-model generation;

repetition;

file placement;

naming;

architectural convenience;

implementation;

popularity;

or confidence.
```

Core Law governance SHALL preserve:

```text
IDENTITY
+
PROVENANCE
+
SCOPE
+
HIERARCHY
+
DEPENDENCIES
+
PRECEDENCE
+
VERSION
+
SUPERSESSION
+
CONTRADICTIONS
+
AUTHORITY
+
REVALIDATION
```

The governing chain is:

```text
SOURCE
  ↓
LAW CANDIDATE
  ↓
IDENTITY
  ↓
PROVENANCE
  ↓
SCOPE
  ↓
HIERARCHY
  ↓
DEPENDENCY ANALYSIS
  ↓
CONFLICT ANALYSIS
  ↓
CANON REVIEW
  ↓
AUTHORITY
  ↓
CANON COMMIT
  ↓
REGISTRY
  ↓
ENFORCEMENT / IMPLEMENTATION
  ↓
VALIDATION
  ↓
CHANGE / SUPERSESSION / REPAIR
```

At every stage:

```text
INTEGRITY > COMPLETENESS

CANON != EMPIRICAL TRUTH

CAPABILITY != AUTHORITY

PROPOSAL != COMMIT

UNKNOWN/GAP != PASS

SUPERSESSION != ERASURE
```

The governing Core Laws principle is:

> **AMOS Core Laws are provenance-bound, scoped, versioned, hierarchy-aware canonical constraints. They govern subordinate architecture only within their declared applicability envelope. No lower-level rule, policy, agent, Skill, implementation, generated artifact, or optimization may silently override a higher valid Core Law. Conflicts must remain visible until governed resolution exists; amendments and supersession must preserve lineage; dependent state must be selectively revalidated after load-bearing law changes; and no canonical AMOS law may be represented as independently verified empirical truth unless evidence outside canonical authority supports that stronger claim.**
