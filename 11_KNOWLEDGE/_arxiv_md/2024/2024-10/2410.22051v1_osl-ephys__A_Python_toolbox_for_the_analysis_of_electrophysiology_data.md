2.2.3 Source Reconstruc9on 
The source_recon module contains tools for coregistraBon, volumetric source

Note that the source_recon module sBll uses low-level MNE-Python funcBons on the 
backend wherever possible. For example, instead of returning speciﬁc SourceEstimate 
classes as in MNE-Python, osl-ephys returns MNE-Python Raw classes with source

Typically, the steps used in the FSL-based coregistraBon and volumetric source 
reconstrucBon pipeline are as follows: 
 
1. Compute surfaces. Extract the inner skull, outer skin (scalp) and brain surfaces from 
structural, T1 weighted MRI (sMRI) data, using FSL (Jenkinson et al., 2012).  
2. CoregistraBon. Coregisters the M/EEG data, head digiBzaBon points (i.e., Polhemus), and 
sMRI data. This is done using Registra9on using Headshapes Including Nose in osl-
ephys (RHINO), analogous to the MATLAB implementaBon (OHBA Analysis Group, 
2014). It consists of calculaBng a linear, aﬃne transform from naBve sMRI space to 
Polhemus (head) space, using headshape points that opBonally include the nose. RHINO 
ﬁrsts registers the Polhemus-derived ﬁducials (nasion, right and leN pre-auricular points) 
in Polhemus space to the sMRI-derived ﬁducials in naBve sMRI space. RHINO then 
reﬁnes this by making use of Polhemus-derived headshape points that trace out the 
surface of the head (scalp), and ideally include the nose, using the iteraBve closest point 
(ICP) algorithm. Finally, these Polhemus-derived headshape points in Polhemus space  
are registered to the sMRI-derived scalp surface in naBve sMRI space. 
3. Forward modelling. This is a wrapper for mne.make_forward_solution.   
4. Source modelling. Typically done using a volumetric LCMV beamformer (Van Veen et al., 
1997), but other methods will be implemented in the future (e.g. Minimum Norm 
EsBmate).  
 
Source reconstrucBon to the volumetric dipole grid can then be followed by use of a pre-
deﬁned parcellaBon to extract parcel Bme courses, and including the reducBon of spaBal 
leakage and correcBon for sign ambiguiBes: 
 
5. ParcellaBon. Parcellates a dipole grid of source esBmates by taking the principal 
component (or spaBal basis set) of all dipoles in a parcel from a chosen (NiNi) 
parcellaBon. MulBple standard parcellaBon templates are supplied (e.g., AAL (Tzourio-
Mazoyer et al., 2002)), as well as fMRI-derived parcellaBons opBmized for M/EEG data 
(i.e., with a lower amount of parcels to match the rank of M/EEG data; e.g., Giles39 
(Colclough et al., 2015), and Glasser52 (Kohl et al., 2023)).

4. Discussion 
We have presented how the osl-ephys toolbox for the analysis of M/EEG data. This is not 
a standalone toolbox, but heavily relies on the widely adopted MNE-Python toolbox, FSL and 
other popular python packages: numpy, scipy, matplotlib, etc. osl-ephys aims to 
augment MNE-Python by providing a conﬁg API for reproducible processing of large 
quanBBes of data, while providing quality assurance and unique funcBonaliBes for data 
analysis. This include funcBons for automaBc and manual data preprocessing, FSL-based 
(Freesurfer independent) volumetric source reconstrucBon, and staBsBcal analysis, in 
parBcular, using GLMs.  
 
Researchers face a number of challenges when analysing M/EEG data. Firstly, analysis is 
complex and heterogenous. The analysis pipeline depends on the nature and quality of the 
data, as well as the experimental design and research quesBon. Therefore, analysis ﬂexibility 
is essenBal for analysis soNware. However, analysis complexity and ﬂexibility come with 
caveats, parBcularly in terms of transparency and reproducibility. In parBcular, it is 
cumbersome and error-prone to manually provide all details of an analysis pipeline in the 
Methods secBon of academic publicaBons. Even with the growing requirement of funders 
and journals to provide analysis scripts upon publicaBon of a manuscript, the full details for 
the analysis pipeline oNen remain unclear.  
 
Therefore, osl-ephys uses a concise and easily shareable config API, which reduces the 
amount of custom wripen scripts and funcBons that the researchers need to write (whilst 
retaining analysis ﬂexibility). In addiBon, osl-ephys keeps track of all processing that took 
place in log ﬁles, and it generates analysis reports that can be used for both reproducibility 
eﬀorts, and quality assurance.  
 
The high complexity also means that no single analysis toolbox can provide all possible 
analyBcal methods, and therefore, the researcher typically needs to sBtch together various 
third-party toolboxes in their analysis pipeline. osl-ephys is built on top of the most 
adopted Python M/EEG analysis toolbox (MNE-Python), and many other Python (and 
MATLAB) toolboxes contain plugins and/or documentaBon on how to use their toolbox in 
combinaBon with MNE-Python. This makes it more straighhorward to use diﬀerent 
toolboxes. AddiBonally, osl-ephys can be used in a modular fashion, and custom-wripen 
and third-party funcBonality can be easily implemented as an extension to osl-ephys by 
supplying the chain/batch funcBons with extra funcBon deﬁniBons.  
 
Another challenge is that high analysis complexity means a high entrance barrier for new 
researchers in the ﬁeld of M/EEG analysis, and/or programming, especially considering the 
mulBdisciplinary nature of the ﬁeld. osl-ephys alleviates this by combining the config 
API a limited number of funcBons (in parBcular the chain and batch funcBons) that the user 
interacts with and taking care of much of the complexity in programming and data 
bookkeeping on the backend. This is further aided by comprehensive documentaBon and

a plahorm for quality assurance.
