An AutomationML Domain Library for the
Formalized Process Description
Hamied Nabizada∗, Rainer Drath†, Felix Gehlhoff∗, Alexander Fay‡
∗Institute of Automation Technology, Helmut Schmidt University Hamburg, Hamburg, Germany
†Institute of Smart Systems and Services, Pforzheim University, Pforzheim, Germany
‡Chair of Automation Technology, Ruhr University Bochum, Bochum, Germany
Abstract—The Formalized Process Description (FPD) accord-
ing to VDI/VDE 3682 provides a standardized graphical notation
for describing processes across engineering domains but lacks a
standardized, tool-independent data format for machine-readable
model exchange. This paper presents an AutomationML (AML)
domain library that formalizes the complete set of FPD language
elements, their attributes, connection semantics, and graphical
representation information as class libraries based on the Com-
puter Aided Engineering Exchange (CAEX) 3.0 metamodel. The
library comprises five interrelated parts: a RoleClassLib defining
the semantic roles, an InterfaceClassLib for connection types,
two AttributeTypeLibs for the information model and diagram
interchange, and a SystemUnitClassLib providing instantiation
templates. Key design decisions regarding inheritance, diagram
structure, hierarchical decomposition, and the representation of
graphical information are discussed along with the alternatives
that were considered. A bidirectional mapping tool demonstrates
the library’s applicability by converting between a web-based
FPD modeler and AML. The library is proposed as a candidate
for Part 3 of VDI/VDE 3682. It is available together with an
example and a feedback function for community input ahead of
standardization at https://aml.fpbjs.net.
Index Terms—FPD, AML, CAEX, domain library, VDI 3682,
process modeling
I. INTRODUCTION
The Formalized Process Description (FPD) according to
VDI/VDE 3682 [1] is a standardized graphical notation for
describing processes across engineering domains. It defines six
object types and four connection types. Product, Energy, and
Information represent states that serve as inputs and outputs
of a Process Operator. A Technical Resource realizes one or
more process operators via usage relationships, and the System
Limit separates the process from its environment. Directed
flow connections represent material, energy, and information
flows, and the notation supports hierarchical decomposition
of process operators into subordinate processes [1]. Part 2 [2]
complements the graphical notation with an information model
that specifies Identification and Characteristics attributes for
each element.
The FPD has been adopted in areas such as capability mod-
eling [3], digital process twins [4], and automated sequence
planning [5]. Despite this growing adoption, the standard does
not define a standardized data format for tool-independent
model exchange. Existing tools such as FPB.js1 and the FPD-
1https://www.fpbjs.net
Editor2 therefore store process descriptions in tool-specific
formats [6]. As a result, exchanging FPD models between
tools requires dedicated mappings or conversions, which lim-
its interoperability and hinders reuse in broader engineering
workflows.
AutomationML (AML) [7] is a vendor-neutral data format
for exchanging engineering information. It uses Computer
Aided Engineering Exchange (CAEX), originally defined in
IEC 62424 [8], as its underlying metamodel. CAEX pro-
vides RoleClasses for semantic roles, SystemUnitClasses as
instantiation templates, InterfaceClasses for typed connection
endpoints, and Attributes for properties. Classes are organized
in reusable libraries, while concrete models are represented as
InstanceHierarchies [9]. This makes AML a suitable founda-
tion for representing graphical description languages by means
of reusable domain-specific libraries that can be interpreted by
AML-compliant tools without modifying the standard itself.
This paper presents an AML domain library that formalizes
the FPD as a set of CAEX class libraries, building on a general
methodology for mapping graphical description languages
into AML [10]. The contributions of this paper are: (1) the
complete AML/CAEX domain library for the FPD, (2) a
discussion of key design decisions and their alternatives, and
(3) a bidirectional mapping tool with round-trip validation.
The library is currently under review in the GMA Technical
Committee 2.19 as a candidate for Part 3 of VDI/VDE 3682.
II. RELATED WORK
Several approaches to machine-readable representations of
the FPD have been proposed. In [11], AML was used to model
specific manufacturing processes directly, rather than mapping
an existing graphical description language to AML. In [12], an
FPD-to-AML mapping was presented that enabled a toolchain
from requirements engineering to plant structure descriptions.
While it established an initial conceptual mapping between
FPD and CAEX elements, the approach was tied to a Mi-
crosoft Visio-based workflow and did not produce a reusable,
tool-independent domain library. In [6], a web-based modeling
tool with a JSON-based exchange format was proposed, and
in [13] an XML representation aligned with the VDI 3682
information model. Both, however, introduce a new domain-
specific data format. In [14], a SysML profile was proposed

that embeds the FPD into an existing modeling framework but

covering graphical representation information such as element
positions and connection routing, so that the original graphical
process description cannot be reconstructed from the model.
The approach presented here differs from [12] by providing
a systematic, reusable domain library that is independent of
any specific modeling tool. Unlike [6], [13], [14], it avoids
introducing a new format by building on the established AML
ecosystem. This paper presents the FPD in detail and discusses
the rationale behind its design decisions.
III. FPD DOMAIN LIBRARY
The domain library consists of five CAEX class libraries:
a RoleClassLib for semantic roles, an InterfaceClassLib for
connection types, two AttributeTypeLibs for the information
model and diagram interchange, and a SystemUnitClassLib for
instantiation templates.
A. RoleClassLib – Semantic Roles
The VDI_FPD_RoleClassLib defines the semantic meaning
of each FPD element. Fig. 1 shows the inheritance structure.
FPD_Object serves as the abstract base class, inheriting
from AutomationMLBaseRole. It carries the shared
attributes Identification, Characteristics, and
ViewInformation
(of
type
FPD_Bounds,
storing
position
and
dimensions).
Five
classes
inherit
from
it:
FPD_SystemLimit,
FPD_State
(with
sub-roles
FPD_Product,
FPD_Energy,
FPD_Information),
FPD_ProcessOperator (an individual processing step),
and FPD_TechnicalResource.
FPD_Process
inherits
from
the
AML
base
role
Structure rather than from FPD_Object. Unlike the six
visible object types, a process serves as the structural container
for a diagram rather than appearing as an element within it.
An alternative would be to let FPD_Process also inherit
from FPD_Object and carry the same shared attributes. The
separate inheritance path was chosen to make this structural
distinction explicit in the type system and to enable AML tools
to recognize processes as containers.
Fig. 1: VDI_FPD_RoleClassLib. The Class annotation indicates
the parent class from which each role inherits.
B. InterfaceClassLib – Connection Semantics
The
VDI_FPD_InterfaceClassLib
(Fig.
2)
models
directed
connections
as
interface
pairs.
FPD_Port
inherits
from
the
AML
base
interface
AutomationMLBaseInterface/Port
and
serves
as
the
base
class.
It
carries
a
PortCoordinate
attribute (of type FPD_Point) that stores the position
of the connection point on the element. Since CAEX
InternalLinks
do
not
carry
direction
semantics,
flow
direction
is
encoded
through
typed
interface
pairs:
FPD_FlowIn/Out,
FPD_ParallelFlowIn/Out,
and
FPD_AlternativeFlowIn/Out. Usage relationships are
modeled via a single FPD_Usage interface rather than an
input/output pair, since the standard defines usage as an
undirected association between a process operator and a
technical resource. An alternative would be to use a single
interface type and encode direction as an attribute; the
typed-pair approach was chosen because it allows AML tools
to determine flow direction purely from the interface types,
without inspecting attribute values. Connections are realized
as InternalLinks between ExternalInterface instances on
the connected elements.
Fig. 2: VDI_FPD_InterfaceClassLib. All interface classes inherit
from FPD_Port, which itself inherits from the AML base interface
Port.

Two
AttributeTypeLibs
formalize
the

The

representation
attributes
based
on
the
OMG
Diagram
Definition (DD) metamodel [16], which was chosen because

and FPD_Point (x/y coordinate). Since the FPD does
not treat connections as first-class object types with their
own identity [1], waypoints are stored on the outgoing
ExternalInterface
of
the
element
from
which
the
link
originates; for usage relationships, this is conventionally
the process operator. An alternative would be to model
connections as separate InternalElements with their own

D. SystemUnitClassLib and Instantiation
The
VDI_FPD_SystemUnitClassLib
(Fig.
5)
provides
instantiation
templates
corresponding
to
the
RoleClasses.
Each
class
references
its
RoleClass
via
SupportedRoleClass.
Where
a
matching
concept
exists in the AML base role library, classes additionally
declare
a
second
role
mapping:
FPD_Product
supports
AutomationMLBaseRole/Product,
FPD_ProcessOperator
supports
AutomationMLBaseRole/Process,
FPD_TechnicalResource
supports
AutomationMLBaseRole/Resource,
and
FPD_Process
supports
AutomationMLBaseRole/Structure.
Classes
such
as
FPD_Energy,
FPD_Information,
and
FPD_SystemLimit have no generic AML counterpart and
are therefore mapped only to their domain-specific roles.
This dual-role mapping enables AML tools to interpret FPD
elements both in their domain-specific semantics and in
terms of generic AML concepts—for example, an AML
tool that queries all elements with the role Resource will
find FPD technical resources without requiring FPD-specific
knowledge.
Two
key
design
decisions
govern
how
concrete
models are instantiated. A concrete FPD model is an
InstanceHierarchy
containing
FPD_Process
instances,
each
representing
a
diagram
with
its
own
coordinate space. Within a process, all object types—system
Fig. 5: VDI_FPD_SystemUnitClassLib. Each entry shows the CAEX
class inheritance (Class) and role mappings (Role).
limit, states, process operators, and technical resources—are
modeled as direct children at the same hierarchy level. The
system limit does not serve as a CAEX container for the
other elements, regardless of their graphical placement inside
or outside it. An alternative would be to nest elements inside
the system limit, reflecting the graphical containment. The flat
structure was chosen because the system limit in the FPD is
a boundary marker rather than a semantic container; nesting
would imply a containment relationship that the standard
does not define.
Hierarchical decomposition is realized through reference
attributes rather than CAEX element nesting. On a process
operator, a refProcess attribute (a named specialization of
the generic refObj attribute type) points to the child process;
on a child process, refObj points back to the parent operator;
on a boundary state, refObj references the corresponding
top-level state. An alternative would be to nest child processes
inside their parent process operators. The reference-based
approach was chosen because it preserves independent coordi-
nate spaces per diagram and supports arbitrary decomposition
depth without deeply nested CAEX structures.
IV. VALIDATION
The library was validated using a bidirectional mapping
tool3 built on the AML Engine SDK (.NET) that converts FPD
models between the web-based modeler FPB.js [6] and the
AML domain library. Validation was conducted on multiple
models of varying complexity, including models with all six
object types, all three flow types plus usage relationships, and
multi-level hierarchical decomposition with boundary states.
Fig. 6 shows a representative example: the process “Heating
with Inspection” as displayed in the AML Editor, including
the CAEX instance hierarchy, the graphical diagram, and the
attributes of a selected element.
For the evaluated models, the mapping was verified to be
lossless in both directions: all objects, attributes (Identification,
Characteristics), connection topologies, decomposition links,
and graphical representation (element positions, dimensions,
connection waypoints) were preserved through a round-trip
conversion (FPB.js →AML →FPB.js). Verification was
performed by an automated comparison of the source and re-
imported models. The resulting AML files were additionally
opened in the AML Editor to verify that the object hierarchy,

V. CONCLUSION
This paper presented an AML domain library that formal-
izes the FPD according to VDI/VDE 3682 as CAEX 3.0 class
libraries. The library covers all object types, their attributes,
four connection types, hierarchical decomposition, and graphi-
cal representation based on the OMG DD metamodel. Key de-
sign decisions were discussed along with the alternatives that
were considered. Since the library builds on AML, FPD mod-
els can be embedded alongside other engineering artifacts—
such as plant structure models or control configurations—
within a single AML project, enabling cross-domain reuse
without additional integration effort.
As the library is a candidate for Part 3 of VDI/VDE 3682,
the design decisions are documented here to support the
ongoing standardization in GMA Technical Committee 2.19
and to enable community feedback. The proposed library,
an example, and a feedback function are available at
https://aml.fpbjs.net. Future work includes the finalization of
the library within the standardization process, validation with
additional independently developed tools, and the application
of the library in industrial engineering workflows.
