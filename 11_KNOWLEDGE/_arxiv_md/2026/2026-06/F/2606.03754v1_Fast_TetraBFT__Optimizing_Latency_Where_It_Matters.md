Abstract
Unauthenticated Byzantine consensus protocols achieve optimal failure resilience while relying only
on authenticated point-to-point channels, not authenticated messages. They are an attractive
building block for blockchains that do not mandate symmetric trust assumptions as well as for future
post-quantum settings. We consider unauthenticated Byzantine consensus in partially synchronous
networks and focus on optimizing its good-case latency – the worst-case time for correct processes
to reach a decision under favorable conditions. A recently proposed ForgetIT protocol achieves
an optimal good-case latency of 3 message delays but employs a highly complex design. We show
that this complexity is unnecessary. To this end, we present Fast TetraBFT – an unauthenticated
Byzantine consensus protocol that achieves optimal good-case latency by augmenting an existing
TetraBFT protocol with a simple fast-path wrapper. Our solution lowers the good-case latency of
TetraBFT from 5 to 3 message delays while preserving its bounded space requirements and low
communication complexity.
1
Introduction
We consider Byzantine consensus in the partial synchrony model [14], which approximates
the behavior of real networks. In this setting, the system is guaranteed to eventually reach a
Global Stabilization Time (GST) after which message delays are bounded by an unknown
constant δ and process clocks track real time. Motivated by the blockchain use case, in recent
years researchers have developed a plethora of Byzantine consensus protocols in this model.
Most of these are authenticated, i.e., they send messages authenticated using cryptographic
signatures. These allow a process p1 to prove to a process p2 that a third process p3 has sent
a given message. In contrast, unauthenticated (aka information-theoretic) protocols rely only
on authenticated point-to-point channels and thus disallow the above pattern. The minimal
assumptions of such protocols make them applicable in a broader range of settings. These
inlcude post-quantum [2] or computationally constrained environments as well as blockchains
that do not rely on global trust assumptions, such as Stellar [16,17] and Ripple [7].
Since realistic networks behave synchronously most of the time, the efficiency of partially
synchronous blockchain implementations is largely determined by their performance under
stable network conditions. In more detail, blockchains often run a sequence of Byzantine
consensus instances, each deciding on the next block in the chain [6,10,16]. A consensus
instance proceeds through a sequence of views 0, 1, 2, . . ., each with a designated leader
process responsible for driving the protocol towards a decision. Since in practice the leaders
are selected to maximize the chances of correct behavior (e.g., by penalizing misbehavior via

Thus, a performance-critical metric for Byzantine consensus protocols is their good-case
latency – the worst-case latency to decision if the consensus instance is started during the
synchronous period (after GST) and the initial leader is correct.
In this paper we consider the problem of optimizing the good-case latency of unauthen-
ticated Byzantine consensus. Assuming the optimal resilience – n ≥3f + 1 processes to
tolerate f Byzantine failures – the lower bound on the good-case latency is 3δ [4]. The first
protocol to match this bound, a signature-free version of PBFT [12], was able to achieve this
only at the expense of a high message complexity – O(n3) per view. Information-theoretic
HotStuff [5] and TetraBFT [20] then lowered the communication complexity to O(n2) per
view, but only at the expense of a higher good-case latency – 6δ and 5δ, respectively. A very
recent proposal, Forget-IT [3], achieved both the optimal good-case latency of 3δ and the
communication complexity of O(n2) per view. Unfortunately, the protocol has a complicated
design, in part because it also minimizes another latency metric, which its authors call robust
good-case latency. This is the worst-case latency of a decision measured from the first time
after GST when a correct leader enters a view (whether 0 or higher).
The rationale for the above metric was to capture latency guarantees under adversarial
conditions, when the protocol is started before GST. We argue that the metric does not
fulfil this function. In practice, what matters under adversarial conditions is how quickly
the protocol recovers after the onset of the synchronous period, i.e., the time to decision
measured from GST. To take a decision in this case, processes need to first exit the views
they were in before GST and enter a “good” view with a correct leader. Processes exit a view
when their timers expire, and the duration of these timers is typically orders of magnitude
larger than δ. Thus, optimizing the latency to the decision after entering a good view is
irrelevant, since the time to decision after GST will be dominated by timer durations.
Given the above considerations, we set out to find a simpler protocol that achieves the
optimal good-case latency and low communication complexity. Our answer is Fast TetraBFT
– a protocol with the good-case latency of 3δ and the communication complexity of O(n2)
per view. It furthermore guarantees optimal resilience and optimistic responsiveness [19],
and can be implemented in bounded space. It is a wrapper around TetraBFT [20] that
introduces a special code path for view 0 and executes a slightly modified TetraBFT in higher
views. Thus, the protocol improves the good-case latency of TetraBFT while preserving its
performance under adversarial conditions. Our wrapper makes only minimal assumptions
about the structure of TetraBFT. For this reason, we hope that its underlying ideas will also
be applicable to lower the good-case latency of future proposals of unauthenticated BFT
consensus protocols.
2
System Model
We consider a distributed message-passing system of n processes, of which at most f can
experience Byzantine failures. As is standard, we assume n ≥3f + 1 and call a set of n −f
processes a quorum. The system is partially synchronous [13,14]: for every execution, there
exist a Global Stabilization Time (GST) and a duration δ such that, after GST, message
delays between every pair of correct processes are bounded by δ; before GST, messages can be
arbitrarily delayed or lost. We also assume a known upper bound ∆on the maximum value of
δ across all executions, i.e., δ < ∆[15,18]. Processes are equipped with hardware clocks that

We assume an application-specific valid() predicate that indicates whether a value proposed
to consensus is valid [11]. In Byzantine consensus, each correct process proposes a valid value
and then has to decide on a value so that: (Validity) a correct process decides on a valid
value; (Agreement) no two correct processes decide on different values; and (Liveness) every
correct process eventually decides on a value.
3
TetraBFT Overview
We build on the TetraBFT protocol [20], whose pseudocode is given in Figures 1–2 (the
code highlighted in red is necessary for Fast TetraBFT and should be ignored for now). The
protocol proceeds in views, and each view v has a designated leader leader(v) whose role
rotates round robin among all processes. We number TetraBFT views starting from 1, since
we use view 0 for Fast TetraBFT. Processes enter a view v upon an upcall new_view(v) from
a view synchronizer (line 4), whose implementation we omit. For concreteness, we could use
the FastSync synchronizer of Bravo et al. [9], which does not rely on authenticated messages
and requires only bounded space. The synchronizer ensures that for some view V entered
after GST, all correct processes enter each view v ≥V and overlap in v for a given duration
(TetraBFT requires 6δ). The structure of each view in TetraBFT is as follows:
Upon entering a new view, processes send a SUGGEST message to its leader with information
to help it make a proposal (line 7). They also broadcast PROOF messages to help other
processes check that the leader’s proposal is correct (line 8).
The leader determines its proposal based on a quorum of SUGGEST messages satisfying a
predicate safe_val_leader, and broadcasts the proposal in a PROPOSE message (line 14).
A process accepts the leader’s proposal if it receives a quorum of PROOF messages satisfying
safe_val_follower. A process accepts only one proposal per view (cf. the voted flag).
Processes go through four rounds of voting on the proposal, sending messages VOTE1 to
VOTE4 (line 20–30). Votes in each succeeding round are sent in response to a quorum of
matching votes from the previous round. When a process receives a quorum of matching
VOTE4 messages, it decides (line 32).
A process stores the last votes it issued in variables V1 to V4. For VOTE1 an VOTE2 it also
keeps track of the last two votes for distinct values using prev_V1 and prev_V2 (lines 18
and 22). These votes are then reported in SUGGEST and PROOF messages (lines 7–8).
4
Fast TetraBFT
Fast TetraBFT runs a special protocol in view 0 (Figure 3), which is driven by an initial
leader. When this leader is correct and the network is synchronous, the protocol decides
within 3δ. Hence, at the beginning of the protocol each process sets a timer for a conservative
bound of 3∆(line 59). When the timer expires (line 60), the process switches to TetraBFT,
disabling the actions in Figure 3 and enabling those in Figure 1 via a flag started_tetra.
The initial leader starts Fast TetraBFT by broadcasting its consensus proposal in a
FAST_PROPOSE message (line 59). Each process accepts only one such proposal (cf. the voted
flag), which it broadcasts in a VOTE0 message (line 67). A process receiving a quorum of
VOTE0s for the same value broadcasts it in a COMMIT message (line 71), and a process receiving
a quorum of matching COMMITs decides (line 73). This ensures the good-case latency of 3δ.

A process sending a COMMIT message for a value x agrees to x being decided, and thus
becomes locked on this value. This is recorded by storing x in val and lock (line 70). The
former variable determines the proposal fed into TetraBFT (line 63), and is initialized to the
process’s own proposal (line 54). The latter constrains the proposals that can be made by
leaders and accepted by followers in TetraBFT: when lock is set to x, any proposals different
from x are rejected (lines 42 and 48). Since view 0 may fail to reach a decision, a process
also needs to be able to unlock the value x it recorded, to allow TetraBFT to decide. Our
main insight is that the process can do this upon receiving f + 1 VOTE2 messages for values
different from x, either directly or within SUGGEST messages (line 9).
4.1
Ensuring Bounded Memory
Fast TetraBFT can be implemented in bounded memory as follows:
For each message type and sender, a process stores the message of this type from this
sender that has the highest view.
To support unlocking (line 9), a process also retains two latest VOTE2 messages from every
sender that were cast for distinct values. This applies to VOTE2s sent both directly and
within SUGGEST messages.
These rules do not compromise liveness because the protocol does not rely on messages from
previous views for any purposes other than unlocking. The above rule for VOTE2 messages
ensures that a process never forgets having received a VOTE2 for a value different from its
lock, so the unlocking condition in lines 9-10 is never missed.
5
Correctness
Validity holds trivially, so we now prove Agreement. First, we show correct processes cannot
lock different values or decide different values in view 0.
▶Lemma 1. If two correct processes lock values x and x′, respectively, then x = x′.
Proof. A correct process locks a value only after receiving a quorum of n−f VOTE0 messages
for it (line 68). Since any two quorums intersect in a correct process, locking different values
x and x′ requires some correct process to send both VOTE0(x) and VOTE0(x′). This cannot
happen since a process only sends a VOTE0 once (the voted flag at line 65).
◀
▶Lemma 2. Any two correct processes that decide in view 0 must decide the same value.

The safety of TetraBFT rules out contradictory decisions in views > 0 (we formalize this
in Appendix A). It thus remains to prove agreement between the values decided in view
0 (line 73) and those decided in the subsequent views (line 32). To this end, we show the
following auxiliary result.
▶Lemma 3. If x is locked by f + 1 correct processes, then no correct process can unlock x.
Proof. Assume toward a contradiction that some correct process unlocks x. Let t be the
earliest time when this happens, and let pi be the unlocking process. Then, by the time t, pi
has received VOTE2(_, xj) from f + 1 processes pj such that every xj ̸= x (line 9). Since at
least one of these processes is correct, it must have sent its VOTE2 following the receipt of
n −f matching VOTE1s for some value x′ ̸= x (line 21). We know that f + 1 correct processes
lock x, so there exists a correct process p which both locks x at some time tl and broadcasts
VOTE1(_, x′) at some time t′ < t. Hence, safe_val_follower(x′, v′) holds at p at time t′.
Also, x is the only value that p can ever lock, so line 48 implies that p has lock = ⊥at time
t′. Furthermore, started_tetra = false at p at tl (line 69) and must be true for p to send
VOTE1 at t′. Then tl < t′, so p must unlock x at some point between tl and t′. Since t′ < t,
this contradicts our assumption that no correct process does so before t.
◀
▶Lemma 4. If two correct processes decide x in view 0 and x′ in a view > 0, then x = x′.
Proof. A correct process decides x in view 0 after receiving a quorum of n −f COMMIT(x)
messages (lines 72). Out of these, at least n −2f must be sent by correct processes, which
have thus locked x (line 70). By Lemma 3, these processes will never unlock x. Then
safe_val_follower ensures that they will never send a VOTE1 message for another value
x′ ̸= x in any view > 0 (lines 48 and 16). This makes it impossible to assemble a quorum of
n −f VOTE1 messages for x′ needed to decide this value in a view > 0.

▶Theorem 5. Every correct process eventually decides.
Proof. Each correct process eventually times out and starts executing TetraBFT (line 63).
If all correct processes eventually have lock = ⊥, then they end up executing unmodified
TetraBFT, which we know is live (we formalize this in Appendix A). Thus, we only have
to consider the case when a non-empty set of correct processes L get locked on a value and

exchange the messages leading to a decision, as required.
