ChemGraph-XANES: An Agentic Framework for XANES
Simulation and Analysis
Vitor F. Grizzi1, Thang Duc Pham2, Luke N. Pretzie1, Jiayi Xu1, Murat Keceli2, and Cong Liu1∗

Abstract
Computational X-ray absorption near-edge structure (XANES) is widely used to probe lo-
cal coordination environments, oxidation states, and electronic structure in chemically complex
systems. However, the use of computational XANES at scale is constrained more by work-
flow complexity than by the underlying simulation method itself. To address this challenge,
we present ChemGraph-XANES, an agentic framework for automated XANES simulation and
analysis that unifies natural-language task specification, structure acquisition, FDMNES input
generation, task-parallel execution, spectral normalization, and provenance-aware data cura-
tion. Built on ASE, FDMNES, Parsl, and a LangGraph/LangChain-based tool interface, the
framework exposes XANES workflow operations as typed Python tools that can be orchestrated
by large language model (LLM) agents.
In multi-agent mode, a retrieval-augmented expert
agent consults the FDMNES manual to ground parameter selection, while executor agents
translate user requests into structured tool calls.
We demonstrate documentation-grounded
parameter retrieval and show that the same workflow supports both explicit structure-file in-
puts and chemistry-level natural-language requests. Because independent XANES calculations
are naturally task-parallel, the framework is well suited for high-throughput deployment on
high-performance computing (HPC) systems, enabling scalable XANES database generation for
downstream analysis and machine-learning applications. ChemGraph-XANES thus provides a
reproducible and extensible workflow layer for physics-based XANES simulation, spectral cura-
tion, and agent-compatible computational spectroscopy.

Introduction
Computational X-ray absorption near-edge structure (XANES) has become an important comple-
ment to experimental X-ray absorption spectroscopy for interpreting local coordination environ-
ments, oxidation states, and electronic structure in chemically complex systems [1, 2, 3, 4, 5, 6].
In practice, however, the primary obstacle to routine, large-scale XANES calculations often lies
not only in the underlying simulation method, but also in the workflow needed to execute each
calculation reliably. A typical study requires preparing or retrieving candidate structures, identi-
fying absorber sites, specifying calculation parameters, generating code-specific inputs, organizing

many independent runs, extracting spectral outputs, applying consistent normalization, and pre-
serving the provenance linking each spectrum to its parent structure. When these steps are handled
manually or through ad hoc scripts, the workflow becomes difficult to reuse, reproduce, and scale.
This bottleneck is particularly acute in settings that require many calculations rather than a
single forward simulation. High-throughput screening, ensemble-based studies, iterative comparison
to experiment, and machine-learning (ML) dataset generation all require large collections of spectra
to be computed and curated consistently [7, 8]. In such settings, the practical value of computational
XANES depends not only on the fidelity of the underlying physics-based method, but also on the
ability to standardize structure preparation, parameter specification, execution, post-processing,
and data organization across many jobs. Because individual XANES calculations are naturally
independent once their inputs have been defined, such workloads are also well suited to task-parallel
execution on high-performance computing (HPC) resources.
Recent progress in language-model-based agents has created new opportunities for scientific
workflow automation [9, 10, 11, 12, 13].
By exposing established domain software as callable
tools, high-level natural-language requests can be translated into structured computational actions,
reducing the need for users to manually compose each step of the simulation pipeline [14, 15, 16].
In computational spectroscopy, this paradigm enables an agent to select the appropriate operation,
populate its parameters through typed interfaces, and orchestrate multi-step workflows spanning
structure retrieval, simulation setup, execution, and post-processing. Rather than replacing the
underlying spectroscopy engine, the agent functions as an orchestration layer over conventional
scientific software, improving accessibility while preserving transparent execution logic [17].
In this work, we build on the original ChemGraph framework [15] to develop ChemGraph-
XANES, a domain-specific extension for automated XANES simulation and curation.
While
the original framework provides a general agentic interface for chemistry workflows, ChemGraph-
XANES introduces XANES-specific tool abstractions, structure-to-spectrum workflow standard-
ization, and scalable execution support for spectroscopy-oriented applications.
Built on ASE,
FDMNES, Parsl, and a LangGraph/LangChain-based tool interface [18, 19, 20], the framework
exposes XANES workflow operations as typed tools implemented as Python functions, enabling
language-model agents to interpret user requests, map relevant quantities onto structured function
arguments, and execute the resulting spectroscopy workflow. At the same time, it standardizes the
path from atomic structure to analysis-ready XANES data through automated structure retrieval,
FDMNES input generation, organized execution, spectral extraction, and consistent normalization,
while preserving provenance through structure-linked datasets. Because the workflow is naturally
task-parallel, it is also well suited for high-throughput deployment on HPC systems, enabling scal-
able XANES database generation for downstream analysis and ML applications. Taken together,
these capabilities establish an agent-compatible workflow layer for reproducible, extensible, and
high-throughput XANES simulation and analysis.
2
Methods
2.1
Workflow overview and agentic orchestration
We developed ChemGraph-XANES as a modular, agent-compatible workflow for automated XANES
calculations.
The framework unifies natural-language task specification, structure acquisition,
FDMNES input preparation, high-throughput execution, spectral post-processing, and provenance
tracking within a single Python-based pipeline. The underlying scientific operations are imple-
mented as ordinary Python functions and exposed to the execution layer as typed tools with
schema-defined arguments. In agentic mode, a large language model (LLM) interprets a user query,
2


## Page 3


selects the relevant tool, and maps user-specified quantities, such as the chemical system, absorber
choice, cluster radius, magnetic settings, or output location, onto structured function arguments.
These arguments are then passed to the same underlying Python routines used in direct scripted
execution, thereby preserving a single source of scientific logic while enabling the workflow to be
driven from natural-language requests.
The current implementation supports both single-agent and multi-agent execution modes. In
the single-agent setting, the model iteratively alternates between reasoning and tool invocation until
the requested workflow is completed. In the multi-agent setting, a planner first decomposes the user
request into subtasks, worker agents execute those subtasks through the same tool abstraction, and
an aggregator combines the resulting outputs into a final response. Further details of the underlying
ChemGraph framework are available in Ref. [15].
The multi-agent mode can additionally incorporate a retrieval-augmented expert agent that
grounds XANES parameter selection in markdown documentation, allowing executor agents to
receive documentation-informed guidance without hard-coding all decision rules directly into the
executor prompt or the simulation backend. This design enables the same XANES workflow to
be invoked from interactive natural-language sessions, notebooks, or conventional Python scripts
without changing the underlying spectroscopy routines. At a high level, the pipeline begins with
either user-provided structures or structures retrieved from a materials database, converts them
into a unified atomistic representation, generates FDMNES input files, executes the calculations,
parses the resulting convolution spectra, and stores the spectra back alongside the originating
structures for downstream analysis. Figure 1 provides a schematic overview of the ChemGraph-
XANES workflow.
2.2
Structure acquisition and curation
For database-driven workflows, bulk structures are retrieved programmatically from the Materials
Project through its Python API [21, 22]. The current implementation queries the materials sum-
mary endpoint using a user-specified chemical formula together with an energy-above-hull threshold
in order to restrict the search to low-energy candidate structures. Retrieved structures are con-
verted from the native Pymatgen representation into ase.Atoms objects, which are used as the
internal structural representation throughout the workflow. Each structure is annotated with its
Materials Project identifier, thereby preserving traceability to the original source and simplifying
later aggregation of results.
To support both interoperability and efficient local reuse, the curated structures are stored
in two complementary formats. First, each structure is exported as an individual .cif file, which
preserves compatibility with standard crystallographic tools. Second, the full collection is serialized
into a local Python object database, atoms db.pkl. This dual representation provides convenient
access for both manual inspection and batch execution. In practice, the serialized database serves
as the default source for subsequent FDMNES input generation when an explicit in-memory list of
structures is unavailable.
2.3
Automatic FDMNES input generation
Automatic FDMNES input generation in ChemGraph-XANES combines deterministic script-based
file construction with an agentic parameter-selection layer. Within the broader ChemGraph multi-
agent architecture, we implemented a retrieval-augmented expert agent that ingests markdown
documentation, indexes its contents into a queryable knowledge base, and retrieves grounded guid-
ance when executor agents must determine how an FDMNES calculation should be parameterized.

The framework further supports planner-worker execution, in which specialized agents decompose
the overall task and dispatch tool calls through a shared orchestration layer. In practice, the expert
agent functions as a domain-knowledge specialist, informing executor agents how to set parameters
such as the absorbing species, cluster radius, magnetic settings, and related calculation options
before the corresponding XANES tools are invoked. Agent decisions are validated against struc-
tured schemas, which translate high-level reasoning into the standardized parameters required by
the backend. By using the same execution pipeline for both agents and researchers, the system
maintains a consistent audit trail, ensuring that FDMNES simulations remain reproducible across
diverse operating modes.
Once the calculation arguments are fixed, FDMNES input files are generated directly from the
ase.Atoms objects. For each structure, the workflow writes both the steering file fdmfile.txt
and the main input file fdmnes in.txt.
Unless the absorbing species is explicitly specified by
the user, the absorbing atom is chosen as the element with the largest atomic number present in
the structure. This should be understood as an implementation-level default for high-throughput
workflows rather than a general scientific assumption, and it can be overridden whenever a different
absorbing edge is desired.
The current implementation writes a fixed FDMNES energy mesh together with a user-defined
cluster radius, which defaults to 6.0 ˚A. Optional magnetic contributions can also be enabled. In
addition, the generated input includes the Green, Density all, Quadrupole, Spherical, and SCF
directives, corresponding to the self-consistent finite-difference workflow used here.
The workflow distinguishes automatically between periodic and non-periodic structures. If all
periodic boundary condition flags are enabled, the structure is written in Crystal mode using the
cell parameters and fractional atomic coordinates. Otherwise, the structure is written in Molecule
mode using Cartesian coordinates and a cubic bounding cell constructed from the atomic positions.
This branching enables a common front-end representation to be used for both crystalline and
molecular systems while still emitting valid FDMNES inputs for each case.
2.4
High-throughput execution, Parsl-based scaling, and provenance tracking
To support high-throughput studies, the pipeline includes a batch input generator that creates
a dedicated run directory for each structure under a common fdmnes batch runs root.
Each
directory contains the corresponding FDMNES input files together with a serialized copy of the
associated ase.Atoms object. The filename of the serialized structure includes the absorbing atomic
number, the Materials Project identifier when available, and the chemical formula. This naming
convention provides a lightweight but effective provenance layer that links each calculation directory
to its structural origin.
Single-run execution is handled by a core routine that reads an input structure through ASE,
creates the output directory, writes the FDMNES inputs, and launches the external FDMNES ex-
ecutable through a subprocess call. The path to the executable is provided through the FDMNES EXE
environment variable. Standard output and standard error streams are redirected to fdmnes stdout.txt
and fdmnes stderr.txt, respectively, which facilitates debugging and post hoc inspection of failed
jobs. After execution, the workflow searches the run directory for FDMNES convolution output
files matching *conv.txt. All matching spectra are parsed and stored as NumPy arrays. If no
convolution output is found, the calculation is marked as failed. Otherwise, the run is considered
successful and the number of extracted convolution files is recorded.
Because each structure gives rise to an independent FDMNES calculation once the input param-
eters are specified, the workflow is naturally task-parallel across structures. This property makes it
well suited to large XANES campaigns and compatible with distributed execution through Parsl,

where many independent structure-level jobs can be dispatched concurrently on HPC systems
while retaining a uniform interface for inputs, logs, and outputs.
In practice, this enables the
same workflow to scale from a single interactive query to large batches of structures, for example
when generating simulation databases for downstream ML applications, surrogate-model training,
or comparative benchmarking across structurally diverse materials.
To assemble the results into a dataset suitable for downstream analysis, the workflow reloads
the serialized structures, attaches the extracted spectral data to the corresponding ase.Atoms
objects under the atoms.info["FDMNES-xanes"] field, and writes the expanded collection to
atoms db expanded.pkl. This step preserves the association between structural inputs and spec-
tral outputs in a form that can be readily reused for subsequent analysis, data curation, and
ML-oriented dataset construction.

3
Results
3.1
Documentation-grounded parameter retrieval
A key feature of ChemGraph-XANES is a documentation-grounded expert agent that consults
external reference material before downstream tool invocation. Instead of relying exclusively on
latent model knowledge, the expert agent queries a local knowledge base derived from the FDMNES
manual and then uses the retrieved passages to produce a grounded response. This design allows the
agent to use retrieved documentation to guide XANES calculation parameter selection, reducing
the need to hard-code all decision rules into the executor prompt or simulation backend and thus
helping to mitigate hallucinated parameter choices.
To illustrate this behavior, we evaluated the expert agent on three representative parameteriza-
tion queries concerning default absorber selection, crystal doping, and default energy-range settings.
All LLM agents were instantiated with GPT-4o. For readability, Table 1 presents condensed traces
containing the user query, the explicit retrieval call, the salient evidence extracted from the manual,
and a verbatim excerpt from the final agent response. The complete raw interaction logs for these
examples are available in the accompanying repository notebook.1
Across all three cases, the agent first invoked the query knowledge base tool with a targeted
search phrase and then produced a response consistent with the retrieved manual content. The
first example is especially instructive because it highlights both the usefulness and the limitations
of agent-mediated summarization: the final response captures the practical default behavior and
correctly points the user to the Z absorber and Absorber keywords, while the retrieved manual
evidence provides the more precise FDMNES convention that the calculated spectra correspond
to atoms sharing the atomic number of the first species listed under Crystal or Molecule. The
second and third examples show that the same retrieval mechanism can recover both procedural
instructions, such as the use of the Doping keyword, and default numerical settings, such as the
standard energy range and step size. Although these examples are qualitative demonstrations rather
than a formal retrieval benchmark, they show that the expert-agent layer can consult external
documentation before answering parameterization questions, improving transparency and reducing
reliance on unsupported free-form reasoning.

3.3
Natural-language specification of a chemical system
We next examined the natural-language interface using the query: “Compute the XANES for Ti
in TiO2.” In contrast to the file-based example discussed above, this request does not provide an
explicit local structure file. Instead, the agent must infer that the user is specifying a chemical
system and absorbing species at a higher semantic level, identify the appropriate workflow for
structure retrieval, and map the request onto the structured arguments needed for the downstream
XANES tools. In practice, this means that the agent must interpret the chemistry-level request,
issue a Materials Project query for TiO2, identify Ti as the absorbing element, infer that this
corresponds to absorber atomic number Z = 22, and pass these structured parameters to the
downstream XANES workflow before triggering the same FDMNES input-generation, execution,
and post-processing pipeline used in direct scripted mode.
Figure 3 shows the resulting normalized spectrum for a Ti absorber in bulk TiO2. The inset
displays the corresponding crystal structure used in the calculation, with Ti atoms shown in light
blue and O atoms in red. This example demonstrates that ChemGraph-XANES can operate not
only on explicit user-supplied files, but also on concise chemistry-oriented natural-language requests
that must first be resolved into structured database and simulation queries.
Such a mode of
interaction is particularly useful in exploratory settings, where a user may wish to query candidate
materials at the level of composition or chemical identity before deciding whether more specialized
local structures, surfaces, or defect models are needed.

4
Discussion
The examples presented here illustrate that the main value of ChemGraph-XANES lies not only
in automating individual XANES calculations, but in providing a unified workflow layer that can
support different modes of interaction while preserving a common scientific backend. In particular,
the framework accepts both explicit structural inputs, such as local POSCAR files, and higher-
level chemistry-oriented natural-language requests, such as specifying an absorber and composition
directly in text. This flexibility is important in practice because computational spectroscopy work-
flows do not begin from a single canonical input format. Depending on the application, a user may
start from a materials database query, a surface model generated in a separate slab-construction
workflow, or a structure file produced by prior DFT or molecular-dynamics simulations. By decou-
pling the user-facing query style from the backend XANES execution logic, the framework makes
these workflows easier to access without changing the underlying simulation procedure.
A second important implication is the suitability of the workflow for high-throughput XANES
generation. Once the relevant parameters have been specified, each structure-level FDMNES cal-
culation is independent, making the overall problem naturally task-parallel. This property allows
ChemGraph-XANES to benefit directly from Parsl-enabled distributed execution on HPC sys-
tems, where many XANES jobs can be launched concurrently while preserving a uniform interface
for inputs, outputs, and provenance tracking. In this sense, the framework is not only useful for

interactive demonstrations, but also for large-scale database generation, comparative spectroscopy
studies, and structure-spectrum dataset construction for downstream machine-learning applica-
tions. The ability to move seamlessly from a single natural-language request to many concurrent
XANES calculations is one of the main practical strengths of the agentic design.
At the same time, the present framework has important limitations that are tied to current
LLM capabilities.
Although the agents can already interpret user requests, select appropriate
tools, and map common calculation parameters onto structured arguments, they are not yet given
unrestricted freedom to modify arbitrary parts of the FDMNES input file. Such unconstrained
autonomy would risk introducing incorrect or poorly justified parameter choices and would weaken
reproducibility. We partly mitigate this limitation through schema-validated tool interfaces and
through the use of a documentation-grounded expert agent, which allows parameter choices to be
informed by the FDMNES manual rather than by unsupported free-form reasoning alone. As LLM
systems become more reliable, one can envision progressively extending the range of parameters
that agents are allowed to control. However, in our view, such flexibility should remain grounded
in external documentation and mediated through structured validation, rather than allowing the
model to alter the full simulation input without constraint.
5
Conclusion
We introduced ChemGraph-XANES, an agentic framework for automated XANES simulation and
analysis that couples natural-language task specification with structured tool interfaces, automated
FDMNES input generation, spectral post-processing, and provenance-aware data curation.
By
acting as an orchestration layer over established physics-based software, the framework preserves a
transparent and reproducible execution pipeline while making XANES workflows easier to access
and reuse. The examples presented here show that ChemGraph-XANES can ground parameter
selection in FDMNES documentation, support both file-based and chemistry-level natural-language
inputs, and scale naturally to high-throughput execution through task-parallel workflows. Together,
these capabilities make the framework a practical foundation for reproducible XANES studies and
structure-spectrum dataset generation for downstream analysis and machine-learning applications.
