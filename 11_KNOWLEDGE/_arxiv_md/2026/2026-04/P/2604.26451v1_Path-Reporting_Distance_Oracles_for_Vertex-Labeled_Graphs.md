Abstract
Let G = (V, E) be a weighted undirected graph, with n vertices. A distance oracle is a data structure
that can quickly answer distance queries, with some stretch factor. A seminal work of [TZ05], given an
integer k ≥1, provides such an oracle with stretch 2k −1, query time O(k), and size O(k · n1+1/k).
Furthermore, this oracle can also report a path in G corresponding to the returned distance.
In this paper we focus on vertex-labeled graphs, in which each vertex is given a label from a set
L of size ℓ. A vertex-label distance oracle answers queries of the form (v, λ), where v ∈V and
λ ∈L, by reporting (an approximation to) the distance from v to the closest vertex of label λ. Following
[HLWY11], it was shown in [Che12] that for any integer k > 1, there exists a vertex-label distance
oracle with stretch 4k −5, query time O(k), and size O(k · n · ℓ1/k).
This state-of-the-art result suffers from two main drawbacks: The stretch is roughly a factor of 2
larger than in [TZ05], and it is not path-reporting. We address these concerns in this work, and provide
the following results.
• First, we devise a path-reporting vertex-label distance oracle, at the cost of a slight increase in
stretch and size. For any constant 0 < ϵ < 1, our oracle has stretch (4k −5) · (1 + ϵ), query time
O(k), and size O(n1+o(1) · ℓ1/k).
• Second, we show how to improve the stretch to the optimal 2k −1, at the cost of mildly increasing
the query time. Specifically, we devise a vertex-label distance oracle with stretch 2k −1, query
time O(ℓ1/k · log n), and size O(k · n · ℓ1/k).

Introduction
Let G = (V, E) be an undirected graph, with positive weights on the edges w : E →R+. An (approximate)
distance oracle is a data structure that can (approximately) answer distance queries. The oracle has stretch
t, if for every pair u, v ∈V , the answer it provides ˜d(u, v) to a given query (u, v) satisfies
dist(u, v) ≤˜d(u, v) ≤t · dist(u, v) ,
where dist(·) is the distance in G with respect to the weights. The main interest is the tradeoff between
the stretch t, the size of the oracle (number of words needed to store it), and the query time. In a seminal
work, [TZ05] showed for any n-vertex graph and any integer k ≥1, a distance oracle with stretch 2k −1,
size O(kn1+1/k) and query time O(k). Subsequently, the size and query time were improved to O(n1+1/k)
and O(1) respectively, [Wul13, Che15]. This state-of-the-art tradeoff is optimal (up to constants), assuming
Erd˝os’ girth conjecture.
A useful feature of a distance oracle is its ability to report not just an approximation ˜d(u, v) to the
distance, but also provide a path in G between u, v of length ˜d(u, v). An oracle with this property is called
path-reporting. The original construction of [TZ05] provides a path-reporting oracle, albeit the improved
one of [Che15] does not. Recently there has been a surge of interest in path-reporting distance oracles
[ENW16, EP16, ACE+20, NS24, ES23, CZ24], most of these were interested in obtaining (almost) linear
size, as the [TZ05] oracles always have size Ω(n log n).
When stating the query time of path-reporting oracles, we will follow the convention of omitting the
length of the returned path. That is, if the algorithm returns a path P in time O(q + |P|), we will write that
the query time is O(q) (since reporting P will always incur time O(|P|)).
1.1
Vertex-Label Distance Oracles
In this paper we focus on distance oracles for vertex-labeled graphs, introduced by [HLWY11]. In this
setting, there is a set L = {λ1, . . . , λℓ} of labels, and each vertex receives a single label from L. We would
like to answer vertex-label queries, which are queries of the form (v, λ), for v ∈V and λ ∈L, and the goal
is to return an approximation for dist(v, λ), which is the distance from v to the nearest vertex of label λ.
Vertex-label queries arise naturally in various applications, where there are multiple vertices that can
provide a service to the source vertex v. For instance, in a network, the labels may indicate different types
of servers that provide certain functionality, or in a road network, the labels may correspond to services such
as gas, food, accommodation, etc. We would like to be able to answer queries such as “how close is the
nearest gas station”, rather than the distance to a particular one.
In [HLWY11] it was shown that the distance oracles of [TZ05] can be adapted to the vertex-label query
setting, with stretch 4k −5 and size O(kn1+1/k), regardless of the number of labels, ℓ. However, if ℓ<
n1/k, then this size is larger than the trivial solution with stretch 1 and size O(n · ℓ), that simply stores all
distances between vertices and labels. To address this issue, Hermelin et al. [HLWY11] devised an oracle
with improved size of O(kn · ℓ1/k), at the cost of increasing the stretch to 2k −1. In [Che12], the stretch
was substantially improved to 4k −5. Both results have query time O(k).
The current state-of-the-art leaves two main concerns. The first is that unlike standard distance oracles,
the vertex-label oracles of [HLWY11, Che12] of size ≈n · ℓ1/k are not path-reporting. Indeed, for many
applications the ability to report paths seems appealing (for instance, rather than obtaining just the distance
to the nearest gas station, we would like to receive a path to it). The second concern is that the stretch is
roughly a factor of 2 away from the conjectured optimum.

1.2
Our Results
In this paper we provide a positive answer to both concerns mentioned above. That is, by slightly increasing
the stretch, we show how to obtain path-reporting vertex-label distance oracles. In addition, we show a
construction that achieves the optimal stretch of 2k −1, at the cost of mildly increasing the query time.
Specifically, for any n-vertex graph, given an integer k > 1 and constant 0 < ϵ < 1, we devise a path-
reporting distance oracle, that answers vertex-label queries in O(k) time, and has stretch (4k −5) · (1 + ϵ)
and size O(n1+o(1) · ℓ1/k). (Alternatively, with stretch O(k) and size ˜O(n · ℓ1/k).) 1
Our second result achieves for any integer k > 1, a vertex-label distance oracle with stretch 2k −1, size
O(k · n · ℓ1/k), and query time O(ℓ1/k · log n). (This oracle can also be made path-reporting, at the cost of
increasing the stretch by a factor of 1 + ϵ, and the size by a factor of no(1).)

Path-reporting construction.
The query algorithm of [Che12], given the query (v, λ), finds a pivot pi(v)
such that there exists some vertex u of label λ with pi(v) ∈B(u). It then returns the sum of distances from
u, v to this pivot pi(v). We take a similar approach, and as long as i < k −1, we can apply the technique of
[TZ05], using clusters, to find a path from v to u via the cluster of pi(v). The issue arises when i = k −1,
then the clusters of vertices in this last level Ak−1 are too large to store. To overcome this hurdle, we apply
a pairwise path-reporting distance oracle, that approximately preserves distances (and reports paths), only
between a given set of pairs. Indeed, we show that the set of pairs containing all the possible required
connections for vertices in Ak−1 is sufficiently small, and the pairwise oracles of [ES23, NS24] induce a
slight increase in stretch and size.
Improved stretch.
The query algorithm mentioned above, given a query (v, λ), tests only the pivots of v.
This one-sided testing enables stretch of 4k−5, similarly to the context of compact routing schemes [TZ01],
where we have access to the bunches of the source v, but not to the bunches of the destination u. In order
to obtain the (conjectured) optimal stretch of 2k −1 for vertex-label queries, we need two-sided testing,
as in [TZ05, Che15], where we also inspect whether the pivots of the destination u are in B(v). Alas, the
destination u is not known, we are only given a label λ. In order to achieve two-sided testing, it seems that
in the i-th iteration, one must check for each vertex u of label λ, whether pi(u) ∈B(v). Unfortunately, this
may result in a linear query time. To deal with this barrier, in the pre-processing phase, for each λ ∈L,
we store all the level i pivots of vertices with label λ, denoted Pi(λ), in a hash table. Then, we can check
if there exists a vertex of Bi(v) in Pi(λ). This will be much faster, since the size of Bi(v), for i < k −1,

1.4
Related Work
In the context of planar graphs, [LMN13] showed a vertex-label distance oracle with stretch 1 + ϵ, size
O(n log n) and query time O(log n · log ∆), where 0 < ϵ < 1 is fixed and ∆is the hop-diameter of the
graph. This result is somewhat inferior to state-of-the-art distance oracles for planar graph, where [LW21]
obtained stretch 1 + ϵ, size O(n) and query time O(1). In [EFW21], a stretch 1 vertex-label distance oracle
for planar graphs is shown, with parameters (size and query) that are at most polylogarithmically larger than
the standard setting.
A closely related problem is the so-called colored distance oracles, which can answer label-to-label
queries. These objects were studied by [KK16, HK25], in the context of detecting patterns in texts, focusing
on the 1 + ϵ stretch regime.

Preliminaries
Let G = (V, E) be an undirected graph with nonnegative weights on the edges w : E →R+. Given a set
L of labels, each vertex is associated with a single label λ ∈L. For λ ∈L, the set of vertices of label λ is
denoted by Vλ.
For vertices u, v ∈V , define dist(u, v) as the length of the shortest path between u, v with respect to the
weights. If H is a subgraph of G, we denote distH(u, v) the distance in H. For a vertex v ∈V and a set
A ⊆V , define dist(v, A) = minu∈A{dist(v, u)}. Additionally, let dist(v, ∅) = ∞.
For every vertex v ∈V and label λ ∈L, we define λ(v) as the closest node to v that has the label λ,
that is, dist(v, λ(v)) = dist(v, Vλ).

Let (v, λ) be the query, for some v ∈V and λ ∈L. The query algorithm consists of three phases. Denote

querying Pi(λ) (recall that this is the closest vertex of label λ to vj such that vj = pi(yj)). Define
Ej = dist(v, vj) + dist(vj, yj). Again, both of these distances are stored in the first item of the data
structure.

Phase 3: Extract xk−1 = λ(pk−1(v)) from the data structure (recall that this is the closest vertex of label λ
to pk−1(v)). Compute Dk−1 = dist(v, pk−1(v)) + dist(pk−1(v), xk−1). These distances are stored

Let i∗= argmin0≤i≤k−1{Di}, and j∗= argmin1≤j≤| ˜B(v)|{Ej}. We return min{Di∗, Ej∗} as
the approximation to the distance from v to λ(v).

The running time of the query algorithm is O(k) for phase 1, O(| ˜B(v)|) for phase 2, and
O(1) for phase 3, so in total it is O(k +| ˜B(v)|). By Claim 2, with high probability for every v ∈V we have
