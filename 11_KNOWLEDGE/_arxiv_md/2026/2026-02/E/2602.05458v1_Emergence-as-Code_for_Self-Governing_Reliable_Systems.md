Abstract
SLO-as-code has made per-service reliability declarative, but user
experience is defined by journeys whose reliability is an emer-
gent property of microservice topology, routing, redundancy, time-
outs/fallbacks, shared failure domains, and tail amplification. As a
result, journey objectives (e.g., “checkout p99 < 400 ms”) are often
maintained outside code and drift as the system evolves, forcing
teams to either miss user expectations or over-provision and gate
releases with ad-hoc heuristics.
We propose Emergence-as-Code (EmaC), a vision for mak-
ing journey reliability computable and governable via intent plus
evidence. An EmaC spec declares journey intent (objective, control-
flow operators, allowed actions) and binds it to atomic SLOs and
telemetry. A runtime inference component consumes operational
artifacts (e.g., tracing and traffic configuration) to synthesize a can-
didate journey model with provenance and confidence. From the
last accepted model, the EmaC compiler/controller derives bounded
journey SLOs and budgets under explicit correlation assumptions
(optimistic independence vs. pessimistic shared fate), and emits
control-plane artifacts (burn-rate alerts, rollout gates, action guards)
that are reviewable in a Git workflow. An anonymized artifact
repository provides a runnable example specification and gener-
ated outputs.

Introduction
Cloud-native platforms excel at desired-state configuration: ver-
sioned specs are reconciled by controllers. Reliability is different.
SLO-as-code can version per-service targets and alert rules, yet
the objectives users care about are end-to-end journeys, not in-
dividual services. In microservice systems, journey reliability is
emergent: it depends on dynamic interactions (topology, routing,
retries/timeouts, fallbacks, shared failure domains) and on nonlin-
ear tail effects across many hops. As Anderson argued, “more is
different”: knowing the parts does not reconstruct the behavior of
the whole [1].
SRE practice operationalized SLOs, error budgets, and burn-rate
alerting as the contract between reliability and velocity [5, 6, 10].
In parallel, OpenSLO and generators like Sloth/Pyrra have made
atomic SLOs ergonomic in Git-based workflows [19, 23, 26]. How-
ever, these toolchains remain largely local: they compile per-service
intent, while journey objectives (“checkout p99 < 400 ms”) are typi-
cally tracked elsewhere and updated manually. When teams change
dependencies, timeouts, fan-out, or fallbacks, they rarely re-derive
the journey objective; drift accumulates. The consequence is struc-
tural: a service cannot be more reliable than its critical depen-
dencies [25], but in microservices which dependencies are critical
(under current routing and redundancy) changes continuously.
Thesis. Journey SLOs should be treated as compiled artifacts
derived from (i) explicit intent (journey objective, control-flow, gov-
ernance policy), (ii) continuously updated evidence about effective
topology/routing (e.g., from tracing, mesh config, or registries), and
(iii) atomic SLOs, under explicit assumptions about correlation and
measurement uncertainty. This is the core idea of Emergence-as-
Code (EmaC): a declarative interface that makes emergent journey
behavior computable, auditable, and actionable.
Contributions. We outline (1) an intent+evidence extension of
SLO-as-code that specifies journeys using a small set of control-flow
operators and binds them to observed topology; (2) compositional
semantics that derive interval (optimistic/pessimistic) bounds for
availability and tail latency under unknown shared fate; and (3) a
governance contract that can compile these bounds into control-
plane artifacts and constrained actions within a MAPE-K loop [9,
11, 14]. We present EmaC as a vision and research agenda rather
than a completed system.
Positioning. Unlike OpenSLO/Sloth/Pyrra, which compile atomic
SLO specs into alerting, EmaC compiles journey intent plus an in-
ferred interaction model into derived journey SLOs with explicit
uncertainty and a derivation trace. Unlike classic dependability
models (RBD/FTA), EmaC targets the cloud-native control plane:
it emits rollout gates and action guards and treats the model as
continuously reconciled. Unlike tracing-based end-to-end latency
modeling (e.g., LatenSeer), EmaC treats the model as a compilation
input and couples it to governance artifacts rather than analysis
alone.
2
Problem: Local SLOs, Global Journeys
2.1
The “sync tax” of journey SLOs
Per-service SLOs can be versioned next to code; journey objectives
are often documented in product specs and dashboards. Keeping
them consistent creates a recurring “sync tax”: topology and rout-
ing evolve quickly, but recomputing journey SLOs is manual and
therefore uncommon. Drift can hide user regressions (local SLOs
green, journey red) or enforce overly conservative budgets that
reduce velocity.

2.2
The nature of emergence
The gap is not a tooling accident. A journey is a network of in-
teracting services and its behavior cannot be reconstructed from
per-service summaries alone [1]. Three forces dominate. (i) Shared
fate. Redundancy only helps when replicas are not correlated; in
practice microservices share zones, clusters, CI/CD, libraries, and
quotas, and common-cause failures can dominate [12, 13, 27]. (ii)
Control-flow. Journeys include conditional paths, hedging, time-
outs with fallback, and partial success; objectives are defined over
a distribution of executions, not a single path. (iii) Tail latency.
Quantiles do not compose; accurate reasoning needs distributions
and causal structure [7, 29].
3
Vision: Governing Emergence as Code
3.1
What is EmaC?
EmaC is a declarative specification for journey-level resilience. It
separates intent (what we want to guarantee and how we are willing
to act) from evidence (what the system is actually doing).
Intent. A spec declares (i) a journey objective (availability and/or
tail-latency), (ii) a control-flow expression over a small operator
set (Section 1), and (iii) governance policy: which automation is
allowed under which bounds. EmaC binds each leaf to an atomic
SLO (e.g., OpenSLO) and to telemetry (metrics/traces).
Evidence and runtime inference. A runtime inference com-
ponent consumes operational artifacts—e.g., traces (OpenTeleme-
try spans), traffic policies/service mesh config, and deployment
metadata—and synthesizes a candidate journey model: the effec-
tive operator graph, branch probabilities, redundancy sets, and
failure-domain hypotheses, each annotated with provenance and
confidence [15, 20]. Crucially, EmaC does not require inference to
be perfect: operators may provide an explicit model (e.g., during
bring-up), while discovery serves as calibration and drift detection.
Failure domains as intent & evidence. Domains are declared
in intent (“these services share fate”) and can be refined by evidence.
When declared and inferred domains disagree, EmaC treats the
mismatch as a reviewable delta and evaluates automation using the
more correlated (more conservative) assignment until resolved.
From intent and the last accepted evidence-backed model, an
EmaC compiler/controller derives: (a) computed journey SLOs
with confidence bounds; (b) allocations of error budget to ser-
vices/domains; (c) burn-rate alerts and multi-window policies [10];
and (d) progressive-delivery gates and action guards [3].
Example. The artifact repository includes an end-to-end check-
out spec with a hedged external dependency and a timeout fallback,
plus generated Prometheus and Argo Rollouts artifacts [2].

P3: Policy/mechanism separation. Git stores intent and the last

4
Computing Emergent Journey SLOs
4.1
Availability with shared fate
A back-of-the-envelope journey estimate multiplies atomic avail-
abilities [25], but shared fate violates independence. Dependability
analysis addresses this via explicit modeling (fault trees/RBDs) and
common-cause failure treatment [12, 13, 27].
EmaC makes shared fate explicit via failure domains attached
to nodes/edges. Because failures are rare in high-availability sys-
tems, domains cannot be inferred from co-failures alone; instead,
inference must combine topology signals (co-location, shared de-
pendencies, shared rollout units) with incident evidence when avail-
able, producing confidence that gates automation (R1).

4.2
Tail-latency composition from distributions
Latency objectives are defined by tail behavior. The “Tail at Scale”
effect shows how small per-component tail risks amplify across
distributed hops [7]. EmaC therefore treats latency evidence as a
distribution (e.g., histograms) and composes distributions along the
operator graph (Table 1). OpenTelemetry provides a standard trace
vocabulary [20], and Prometheus provides histogram primitives and
server-side quantile estimation [21, 22]. Tracing can additionally
support causal models that estimate end-to-end distributions and
enable what-if analysis [29].
Implementability. In practice, composition can be performed
on discretized distributions (histogram buckets) using discrete con-
volution, max/min, mixtures, and order statistics; the compiler can
emit derived SLIs as synthetic metrics consumed by alerting and
gates. For operators that couple success and time (e.g., Timeout),

Uncertainty and drift. Derived latency SLOs are intervals: a

between predicted and observed end-to-end distributions provides
a drift signal: either instrumentation is stale or the inferred model
has changed.
5
From Computation to Self-Governance
5.1
Why computation alone is not enough
SLO computation matters only when it constrains control-plane
decisions (alerts, gates, and actions). Today, controllers reason in
terms of raw metric thresholds, while SLO owners reason in terms
of journeys and budgets. EmaC proposes a governance contract:
derived journey SLOs and budgets become the API between relia-
bility intent and automation. This aligns with MAPE-K autonomic
principles [11, 14], but makes the knowledge base versioned and
reviewable like code.
5.2
Compilation targets
A practical EmaC toolchain can compile into existing platform arti-
facts. Alerting. From a journey objective, generate burn-rate alerts
(including multi-window policies) and contributor alerts for domi-
nant services/domains [10]. Progressive delivery. Argo Rollouts
provides AnalysisTemplates/AnalysisRuns for promotion/rollback
based on metrics [3]; EmaC can generate gates that check pes-
simistic journey burn-rate and latency bounds over short/long ca-
nary windows. Git workflow. Git remains the source of intent
and the last accepted model; compilation emits generated mani-
fests/CRDs (e.g., PrometheusRule, AnalysisTemplate) surfaced as
reviewable diffs [16]. Inference may run continuously, but it pro-
poses signed model deltas with provenance and predicted bound
impact; policy can auto-accept low-risk/high-confidence changes
or open a PR for review (P5/R3).
5.3
Safe action spaces
Self-governing resilience is credible only with a constrained ac-
tion space. Typical capabilities include traffic shifting, scaling, and
toggling fallbacks, but only within declared bounds. EmaC treats
actions as declared capabilities attached to components (action
type, parameter bounds, preconditions, rollback), and uses policy
(e.g., admission-style constraints) to permit actions only when the

5.4
Walkthrough: what is in the artifact
repository
EmaC is intentionally not an “architecture diagram language”: the
goal is to govern an evolving socio-technical system by compil-
ing constraints over observed interactions, not by freezing a static
blueprint. Microservice platforms increasingly exhibit self-adaptive
behavior (traffic shifting, retries/hedges, progressive delivery, auto-
scaling) that changes effective dependencies at runtime [8]. In this
setting, “reliability work” becomes the work of maintaining control
interfaces: the objective, the operator semantics, the confidence we
have in the evidence, and the bounded action space. EmaC makes
these interfaces explicit and audit-friendly; it treats the journey
model as a versioned hypothesis whose uncertainty is surfaced as
bound width, so automation can default to conservative decisions.
This supports a pragmatic “antifragile” posture where systems can
adapt under bounded risk instead of relying on manual heroics [18].
To make the contract concrete, the repository includes a runnable
checkout example that exercises conditional control-flow, hedging,
and timeout fallback. At a glance, the journey intent is a small
operator tree bound to atomic SLOs and telemetry:
checkout := Series(Frontend,
Cond(p_hit; Cache, Catalog),
Timeout(200ms; Race(PayA, PayB), Queue)).
objective: A >= 99.9%, p99 <= 400ms.
From this spec and the last accepted inferred model, the compiler
emits (i) synthetic SLIs for the pessimistic availability bound 𝐴−
and an upper confidence bound on p99, (ii) Prometheus record-
ing/alerting rules for multi-window burn-rate, (iii) an Argo Roll-
outs AnalysisTemplate gating promotion on these pessimistic sig-
nals, and (iv) a provenance report that links each generated arti-
fact back to operators, assumptions, evidence windows, and domi-
nant contributors. All inputs/outputs are provided as inspectable
YAML/JSON in the anonymized repository [2].
6
Research Agenda
EmaC raises research questions across software engineering, sys-
tems, and dependability. R1: Failure-domain inference under
weak signals. How can we infer/refine shared fate when failures
are rare, combining topology evidence, incidents, and controlled
experiments, while producing confidence scores and operator over-
ride hooks? R2: Compositional tail latency under retries and
feedback. Retries, timeouts, and queueing create feedback loops;
what abstractions preserve analyzability while capturing domi-
nant tail effects? R3: Confidence-gated reconciliation. What
confidence and risk measures decide when an inferred delta can
auto-update generated artifacts vs. require review, and how should
reconciliation be rate-limited to avoid thrashing? R4: Counterfac-
tual what-if analysis. Can EmaC predict how a change (fallback,
timeout, routing) shifts journey distributions and budget burn with
bounds useful for gates? R5: Human factors and ownership.
How should the language surface uncertainty without overwhelm-
ing teams, and what workflows make journey SLOs maintainable?

Related Work
SRE, SLOs, and error budgets. SRE literature establishes SLOs
and error budgets as the interface between reliability and velocity
and develops burn-rate alerting [5, 6, 10]. The calculus of service
availability emphasizes dependency-driven limits [25]. EmaC tar-
gets a gap: making journey objectives computable from architecture
and tying automation to derived budgets as the system evolves.
SLO specifications and tooling. OpenSLO standardizes SLO
expression, and tools such as Sloth/Pyrra compile atomic SLOs
into Prometheus alerting rules [19, 23, 26]. EmaC instead compiles
journey intent plus an evidence-backed interaction model (topol-
ogy/routing/redundancy and failure domains) into derived journey
SLOs, bounds, and rollout gates.
SLO decomposition and allocation. Prior work decomposes
an end-to-end objective into per-service budgets and optimizes
allocations (e.g., ParSLO, CASLO) [17, 28]. EmaC is complementary:
it focuses on specifying and continuously reconciling the journey
model (control-flow and shared fate) on top of which allocation
operates.
GitOps and progressive delivery. GitOps popularized im-
mutable intent and controller reconciliation; Argo Rollouts opera-
tionalizes automated promotion/rollback from metric analysis [3].
EmaC uses these as compilation targets while providing a bounded,
versioned journey model that connects user objectives to low-level
metrics.
Latency modeling. Tail amplification is well documented [7].
Tracing-based work such as LatenSeer builds causal models of
end-to-end latency distributions [29]. EmaC is compatible with
such techniques but proposes a compiler/controller interface that
produces governance artifacts rather than analysis alone.
Self-adaptation and dependability. Autonomic computing
and architecture-based adaptation motivate closed-loop control [9,
11, 14]. Dependability research emphasizes explicit treatment of cor-
relation and common-cause failures [4, 12, 13, 27]. EmaC connects
these ideas to cloud-native operations by treating the knowledge
base as code and compiling conservative bounds into control-plane
constraints.
8
Conclusion
Reliability in microservices is emergent from interactions, yet cur-
rent SLO practice remains mostly local. EmaC is a vision for making
end-to-end journey reliability computable from intent plus evidence,
and for compiling conservative bounds into reviewable alerts, roll-
out gates, and constrained actions.
