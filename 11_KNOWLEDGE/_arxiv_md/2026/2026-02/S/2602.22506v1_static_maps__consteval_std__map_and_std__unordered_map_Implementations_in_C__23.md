Abstract
Using consteval from C++23, we implement efficient, new versions of std::map and
std::unordered_map for use when the keys are known at compile time.
We demonstrate
superior performance of our unordered_map on three demonstration use-cases: Lookup of ele-
mental mass from atomic symbol, lookup of amino acid from codon, and modification of stock
prices from S&P 500 ticker symbols all produced runtimes < 40%, < 35%, < 73% of the respective
runtimes of the std implementations. Our library runimes were < 80%, < 45%, < 97% of the
lookup time of Frozen, an alternative perfect hashing implementation in C++ for problems also
using constexpr keys. To our knowledge, this makes our library the overall fastest drop-in
(i.e., with a similar API) alternative to std::unordered_map. On one arbitrarily chosen demo,
we demonstrate runtimes < 35% of PTHash and < 89% gperf, state-of-the-art but not drop-in
hashing libraries via external tools.
Keywords: data structures, C++, hashing, perfect hashing

Introduction
1.1
Mapping
Mapping members of a collection keys K to their corresponding values V is a fundamental task in
computer science. Where a naive approach performs lookup by comparing against all keys in O(n),
“ordered mapping” uses a balanced binary tree to guarantee O(log(n)) lookup and insertion on a
collection of n = |K| keys [1–4]. Red-black trees are currently the prevalent implementation used for
std::map [5]. In practice, users of ordered maps on a fixed collection of keys sometimes implement
by sorting an array of keys and searching with binary search rather than the greater overhead (e.g.,
pointers to two child nodes) of the dynamic trees specified by AVL and red-black trees.
1.2
Hashing
Hashing uses a function mapping keys to a codomain in Z. In doing so, hashing algorithms produce
several bits at a time (using parallelism in the processor’s ALU) rather than the single bit achieved
by a compare in a balanced binary search tree. We will denote this “raw” hash of the key as
hraw(x), x ∈K. These hashes can use an integral SIZE_TYPE of 64, 32, 16, or 8 bits, but in practice,
users generally default to std::size_t, which is specified as ≥16 bits [6]; however, in practice,
x86-64 implementations commonly use 64-bits. These raw hashes are then mapped to Z/rZ via
htable, where r is the table size. E.g., a simple implementation would use htable(i) = i mod r.

1.4
consteval maps
Here we implement a consteval ordered map by automating the conversion of a fixed collection
of keys from a binary search tree to a sorted array.
We also implement unordered_map with
compile-time perfect hashing.
Both implementations use the new consteval qualifier from C++23, which specifies a routine
must run at compile time [11]. This allows constexpr lookup of keys, meaning keys known at
compile time will have lookup optimized out while still supporting lookup of keys unknown at
compile time. The library delivers state-of-the-art performance on three demonstration problems:
looking up atomic mass from atomic symbol, looking up amino acid from codon, and modifying
share price using a stock’s ticker symbol.
In addition to std::unordered_map, we compare to three hashing libraries: Frozen [12] (an
alternative drop-in replacement for std::unordered_map), PTHash [13] (a C++ library), and gperf
[14] (an external tool that accepts keyset K and generates C++ code defining a hash function). We
demonstrate superior performance to each of these libraries.

2.1
Implementation
Our map implementation is straightforward, using the constexpr std::sort implementation to sort
a collection of key-value pairs at compile time. Lookup is performed via std::lower_bound on the
sorted array of keys.
From here on, we focus on our implementation of unordered_map.

2.1.2
Class hierarchy
Perfect hashing eliminates the need to store keys for collision resolution. This can reduce the memory
footprint of a hash table, especially in cases where the values take little space. Nonetheless, a
program may iterate over the keys or values in which case the hash table can encapsulate this
data. std::unordered_map provides functions for retrieving the keys or values, so our maximal
unordered_map provides those features using the most generally applicable method. For increased
performance in common cases, we provide alternative classes with restricted functionality. All three
classes use at() to check the validity of key lookup and do not check key validity when using [].
No classes result in undefined behavior or out of bounds memory access if at() is used for lookup;
however, lookup of keys x ̸∈K may result in retrieval of a valid value instead of an error for some of
the classes. When using [], none of the classes check if the key x ∈K.
We use encapsulation rather than inheritance for cleaner organization and to avoid vtable lookup
from the ABC design pattern.
DangerousUnorderedMap (keys not stored, values stored directly within secondary table,
non-iterable): DangerousUnorderedMap is our primary building block that implements perfect
hashing of keys to values. It is so named because element access with [] can produce undefined
behavior when lookups are called with a key x ̸∈K. at() verifies that the primary hash bin isn’t
empty to prevent any out-of-bounds access of memory. But if an invalid key x ̸∈K is queried with
at(), it may still collide with some valid key y ∈K in the map and retrieve a valid value for that
invalid key without raising a warning or error. This class does not allow iteration over the keys or
values. We use this class internally in the other classes.
unordered_map_small_values (keys stored, values stored directly within secondary
table, iterable): For cases where the values are small types, unordered_map_small_values
encapsulates DangerousUnorderedMap<K,V>. This means the values are stored directly within the
secondary table rather than storing integer indices (thus avoiding an array lookup). The keys and
values are also stored in the unordered_map_small_values class in the order they were originally
provided. This is used to make it iterable, but results in storing all values twice (once in the
encapsulated DangerousUnorderedMap member and once in the value array). Lookup of an invalid
key x ̸∈K may return a valid value silently. In cases where values are small, this avoids a secondary
lookup, but with fewer safeguards when looking up invalid keys.
unordered_map (keys stored, value indices stored in secondary table, iterable): For
the general case, our unordered_map stores keys and values in their original order and encapsulates

2.1.3
consteval generation of pseudorandom numbers
Random number generators from the standard library cannot be called at compile time, so we
implemented a simple generator class exclusively for compile time. The algorithm is a 64-bit version
of xorshift [15, 16]. If no seed is provided, we automatically generate a seed from the compile
timestamp using the standard __DATE__ and __TIME__ macros.
These random numbers are used to generate values for k(primary), k(secondary).

We implement a custom algorithm for multiplying two numbers modulo a large prime. This
algorithm leverages the standard behavior of unsigned 64-bit integers wrapping around to 0 at 264.
Because our chosen primes are close to the maximum integer that can be stored in 64 bits, a modulo
can be accomplished by a comparion and possible subtraction faster than the standard modulo
operator %. When multiplying a · b mod P, the wraparound behavior is equivalent to a modulo
operation by 264, so we can avoid using the modulo operator again. The adjustment is a multiple of
264 −P, where P is our large prime. A similar operation can be done with smaller sizes of integers
as well.
2.1.5
Flexible SIZE_TYPE
Because many applications of hash maps have |K| = n ≪232 keys, it can be worthwhile to use
smaller integer types than std::size_t. Using smaller integer types can also increase the throughput
of SIMD parallelism for the hashing process. In particular, using 32-bit integers instead of 64-bit
integers allows for the hash function to perform a multiplication without handling numbers larger
than the 64-bit integer limit. Furthermore, a bucket size must be stored for every value of the
primary hash, so using a smaller integer type allows more of that array to fit in cache at one time.
The constructor determines the size type by default from the number of keys.

2.1.6
Avoidance of secondary hashing
When only one key is found for a primary hash, unordered_map can simply return element 0 of
the appropriate secondary table (which will have size 1), thereby avoiding the need of secondary
hashing. This speedup is more pronounced when few collisions occur in the primary table. This can
be achieved by increasing δ, although using too large a δ will stress the CPU cache more.
2.1.7
Factory construction
We allow customization of the size type and the space allocated to the tables. We also provide
a feature called USE_SALT that changes the values from the raw hash function. No two distinct
values can produce the same value when each XORed with a fixed value; therefore, XOR with a
fixed salt produces a random shuffling of raw hashes. For the cost of a single XOR (1 clock cycle
on many modern CPUs), a lower secondary hash frequency may be required. The best values for
these parameters would come from benchmarking on a specific keyset K. For a more convenient
process, we provide a factory function make_unordered_map that can infer good parameter values
from the keyset K. The ordinary constructor must determine allocation sizes for class members
(e.g., arrays) from template parameters, so they cannot depend on inferred parameters using the
existing C++ standards. make_unordered_map resolves this by choosing such parameters outside of
the constructor. Here the geometric bound on the expected time for finding k(primary), k(secondary)
can be used to time out and declare a given SIZE_TYPE unsuccessful.
Specifically, this factory function applies the raw hash to the keyset K and truncates the values
to different sizes. It selects minimum size where collisions do not occur. In the event that any values
differ by exactly the large prime for that size type, we enable USE_SALT to avoid a collision.
To use these functions, the data must be placed in a constexpr variable first for passing as a
template argument:
static constexpr auto data_array = std::to_array<std::pair<key_t, value_t> >(
{{key0,val0}, ...} );
auto key_to_value = static_maps::make_unordered_map<data_array>();
As an added advantage, other template parameters (such as n, the number of key-value pairs) will
be inferred, so this method is more robust to changes in the data. The initializer list of key-value
pairs can be imported from an external data source via #include.
One parameter that is not inferred is δ, implemented via DELTA_PRIMARY. It controls the constant
factor in the O(n) size of the table. We calculate the exact constant factor by rounding DELTA_PRIMARY
up to the nearest power of two. Rounding to a power of 2 makes for more efficient modulo by
bitmasking or casting to the appropriate integral type. The O(n) bound guarantees that some
factor will work in a reasonably short compilation but does not suggest what the factor should be in
practice. The effects of using different values vary depending on the system, so we did not implement
an algorithm to infer its value.

2.1.8
Drop-in API
Where a std::unordered_map is already being used with a static keyset K, the only code change
required is to change the namespace from std and add the number of keys to the template parameters
(after value type T). If the KeyEqual or Allocator optional template parameters are being set, our
code will not work without modification.
Lookup speed may be increased by tuning the template parameters manually. Enabling USE_SALT
may lower collisions and improve cache performance, but it adds the overhead of an XOR operation
during hashing (1 clock cycle on many modern CPUs)). DELTA_PRIMARY controls how big the
primary table is. Decreasing DELTA_PRIMARY generally increases compilation time and decreases
memory footprint, which can improve cache performance. To modify R_SECONDARY_TOTAL, derive its
value from get_secondary_table_total_size_bound(N, DELTA_PRIMARY, tau) with your chosen
τ. That function is in calculate_table_size.hpp. Lower τ values generally increase compilation
time but decrease the number of keys which need to run the secondary hash function. Values of
τ ≤1 could make compilation infeasible, but a value just above 1 tends to work well. Note that τ
could not be its own template parameter because it is a floating point number.
2.1.9
caching the unordered_map before low-latency access
Because construction is done at compile time, the hash table will be found in the .rodata section
and be immutable. This has advantages (neither allocations nor time for construction at runtime);
however, before low-latency use of the [] operator, recently having touched the keys and values is
advantageous. To this end, our library provides a cache() member function which iterates through
all keys and looks up the corresponding value at runtime. To prevent it from being optimized
out, a total is computed over the values in a volatile double value (an integral type risks being
optimized out). This can prepare a unordered_map immediately before low-latency access is required,
increasing hits to the CPU cache.
2.2
Runtime experiments
An unordered_map can also be used to lookup keys based on some input at runtime. Having fixed
keys lets lookups skip collision detection, since we choose a perfect hash during compilation. So,
lookups take less time while the program is running. These demos focus on speed gains when
performing access operations at runtime.
Note that the same unordered_map could be used to look up a collection of constants at compile
time for readability. For code that is already doing this, switching to static_maps::unordered_map
would immediately decrease runtime.
When the key is known at compile time, the lookup is
performed during compilation and the value is placed as a literal in the resulting program. There is
then zero runtime impact of using a lookup.

4
Discussion
A constexpr map or unordered_map removes any runtime impact of a lookup where the key is
known at compile time. Both Frozen and static_maps provide this advantage. However, Frozen
uses its own string type, necessitating explicit type changes in existing projects to adopt a constexpr
unordered_map. static_maps supports std::string_view which can wrap std::string and char*
strings. This benefit applies to new applications of consteval maps and hash maps.
16


## Page 17


4.1
map
While static_maps::map is an alternative to std::map, note that the compiler does optimize
std::map more effectively in the codon demo (Figure 1).
4.2
unordered_map
The demos show that constexpr hash maps benefit runtime lookup in a more pronounced manner.
Our static_maps::unordered_map outperforms all competition to varying degrees (Figure 2 and
Figure 3). But overall, it appears to be a better performer in general. The benefits are in both
construction time and time per lookup but do not diminish when lookups begin to dominate the
runtime, as in the codon to amino acid demo.
Preliminary evidence suggests read-only demos benefit more. The stocks demo with mutable
values is still significantly faster than std::unordered_map, but more similar to Frozen. Even
though the full map is not constexpr, shifting some of the work to compile time and using a perfect
hash still shows improvements.
By comparison to Frozen, we also see that static_maps has runtime benefits beyond those
inherent to constexpr. Our implementation of the hash map includes optimizations like small integer
sizes, custom modulo functions, and storing values directly in the table. This improves lookup times
over the constexpr and constinit maps provided by Frozen. As lookups dominate the runtime
of the application, the benefits become more apparent (such as in the codons demo). The time to
write values remains competitive as well, slightly faster than Frozen on the stocks demo, but also
notably with lower variance (which is helpful for low-latency applications such as trading). All of
these demos are run with generally applicable parameters. While we did not customize static_maps
for each demo for fairness (i.e., using a fixed δ for all demos), the ability to customize could improve
performance further on specific keysets. Frozen does not provide this kind of interface for modifying
its operation.
Other perfect hashing solutions such as gperf require more friction to use. static_maps compares
favorably in both convenience and runtime to these alternatives. In our element to mass demo,
our runtime was 34% of the same demo using a hash function from PTHash. PTHash focuses its
benchmarks on keysets of a million keys or more, so it has separate use cases which we have not
covered. The lookups must be implemented by the user of the library, since PTHash just finds a hash
function. Altogether, static_maps would be preferable in cases where a std::unordered_map is a
component of a program and tables are not being used as a database. On the other hand, gperf
generates code which can be customized to use as a hash map. This command line tool competes
admirably to replace a std::unordered_map in static-keyset scenarios. The resulting interface
differs from std::unordered_map enough that it is difficult to switch a large project to using gperf,
especially if the keyset may need to be changed for future builds. static_maps::unordered_map
improves over gperf in these aspects and still has a runtime 88% of an gperf-generated map in our
element to mass demo.
Altogether, the static_maps library provides compelling alternatives to the standard library’s
map classes for high-performance code. In our survey of options for mapping static keysets, it
provided the fastest runtimes in each relevant scenario and can be adapted fairly well to other
scenarios. For instance, if the number of lookups were significantly decreased, a lower δ may be
preferred, decreasing construction time (which would be weighted with relatively higher importance)
at the cost of increased secondary hashing frequency (which would be weighted with relatively lower
importance).
Compilation times are higher using our library (Table 1). Even so, they remain fairly modest

overall. Greater use of static constexpr qualifiers throughout may be useful to helping the compiler

unordered_map types instantiated. The downsides of avoiding recompilation include less inlining
unless the compiler can use Link Time Optimization.
4.3
Future ideas
4.3.1
Smaller raw hashes
The hash function that is run at every lookup includes generating a raw hash, which outputs a 64-bit
integer. For fairness, we did not modify this behavior, even when we’re truncating these values to
use a smaller SIZE_TYPE. A raw hash that can adapt to smaller integer types may improve runtime
further if the compiler does not already optimize this operation.
4.3.2
Dynamic keysets
For dynamic use cases where new keys may be added at runtime, a wrapper class could be devised in
a vein similar to how we made the values mutable. A hash map class could encapsulate a constexpr
hash map queried first on lookup then revert to a dynamic hash table for keys not known at compile
time. For online applications where regular rebuilds would update the keyset, this could achieve
similar runtime speeds to the fixed keyset situations.
5
Availability
5.1
Compiler compatibility
The library compiles under gcc 15.2.1 with argument -std=c++23. Often, -fconstexpr-ops-limit
will need to be increased from its default value (225 at time of writing), and for large keysets
-fconstexpr-loop-limit may also need to be increased (default 218) [18].
The library also compiles under clang 21.1.6, again with -std=c++23. The relevant limit for
clang is -fconstexpr-steps, which often needs increased to a value above 220.
To compile the demos in clang, -fconstexpr-steps=100000000 is a sufficient value for all demos.
The stock to price demo under clang also requires -fexperimental-new-constant-interpreter
[19].
Earlier versions of both these compilers have experimental support for C++23 features, and we
used some earlier versions of gcc and clang during development. The precise past versions on which
the entire library compiles are not known.
