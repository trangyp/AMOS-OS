Abstract
The prevalence of malicious packages in open-source repos-
itories, such as PyPI, poses a critical threat to the software
supply chain. While Large Language Models (LLMs) have
emerged as a promising tool for automated security tasks,
their effectiveness in detecting malicious packages and indi-
cators remains underexplored. This paper presents a system-
atic evaluation of 13 LLMs for detecting malicious software
packages. Using a curated dataset of 4,070 packages (3,700
benign and 370 malicious), we evaluate model performance
across two tasks: binary classification (package detection) and
multi-label classification (identification of specific malicious
indicators). We further investigate the impact of prompting
strategies, temperature settings, and model specifications on
detection accuracy. We find a significant "granularity gap"
in LLMs’ capabilities. While GPT-4.1 achieves near-perfect
performance in binary detection (F1 ≈0.99), performance
degrades by approximately 41% when the task shifts to iden-
tifying specific malicious indicators. We observe that general
models are best for filtering out the majority of threats, while
specialized coder models are better at detecting attacks that
follow a strict, predictable code structure. Our correlation
analysis indicates that parameter size and context width have
negligible explanatory power regarding detection accuracy.
We conclude that while LLMs are powerful detectors at the
package level, they lack the semantic depth required for pre-
cise identification at the granular indicator level.

Key Concepts
In this section, we discuss several key concepts. PyPI Pack-
age Registry (PyPI) is the primary package registry for the
Python ecosystem and a critical component of its software
supply chain. PyPI hosts 717,280 packages [2] and supports
frequent updates, automated publishing, and rapid dependency
resolution. Malicious Packages refer to software packages
that intentionally embed harmful functionality designed to
compromise the confidentiality, integrity, or availability of a
system. Malicious indicators are observable signals in pack-
age metadata, source code, or runtime behavior that suggest
the presence of malicious intent. These indicators may be
coarse-grained, such as suspicious package names, or fine-
grained, such as specific API call sequences, data flows from
sensitive sources to untrusted sinks, or obfuscated control
structures. Malicious indicators can appear at different ab-

Related Work
This section discusses the existing literature related to mali-
cious package detection and large language models (LLMs).
Malicious Package Datasets. Early efforts collected real-
world malicious packages across ecosystems such as PyPI,
npm, and RubyGems [3–8]. More recent datasets provide
finer granularity, including statement-level annotations and
taxonomies of malicious indicators [9], as well as ATT&CK-
aligned labels generated with LLM assistance [10]. Empirical
Analysis on Malicious Packages. Several works characterize
the prevalence, evolution, and behavioral patterns of malicious
packages in the wild. Several large-scale analyses examine
discrepancies between benign and malicious packages with
respect to metadata, static code features, and runtime behav-
ior [7, 11, 12]. Empirical evaluations of existing malicious
package detectors find the prevalence of false positives in the
operational context [4,8].
Static Analysis-based Detection Approaches. Specifi-
cally, existing works leverage metadata features [13], code
metrics [14, 15], cross-language features [16], anomaly de-
tection over installation scripts [17–19], and differential anal-
ysis between source repositories and released artifacts [20–
23]. More advanced techniques incorporate inter-procedural
dataflow analysis [20], call graph analysis [24], code slic-
ing [25, 26], bytecode analysis [27], and behavior graph
construction [28]. Dynamic Analysis-based Detection Ap-
proaches. Several works applied the sandboxing technique
for package installation and execution to extract behavioral
traces [29–32]. [33] applies kernel-level instrumentation to
collect fine-grained runtime features for machine learning
classifiers. Other approaches emphasize analyst-in-the-loop
investigation and surface salient runtime signals [34].
Machine Learning-based Detection Approaches. Pre-
vious work applies traditional classifiers to static features,
dynamic behaviors, or their fusion [15,35,36]. Graph learn-
ing has been used to model behavioral dependencies across
APIs and execution paths [28]. While meta-learning and en-
semble approaches also combine static metadata with dy-
namic API traces to reduce error rates [37]. Large Language
Model (LLMs)-based Detection Approaches. Several stud-
ies employ LLMs directly as classifiers for malicious source
code, often enhanced with few-shot learning, and retrieval-
augmented generation (RAG) [38,39]. Others integrate LLMs
into static analysis pipelines, for example, to identify sen-
sitive APIs [40, 41], refine feature sets [40], or assist code
slicing [42]. Multi-agent architectures further decompose
analysis tasks across specialized LLM agents to improve ro-
bustness [43]. Beyond detection, LLMs have been used to

summarize malicious behaviors [44] and automatically gener-
ate detection rules such as YARA or Semgrep signatures [45].
LLMs Evaluation on Security-related Tasks. A grow-
ing body of work critically evaluates LLMs across diverse
security-related tasks. Comparative studies consistently re-
port highly variable performance across models, datasets, and
tasks, with frequent false positives and non-deterministic out-
puts [46–49]. Evaluations in vulnerability detection show that
LLMs perform reasonably well for vulnerabilities requiring
local reasoning but struggle with complex, cross-procedural
semantics [50–52]. Studies of LLM-based agents and bench-
marks further indicate substantial performance gaps in real-
world security workflows [48,53–55]. Finally, several works
caution against overestimating LLM capabilities, arguing that
their effectiveness is task-dependent and often inferior to
expert-driven or hybrid approaches [49, 53, 56–58]. Over-
all, these findings motivate a systematic investigation into the
factors that impact LLM detection accuracy.
In particular, LLMs require investigation of detection accu-
racy at both the package and indicator levels, while accounting
for prompting strategies, model scale, context window, and
code complexity. This work addresses this gap through an em-
pirical evaluation of LLMs for malicious package detection,
explicitly analyzing the causes of their variable performance.

Methodology
This section details the construction of our dataset, model
configurations, and the evaluation metrics used to analyze
performance, consistency, and correlation.
4.1
Task Formulation
We formulate two classification tasks to evaluate LLMs’ ca-
pabilities for malicious package detection. Task 1: Malicious
Package Detection (Binary Classification). The objective of
this task is to determine if an LLM can distinguish between
benign and malicious packages based on source code. Task
2: Malicious Indicator Identification (Multi-Label Classi-
fication). The objective of this task is to assess whether the
models can identify specific malicious indicators in the code.
4.2
Dataset Construction
We construct two datasets to perform Tasks 1 and 2. Task
1 requires a mixed corpus of benign and malicious pack-
ages to evaluate the models’ ability to distinguish between
them. Task 2 requires a malicious dataset with statement-
level annotations to assess the validity of the models’ reason-
ing. The PyPI ecosystem hosts 717,280 packages [2], while
pypi_malregistry records over 10,000 malicious pack-
ages. Based on the data, we estimate a real-world benign-to-
malicious package ratio of approximately 73:1. Since experi-
menting with the exact real-world ratio is resource-intensive,
we maintain a 10:1 benign-to-malicious ratio following the
methodology established in [59]. The distribution remains
computationally feasible while ensuring that benign packages
outnumber malicious ones to reflect a skewed ecosystem.
Malicious Package Dataset. We require a dataset that pro-
vides statement-level annotations for malicious indicators in
malicious Python packages, where the dataset contains labels
for specific lines of code rather than just a single label for
the entire package, pinpointing the exact location where mali-
cious behavior (such as data exfiltration, payload dropping)
is triggered. To the best of our knowledge, only one study has
constructed such a dataset [9]. The dataset contains 370 mali-
cious packages, 2,962 indicators, and 396 individual files, and
is annotated with a taxonomy of 47 malicious indicators orga-
nized into 7 high-level categories (see Appendix A). Benign
Package Dataset. We initially collect 9,127 benign packages
from the dataset provided by the MalGuard study [40]. We
analyze the dataset and found a heavy-tailed distribution, with
a mean of 134,148 lines of code (LOC) but a median of only
288. Malicious packages are typically small, as in our mali-
cious dataset, the median LOC is 36. To align with the size of
the malicious dataset and maintain compatibility with LLMs’
context windows, we filtered packages with a minimum of 20
LOC, rank them in ascending order, and chose the top 3,700
packages. In this way, the highest LOC we observe is 260.

from commercial-level performance. Furthermore, we evalu-

an advantage over general reasoning (general models) capa-

4.4
Model Configuration
We employ several prompting strategies and temperature set-
tings to evaluate different levels of reasoning. Additionally,
we investigate the consistency of LLMs’ responses.
Prompting Strategy. Prompt Strategy directs the reasoning
process. Although model weights remain static, input prompts
govern how the model attends to specific tokens. Effective
strategies shift the answer from intuitive guessing to logical
derivation. In our study, we employ five strategies to assess a
range of reasoning depths. We list the prompting strategies in
increasing order of complexity and inference cost: Zero-Shot
(an unguided baseline), Few-Shot (in-context learning), Chain-
of-Thought (linear, logical deduction), Self-Consistency (con-
sensus among parallel paths), and Tree-of-Thought (advanced
branching logic). This progression reflects an increase in com-
putational requirements, as each subsequent strategy entails
larger input contexts, expanded token generation, or multi-
ple model passes to produce the final output. We provide
the detailed specifications for all prompt templates in Ap-
pendix B. For the remainder of the paper, we denote Zero
Shot, Few Shot, Chain of Thought, Self-Consistency, and Tree
of Thought as ZS, FS, CoT, SC, and ToT, respectively.
Temperature. Temperature modulates the model’s proba-
bility distribution. Lower temperatures sharpen the distribu-
tion, thereby favoring precision. A higher temperature broad-
ens the distribution, thereby allowing for a more diverse se-
lection. For open-source models, we evaluate levels: lowest
(0), median (0.5), and highest (1). For the proprietary model,
we evaluate only the lowest (0) and the highest (2) due to
resource constraints. Throughout this paper, we denote the
temperature settings of 0, 0.5, 1, and 2 as T0, T0.5, T1, and T2
respectively.
Consistency. Models are inherently non-deterministic.
Even with identical inputs, variations in floating-point op-
erations can result in different outputs. To investigate the
non-determinism, we regenerate each response five times for
open-source models. We limit proprietary model regeneration
to three trials due to monetary constraints.
Configuration. For the remainder of the article, we define
the term ‘configuration’ as a combination of a temperature
value and a prompting strategy.
4.5
Sampling Strategy
Our experimental design involves 13 LLM models, 5 prompt
strategies, and 3 temperature settings. For binary classifica-
tion, which consists of a dataset of 4,070 (3,700 benign + 370
malicious) packages, the total number of responses would
be 793,650 (4,070 packages × 13 models × 5 prompts × 3
temperatures). For multi-label classification, which consists
of a dataset of 370 packages and each response being regener-
ated 5 times, the total number of responses would be 72,150
(370 packages × 13 models × 5 prompts × 3 temperatures).
Conducting an experiment of this scale is computationally
infeasible. Hence, we adopt sampling strategies for the two
tasks mentioned in section 4.1.
Binary Classification. We use both benign and malicious
packages, selecting 2.5% from each dataset. We get a result
set of 10 malicious packages (2.5% of 370 malicious pack-
ages) and 93 benign packages (2.5% of 3,700). Using these
subsamples, we generate a total of 19,570 responses (103
packages × 12 open-source models × 5 prompts × 3 temper-
atures + 103 packages × 1 proprietary model × 5 prompts
× 2 temperatures). We use a fixed seed so that all the con-
figurations receive the same set of packages, maintaining the
integrity of our comparative analysis. Multi-Label Classi-
fication. We use a configuration-specific sampling strategy,
selecting 10% of the malicious packages (37 files) for each
configuration. We generate a total of 34,410 responses (12
open-source models × 37 files × 5 prompts × 3 tempera-
tures × 5 iterations + 1 proprietary model × 37 files × 5
prompts × 2 temperatures × 3 iterations). While the data
samples vary across configurations, they remain consistent
within each configuration to ensure a fair comparison.
4.6
Evaluation Framework
RQ1: Performance Analysis. We evaluate the performance
of LLMs in identifying malicious software packages and in-
dicators, as follows: (a) We assess the binary classification
performance of models across all 15 configurations using the
F1 score. This phase includes analyzing performance vari-
ations across prompt strategies and temperature settings, as
well as identifying outliers in the results. (b) We examine how
effectively models identify malicious indicators by treating
this as a multi-label classification task. We calculate the F1
score for every individual malicious indicator present in a
malicious package. Additionally, we compute macro, micro,
and weighted F1 scores to assess the overall performance
of models across all configurations. (c) Based on the results
from the previous task, we identify and rank the top 10 mod-
els and configurations using the macro, micro, and weighted
F1 scores. We further discuss the results. (d) We select the
best-performing model based on the Weighted F1 score. We
choose this metric because the dataset exhibits significant
class imbalance, evidenced by a high variance in indicator
frequency (median frequency of 35.0, standard deviation of
82.23). The Weighted F1 score accounts for this frequency,
providing the most representative metric for the distribution.
We then apply this model to the entire population of 370
malicious packages to analyze performance across specific
indicators. (e) We quantify the performance gap between
high-level malicious package detection (using the F1 score)
and fine-grained malicious indicator identification (using the
Weighted F1 score). We compare performance across groups
by model and configuration to determine whether granularity
affects model accuracy.

RQ2: Consistency and Reasoning Analysis. To evaluate
the consistency of model predictions and the soundness of
their reasoning, we perform two primary procedures: (a) We
regenerate every response five times, as detailed in Section
4.4. We calculate the standard deviation of the F1 scores
to quantify the variability of the model’s output. We then
rank the models based on this standard deviation, where a
lower value indicates greater consistency in identifying ma-
licious behavior. (b) To evaluate the logical validity of the
model’s output, we randomly sample 100 responses (using a
fixed seed) from the best-performing model and configuration
identify in RQ1. We compare the model-generated reasoning
against the ground truth reasoning provided in the malicious
package dataset. Additionally, we consider the confidence
score associated with each response to judge the reasoning, al-
lowing us to assess the model’s metacognitive alignment with
its own output quality. Finally, we analyze specific instances
of correct and incorrect reasoning, identifying scenarios where
the model fails to construct a sound logical path.
RQ3: Correlation Analysis. To assess how model speci-
fications and configuration settings affect malicious indica-
tor identification performance, we compute Spearman rank
correlation coefficients to evaluate relationships between the
Weighted F1-score and five key variables: parameter size, con-
text width, temperature, code complexity (measured through
cyclomatic complexity), and prompting strategy. We explicitly
rank the prompting strategy based on increasing complexity
and inference cost, as detailed in Section 4.4. While Pearson’s
correlation coefficient identifies linear proportional trends, in
which an increase in one variable is accompanied by a propor-
tional change in another at a constant rate, we use Spearman’s
rank correlation to detect monotonic trends. Monotonic trends
are relationships where variables consistently move in the
same direction (e.g., as one increases, the other consistently
increases or decreases) but not necessarily at a constant rate or
in a straight line. We select this method because Spearman’s
rank correlation does not assume normality and is specifically
suitable for evaluating ranked distributions, making it more
appropriate for our nonlinear configuration data. [60]

Findings
In this section, we present the experimental results regarding
our three research questions. In Section 5.1, we evaluate the
capabilities of Large Language Models in detecting malicious
software packages (high-level) and identifying malicious in-
dicators (fine-grained) in those malicious software packages
(RQ1). In Section 5.2, we measure the reliability of these
models by examining the consistency of their output and the
soundness of their reasoning (RQ2). Finally, in Section 5.3,
we investigate how factors such as parameter size, context
width, prompting strategies, temperature, and code complexity
correlate with performance measure (RQ3).

Key Takeaway. In the results, we observe variability in
model performance (µ = 0.57, σ = 0.18). The mean indicates
that the average LLM is unreliable at detecting malicious
packages. Additionally, the standard deviation suggests a gap

allows attackers to avoid the identity verification required for
SSL certificates. Avoiding certificates removes a traceable pa-
per trail. Models struggle to distinguish careless coding from
deliberate attack. Finally, Crypto Wallet Harvesting registers

and mid-sized models. Examples include QWENC, LLAMA,

ever, the models experience moderate fluctuations at T0.5. The
Low Stability Cluster (µSD ≥0.09) comprises the largest pa-
rameter models. The models are GP120, MIXTR, PHI04,

5.2.2
Soundness of Reasoning
We analyze 100 LLAMA-generated responses at T0 using ZS
for malicious indicator identification. We find that the mod-
els provided 83 correct, 11 incorrect, and 6 partially correct
reasons. We explain the findings in this section.
Semantic Understanding. The model demonstrates
a strong ability to interpret the code syntax, but oc-
casionally struggles with semantic understanding. The
models excel at identifying dangerous built-in
func-
tions like subprocess.Popen, os.system, and exec(). In
candyload-9.27/setup.py, the model correctly identifies
that a subprocess was used to execute a shell command. How-
ever, they sometimes fail to distinguish between standard and
malicious utility times. In httptool-4.14/setup.py, the
model misclassifies distutils.core as a malicious utility.
Although the utility is capable of malicious code execution,
no such exploitation occurs in this case; rather, the model
hallucinates a justification.
Pattern Matching. The model detects specific techniques
used by malicious package authors to evade detection.
For example, in advirtual-10.61/setup.py, the model
identifies a shell command and recognizes the usage of a
common pattern, CREATE_NO_WINDOW and -Hidden Window
flags. The model correctly reasons that these flags are in-
tended to hide the execution from the user. However, the
model also struggles to interpret common coding patterns.
In advpruebitaa6-1.0.0, the model misclassifies a benign
Base64 decoding function as malicious. The error likely oc-
curs because the model identifies such patterns in its training
data where encoding functions are frequently used for ma-
licious intent. The behavior shows how models use pattern
matching to identify indicators.
Heuristic Reasoning. Heuristic reasoning is the use of
10


## Page 11


mental shortcuts or established patterns to reach conclusions
instead of logical analysis. In our study, the models employ
shortcuts by repeatedly flagging proton.me email addresses
as suspicious in packages such as adpyw-10.70. The model
likely learns the correlation between privacy-focused email
services and malicious activity, but the logical link is weak.
On the other hand, the model used external knowledge to
identify typosquatting in librandloaded-5.52, recognizing
that the package name is suspiciously similar to a popular li-
brary. The findings demonstrate that the models rely on broad
patterns and external context to make informed decisions.
Metacognition Ability. Metacognition refers to a model’s
ability to evaluate its own reasoning process. [61] In LLMs,
the metacognition is often expressed through confidence
scores that reflect how confident a model is about its reasoning.
Our findings show that the model demonstrates metacognitive
ability by assigning high-confidence (0.95 and 0.99) scores
to concrete threats such as reverse shells in blypack-0.5
and hidden windows in advirtual-10.61/setup.py. More-
over, the model correctly reduces the confidence scores
to 0.5 and 0.4 for ambiguous or weak indicators, such
as generic emails (1inch-8.9) and software versioning
(advirtual-10.61/setup.py), respectively. The ability to
assign confidence scores based on the strength of evidence
suggests that the model can distinguish between certain mali-
cious behavior and suspicion. [59]
Reasoning Failures. Reasoning failure is the sig-
nificant divergence of a model’s response from three
core pillars of logic: coherence, context, and factuality
[62]. In our study, we observe reasoning failure when
the LLMs flag the standard Microsoft::Windows clas-
sifier in beautifulsoup-requests-12.15.13 as suspi-
cious, which is an incorrect classification. Similarly, in
advpruebitaa6-1.0.0, the model identifies a decoder prim-
itive but fails to analyze the content being decoded. We verify
that the content is benign. The findings demonstrate that the
model often stops reasoning at the surface level, identifying
a suspect feature without investigating whether its specific
context was actually malicious.
Key Takeaway. We observe differences in the capabili-
ties of LLMs across different logical frameworks. Deductive
reasoning is the strongest zone, as models are efficient at
following "if-then" rules. For instance, a hidden window com-
bined with an execution shell leads to the conclusion of a
malicious package. In comparison, abductive reasoning is
moderately effective. Instead of substantive proof, models
rely on best guesses based on statistical patterns. Such pat-
terns often lead to the use of stereotypes, such as assuming
that a privacy-focused email address implies criminal intent.
Contextual reasoning is the weakest capability of the mod-
els. Models struggle to understand the developer’s intent; for
example, in the case of reverse shells, they often fail to distin-
guish between legitimate administrative tools and malicious
packages.

Threats to Validity
Internal Validity. We acknowledge the risk of data contami-
nation, as closed training sets for models like GPT-4.1 may
include our malicious samples. If so, high detection scores
might stem from memorization rather than semantic reason-
ing. We recognize the impact of non-determinism, observing
stochastic outputs even at fixed temperatures. We mitigate this
by conducting five trials for open-source models and three for
proprietary ones, though we cannot guarantee that different
random seeds would not yield slightly different rankings.
External Validity. We limit our scope to the PyPI ecosys-
tem. We observe that malicious patterns in Python differ sig-
nificantly from those in compiled languages like C++. Conse-
quently, we cannot generalize our findings to other ecosystems
(e.g., npm, Maven) that rely on distinct syntactic structures.
We acknowledge the discrepancy between our experimental
imbalance (10 : 1) and the real-world skew (73 : 1), attributed
to computational constraints. Consequently, we cannot guar-
antee that precision scores hold in production, where the "base
rate fallacy" often amplifies false positives.
Construct Validity. We rely on the accuracy of the ground
truth annotations. We assumed the taxonomy of 47 indicators
captures the full spectrum of intent; consequently, any mis-
labeling or missed indicators would affect our precision and
recall metrics. We employ sampling for the multi-label task
due to computational constraints. Although we use stratified
random sampling, we cannot verify that the subsets fully cap-
ture the population’s complexity, as unsampled outliers may
influence the final F1 Scores.
Conclusion Validity. We utilize standard metrics and
Spearman correlation. We observe that Spearman fails to cap-
ture non-linear interactions. Consequently, we caution against
interpreting low coefficients as definitive proof of zero causal-
ity, attributing findings to our specific dataset configuration.

Conclusion
In this paper, we present an evaluation of 13 Large Language
Models for detecting malicious software packages in the PyPI
ecosystem. We evaluate these models on 3,700 benign and
370 malicious packages and quantify their performance in
binary detection and fine-grained indicator identification. Our
findings reveal a granularity gap in the capabilities of cur-
rent LLMs. While state-of-the-art models such as GPT-4.1
achieve near-perfect performance in binary classification, per-
formance degrades significantly when identifying malicious
indicators. This disparity suggests that while models can effec-
tively flag suspicious packages using heuristics, they struggle
to decompose the complex, context-dependent logic required
to accurately attribute malicious intent. We further identify
that model architecture plays a more significant role than
sheer scale. General-purpose models such as LLAMA per-
form most consistently, whereas specialized Coder models
demonstrate superior capability in detecting structurally rigid
attacks. Our correlation analysis also shows that factors such
as parameter size, context width, and cyclomatic complexity
possess negligible explanatory power regarding detection ac-
curacy. To sum up, LLMs demonstrate potential for defense
but currently lack the reliability to function independently.
Therefore, they should be deployed as complementary com-
ponents rather than as standalone detectors.

This section provides a stakeholder-based ethics analysis

Stakeholders and Potential Impacts Our work evaluates
13 Large Language Models (LLMs) for malicious package
and malicious indicator detection across 4,070 Python pack-
ages, including 370 malicious samples with 47 annotated
indicators.
• Open-source developers and end users benefit from
improved defensive understanding. However, the risk is
that adversaries may exploit performance gaps.
• Security teams and PyPI maintainers gain guidance

• LLM vendors and open-source model communities
receive comparative performance evidence, however, the

• Adversaries could, in principle, infer weaknesses in

• Society at large: is impacted through the downstream

Ethical Principles Considered (Menlo Report)
Beneficence. Our study helps defenders understand the
granularity gap that LLMs achieve strong binary detection
(F1 = ∼0.99 for GPT-4.1) yet degrade by ∼41% when iden-
tifying fine-grained malicious indicators.
Respect for Persons. The study uses public open-source
packages and metadata without interacting with human sub-

already in datasets is used.
Justice. We report class imbalance—e.g., the 10:1 benign-

Respect for Law and Public Interest. All analyzed pack-
ages are publicly available. We provide full methodological
transparency, including sampling procedures, evaluation con-
figuration, and limitations.

Dual-use risk. Indicator-level performance tables (e.g.,

loading) could theoretically help adversaries. To reduce harm:

Operational misuse. High binary accuracy may encourage

Institutional Oversight

Appendix A: Malicious Indicators
This section presents 47 malicious indicators identified in 370
malicious Python packages. These indicators are organized
into seven categories. A single line of code may contain
multiple indicators. For each indicator, we provide a definition
adapted from the original paper [9].
Execution Stage
This category characterizes malicious behaviors based on the
point in the package lifecycle at which they execute, such as
during installation or import.
17


## Page 18


Import-Time Execution
Attackers embed executable payloads directly in module-level
code (often within __init__.py) so that malicious logic runs
immediately upon import PACKAGE_NAME.
Install-Time Execution
By placing arbitrary code in the top-level scope of setup.py,
adversaries ensure the payload executes automatically during
installation.
Lifecycle Hook Hijack
Standard installation hooks (e.g., install, build, sdist)
are overridden so attackers can inject malicious logic during
specific build phases.
Execution Mechanism
This category captures the techniques used to execute mali-
cious code, independent of when execution occurs.
Dynamic Evaluation
Functions such as eval() and exec() are used to run code
stored as strings, enabling payloads to be assembled only at
runtime and evade static analysis.
Conditional Payload Trigger
Execution is restricted to specific operating systems, enabling
targeted attacks and preventing execution in non-target envi-
ronments.
Binary Execution
Compiled binaries bundled with the package are executed to
bypass Python-level inspection and leverage low-level system
capabilities.
Hidden Code Execution
Background tasks or hidden subprocesses are spawned to
reduce process visibility and evade basic monitoring.
Dynamic Module Import
Modules are imported using dynamically constructed strings
to conceal dependencies and hinder static dependency scan-
ning.
Dynamic Package Install
Dependencies are installed at runtime instead of being de-
clared in package metadata, bypassing static dependency anal-
ysis.
Script File Execution
External script files (Python, Bash, PowerShell) are executed
to place malicious logic outside the primary codebase.
Shell Command Execution
Raw shell commands are executed, granting access to power-
ful system utilities and privileged operations.
Exfiltration
This category includes techniques used to extract data or files
from the victim system through covert or disguised channels.
Data Exfiltration
Selected sensitive data—such as environment variables or
tokens—is exfiltrated to attacker-controlled endpoints.
File Exfiltration
Entire files are collected and uploaded for extraction.
DNS Tunneling
Data is encoded into DNS queries, creating a covert outbound
communication channel that bypasses routine network inspec-
tion.
Webhook Exfiltration
Messaging APIs (Telegram, Slack, Discord) are misused to
exfiltrate stolen data via legitimate-looking communication
channels.
Suspicious Domain Exfiltration
Stolen files and credentials are sent to attacker-controlled
domains associated with known malicious infrastructure.
System Impact
These indicators involve reading, writing, or modifying local
files and configurations on the victim machine.
Environment Modification
System environment variables are altered to redirect execution
or load malicious binaries.
Startup File Persistence
Autostart entries are modified to ensure malicious execution
upon system boot or user login.
18


## Page 19


Crypto Wallet Harvesting
Filesystem paths are scanned to locate wallet files and associ-
ated private keys.
Directory Enumeration
Directory contents are enumerated to identify high-value files
such as credentials or configuration data.
System Info Reconnaissance
System metadata is collected to profile the execution environ-
ment or detect sandboxes.
File Relocation
Files are moved to persistent or hidden locations to maintain
long-term presence.
File Deletion
Files are deleted to remove evidence or hinder forensic analy-
sis.
Arbitrary File Write
Files are written to disk to stage payloads or support further
compromise.
Sensitive Path Write
Files or directories are written to privileged system locations
to gain persistence or manipulate system behavior.
Network Operation
These indicators describe malicious network activity dis-
guised as legitimate communication.
Geolocation Lookup
External IP-lookup services are queried to determine the vic-
tim’s geolocation and timezone.
Mining Pool Connection
Connections to cryptocurrency mining pools are initiated to
enable unauthorized mining.
Suspicious Connection
Connections are made to attacker-controlled, typosquatted, or
newly registered domains.
Archive Dropper
Remote archive files are downloaded and unpacked on the
victim system.
Binary Dropper
Compiled binaries are downloaded for execution on the victim
machine.
Payload Dropper
Payloads are retrieved after installation to keep initial package
contents benign-looking.
Script Dropper
Script files are downloaded for dynamic execution, enabling
flexible attack logic.
Reverse Shell
Reverse connections to attacker-controlled servers provide
interactive command execution capabilities.
SSL Validation Bypass
SSL certificate validation is disabled to communicate with
untrusted servers.
Unencrypted Communication
Unencrypted HTTP is used to exchange sensitive data in plain
text.
Defense Evasion
These indicators represent obfuscation and evasion techniques
used to conceal malicious intent and bypass detection mecha-
nisms.
ASCII Art Deception
Malicious logic is placed near ASCII art or similar distractions
to reduce scrutiny during manual review.
Computational Obfuscation
Bitwise operations, dynamic attribute lookups, and similar
tricks are used to obscure logic until runtime.
Encoding-Based Obfuscation
Payloads are encoded and decoded only at execution time to
evade signature-based scanners.
19


## Page 20


Encryption-Based Obfuscation
Encrypted payloads are decrypted only at runtime, complicat-
ing reverse-engineering efforts.
Embedded String Payload
Payloads are hidden inside strings and later reconstructed or
executed.
Error Suppression
Exceptions are intentionally suppressed to hide abnormal
behavior and avoid detection.
Metadata
These indicators involve anomalous or deceptive package
metadata used to disguise malicious intent.
Suspicious Author Identity
Author metadata uses placeholder names or anonymous email
addresses to obscure attribution.
Combosquatting
Malicious package names combine known library names with
additional tokens to mimic official extensions.
Suspicious Dependency
Unusual or unnecessary dependencies are declared to intro-
duce harmful libraries or enable execution capabilities.
Description Anomaly
Descriptions contain nonsensical text, random characters, or
keyword stuffing.
Decoy Functionality
The package’s stated purpose masks malicious behaviors that
differ significantly from the advertised functionality.
Metadata Typosquatting
Package names closely resemble those of popular libraries,
differing only by minor spelling changes.
