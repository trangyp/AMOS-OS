Abstract
Heterogeneous Internet of Things (IoT) systems suffer from fragmentation across hardware architectures,
networking stacks, and data serialization formats. Existing standards (such as MQTT, CoAP, and
DDS) rely on address-bound, imperative routing models that require hardcoded configurations and
leave no flexibility for runtime schema translation. This paper presents TIP (The Intent Protocol),
a decentralized, declarative network protocol. Instead of addressing specific physical endpoints,
nodes submit abstract intents specifying desired capabilities, schemas, and Quality of Service (QoS)
constraints. The TIP Engine resolves matching nodes using a hybrid discovery mechanism combining
local multicast DNS (mDNS) with Kademlia Distributed Hash Tables (DHT). Selection is optimized
via a multi-criteria scoring algorithm incorporating network latency, historical reputation, and contract
compliance. Mismatched data representations are reconciled on-the-fly inside isolated WebAssembly
(WASM) sandboxes compiled dynamically from TOML specifications. Security is enforced through
Ed25519 signatures, X25519 key exchanges, and ChaCha20-Poly1305 payload encryption. Evaluation
of our reference implementation in Rust and C++ shows sub-millisecond translation overhead and
robust resilience under industrial conditions.

Introduction
The Internet of Things (IoT) has grown exponentially, connecting billions of constrained nodes across
smart cities, power grids, and industrial manufacturing plants [1]. This expansion, however, is crippled
by fragmentation. Hardware architectures run different instruction sets, communication networks utilize
incompatible media, and applications serialize data using conflicting formats (e.g., JSON, Protocol Buffers,
or raw endian-dependent integers).
From a mechatronics engineering and industrial automation perspective, traditional manufacturing lines
rely on Programmable Logic Controllers (PLCs) running sequential routines written in Ladder Logic
(LD) or Structured Text (ST) according to the IEC 61131-3 standard [2]. These systems are highly rigid;
variables are bound directly to physical memory addresses and hardware register maps (e.g., Modbus
registers, PROFIBUS slots, or EtherNet/IP assembly objects).
Industrial fieldbuses present distinct interoperability challenges. For instance, Modbus RTU/TCP operates
on a polled master-slave architecture with no self-description; registers are raw 16-bit blocks, and whether
they represent a signed integer, a scale-factor float, or character bytes is entirely up to the hardcoded
parsing logic of the client. Similarly, high-speed buses like EtherNet/IP or PROFINET rely on electronic
data sheets (EDS) or GSDML configuration files which must be compiled into the PLC project at design

declarative networking model where applications request what capability they require, rather than
specifying where or how to execute the request. The network dynamically resolves the request, translates
incompatible schemas, and delivers the data securely.
This paper provides the following contributions:
1. A decentralized architecture integrating mDNS and Kademlia DHT for zero-configuration capability
discovery.
2. A multi-criteria selection model formulating candidate utility as a function of network RTT, node
constraints, and trust scores.
3. A sandboxed schema translation engine using WebAssembly compiled on-the-fly from simple
TOML configurations.
4. A zero-trust security framework incorporating Ed25519 signatures, X25519 ECDH key exchanges,
and ChaCha20-Poly1305 encryption.

Related Work
Current IoT interoperability focuses on semantic middleware, standardized IoT specifications, or protocol
gateways. Lightweight transport standards like MQTT and CoAP [4] provide low-level transmission
but lack built-in dynamic schema negotiation or zero-configuration decentralized discovery. Standards
like Matter [5,6] standardize local smart home device topologies, but they run into limitations regarding
WAN scalability, multi-factory federation, and runtime unit/type conversion. Other semantic architectures
such as W3C Web of Things (WoT) [7] and oneM2M [8] define metadata models for describing device
interactions, yet they do not specify a unified binary transport routing layer. On the industrial automation
side, OPC UA [9] provides extensive object modeling and information architecture, but its substantial
CPU and memory footprint makes it unsuitable for resource-constrained 8-bit or 16-bit microcontrollers.
TIP addresses this gap by combining decentralized peer-to-peer routing, lightweight binary serialization,
and sandboxed execution.

3.2
Binary Wire Format & CoAP Encapsulation
To keep the footprint small for constrained microcontrollers, TIP utilizes the Constrained Application
Protocol (CoAP, RFC 7252) running over UDP as its transport layer. TIP packets are not sent raw over
UDP; instead, they are encapsulated as the binary payload of standard CoAP messages. For example, a
data request is mapped to a CoAP POST request targeting the URI coap://<provider-ip>/tip with the
CoAP Content-Format option set to application/octet-stream (42). This encapsulation allows
standard CoAP gateways, routers, and firewalls to forward and manage TIP traffic without modification,
while microcontrollers running lightweight CoAP engines (such as Erbium or microcoap) can easily
extract the TIP binary frame from the CoAP payload option.
All packets are framed with a fixed 116-byte header prepended to the serialized CBOR (Concise Binary
Object Representation) payload. This layout enables high-speed hardware parsing, packet verification, and
replay detection before payload processing.

Detailed Header Field Specifications
To ensure robust parsing and zero-trust security at the edge, each header field performs a specific role:
• Magic Number (2 bytes): Constant 0x5449. Used for instantaneous packet filtering at the socket
layer.
• Version (1 byte): Indicates the protocol version (0x01), ensuring backward compatibility.
• Packet Type (1 byte): Delineates the control flow state (e.g., discovery, negotiation, contract, data).
• Transaction ID (16 bytes): A UUID v4 generated by the requester. Associates responses with
active requests.
• Payload Length (4 bytes): Big-endian integer specifying the length of the trailing CBOR payload.

• Signature (64 bytes): Ed25519 cryptographic signature generated with the sender’s private key,

3.4
Packet Parsing and Validation Pipeline
When a node receives a packet, it executes the following sequential parsing pipeline:
1. Header Extraction: Reads the first 116 bytes of the incoming CoAP payload.
2. Magic Number Check: Rejects the packet immediately if bytes 0–1 do not equal 0x5449.
3. Checksum Verification: Recomputes the CRC32 checksum over the header (bytes 0 to 47 and 52
to 115) and the trailing payload. If it matches the Checksum field, the packet integrity is confirmed.
4. Signature Authentication: Validates the Ed25519 signature (bytes 52–115) using the public key of
the sender. This verifies the identity of the source.
5. Replay Check: Compares the Timestamp and Sequence Number against the sliding window cache
(Section VI-A).
3.5
Packet Types and Flags
Packet types denote the state of the communication pipeline:
• DISCOVERY ANNOUNCE (0𝑥00) and DISCOVERY QUERY (0𝑥01) manage decentralized discovery.
• INTENT REQUEST (0𝑥02) and INTENT PROPOSAL (0𝑥03) negotiate capabilities.
• CONTRACT ACCEPT (0𝑥04) and CONTRACT SIGNED (0𝑥06) establish session bounds.
• DATA REQUEST (0𝑥07) and DATA RESPONSE (0𝑥08) execute transactions.
The Flags field (32-bit) contains bitmasks: REQUIRES ACK (0𝑥01), IS COMPRESSED (0𝑥02), IS ENCRYPTED
(0𝑥04), HAS ADAPTER (0𝑥08), and IS STREAMING (0𝑥40).

Orchestration & Algorithms
4.1
Dual-Phase Discovery & Kademlia DHT Routing
TIP implements a parallel, dual-phase discovery strategy (Algorithm 1) to minimize resolution latency. It
queries the local cache, fires multicast DNS browses on the local link, and parallelizes WAN queries via
Kademlia DHT key resolution.
Phase 1: Local Link Discovery (mDNS): On the local network segment, nodes advertise and lo-
cate capabilities using multicast DNS (mDNS) [10] over UDP port 5353 using the multicast address
224.0.0.251 (IPv4) or ff02::fb (IPv6). Each node registers its active capabilities as DNS Service
Discovery (DNS-SD) Pointer (PTR), Service (SRV), and Text (TXT) records according to the DNS-SD
specification [11]. The TXT record contains metadata such as the supported schema, version, and security
options. When a node submits an intent, the local orchestrator issues a fast mDNS query. If a local
provider matches, discovery completes in under 10ms, avoiding external network round-trips.
Phase 2: Wide Area Discovery (Kademlia DHT): If local discovery fails or a WAN contract is requested,
the system queries a decentralized Kademlia Distributed Hash Table (DHT) [12]. While structured
peer-to-peer overlay systems such as Chord [13] route requests using circular finger tables, Kademlia
routing relies on the XOR distance metric:
𝑑(𝑥, 𝑦) = 𝑥⊕𝑦
(4)
which complies with the mathematical properties of a metric (identity, symmetry, and triangle inequality).
Each node maintains a routing table organized into 𝑘-buckets, where each bucket covers a specific distance
range 2𝑖≤𝑑< 2𝑖+1 from the host. When local mDNS fails, the node issues parallel queries (configured by
the concurrency parameter 𝛼) to the 𝛼closest nodes in its routing table using FIND NODE RPCs, iteratively
routing closer to the target capability key until the provider node is found.

Decoupled Schema Adaptation
Heterogeneous IoT systems frequently output data in incompatible formats. When the matched provider’s
schema 𝑆prov differs from the requester’s desired schema 𝑆req, TIP invokes its runtime translator registry.
5.1
Dynamic JIT Compilation Pipeline
Rather than requiring developers to manually write and upload binary translation files, adapters are
declared using simple TOML descriptors. The compilation pipeline is executed dynamically:
1. TOML Parsing: The system administrator or AI agent defines a conversion formula, e.g.:
[adapter]
id = "pulse_to_ml"
source_schema = "u32"
target_schema = "f32"
formula = "x␣*␣0.2"
2. WAT Generation: The ‘TipCore‘ translator parsing engine reads the formula and generates
corresponding WebAssembly Text (.wat) instructions.
3. Bytecode Compilation: The engine compiles the WAT code into raw WebAssembly binary
bytecode using the ‘wat2wasm‘ library.
4. Registry Cache: The bytecode is cached in the registry, indexed by the hash of the source and
target schemas.

During transaction processing, the orchestrator instantiates a sandboxed WASM runtime utilizing
Wasmtime [16]. Edge-side WebAssembly runtimes have gained significant traction for secure, near-native
execution in virtualized settings [17–20]. Wasmtime compiles stack-based bytecode into native machine
instructions on startup using the Cranelift code generator.
Memory safety is guaranteed by allocating a virtual contiguous block of memory (linear memory) bounded
by the WebAssembly runtime constraints. To pass complex structures like CBOR payloads:
1. The host allocates a buffer inside the guest’s linear memory.
2. The host writes the input serialized CBOR bytes directly into this linear memory block.
3. The host invokes the guest’s exported translation function, passing the memory offset and length as
arguments.
4. The guest processes the payload, writes the result to a separate memory offset, and returns the
pointer/length.
5. Any read/write attempt outside the guest’s isolated linear memory range is caught by the host CPU’s
memory management unit (MMU) hardware protection and trapped. This prevents buffer overflows,
memory leakage, or unauthorized access from the guest WASM sandbox into the main TIP daemon
memory.

Security & Trust Analysis
6.1
Anti-Replay Mechanism
Replay protection is modeled on a sliding window cache combined with cryptographic timestamps. A
packet is discarded if its timestamp 𝑡pkt varies from the local node clock 𝑡local by more than a skew window
Δ:
|𝑡local −𝑡pkt| > Δ
(8)
Within this window, a hash of the sequence number 𝑆𝑒𝑞XORed with the timestamp is checked against a
local Least Recently Used (LRU) cache of seen nonces. Duplicate nonces trigger immediate socket drops.
6.2
Key Exchange & Secure Session Tunnels
Nodes establish ephemeral encrypted tunnels using X25519 Diffie-Hellman key exchange. The key
negotiation sequence is structured as a pattern of the Noise Protocol Framework [21]. Requesters and
providers exchange ephemeral public keys 𝑃𝐴and 𝑃𝐵to compute a shared secret:
𝐾shared = ECDH(𝑆𝐴, 𝑃𝐵) = ECDH(𝑆𝐵, 𝑃𝐴)
(9)

Conclusion
This paper presented TIP, an intent-based, decentralized protocol that decouples applications from fixed
endpoints. By combining hybrid discovery, multi-criteria negotiation scoring, dynamic WASM translation,
and zero-trust cryptography, TIP achieves secure, self-healing interoperability for heterogeneous IoT and
mechatronic automation systems.
