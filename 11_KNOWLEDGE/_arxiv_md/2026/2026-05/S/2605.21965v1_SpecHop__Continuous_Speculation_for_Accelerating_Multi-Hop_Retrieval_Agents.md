Abstract
Large language models increasingly use external tools such as web search and
document retrieval to solve information-intensive tasks. However, multi-hop tool
use in complex tasks introduces substantial latency, since the model must repeatedly
wait for tool observations before continuing. We study how to accelerate such
trajectories without changing the final trajectory the model would have taken
without acceleration, assuming access to faster but less reliable speculator tools.
We develop a theoretical framework for lossless speculation in multi-hop tool-
use settings, characterizing the optimal achievable latency gain. We propose
SPECHOP, a continuous speculation framework that maintains multiple speculative
threads, verifies predicted observations asynchronously as target tool outputs arrive,
commits correct branches, and rolls back incorrect ones. This preserves accuracy
while reducing wall-clock latency. We show that SPECHOP can approach oracle
latency gains with enough active threads. Empirically, on retrieval-augmented
multi-hop tasks, SPECHOP closely matches theoretical predictions and reduces
latency by up to 40% in some settings.

Introduction
Large language models (LLMs) are increasingly equipped with external tools, including web search,
document retrieval, code execution environments, and APIs [15, 34, 12, 4, 1]. This enables more com-
plex tasks, such as deep research, agentic workflows, interactive decision making, and information-
intensive reasoning that requires interaction with external environments [25, 24, 11, 3, 29]. In
these settings, the model’s trajectory is no longer a single forward generation, but a multi-step
process of reasoning, tool calls, observations, and further reasoning. In this work, we focus on
information-gathering tools, such as web search and database retrieval [33, 6, 23, 26].
Enabling language models to call external tools improves performance, but also introduces substantial
execution latency [35, 20]. Because inference trajectories are sequential, the model may reason, wait
for a web search result, reason again, retrieve documents from a database, and continue this process
over multiple hops. Thus, total latency depends not only on model decoding, but also on external tool
calls. Recent profiling studies show that this bottleneck is significant in practice: in deep-research
agents, web search can account for 73% of end-to-end latency on average for GPT-5, and up to 91%
in more complex cases [13]. In this work, we accelerate such multi-hop tool-use trajectories without
changing the trajectory the model would have taken without acceleration.

original tool call runs in parallel, then verifies the result to preserve accuracy and reduce latency
when speculation succeeds. Building on this setup, we develop a theoretical framework for lossless
speculation in multi-hop tool-use trajectories. We first study an oracle-verification setting, where

Motivated by our theoretical analysis of such setup, we propose SPECHOP, a continuous speculation
framework that pushes toward the oracle latency gain. Rather than waiting idly for each target tool
call to return, SPECHOP keeps a speculative pipeline active throughout the trajectory. It maintains
multiple parallel threads, each corresponding to a different speculative stage of the same underlying
trajectory, and continues speculating future hops while previous target calls are still running. When a
target output becomes available, a verifier checks whether the corresponding speculative observation
is equivalent to the target observation. If verification succeeds, SPECHOP commits the speculative
branch and extends it with new speculative threads; if verification fails, it discards downstream
speculative work and resumes from the last verified state (See Figure 1). Thus, SPECHOP preserves
the original trajectory under verification while reducing wall-clock latency.
We theoretically study SPECHOP and show that it can close the gap to the oracle latency gain while
remaining lossless. We characterize the required number of active threads in terms of the speculator’s
relative latency and the fraction of time spent on external tool calls. Empirically, we evaluate
SPECHOP on retrieval-augmented multi-hop QA tasks (2WikiMultihopQA [6], MuSiQue [23], and
DeepResearch-9K [29]) with web search or Wikipedia retrieval as the external tool, and either an
LM-based speculator or a fast cache-based speculator. Across these settings, latency matches our
theoretical predictions, with SPECHOP preserving task accuracy while achieving up to 40% latency
gain over standard multi-hop execution.

Related Work
Speculative decoding.
Autoregressive token generation in large language models can create
memory-bandwidth bottlenecks during inference [8, 30]. Speculative decoding mitigates this through
a “draft-then-verify” paradigm, where a smaller draft model proposes tokens that are verified by
2


## Page 3


a larger target model, yielding mathematically lossless outputs that match the target model dis-
tribution [2, 8]. Recent work extends this idea with multiple drafters [10], parallel speculative
pipelines [37], and draft/target models with different vocabulary spaces [21]. Our work shares the
draft-then-verify philosophy, but speculates over tool observations rather than tokens.
Foundations of speculative execution.
Speculative execution originates in computer architec-
ture, where it is used to overcome instruction-level bottlenecks and avoid stalls from conditional
branches [18]. Branch-prediction methods estimate future control flow using history registers and
execution patterns [36], while speculative mechanisms execute predicted instructions before they
are guaranteed to be needed, verify them once the true control flow is known, and roll back upon
misprediction [19, 22]. SPECHOP adapts this classical systems principle from instruction-level
execution to trajectory-level tool use in language model agents.
Agentic tool use and retrieval-augmented generation.
Equipping language models with external
tools, especially retrieval [9] and search, has become central to retrieval-augmented generation and
agentic frameworks [14, 27, 17, 32]. Accelerating retrieval-augmented agents has recently been
studied from several complementary angles. Wang et al. [28] focus on static retrieval at the beginning
of the pipeline, using multiple speculative RAG models with different retrieved documents and later
verifying with a larger generalist LLM to reduce latency without sacrificing accuracy. Sui et al. [20]
propose anticipating tool-call needs earlier by identifying patterns in the model’s generation, allowing
the system to launch tools before the model explicitly reaches the tool-call point. Closest to our work,
Ye et al. [35] show that some external calls can be replaced by faster speculative models, providing
empirical evidence that individual tool-use hops can sometimes be accelerated through speculation.

Accelerating Multihop Tool-Use Trajectories
Language models capable of tool use answer queries by invoking external tools when additional
information or computation is needed. They often decompose a query into intermediate steps, each
resolved either from parametric knowledge or through tools such as web search, document retrieval,
or databases of documents such as Wikipedia articles. This behavior is common in settings studied by
DeepResearch [29] and multihop question-answering datasets [6, 23, 33]. Given a query q, the model
M follows an iterative tool-augmented trajectory: it generates intermediate reasoning, calls tools,
receives observations, updates its state, and repeats this process until producing the final answer.
Formally, for a query q, the model M follows an inference trajectory over states s0, s1, . . . , sN,
where s0 is induced by the query and sN is terminal. At each state si for 0 ≤i < N, the model
conditions on the prior context, generates an intermediate segment τ i, and selects a tool action ai.
The tool returns an observation oi, which is added to the context to form the next state si+1. From
sN, the model generates the final answer f.

3.1
Access to a Speculator Tool
Following [35], we assume access to a speculator tool that can replace the original target tool. The
speculator has two key properties. First, unlike the target tool, the speculator is approximate: there is
uncertainty about whether its returned observation is true. Second, the speculator is faster than the
target tool, and therefore can potentially reduce wall-clock latency when its output is correct.
Speculator accuracy.
The speculator’s accuracy depends on the target tool and task. Following
Ye et al. [35], we model the speculator as succeeding at each hop with probability p > 0, where
success means that the speculative observation leads the model to the same next state as the target-
tool observation. This can occur when the needed factual information is already captured by an
off-the-shelf model’s parametric knowledge, or is available in a smaller database or cache. Prior work
suggests such speculators can be useful in practice, achieving nontrivial success probabilities.
Speculator latency.
Let Tspec be the random variable denoting the latency of the speculator,
including the time required to produce the speculative observation and enable the model to transition to
the next state. We assume that the speculator is more efficient than the target tool, i.e., Tspec < Ttarget.
We make the following assumptions to leverage speculators while preserving the target-tool trajectory.
Assumption 1 (Fast approximate speculator) There exists a speculator S that can be used in place
of the target tool T . Given the same action ai, the speculator produces a speculative observation
ˆoi = S(ai) in time Tspec < Ttarget. With probability p > 0, this speculative observation induces the
same next state as the target-tool observation oi = T (ai). That is, with probability p, we have
Update(si, τ i, ai, ˆoi) = Update(si, τ i, ai, oi).
Assumption 2 (Verifiable equivalence) There exists a verifier V that can determine whether the
speculative observation is equivalent to the target-tool observation for the purpose of the model’s
next state. Formally, the verifier takes the current state, generated segment, action, speculative
observation, and target observation, and returns
V(si, τ i, ai, ˆoi, oi) ∈{0, 1}.
When V(si, τ i, ai, ˆoi, oi) = 1, the system is allowed to commit the speculative transition. When the
verifier returns 0, the system has to discard the speculative branch.
Verification in information retrieval.
In information-retrieval setups, verification can check
whether the target tool and speculator provide the required information, e.g., the same factual
knowledge or semantically equivalent evidence for the model’s inquiry. A restrictive verifier lowers
the success rate p, while a looser verifier that ensures the speculative observation is sufficiently
informative can preserve the trajectory to some extent and maintain task accuracy with higher p.
3.2
Leveraging Speculation for Fast and Accurate Trajectories
We parameterize the latency profile of the system using two dimensionless quantities. First, we
define the relative speculator latency α ≜E [Tspec]/E [Ttarget]. Since the speculator is assumed to
be faster than the target tool, we have α < 1. Second, we define the decoding-to-tool latency ratio
β ≜E [Tseg] /E [Ttarget]. This quantity measures how much time is spent on model-side segment
generation relative to target-tool execution.
We first characterize the best theoretical latency gain achievable with the speculator S. To do so, we
analyze an idealized oracle-verification setting that upper bounds the possible gain from speculation.

the speculative observation is produced, an oracle verifier determines whether it would match the
target-tool result, without waiting for the target tool to finish. If speculation succeeds, which happens
with probability p, the system proceeds using the speculative result; otherwise, it waits for and falls

3.3
SPECHOP with a Bounded Speculative Window
We describe an algorithm that maintains up to k parallel threads, enabling speculation while verifying
each speculative transition against the target tool. Suppose the model is at state si. It generates the
segment τ i and action ai. We create an original verifier thread T1 that calls the target tool on ai. In
parallel, we invoke the speculator on the same action; using the speculative observation, the model
transitions to a speculative next state and continues execution, creating a speculative continuation T2.
Then, T2 generates the next segment and action, launches the target tool, and in parallel invokes the
speculator again to create T3. This process repeats: each thread calls the target tool for its current
action, while the next thread is created by speculating that action’s observation and continuing from
the speculative state. The system continues until it maintains k active threads, denoted by T1:k.
When the target tool result from T1 returns, the verifier V compares it with the speculative observation
used to create T2. If verification fails, then all T(2:k) are discarded, and the system resumes the
thread T1 for next hop at state si+1. If verification succeeds, then T1 is discarded and T(2:k) remain
valid continuations from the verified state. The same procedure is then applied recursively: when
the target-tool result from T2 returns, it is compared against the speculative observation used to
create T3. If verified, T2 is discarded and T(3:k) remain valid; otherwise, all threads are discarded
and the system resumes T2 from the verified state si+2. In general, the algorithm either verifies all
speculative transitions and advances to si+k, or encounters the first failed verification at some Tj,
discards all downstream threads T(j+1:k), and resumes from the corresponding verified state si+j.

In the bounded-window version, the system creates up to k threads and then waits for verification
before deciding which speculative trajectory to retain. When speculation is consistently successful,
this can still create a bottleneck: once the window is exhausted, the system may wait for the target-tool
output of the last thread before creating further speculative continuations.
The continuous version avoids this by keeping k active threads at all times. Whenever the earliest
unresolved speculation is verified, the corresponding verifier thread is discarded, the window shifts
forward, and the system immediately extends the frontier by speculating from the last active thread.

verified target-tool state. Thus, as long as speculation remains valid, the system keeps speculating

Experiments
In this section, we empirically evaluate SPECHOP. We first describe the experimental setup in
Section 4.1. We then present our main results in Section 4.2, showing that SPECHOP substantially
reduces wall-clock latency. Additional analyses and ablations can be found in Appendix C).
4.1
Experimental Setup
Datasets.
We evaluate SPECHOP on three multi-hop question-answering datasets: 2WikiMulti-
hopQA [6], MuSiQue [23], and DeepResearch-9K [29]. For 2WikiMultihopQA and MuSiQue, the
per-example hop budget is derived from their dataset attributes (i.e., number of distinct Wikipedia titles
appearing in supporting_facts for 2WikiMultihopQA, and length of question_decomposition
for MuSiQue), ranging from 2 to 4 hops. We allow our model the budget of 2 extra hops for each
sample. For DeepResearch-9K we evaluate samples with difficulty 2 (difficulty ranges from 1 to 3),
as they provide challenging tasks that need multiple hops of retrieval for answering, and are not too
complex for models in our parameter range, and we allow fix budget of 10 hops for samples.
Generator Model (M).
Our primary generator is CoRAG-Llama3.1-8B-MultihopQA [26], which
is trained to generate intermediate sub-questions hop-by-hop, making it a natural fit for continuous
speculative execution. Appendix C.1 also reports additional experiments with GPT-5 [16] as M.
Target Tool (T ).
We evaluate two distinct retrieval backends as our target tools. (1) E5 Retrieval: A
local HTTP service querying a KILT/Wikipedia passage corpus, returning the top 5 nearest-neighbor
passages for each sub-question (2) Web Search: A DuckDuckGo-based web retrieval tool returning 5
search results per query, with a 3-second page-fetch timeout.
Speculator (S) and verifer (V)
We mainly use LLMs as speculator, including Llama 3.1 8B [5],
Qwen 3 8B [31], GPT-4o mini, and GPT-4o [7]. These models span different speed–accuracy trade-
offs, inducing distinct (p, α) values. Since SPECHOP only requires a fast substitute for the target tool
T , we also evaluate a cached retrieval backend as the speculator in Section 4.2. We use a deterministic
rule-based verifier that compares the target-tool sub-answer with the speculative sub-answer for each
hop and decides whether to accept the speculation. The verifier relies on normalization, exact match,
and token-set Jaccard similarity. Appendix D.1 provides implementation details, and Appendix C.3
reports a human evaluation of its reliability.
Standard multi-hop execution.
Given an input question, M generates a sub-question at each hop.
The target tool T retrieves top documents containing the answer to the sub-question, and M uses
them to produce a sub-answer. The resulting (sub-question, sub-answer) pair is added to the context
for generating the next sub-question. After the hop budget is reached, M uses the original question
and all N (sub-question, sub-answer) pairs to generate the final answer.
Appendix D.1 contains more details on the experimental setup, including generation hyperparameters,
specific target tool configurations, early stopping criteria, and SPECHOP simulation methodology.

4.2
Results
We run continuous SPECHOP with k →∞setting, meaning that we do not impose a limit on the
number of active threads. The algorithm dynamically creates new threads until the first unresolved
thread is verified, allowing speculative continuations to yield additional latency reduction.
SPECHOP achieves significant latency reduction across settings.
We use hat notation (e.g., ˆp, ˆα,
ˆβ) to denote empirical values measured in our experiments, distinguishing them from their theoretical
counterparts. As shown in Table 1, SPECHOP achieves latency gains that closely match the optimal
theoretical limits (RelLat∗) across three datasets, two target tools T , and diverse speculators S. In
the Web search setting, network-bound fetching creates a large bottleneck, making local speculative
generation much faster and yielding low relative speculator latency (ˆα). GPT-based speculators incur
API overhead and thus have higher ˆα than local Llama and Qwen models, but they achieve higher
speculation success rates ˆp. We omit GPT speculators for the E5 target tool as their API latency is
not consistently lower than local E5 retrieval latency (ˆα > 1), violating faster speculator assumption.
Overall, SPECHOP’s empirical relative latency (RelLat) tightly approaches the optimal bounds. For
example, using GPT-4o as the Web-search speculator on 2WikiMultihopQA achieves RelLat = 0.60,
corresponding to a 40% reduction in total execution time, close to its optimal limit of 0.50.

tightly preserves the task accuracy and final answer quality of the standard sequential execution.

threads inherently increases the total number of parallel executions. By restricting SPECHOP to
smaller active threads, it provides a flexible trade-off between maximizing latency reduction and
controlling computational overhead. Figure 2 illustrates this dynamic for the continuous SPECHOP

a moderate compute overhead: the average number of T calls increases from 5.48 in standard
sequential execution to 10.69, while M calls increase from 5.48 to 17.83. Finally, we note that while
our theoretical analysis focuses on avoiding starvation and derives bounds based on (ˆα, ˆβ), the shape
of this trade-off curve is also strongly influenced by the speculator’s empirical success probability
ˆp and behavior; when the speculator is weak, larger values of k are less useful. Evaluation of this
trade-off across additional configurations, including GPT-5 as M, is provided in Figure 4.
SPECHOP is not limited to LLM speculators.
In retrieval-augmented systems, a small optimized
cache can answer queries much faster than full retrieval or web search, but a naive cache-first strategy
is unreliable because incomplete or misleading cache results can compound errors. SPECHOP instead
uses the cache as a speculator, using its low latency while verifying outputs against the target tool T .
We implement a fast E5-cache backend containing only 5%, 10%, or 25% of the Wikipedia index,
selecting “heavy-hitter” passages by Wikipedia in-degree as a proxy for centrality. As shown in
Figure 3, increasing the cache fraction from 0.05 to 0.25 steadily improves ˆp, exceeding 60% for E5
retrieval and 50% for Web Search. Since the local cache is much faster than web search (ˆα ≈0.05),
this yields substantial speedups; at 0.25 cache fraction, SPECHOP reduces Web Search relative latency
to RelLat = 0.64, demonstrating that simple, high-speed data subsystems can seamlessly accelerate
complex reasoning agents when paired with continuous verification.
5
Conclusion
We accelerate multi-hop information-intensive trajectories by proposing SPECHOP, which leverages
a speculator to continuously advance speculative execution. We provide a theoretical framework to
study the latency of our algorithm and compare it with the optimal achievable gain. Empirically, we
show that SPECHOP closely follows the theory and reduces latency while preserving task accuracy.

Implementation Details
D.1
Additional Implementation and Setup Details
This section details the system configurations and execution rules omitted from the main text for
brevity. All of our experiments are done with two NVIDIA L40 48GB GPUs, to load and use the
generator model (M), speculator (S), and target tool (T ).
Generation Hyperparameters.
To ensure deterministic evaluation and minimize generation vari-
ance, all local generator models (M) are served using vLLM with greedy decoding (temperature
= 0.0). During standard multi-hop execution, the generator produces sub-queries with a 64-token
cap, and intermediate/final answers with a 128-token cap. When utilizing LLMs as speculators (S),
we enforce a strict 16-token generation cap to minimize the speculative latency (tspec).
Dataset Splits and Early Stopping.
We evaluate on the validation splits for 2WikiMultihopQA
and MuSiQue, and the train split for DeepResearch-9K (as it is the standard release split for the
benchmark). During inference, to prevent infinite loops or degenerate trajectories, the pipeline
halts if M generates the exact same sub-query twice (determined via normalized string matching).
Furthermore, if the target tool (T ) repeatedly fails to find relevant context—returning the literal string
“No relevant information found”—we terminate the trajectory early. We allow one such failure for
2WikiMultihopQA and MuSiQue, and two failures for DeepResearch-9K before aborting.
Target Tool (T ) Backends.
For the E5 Retrieval target tool, queries are encoded with a maximum
length of 64 tokens using the intfloat/e5-large-v2 model. For memory efficiency during parallel
retrieval, the passage index is loaded via shards and queried using int8 row-wise quantization. For
the Web Search target tool, the system fetches the HTML of the returned DuckDuckGo URLs in
parallel. Each page’s visible text is extracted and truncated to 10,000 characters. The total target tool
latency (ttarget) incorporates both the search API response time and the maximum page-fetch time
across the parallel requests (capped strictly by the 3-second timeout).
Cached-Retrieval Speculator (S).
For the experiments evaluating a fast cache retriever as the
speculator, the speculative backend is implemented as a smaller E5 index built from a heavily sharded
subset of Wikipedia passages. The generator (M) then produces the speculative observation (ˆoi)

Latency Measurement and Simulation.
To ensure strict comparability and isolate the temporal

D.4
Deterministic Rule-Based Verifier (V) Implementation
To ensure trajectory losslessness without the latency overhead of an LLM-based evaluator, we utilize a
lightweight, deterministic rule-based verifier (V). Because the integrity of the speculative framework
relies entirely on preventing false positives, our implementation employs a set of conservative
heuristics to guarantee that only factually equivalent observations are accepted.
The verifier compares the speculative observation (ˆoi) with the target tool’s observation (oi) through
a strict evaluation pipeline. First, both texts undergo standard normalization (lowercasing, diacritic
and punctuation removal). The verifier then immediately rejects any speculative outputs that match
common refusal or uncertainty patterns (e.g., “I don’t know,” “information unavailable”) to prevent
the trajectory from absorbing uninformative responses.
For factual verification, the system enforces a strict numeric consistency check: if the target obser-
vation contains multi-digit numbers (such as years or quantities), the speculative observation must
contain matching numeric values, otherwise it is automatically rejected. Final acceptance requires
either a direct substring match or a high degree of lexical overlap. Specifically, after filtering out
standard English stopwords, the speculation must achieve either ≥72% token coverage or a Jaccard
similarity of ≥0.55. For exceptionally short answers (under 5 characters), the verifier defaults to
requiring a perfect token match. This robust, cautious design ensures that speculative threads only
commit when they deliver the precise factual payload required by the generator model (M).
E
Limitation
SPECHOP requires a fast, approximate speculator (S) and a reliable verifier (V), as formalized in
Assumptions 1 and 2. In domains where these tools are unavailable, or where verifying an answer is
as expensive as executing the full target tool (T ), the latency reduction from continuous speculation
cannot be achieved. Furthermore, while SPECHOP achieves significant latency reduction in many
settings, it generally introduces a noticeable increase in overall computation cost. Because the
framework maintains a continuous window of active threads, it requires running multiple parallel
instances of models and tools simultaneously. Nevertheless, SPECHOP remains a highly practical
solution in scenarios where minimizing wall-clock latency is critical and a higher computational
overhead is a tolerable trade-off.
