Extrapolative Weight Averaging Reveals
Correctness–Efficiency Frontiers in Code RL
Kunhao Zheng1,2, Pierre Chambon1, Juliette Decugis1, Jonas Gehring1, Taco Cohen1, Benjamin
Negrevergne2, Gabriel Synnaeve1
1Meta Superintelligence Labs - FAIR, 2Université Paris-Dauphine PSL
Linear interpolation between fine-tuned checkpoints has been shown to trace the Pareto front between
competing objectives, but whether extrapolative weight averaging can extend such frontiers to new
checkpoints useful at inference time, without additional RL training, remains unclear. We study
this question in RL for competitive programming, where hidden unit tests under time and memory
limits enforce both functional correctness and computational efficiency. Starting from a shared
initialization, we train checkpoints under nested unit-test coverage: low-coverage rewards require
passing smaller-input tests, while high-coverage rewards require passing progressively larger tests up to
the full suite. This sweep reveals the emergence of a correctness–efficiency frontier: on hard problems,
higher-coverage reward reduces optimization failures but increases correctness failures, leaving solve
rate nearly unchanged. Interpolation between low- and high-coverage checkpoints recovers this frontier,
while extrapolation extends it beyond the trained endpoints. Both the frontier and its extrapolative
continuation appear across three inference settings, pure reasoning, tool use, and agentic coding,
and across two model scales, 32B and 7B. At the problem level, moving along the frontier changes
which problems are solved, making extrapolated checkpoints complementary policies in inference-time
scaling. Ensembles with extrapolative weight averaging broaden coverage and improve pass@250 on
LCB/hard by 3.3% over the best single checkpoint at matched sample budget. These results show
that nested unit-test coverage in code RL induces a frontier that extrapolative weight averaging can
navigate, extend, and exploit.

Introduction
Weight averaging offers a simple way to navigate between related checkpoints. Prior work shows that check-
points sharing an initialization can often be averaged without destroying performance, and that interpolation
in RL can trace trade-offs between training objectives (Frankle et al., 2020; Wortsman et al., 2022; Ilharco
et al., 2023; Ramé et al., 2023). Most of this work stays inside the convex hull of trained checkpoints. The
question we ask is whether extrapolation between related RL checkpoints can continue a learned frontier
beyond that hull, without additional training. To answer this cleanly, we need a checkpoint family that shares
an initialization, varies along an ordered axis, and differs in a semantically interpretable way.
Competitive programming provides exactly this kind of setting since a solution is expected to be both correct
and algorithmically efficient. Relaxed tests can reward brute-force programs that work on small inputs,
whereas larger stress tests reject the same programs under the problem’s time and memory limits. This
makes verifier strictness a natural experimental axis for code RL. We vary strictness through nested input-size
thresholds, so stricter rewards demand success on progressively larger tests while keeping the task distribution
and initialization fixed. Starting from a shared SFT checkpoint, we train independent RL runs under several
coverage levels to control the reward strictness, producing an ordered family of checkpoints along a single
interpretable axis.
On hard problems, this ordered family does not collapse to a simple ranking by reward strictness. Instead, it
traces a correctness-efficiency frontier. This frontier gives extrapolative weight averaging a concrete target:
interpolation should recover the known verifier-induced axis, while extrapolation tests whether the same axis
continues beyond the checkpoints produced by RL (Figure 1).
We organize the paper around three questions:
1. What frontier does nested unit-test coverage create? Nested coverage gives a controlled axis along which
stricter rewards reduce optimization failures but increase correctness failures on capability-matched
problems, leaving solve rate nearly unchanged (Section 3.1).
2. Can extrapolative weight averaging go beyond trained checkpoints? Interpolation between low- and high-
coverage endpoints recovers the frontier traced by independently trained checkpoints, while extrapolation
continues the same frontier beyond the RL endpoints. This continuation appears across pure reasoning,
tool use, agentic coding, and the model scales we study (Sections 3.2-3.4).
3. Why is extrapolative weight averaging useful? Extrapolated checkpoints are complementary policies:
they solve different hard problems. Ensembling checkpoints along the extended frontier converts this
complementarity into broader solved-set coverage, improving LCB/hard pass@250 by 3.3% over the best
single checkpoint under matched sample budget, with more diversity. (Section 4.1).
Section 4.2 delimits the claim: static reward shaping over the same nested outcomes stays on the frontier,
while failure-conditioned training provides an exploratory contrast for what additional information may move
the frontier itself.

Extrapolative Weight Averaging: Hypothesis and Setup
We study linear weight averaging between two RL checkpoints θA and θB,
θα = α θB + (1 −α) θA,
(1)
where α ∈[0, 1] gives interpolation and α /∈[0, 1] gives extrapolation. The first empirical check is interpolation:
if this arithmetic is meaningful in our setting, interpolated checkpoints should recover sensible behavior
between the trained endpoints, in line with prior results (Ramé et al., 2023). The main question is whether
the same arithmetic remains meaningful outside the interval spanned by trained checkpoints.
This question is meaningful only when α corresponds to one controlled difference: they should share an
initialization, differ along a single interpretable axis, and keep the rest of training fixed. Otherwise the
averaging direction mixes several changes at once, and behavior outside the trained interval is hard to attribute
to one underlying cause.

Verifier strictness in competitive programming provides such an axis. Relaxed tests reward programs that
pass smaller inputs, whereas stricter tests increasingly demand asymptotically efficient algorithms. This
leads to a concrete hypothesis: RL checkpoints trained under progressively stricter rewards may induce a
correctness-efficiency frontier. If they do, interpolation should recover that frontier and extrapolation may
continue it beyond the checkpoints that RL itself produced. We instantiate this axis as follows.
Training family.
We instantiate the verifier-strictness sweep separately in three RL settings of increasing
interaction capability: pure reasoning, which generates code after single-turn reasoning; tool use, which
interleaves reasoning and Python tool call in multi turns; and agentic coding, which uses a sandboxed terminal
with file-system access. In each setting, we train independent RL runs from a shared SFT checkpoint on
CodeContestsPlus (Wang et al., 2025) (1× variant), under a nested family of unit-test rewards indexed by the
input-length threshold 10k:

Lower k accepts more submissions; higher k demands asymptotically efficient algorithms. We sweep k ∈
{2, . . . , 6, ∞} to span the no-pressure to strict-pressure endpoints, with this range chosen by the unit test
distributions in CodeContestsPlus (Appendix C.1).
Evaluation.
We evaluate checkpoints sampled throughout training, including the final checkpoints, on the
same held-out benchmark with full test coverage. The benchmark is LiveCodeBench (LCB) v5 (Jain et al.,
2025) (20240801-20250201), with easy, medium, and hard split.
Outcome taxonomy.
We sort each problem’s tests by input size and stop at the first failing test, which
classifies every code submission into one of four mutually exclusive outcomes:
correct (all tests pass),
optimization failure (resource limit exceeded after passing all smaller ones), correctness failure (wrong answer
or runtime exception within resource limits), and format error (unparsable output). Optimization failure does
not guarantee algorithmic correctness; a submission may contain a bug masked by the resource limit. To
validate our design, Appendix I shows that the main trade-off is robust to timeout-label ambiguity under
extended time budgets and LLM-based judgment, and Appendix I.2 shows that memory exhaustion is a
non-trivial part of optimization failure.
Models.
We study at both 32B and 7B scale, in both cases we start from a pre-RL SFT checkpoint to
ensure that we study the effect of RL itself rather than layering RL on an already RL-trained model. We run
extended RL for thousands of steps, to check whether the observation continues to hold over longer training.
For 32B model, we use CWM-SFT (FAIR CodeGen team et al., 2025). Specially for tool-use environment, we
conduct two iterations of rejection sampling to teach the tool-call format and use the resulting checkpoint as
the starting policy of our experiments (Appendix C.5). For 7B model, since Qwen-2.5 7B (Qwen et al., 2025)
does not provide a public pre-RL SFT reasoning checkpoint, we fine-tune its base model ourselves on the
public OpenCodeReasoning-2 (Ahmad et al., 2025) and OpenMathReasoning (Moshkov et al., 2025), giving
us full control and transparency over the SFT datamix. Training details are in Appendices C.2 and C.5.
3
Extrapolation Extends the Correctness-Efficiency Frontier
We first establish the prerequisite empirical structure for the paper: varying verifier strictness induces a
frontier between optimization failures and correctness failures on hard problems (Section 3.1). We then test
the hypothesis: linear interpolation recovers this frontier (Section 3.2), and linear extrapolation continues it
beyond what any single RL run reaches (Section 3.3). We close by showing a strong generalization of both
the frontier and its extension by extrapolative weight averaging across RL environment settings and model
scales (Section 3.4).

3.2
Linear interpolation recovers the frontier
Interpolation between a lower-coverage endpoint θlow and a higher-coverage endpoint θhigh, namely θα =
(1 −α)θlow + αθhigh with α ∈[0, 1], recovers the frontier traced by the independently trained verifier sweep.
As α moves from 0 to 1, solve rate stays nearly flat while optimization failures give way to correctness failures
in a smooth progression (Figure 1). Two checkpoints therefore reconstruct the same trade-off that otherwise
required a full family of RL runs. A single interpolation direction in weight space is sufficient to traverse that
frontier.
Prior work shows that interpolation can navigate a multi-objective trade-off between checkpoints trained
under different rewards (Ramé et al., 2023). In our case, the trade-off is not designed by specifying separate
objectives since the rewards are nested and monotone improvement is plausible in theory. Empirically, the

This continuation remains stable over a broad range of extrapolation coefficients. For α ∈[−0.5, 1.5], solve
rate stays nearly flat even though this interval already extends beyond the two trained endpoints, while
optimization failures fall and correctness failures rise along the same pattern seen inside the trained interval
(Figure 4). At more extreme coefficients, the same pattern remains visible, but solve rate drops because
format errors rise sharply, mostly through token exhaustion. Extrapolative weight averaging therefore extends
the verifier-strictness sweep beyond the range reached by RL, until model generations collapse.
3.4
Extrapolative weight averaging generalizes across inference settings and model scales
Figure 5 extends the 32B tool-use case in Figure 1 to the two remaining 32B inference settings. In both pure-
reasoning and agentic coding, interpolation recovers the correctness-efficiency frontier inside the trained interval,
and extrapolation continues the same frontier beyond it. Agentic coding shows the cleanest continuation.
Pure reasoning follows the same trend, but with visibly more scatter and earlier degradation at extreme
coefficients.
The scale comparison follows the same capability-relative pattern as Section 3.1. For the 7B model, Figure 5
shows both LCB/medium and LCB/hard, which shows the same frontier and extrapolative continuation. The
stable range for extrapolation is narrower at 7B, especially on the low-α side where format errors dominate
once α < −1 (Appendix D.1). Extrapolative weight averaging therefore generalizes across inference settings
and across model scale once problem difficulty is matched to model capability, while the width of the stable
regime is setting dependent.

4.2
What moves the frontier, and what does not
The reward-shaped variants we tested stay on the frontier.
The discrete and continuous reward-
shaped variants we tested both lie on the same LCB/hard frontier as the verifier-threshold runs. A simplified
KL-regularized view helps explain why this is plausible: static reward shaping averages the same nested
threshold rewards, so the shaped optimal policy remains tied to the same family of single-threshold optimal
policies (Appendix F).
Failure-conditioned training begins to shift the frontier.
We next ask whether failed attempts
themselves provide training signal beyond a static reweighting of the same outcomes. In online-fixing, each
failed rollout triggers additional worker-side sampling from a prompt built from the original problem, the failed
code, and aggregated execution statistics. To separate information from budget, we keep trainer compute
fixed, allow extra worker compute only adaptively after failures, and compare against a compute-matched
resample-only control that uses the same extra adaptive worker compute but uses the original problem
statement only. We evaluate both the original code-generation task, measured by pass@1 from the problem
statement alone, and the repair task, measured by fix@1 given the failure context. The clearest case is 32B
pure reasoning: relative to the matched control, online-fixing raises fix@1 on LCB/hard from 14.2% to 17.9%
and pass@1 on full LCB from 61.2% to 62.6% (Appendix G.3). Outside this setting, transfer back to the
original code-generation task is smaller and less consistent. We therefore treat this as exploratory evidence
that richer failure information can begin to push the frontier outward at fixed trainer compute.

Related Work
RL for code reasoning and test quality.
Reinforcement learning with verifiable rewards has become a
standard post-training recipe for code reasoning, from single-turn generation to tool-integrated and agentic
settings (Guo et al., 2025; Liu et al., 2025; MiniMax et al., 2025; Xue et al., 2025; FAIR CodeGen team
et al., 2025; Kimi Team et al., 2026). Benchmarks such as CodeContests (Li et al., 2022), APPS (Hendrycks
et al., 2021), and TACO (Li et al., 2023) established code generation under executable tests as a central
evaluation setting. Later work sharpened the role of test quality, including EvalPlus (Liu et al., 2023),
LiveCodeBench (Jain et al., 2025), and CodeContestsPlus (Wang et al., 2025). At inference time, a parallel
line studies how additional inference compute improves code generation through larger candidate pools,
public-test filtering, and iterative candidate refinement (Li et al., 2022; Zheng et al., 2025b; Li et al., 2025a).
Other methods use simulated execution for self-fixing (Maimon et al., 2026) or trajectory reuse in agentic
coding (Kim et al., 2026). During training, other work moves beyond a single outcome reward by adding
richer execution-level or process-level signals, through execution feedback (Gehring et al., 2025), process-level
rewards (Li et al., 2025b; Dai et al., 2025), and self-verification with generated tests (Jin et al., 2025).
Linear mode connectivity, model merging and extrapolation.
Frankle et al. (2020) shows that vision
networks trained from the same initialization can often be connected by low-loss linear paths. Model merging

exploits this structure through model souping (Wortsman et al., 2022), task vector editing (Ilharco et al., 2023),
and layer-wise variants (Yang et al., 2024; Wang et al., 2024; Lin et al., 2024). Closest to our interpolation
result is Rewarded Soups (Ramé et al., 2023), which shows that interpolating checkpoints trained under
explicitly different rewards traces a multi-objective Pareto front. Follow-up work extends this idea to reward
models and policy models (Ramé et al., 2024; Ramé et al., 2024). Our setting differs in that the checkpoints
are trained under a nested family of stricter and looser verification regimes within the same binary pass-fail
signal, rather than under explicitly different reward objectives. Recently, Neural Thickets (Gan and Isola,
2026) provides a complementary view of weight-space diversity through random perturbation and ensembling.
For extrapolation, the nearest precedents are ExPO (Zheng et al., 2025a), AlphaRL (Cai et al., 2026) and
Wang et al. (2026), which extrapolate along a single post-training trajectory (SFT-to-DPO or early-to-late
RL). In our setting, by contrast, the extrapolation is between two RL checkpoints, and it continues the same
frontier beyond what either training run reaches.
Correctness and efficiency in code.
Recent work increasingly treats efficiency as an essential dimension
of code quality alongside correctness. Mercury (Du et al., 2024) introduces efficiency-stratified evaluation
to distinguish correct-but-slow solutions from efficient ones. ECCO (Waghjale et al., 2024) studies the
tension between improving efficiency and preserving correctness in model-generated code. Related benchmarks
extend this concern to algorithmic efficiency (Huang et al., 2024; Chambon et al., 2025), GPU kernels, and
software engineering workloads (Ouyang et al., 2025; Ma et al., 2025). Afterburner (Du et al., 2025) uses a
self-improving loop with RL to improve code efficiency. These works study settings where efficiency is made
explicit, either in the benchmark or in the objective, leaving open what standard unit-test RL does when
correctness and efficiency are folded into the same pass-fail supervision.
6
Discussion and Limitations
Nested rewards need not yield nested policies.
In our setting, the rewards are nested by construction.
However, empirically, the learned policies during on-policy RL are not ordered by dominance. Stricter
verification does not produce a nested sequence of better checkpoints on hard problems. Instead, it moves
policies along the frontier, trading off optimization failures and correctness failures. More broadly, nested
rewards do not guarantee nested learned behavior, likely because on-policy RL changes which solution modes
are reinforced.
Extrapolative weight averaging turns sharpening into diversity.
The frontier is useful as its points
are complementary policies, rather than one point dominates the others. Extrapolative weight averaging
makes this complementary nature accessible beyond the checkpoints reached by individual RL runs. This
gives a different view of RL sharpening effect (Yue et al., 2025; Cui et al., 2025; Wu et al., 2026): even if each
checkpoint sharpens towards a particular solution mode, extrapolative weight averaging provides a controlled
axis to vary which mode is favored. This points to two promising research directions. At inference time, how
to design frontier-aware inference procedure to recover diversity by sampling across these sharpened policies.
During RL training, how to incorporate weight extrapolation in the worker side to offer a way to increase
rollout diversity.
Beyond a single verifier frontier.
As preliminary evidence, Appendix A averages two checkpoints opti-
mized for different sampling behavior: one with stronger pass@1 and one with stronger pass@k. Interpolation
traces a smooth Precision-Recall curve, and yields ensembles that outperform single-checkpoint sampling
at larger budgets. Although extrapolation adds only modest gains, the broader message is encouraging:
extrapolative weight averaging may provide a cheap way to extend the frontier and navigate different behavior
pattern, whenever a shared-initialization checkpoint pair lies on a meaningful frontier.
Limitations.
Our experiments are confined to competitive programming domain, but they are not confined
to a single RL environment setting. Our experiments show that the frontier appears across pure-reasoning,
tool-use, and agentic coding, which span from single-turn generation to richer sandbox feedback, suggesting
that the effect is tied to verifier-induced optimization pressure rather than to one inference interface. Applying
9


## Page 10


the same analysis to other domains such as SWE tasks and kernel generation requires first identifying a
comparable ordered axis, such as test-suite strength or performance tolerance. The input-length thresholds
are a coarse proxy for test-case scale and the optimization stress it induces, while our experiments show that
it is a reliable proxy that consistently exposes the trade-off. Our ensemble comparisons match code generation
count rather than token or wall-clock cost. This is most appropriate in settings where rollouts are easy
to scale and malformed generations can be filtered and replaced, but matched-token or matched-wall-clock
evaluation would be a stricter test. Appendix H gives weight-space analysis of the frontier: the endpoint
difference is high-rank and spread across layers, while layer stitching experiments suggest that the behavioral
control mainly comes from the middle layers. This leaves a more mechanistic version of the study open: one
could train RL with explicit constraints, such as LoRA or frozen-layer variants, and test whether the frontier
direction can be made more localized by construction.
7
Conclusion
Extrapolative weight averaging reveals that code RL checkpoints trained under nested verifier strictness lie on
a correctness-efficiency frontier. On hard competitive-programming problems, stricter verification does not
reliably increase solve rate; it rotates failures between inefficiency and incorrectness. Interpolation recovers
this frontier, extrapolation extends it, and extrapolated checkpoints provide useful diversity for inference-time
scaling. Moving beyond the frontier will likely require not only stricter tests or smoother scalar rewards, but
training signals that reveal why programs fail and help models reduce semantic and computational failures
together.
Reproducibility Statement
All base models, training datasets, and evaluation benchmarks used in this work are publicly available,
including Qwen 2.5 7B, CWM-SFT 32B, CodeContestsPlus, OpenCodeReasoning-2, OpenMathReasoning,

provides the experimental details needed to independently reconstruct the main settings from public assets.

A Second Weight-Space Frontier: Pass@1 vs Pass@k Performance
The main experiments use nested verifier coverage to create a controlled correctness-efficiency axis. To test
whether the weight-averaging geometry is specific to that axis, we ran an auxiliary experiment between two
RL checkpoints, trained from the same initialization (the SFT checkpoint from Qwen 2.5 7B as described in
main text) but optimized for different sampling behavior. The firstll is trained using standard GRPO which
exhibits stronger pass@1, and the second is trained under pass@8 objective as shown in Tang et al. (2025).
We form interpolation and extrapolation checkpoints:
θα = α θp@8 + (1 −α) θp@1,
and evaluate checkpoints for α ∈[−0.5, 1.5] on LCB v5 + v6 (20240801-20250501), 454 problems in total,
with temperature 1.0 and 200 samples per prompt.
Interpolation produces a smooth behavioral frontier.
Figure 10 shows that interpolation traces a
smooth curve in pass@1/pass@100 space. We follow the Precision/Recall framework (Verine et al., 2025) which
uses pass@1 as a proxy for Precision, and pass@100 - pass@1 as a measure for Recall. Moving along the curve
changes both the Precision (pass@1) and the Recall (pass@100 −pass@1). This confirms that the interpolation
direction captures a meaningful behavioral axis even when the endpoints differ by training objective rather
than by verifier coverage. Extrapolation is stable near the endpoints but gives diminishing returns: the most
extreme extrapolated checkpoints (α = −0.5, α = 1.5) degrade on both pass@1 and pass@100.

C.3
7B Model RL Training Details
We train with a simplified asynchronous online RL recipe as shown in FAIR CodeGen team et al. (2025),
namely Dr.GRPO (Liu et al., 2025) using DAPO-style (Yu et al., 2025) asymmetric clipping (ϵlow=0.2,
ϵhigh=0.25) and zero-advantage skipping, with no KL penalty (β=0) and no reference model. Each prompt
produces 16 rollouts at temperature 1.0. We use AdamW (β1=0.9, β2=0.95, weight decay 0.1) with learning
rate 1.4×10−7, 100 warmup steps followed by a constant schedule, and gradient norm clipped at 0.1. Batching
is token-based with a maximum of 32,768 tokens; sequence length is 32,768. The worker model is updated
every 4 gradient steps in the trainer side. Training runs for 6,000 steps across 32 H100 nodes (no tensor
parallelism) in bf16 with selective activation checkpointing, with 1:1 trainer:worker ratio. No FP8 is used for
RL training.
We train on CodeContestsPlus (1×) with binary reward, sweeping the input-length threshold k ∈{2, . . . , 6, ∞}
across independent runs. Evaluation on LCB/v5 is with temperature 0.6, top-p 0.95, and 10 samples per
problem. A single full RL run takes ∼19 hours wall-clock.

32B Pure-Reasoning and Agentic Coding RL Training Details
Both the pure-reasoning and agentic-coding settings start from the same CWM-SFT 32B checkpoint and
share most hyperparameters with the tool-use setting described above. We list the shared configuration first,
then note setting-specific differences.
Shared configuration.
Both settings use Dr.GRPO with DAPO-style asymmetric clipping (ϵlow=0.2,
ϵhigh=0.25) and zero-advantage skipping, with no KL penalty and no reference model. Reward function is
binary. AdamW with learning rate 1.4 × 10−7, constant schedule with 400-step warmup, and gradient norm
clipped at 0.1. Each prompt produces 16 rollouts at temperature 1.0. The trainer-to-worker ratio is 1:1, with
the model updated every 4 worker steps. Training uses 256 H100 GPUs (32 DP × 8 TP) with FSDP in
bf16, torch.compile, and selective activation checkpointing. Pure reasoning trains for 8 000 steps (∼44 hours
per run); agentic coding trains for 4 000 steps (∼16 hours per run). We sweep the input-length threshold
k ∈{2, . . . , 6, ∞} across independent runs, identical to the tool-use setting.
Pure reasoning.
The pure-reasoning setting use sequence length 32 768 and no tool calls. The model
generates a single reasoning trace in a <think> block followed by the code submission. Evaluation uses
temperature 0.6 and top-p 0.95 with 10 samples per problem.
Agentic coding.
The agentic setting uses a sandboxed terminal environment backed by Modal, a cloud
sandbox service, with sequence length 61 440 and up to 72 interaction turns per trajectory. The model can
execute arbitrary shell commands, write and run code, and observe terminal output within a sandbox that
enforces a 120-second session timeout and 1-8 GB memory limits with network access blocked. Evaluation
uses temperature 1.0 and top-p 0.95 with 5 samples per problem.
C.5
32B Tool-Use Model Training Details
We describe two parts of the 32B tool-use setup here.
First, two RL-to-SFT bootstrapping iterations build one shared SFT initialization, because CWM-SFT does
not reliably use our stdin-oriented python-io interface for competitive-programming tasks.
Second, starting from that same initialization, i.e., SFT checkpoint, the final RL phase launches the verifier-
strictness sweep analyzed in the main text. In this final sweep, the compared checkpoints are trained under
nested binary coverage rewards, with the task distribution, tool interface, and RL hyperparameters fixed
across thresholds. Thus the comparison varies unit-test coverage, not the earlier bootstrapping curriculum.
The bootstrapping iteration proceeds as follows:
1. Iteration 0 (RL). Starting from CWM-SFT, run RL with reward shaping on competitive-programming
problems to teach the model to invoke a Python interpreter that accepts standard input (python-io).
Correct trajectories are collected, filtered and downsampled for SFT.
2. Iteration 1 (SFT →RL). Distill the collected tool-use trajectories from Iteration 0 via SFT back into
CWM-SFT; then run RL on CodeContestsPlus with reward shaping that encourages a stress-testing
tool (python-stress), lets the model generate large inputs and check whether its solution timeouts. This
tool functions the same as normal python tool but uses a different name for better behavior tracking.
Correct trajectories are collected, filtered and downsampled for SFT.
3. Iteration 2 (SFT). Distill the collected tool-use trajectories from Iteration 1 via SFT back into CWM-SFT.
Finally, we launch the RL sweep under different input thresholds, starting with the SFT checkpoint produced
from Iteration 2.
C.5.1
Iteration 0: Tool-Use RL
We start from CWM-SFT 32B, which can reason in a <think> block but has never used a Python tool
for code that reads from stdin. We run RL with Dr.GRPO on CodeContests/train (12 275 problems) with
two tools available: python (execute a code snippet) and python-io (execute code that requires stdin). The
20


## Page 21


prompt includes a small number of few-shot examples demonstrating python-io usage. The reward function
gives hierarchical partial credit for tool invocation: full reward (+1) for passing with python-io in the first
turn, reduced credit (+0.8, +0.5, 0) for passing with progressively less desirable tool usage, and asymmetric
penalties on failure that are smaller when the model at least attempted tool use. This encourages the model
to explore tool use early in training.
C.5.2
Iteration 1: Distillation and Stress-Testing RL (SFT →RL)
SFT phase.
From the Iteration 0 RL run, we collect trajectories that (i) contain at least one python-io
call and (ii) lead to a correct final answer. We apply diversity filtering to balance across dialog lengths, tool
usage patterns, and task coverage, reducing the dataset from 804k to 276k examples. We also filter to a
maximum of 32 768 tokens per trajectory and reformat reasoning tokens from the <think> tag into the native
<|reasoning_thinking_start|> format reserved for CWM-SFT. SFT trains for 1 600 steps at learning rate
10−6, starting again from CWM-SFT but not the RL checkpoint, with batch size 2 and sequence length 32 768
across 32 H100 nodes (32 DP × 8 TP). Linear layers use rowwise FP8 quantization; all other computations
are in bf16.
RL phase.
Starting from the SFT checkpoint, we run RL on CodeContestsPlus (1×) with the same
tool-use environment as iteration 0 plus the python-stress tool, which lets the model write an input generator
alongside its solution and reports wall-clock execution time. The reward function shifts the shaping target
from python-io to python-stress: full reward (+1) for passing when python-stress was used anywhere in the
trajectory, reduced credit (+0.5) for passing with only generic tool use, and a small penalty (−0.2) for failing
despite using python-stress versus full penalty (−1) for failing without any tool use. This encourages the
model to adopt stress testing for efficiency verification before submission.
C.6
Iteration 2: Distillation and RL Sweep
SFT phase.
We adopt the same SFT strategy as Iteration 1. Instead of merge the SFT dataset gathered
from Iteration 0 and Iteration 1, we use exclusively the dataset from Iteration 1 which supersets the behavior
presented in Iteration 0. We use the same hyperparameters and training steps as in Iteration 1.
RL phase.
Starting from the SFT checkpoint, we run RL on CodeContestsPlus (1×) with the same tool-use
environment as iteration 1. The reward function becomes binary which grades only the final correctness. This
is the RL run where we sweep different test coverage threshold.
C.6.1
Shared RL hyperparameters
Both RL iterations use Dr.GRPO (Liu et al., 2025) with DAPO-style (Yu et al., 2025) asymmetric clipping
(ϵlow=0.2, ϵhigh=0.25) and zero-advantage skipping, with no KL penalty and no reference model. We use
AdamW with learning rate 1.4 × 10−7, constant schedule with 400-step warmup, and gradient norm clipped at
0.1. Each prompt produces 16 rollouts at temperature 1.0, with a maximum of 6 tool calls per trajectory. The
trainer-to-worker ratio is 1:1, with the model updated every 4 worker steps. Training uses 256 H100 GPUs
(32 DP × 8 TP) with FSDP in bf16, torch.compile, and selective activation checkpointing. The two iterations
differ in training data, reward target, sequence length, and step count: iteration 0 trains for 4 000 steps on
CodeContests/train with python-io reward shaping and sequence length 131 072; iteration 1 and 2 trains
for 8 000 steps on CodeContestsPlus (1×) with python-stress reward shaping and binary pass-fail reward
respectively and sequence length 65 536 (approximately 18 hours per run).
Observation.
During iteration 0, we ran RL on both DMC/train and CodeContestsPlus. The two training
sets yield similar overall pass rates, but different error profiles: CodeContestsPlus produces fewer timeouts
and more wrong answers. This observation motivated the core investigation of this paper (Section 3).

G.4
Additional Online-Fixing Results
The sections in the main text establish that the trade-off is robust across settings and scales. Longer training
can still push the frontier outward, but a sharper question is whether a different use of the same training
budget can improve it at matched trainer compute. The online-fixing experiments in this appendix address
that question by changing how worker-side sampling is spent after failures.
Online-fixing changes two aspects of training at once: it spends more worker-side sampling on problems the
model currently fails on, and it augments the online prompt distribution with failure-conditioned prompts.
The resample-only control matches the extra retry budget without adding failure context, so it isolates the
value of the failure-conditioned prompt itself.
A key property of the design is that it keeps trainer compute fixed while increasing worker compute adaptively
after failures. The computation graph is cut at the boundary between the failed rollout and the fixing prompt,
so the fixing rollout is treated as a new sample rather than a second turn in the same trajectory. The trainer
therefore processes the same number of gradient steps regardless of how many failure-conditioned rollouts are
spawned.

Weight-Space Geometry
This appendix characterizes the weight-space direction that separates the two RL endpoints along three
axes: the singular-value spectrum of each layer’s weight difference (Section H.1), the distribution of squared
weight change across layers (Section H.2), and layer stitching experiments that isolate causal contributions to
behavior (Section H.3).
The central finding is a dissociation. RL modifies every layer by similar magnitudes and in high-dimensional
directions: the top 10 singular values explain only 10 to 19% of the variance within each layer (Section H.1),
and the total squared weight change is nearly uniform across layers 2 through 63 (Section H.2). Yet behavioral
sensitivity is concentrated in the middle of the network. Layer stitching shows that the first and last quarter
of layers (0 to 15 and 48 to 63) are nearly inert, while the middle half (16 to 47) carries the full trade-off shift,
with layers 24 to 31 accounting for roughly half of it (Section H.3).

cumulative variance explained by the top k singular values. Figure 31 shows the result, normalized by the
rank of each matrix. No component type is low-rank: the top 10 singular values of each layer’s difference
explain only 10 to 19% of variance, and even at 20% of rank no component exceeds 80% explained variance.

Error Taxonomy Validation with Extended Reclassification
A submission that exceeds resource limits does not necessarily implement a correct algorithm; it may contain
a bug masked by the resource limit. To assess the sensitivity of our results to this ambiguity, we apply a
two-stage reclassification protocol to every submission originally labeled as an optimization failure. We detail
the protocol in Section I, with Figure 35 showing the comparison of the extended reclassification and the
raw sandbox signal used in the main text. Section I.2 reveals one interesting finding: a substantial fraction
of timed-out submissions are in fact memory-exhaustion failures masked by the time limit. Whether a slow
submission will eventually exhaust memory or time is fundamentally difficult to determine without running it
to completion, which we believe explains why most existing work aggregates both failure modes into a single
timeout category.

I.2
Hidden Memory Exhaustion in Timeout Labels
Standard competitive-programming evaluation pipelines enforce both a time limit and a memory limit, but
when a submission exceeds the time limit first, the sandbox reports a timeout regardless of whether the code
would also have exhausted memory. Memory exhaustion is therefore aggregated into the timeout category,
making it invisible in downstream analysis.
Our extended re-evaluation (Stage 1 of the reclassification protocol, Appendix I) surfaces this hidden failure
43


## Page 44


mode. Under the 100× time budget, 5% to 14% of originally timed-out submissions across all settings
and thresholds terminate with an out-of-memory error rather than a wrong answer or a continued timeout
(Table 5).
These submissions implement memory-intensive algorithms (e.g., building large lookup tables or storing full
search trees) whose true failure mode is masked by the shorter time limit. Since competitive-programming
benchmarks are the primary training and evaluation environment for code RL, this conflation means that
a non-trivial fraction of what existing work treats as “slow but possibly correct, i.e., timeout error” code is
in fact code that would crash from memory exhaustion even given enough time. Disentangling time and
memory failures may be important for designing reward signals that distinguish algorithmic efficiency from
implementation correctness.
