Abstract
Code reasoning refers to the task of predicting the output of a program given its
source code and specific inputs. It can measure the reasoning capability of large
language models (LLMs) and also benefit downstream tasks such as code gener-
ation and mathematical reasoning. Existing work has verified the effectiveness
of reinforcement learning on the task. However, these methods design rewards
solely based on final outputs or coarse-grained signals, and neglect the inherent
consistency of the stepwise reasoning process in the task. Therefore, these meth-
ods often result in sparse reward or reward hacking, which limits the full play of
enhanced learning capabilities. To alleviate these issues, we propose CodeThinker,
a consistency-driven reinforcement learning framework for code reasoning. Specif-
ically, the CodeThinker has three key components: 1) a stepwise reasoning-aware
model training module, which utilizes a consistency tracing paradigm as a template
to synthesize training data that captures the stepwise reasoning process, 2) a dy-
namic beam sampling strategy, which aims at improving the quality of sampled
samples under a fixed sampling budget, and 3) a consistency reward mechanism
that can effectively alleviate the reward hacking. Experiments on three popular
benchmarks show that CodeThinker achieves state-of-the-art performance across
multiple LLMs. For instance, it outperforms the strongest baseline by 4.3% in
accuracy when deployed on Qwen2.5-Coder-7B-Instruct. We also validate the
effectiveness of CodeThinker on downstream tasks. Results show that without
additional training, CodeThinker obtains average accuracy gains of 5.33 and 3.11
percentage points on mathematical reasoning and code reasoning tasks covering 17
programming languages, respectively.

Code Reasoning Training Data Construction
Existing training datasets for code reasoning suffer from insufficient logical complexity. For instance,
synthetic code datasets built with Python built-in functions (e.g., list.append()) in prior work [32]
generally lack elaborate logical structures, providing limited training value for code reasoning models.
To address this limitation, we construct a competition-level code reasoning training dataset named
LeetCodeReasoning built upon LeetCodeDataset [36], which is sourced from the LeetCode algorithm
competition platform. The construction pipeline of our dataset consists of four steps.
Step 1: Static Filtering
We employ Abstract Syntax Trees (AST) [9, 1] to perform static analysis
on the code within the LeetCodeDataset. We retain only function-level code, filter out samples
containing fewer than five lines of code, and remove redundant information such as blank lines,
comments, and function signatures. Following this step, we obtain 1,673 distinct code snippets.
Step 2: Unit Test Generation
Leveraging Qwen3-32B [38], we generate 15 sets of function
inputs for each of the 1,673 functions obtained in the previous step. Since the model only needs
to comprehend the function signature and input format, this generation task is straightforward and
yields high-quality results. This step produces a total of 25,095 (code, input) pairs.
Step 3: Execution Filtering
We execute each function with its corresponding generated input
to obtain the expected output, forming (code, input, output) triples. We then apply rigorous
filtering: discarding samples that failed to execute, samples that timed out (2s), and so on. Following
this step, we retain 10,132 samples.
Step 4: Similarity Filtering
Inspired by Tang et al. [32], we use the all-mpnet-base-v2 sentence
embedding model to vectorize the code from the 10,132 samples obtained in the previous step, as well
as code from three benchmarks: CRUXEval [13], LiveCodeBench [18], and REval [4]. Subsequently,
we compute the cosine similarity between our sample code and the benchmark code, and filter out all
samples with a similarity score of 0.90 or higher.
After the four steps above, we obtain 9,142 samples, covering 651 distinct functions, with an average
of 14.04 unit tests per function. Compared to existing datasets, our LeetCodeReasoning exhibits
higher logical complexity. Refer to Section C view the detailed comparison of our LeetCodeReasoning
with existing datasets in terms of logical complexity.

CodeThinker
In this section, we first introduce consistency tracing, a novel code reasoning paradigm proposed
in Section 3.1. As shown in Figure 2, CodeThinker comprises two training stages: consistency
tracing warm-up and reinforcement learning with GRPO [29]. We use Qwen3-32B [38] to generate
high-quality samples in consistency tracing format, which is used to train the LLMs with SFT
(Figure 2 (A)). In GRPO stage of CodeThinker, we mainly explain the proposed dynamic beam
sampling strategy in Section 3.2, and the proposed consistency reward mechanism in Section 3.3.
3.1
Code Reasoning Paradigm: Consistency Tracing
Existing paradigms for code reasoning primarily fall into one mainstream category, which is the
vanilla tracing employed by Tang et al. [31] (Figure 1 (B)). This paradigm guides LLMs to conduct
explicit thinking with the entire program as the basic granularity and directly yields final results.
Nevertheless, it lacks explicit tracking of intermediate program variables during the reasoning
procedure. As a result, valuable information cannot be effectively extracted from the thinking flow to
reflect execution consistency, and the reasoning process is decoupled from the real program state,
which frequently leads to errors in deducing variable values.
To address the above issues, we propose a novel code reasoning paradigm named Consistency Tracing
(ConTra) on the consistency. This paradigm requires LLMs to first divide a given program into
several code blocks based on the logical coherence of the outermost code. As shown in Figure 1 (C),
the outermost loop block will be treated as a separate block for only one reasoning. After that,
ConTra requires LLMs to reason through each block sequentially. Within the ConTra paradigm,

3.2
Dynamic Beam Sampling Strategy
The regular sampling strategy in the GRPO involves providing a prompt to LLMs and having them
generate multiple independent samples in a single step; however, for the relatively challenging task
of code reasoning, the quality of the generated samples is generally low. To improve the upper tail
of sampled trajectory quality under a fixed sampling budget, we propose a novel sampling strategy
named Dynamic Beam Sampling (DBS), as detailed in Algorithm 1.
Overall, unlike regular sampling in GRPO, DBS dynamically reallocates all subsequent sampling
budget to the current highest-scoring partial trajectories based on intermediate PRM scores; if multiple
trajectories share the highest score, the budget is divided equally among them. A schematic diagram
of the dynamic beam sampling strategy is shown in Figure 2 (B).

Experiments
In this section, we present the experimental setup in Section 4.1. After that, we conduct extensive
experiments to address the following four research questions (RQs): RQ1: How effective is Code-
Thinker compared to baselines? RQ2: What are the impacts of different modules in CodeThinker?
RQ3: How effective is CodeThinker on different base models? RQ4: How effective is CodeThinker
when generalizing to other domains?
4.1
Experimental setup
Models
We adopt Qwen2.5-Coder-7B-Instruct [17] (QC-7B) as the primary base model. To evaluate
generalizability across model families and scales (RQ3), we further experiment with the 14B (QC-
14B) and 32B (QC-32B) variants from the same series, as well as DeepSeek-Coder-6.7B-Instruct [14]
(DC-6.7B) and Llama3-8B-Instruct [11] (Llama3-8B).
CodeThinker Implementation Details
We evenly split the LeetCodeReasoning dataset into two
subsets: LeetCodeReasoning-SFT and LeetCodeReasoning-GRPO. Unless otherwise specified,
parameter α in Equation (3) is set to 1, and the group size of GRPO is set to 8, where 4 sampling
budgets are allocated to regular sampling and the remaining 4 to DBS. All models are trained for 3
epochs in both the SFT and GRPO stages. Full training details are provided in section G.
Baselines
We compare against the following baselines: (i) CodeIO [20] trains LLMs using vanilla
tracing data to predict code output from input. (ii) SemCoder [8] trains LLMs with monologue-style
reasoning chain-of-thought. (iii) CodeReasoner [31] applies GRPO with ORM after SFT warm-up to
improve code reasoning. (iv) ExecVerify [32] introduces a verifiable white-box execution reward
for GRPO to enhance code reasoning. (v) CWM [34] performs intermediate pre-training on code
environment trajectories followed by multi-task RL with verifiable rewards. Since CWM is a 32B
model trained from scratch, we directly compare it against QC-32B-CodeThinker. Unless otherwise
specified, all baselines share the same base models and training configurations as CodeThinker. Refer
to Section A.2 and Section H for details.
Benchmarks
We evaluate on three code reasoning benchmarks: (i) CRUXEval [20] contains 800
samples covering both input and output prediction. We use the output prediction subtask (CRUXEval-
O) in our main experiments. (ii) LiveCodeBench[8] collects problems from LeetCode, AtCoder,
and CodeForces, with 479 samples for output prediction task: LiveCodeBench-O (LCB-O). (iii)
REval[31] evaluates LLMs’ ability to perform intermediate behavioral reasoning and to assess the
logical consistency of their inferences. In our main experiments, we select a subset of 651 test
samples focused exclusively on function-level output prediction subtask: REval-FO. All experiments
are repeated five times and we report the average.

5.2
Analysis of Reasoning Consistency Score
First, we introduce the concept of the Reasoning Consistency Score (RCS). Since our ConTra
reasoning paradigm is modular, we define the RCS as the proportion of correctly completed reasoning
blocks relative to the total number of code blocks. (For example, if a given piece of code consists of
four blocks, and the model begins to make errors starting from the third block, then the RCS is 0.5.)
We analyze the RCS of Qwen2.5-Coder-7B-Instruct on three mainstream benchmarks before and after
CodeThinker training, as shown in Figure 3(B). From the figure, we can see that after CodeThinker
training, the RCS has improved from 14.62 to 55.08, which proves that CodeThinker is indeed
teaching the model to perform sequential code reasoning and avoid hacking situations where the
process is incorrect but the result is correct. Additional results can be found in Section F.3.

Conclusion
Guided by consistency in code reasoning task, we propose CodeThinker. We design a consistency-
based code reasoning paradigm named ConTra, and construct a competition-level training dataset
called LeetCodeReasoning. Leveraging consistency, we put forward a sampling strategy termed
DBS, which improves the quality of sampled examples without increasing the sampling budget. In
addition, we propose a reward mechanism integrating gated ORM and PRM base consistency, which
can mitigate the issue of reward hacking. After a large number of experiments, we have proved the
effectiveness of CodeThinker compared to baselines. For example, QC-7B is trained by CodeThinker
and improved by 4.3% compared to the best baselines. We also demonstrate the effectiveness of
our DBS sampling strategy (+1.09 percentage points) and discover the improvements in the ability
of the trained model with CodeThinker. In other areas such as multilingual code reasoning (+3.11
percentage points) and mathematical reasoning (+5.33 percentage points) without extra training.

A
Related Work
A.1
Evaluating LLMs on Code Execution Reasoning Task
CRUXEval [13]
CRUXEval introduces 800 short, self-contained Python functions (3–13 lines)
paired with deterministic input/output, and decomposes execution reasoning into output prediction
(CRUXEval-O) and input prediction (CRUXEval-I). Functions are filtered to be solvable mentally by
an undergraduate-level programmer, making CRUXEval a clean lens on the foundational execution-
following capability of code LLMs.
LiveCodeBench [18]
LiveCodeBench addresses contamination and benchmark saturation by con-
tinuously sourcing date-tagged problems from LeetCode, AtCoder, and CodeForces, so that a model
can be evaluated only on problems posted after its training cutoff. In addition to code generation, it
covers self-repair, test-output prediction, and a code-execution scenario inherited from CRUXEval-O
over more complex, human-written competition functions.
REval [4]
REval explicitly probes the intermediate runtime behavior of a program, defining
four tasks adapted from HumanEval and ClassEval—next-line prediction, executed-line judgment,
variable-state tracing, and final-output prediction. It further introduces an Incremental Consistency
score that penalizes models which give the right answer to a downstream task while failing an
upstream one, putting consistency at the center of code reasoning evaluation.
CRUXEval-X [37]
CRUXEval-X extends CRUXEval to a multilingual setting, automatically
translating the original Python tasks into 19 programming languages via a test-guided “translate–
execute–repair” pipeline that preserves content consistency across languages. The resulting bench-
mark contains roughly 19,000 test cases and reveals strong cross-language correlations as well as the
often-poor cross-lingual generalization of Python-trained code LLMs.
A.2
Enhancing LLMs’ Performance on Code Execution Reasoning Task
CodeIO [20]
CodeIO turns large-scale code corpora into a unified input/output prediction learning
task, where the model is fine-tuned to predict function outputs (or feasible inputs) entirely in natural-
language chain-of-thought, thus decoupling reasoning primitives—logic-flow planning, state-space
search, decision-tree traversal—from code-specific syntax. A multi-turn variant, CodeIO++, further
uses execution feedback to revise incorrect predictions.
SemCoder [8]
SemCoder proposes monologue reasoning: a forward monologue narrates each
line’s effect, the executed control flow, and variable changes, while a backward monologue abstractly
describes possible prior states for non-invertible operations such as sorting or aggregation. Trained
on the curated PyX corpus, this scheme yields strong CRUXEval-I/O performance with only 6.7B
parameters but produces highly verbose traces and lacks any machine-verifiable variable-tracking
signal.
CWM [34]
The Code World Model is a 32B open-weights LLM trained from scratch with extensive
mid-training on Python interpreter traces and agentic Docker trajectories, and post-trained with multi-
task RL on verifiable coding, math, and software-engineering environments. Its execution-reasoning
paradigm forces the model to emit explicit line-level program state after every executed statement,
achieving strong long-horizon state tracking under teacher forcing but generating verbose traces that
are prone to action hallucination on real programs.
CodeReasoner [31]
CodeReasoner is a two-stage post-training framework—instruction tuning
followed by GRPO reinforcement learning—that distills a teacher’s CoT during SFT and then applies
pure outcome rewards (final-answer correctness only) during RL to encourage concise, accurate
reasoning. Its training data is synthesized around Python built-in methods, which limits algorithmic
depth, and its outcome-only reward leaves intermediate reasoning steps unsupervised.
ExecVerify [32]
ExecVerify augments the outcome reward with verifiable white-box signals: from
interpreter traces it deterministically constructs control-flow questions (next-statement prediction)

Preliminaries: Group Relative Policy Optimization (GRPO)
We briefly review the GRPO algorithm [29] that underpins the RL stage of CodeThinker, and clarify
how its sampling, advantage estimation, and surrogate objective interact with our consistency reward
in Equation (3).
From PPO to GRPO
Standard PPO [28] optimizes a parameterized policy πθ via a token-level
clipped surrogate objective and relies on a learned value network to estimate per-token advantages.
In settings where rewards are only available at the trajectory level—as is typical for verifiable
reasoning, math, and code execution tasks—training the value network is both expensive and unstable.
GRPO removes the value network entirely and instead estimates advantages through a group-relative
normalization of rewards over multiple rollouts that share the same prompt. This yields a critic-free,
memory-efficient algorithm that has empirically proven well-suited to reasoning RL post-training.

Three properties of GRPO are particularly aligned with our

reward-shaping detour, while the hard gate I[Rproc = 2] is preserved end-to-end.

is treated as a format violation and assigned zero reward.

blocks in the model output equals the number of ground-truth blocks; (ii) each block’s LINENO range

J
Limitation and Future Work
Language and execution environment coverage
LeetCodeReasoning is built on top of LeetCode-
Dataset, so all training data is in Python. Although our cross-language evaluation on CRUXEval-X
(Table 12) shows that CodeThinker trained purely in Python still yields consistent gains across
17 other programming languages, we have not yet retrained on languages with runtime semantics
markedly different from Python (e.g., manual memory management in C/C++, or strict static typing
in Java), and whether retraining further improves performance remains open. A natural next step is
to extend CodeThinker to more language runtimes, or to port it onto a unified symbolic execution
engine so that block-level states can be verified in a language-agnostic way.
Problem complexity and real-world code
Constrained by LeetCodeDataset, our LeetCodeRea-
soning data is at the single-function level, which is still far from complex real-world, particularly
repository-level code. Mainstream code reasoning benchmarks such as CRUXEval, LiveCodeBench,
and REval share the same limitation. A promising direction is to lift code reasoning to the repository
level, design evaluation protocols for repository-level code reasoning, and apply CodeThinker to such
tasks.
Granularity in the ConTra code reasoning paradigm
Our ConTra paradigm operates at code-
block granularity, a design choice that keeps the generated execution trajectory both human-readable
and machine-verifiable while controlling its length. However, this granularity is fixed at the extraction
stage: simple blocks may be over-annotated, while loops or recursive blocks with rapidly changing
states may be too coarse to be fully parsed. An adaptive ConTra variant that dynamically chooses
block boundaries based on cyclomatic complexity or local data-flow density could provide finer
signals where it matters and coarser signals elsewhere.
Beyond code execution reasoning
We view code execution reasoning as a means to probe the
depth of code understanding rather than the ultimate goal. The reward mechanism we designed
reflects an underlying consistency principle, whose applicability extends far beyond input-output
prediction. We are actively exploring this principle in other settings, including unit-test-guided code
generation, fault localization, repository-level code edit prediction, and execution-trace generation for
long-horizon code agents. A comprehensive empirical study of these extensions is left to future work.
