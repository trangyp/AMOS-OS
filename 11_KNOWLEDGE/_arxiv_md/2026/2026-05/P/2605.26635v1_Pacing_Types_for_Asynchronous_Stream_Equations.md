Abstract. Stream-based monitoring is a runtime verification approach
where a monitor aggregates streams of input data from sensors and other
sources to give real-time statistics and assessments of a system’s health.
One of the central challenges in designing reliable stream-based moni-
tors is to deal with the asynchronous nature of data streams: in concrete
applications, the different sensors being monitored produce values at dif-
ferent speeds, and it is the monitor’s responsibility to correctly react
to the asynchronous arrival of different streams of values. To ease this
process, modern frameworks for stream-based monitoring such as RT-
Lola enable users to finely specify data synchronization policies via a
system of pacing annotations. While this feature simplifies the design
of monitors, it can also lead users to write inconsistent policies, where
synchronization between two streams is explicitly requested via annota-
tions, but cannot always be achieved. To mitigate this issue, this paper
presents pacing types, a novel type system implemented in RTLola to
ensure that monitors for asynchronous streams are free of timing incon-
sistencies. We give a formal semantics to pacing annotations for a core
fragment of RTLola, and present a soundness proof of the pacing type
system. For an additional level of guarantees, we machine-checked the
soundness proof using the Rocq proof assistant.

Introduction
Runtime verification is a safety assurance mechanism in which systems are mon-
itored during their execution. Runtime verification is particularly useful for in-
creasing the reliability of complex cyber-physical systems (CPS) for which ob-
taining a model for static verification is difficult or impossible. Stream-based
monitoring is an approach to runtime verification in which a monitor collects
data through input streams, which are then combined and aggregated in output
streams to give real-time assessments of a system’s health.
While, there exist many formalisms and programming languages to describe
stream-based monitors [11,13,3,20,15,23], we focus on the stream-based specifi-
cation language RTLola. In RTLola, a monitor is specified by listing equations
relating input and output streams. Certain boolean output streams, called trig-
gers, indicate whether the system being monitored is behaving as expected.
From a system perspective, monitors are passive components. They react to
inputs from the system as they arrive. If different system sensors generate inputs

Related Work
Runtime verification has been studied since the late 90s [21]. Specifications
are often expressed in temporal logics such as LTL [2] and MTL [1]. Applica-
tions include Markov Decision Processes [19,17], cyber-physical systems [3], and
software [18]. Stream-based monitoring framework like Lola [11], RTLola [4],
Tessla [20], and HStriver [15] provide expressive specification languages coupled
with efficient monitoring infrastructures.
Synchronous programming languages such as LUSTRE [16], ESTEREL [8],
and Z´elus [7] share similarities with stream-based languages for monitoring. In
particular, both paradigms need to address timing inconsistencies (ensuring that
values exists when they are requested). Synchronous languages use notions of
clocks [14,10,22], and associated static analyses to resolve timing issues. We

Asynchronous Streams in RTLola
This section provides a high-level overview of RTLola and its pacing annota-
tions using a battery management system as an example. In RTLola, monitors
are specified by declaring a list of named input and output streams. As an ex-
ample, consider the following RTLola specification which monitors excessive
power draw:
1
input battery_lvl
2
output drain := battery_lvl.prev(or: battery_lvl) - battery_lvl
3
output warning := drain > 5
The input stream battery lvl captures the current battery level measure-
ment. The output stream drain computes the charge loss by subtracting the cur-
rent battery level from the previous one, accessed via battery_lvl.prev(or:...).
The argument after or: provides a default value for the first evaluation step. This
example illustrates the core concepts of input and output streams and the use
of stream offsets to express temporal properties.
Handling Asynchronous Inputs. In practice, a monitor often requires access
to multiple sensors to produce meaningful verdicts about the system’s health. For
example, the previous specification can be refined to monitor that the battery
does not overheat while it is charging. For this, an additional input stream
temperature captures the current temperature of the battery being monitored:
1
input battery_lvl: Int
2
input temperature: Int
3
output drain := battery_lvl.prev(or: battery_lvl) - battery_lvl
4
output warning := drain < 0 && temperature > 50
Importantly, RTLola does not make the assumption that streams are syn-
chronized: different inputs might arrive at different rates. This raises the question
of how to interpret an expression like drain < 0 && temperature > 50 in the pre-
vious specification. More precisely, it is not clear what the value of this expression
should be if one of the two inputs is not available at the time of evaluation. For
example, the monitor could take the last defined value of the stream or wait for

all values to be available. However, both solutions would negatively impact the
precision of the monitor. Implicitly taking the last defined values would allow to
mix measurements performed at very different time points and whose compari-
son is, therefore, difficult to interpret. Similarly, waiting for all values to arrive
might result in dangerous situations being missed. Instead, RTLola permits
more fine-grained handling of the asynchronous arrival of data via a combina-
tion of pacing annotations and a selection of synchronous and asynchronous
access operators.
Synchronous and Asynchronous Accesses. To facilitate the handling of
multiple inputs arriving at different paces, RTLola distinguishes between syn-
chronous and asynchronous stream accesses. A synchronous access requires the
stream being accessed (i.e., the stream the access refers to) to have a value at
the same time as the accessing stream (i.e., the stream that contains the access
in its expression). Direct accesses (such as drain and temperature in the pre-
vious example) and prev accesses are synchronous by design. This means that
in the previous example, the stream warning can only produce a value when
both drain and temperature are also producing a new value simultaneously. This
restriction can be problematic if different sensors generate values at arbitrary,
non-overlapping time points. In particular, this could prevent warning from ever
being evaluated, thus never issuing the intended warning.
To address this issue, RTLola also provides an asynchronous hold access. A
hold access retrieves the last produced value of the accessed stream, regardless
of when it was generated. If no such value exists, a default value is returned,
similar to prev. Unlike prev though, the hold operator may also reference the
current value if the accessed stream produces a value at the same time as the
accessing stream. Using a hold access the specification in Section 2 can be refined
as follows:
1
input battery_lvl: Int
2
input temperature: Int
3
output drain := battery_lvl.prev(or: battery_lvl) - battery_lvl
4
output warning := drain < 0 && temperature.hold(or: 0) > 50
Replacing the synchronous access to temperature in warning with a hold elimi-
nates the requirement for temperature and battery lvl to update simultaneously,
allowing warning to be evaluated whenever a new battery level is measured. Fig-
ures 1a and 1b illustrate the difference between synchronous and asynchronous
access on an example trace. Black continuous arrows represent synchronous de-
pendencies, while light gray arrows indicate dependencies due to default values
and dashed arrows indicate asynchronous dependencies. On the left, the stream
warning accesses temperature synchronously, via prev. On the right, temperature
is accessed asynchronously via hold.
We note that with a synchronous access, warning only produces a value at
time three, when both temperature and battery lvl receive new values. Using
an asynchronous access instead, warning also produces values at steps one and
five in addition to time step three, resulting in a more precise verdict.

The pacing annotation x @b requires that x evaluates whenever b receives
a new value. Similarly, the annotation y @a requires y to update whenever a
receives a new value. As demonstrated in Figure 3b, these requirements cannot
always be met at runtime! At time point three, the stream y is expected to have
a value (because a also has a value). Since y contains a direct access to x, it
cannot evaluate (because x does not have a value at time point three). The goal
of the type system presented in this paper is to reject such invalid specifications,
ensuring that a stream value can always be computed when it must be computed.
We note that one way to “repair” the specification in Figure 3a would be
to replace the synchronous access to x in y with a hold access. However, this
change alters the semantics by removing the requirement that x must produce
a new value whenever y produces a new value. With the hold operator, y keeps
producing fresh values (based on old values of x) even if x stops updating.
2.2
A Type-driven Solution
To prevent timing inconsistencies, RTLola uses a type system. First, we observe
that the asynchronous hold stream access never causes timing inconsistencies, as

same time points as the stream containing the access.

Pacing Types
To formalize pacing annotations and their properties, we focus on a core lan-
guage modeling the key features of RTLola, here dubbed µRTLola (for micro
RTLola). In essence, µRTLola programs represent a set of constraints over
input and output stream variables drawn from (disjoint) sets Vin and Vout re-
spectively. For a fixed set of (named) input streams, these constraints describe
which set of (named) output streams are valid reactions to the inputs. Because
of this declarative view, we refer to µRTLola programs as specifications. For
clarity, we only formalize constraints over integer-valued streams, but µRTLola
can be extended to arbitrary data types in a straightforward manner1.
3.1
Syntax of µRTLola
Constraints on stream variables are expressed via a list of equations of the form
x @ τ := e. In these equations, x ∈Vout is the name of an output stream
being constrained, and e is a stream expression over input and output variables.
Finally, τ is a positive boolean formula over input variables describing when the
output stream x must be evaluated depending on the availability of inputs. We
call τ a pacing annotation.
Stream expressions can be constant values v ∈Z, stream variables x ∈
Vin⊎Vout, arithmetic functions applied to sub-expressions, references to previous
values x.prev(e), or hold accesses x.hold(e). In x.prev(e) and x.hold(e),
x ∈Vin ⊎Vout is the name of an arbitrary input or output stream, and e is a
default expression representing what value the expression should take if there is
no previous value for x (in the case of prev) or if there is no value to hold (in
the case of hold). The exact syntax of specifications, stream expressions, and
pacing annotations is defined below.

3.3
Type System for Pacing Annotations
To determine whether a given specification is consistent, we use a type system.
Our type system uses typing judgements of the following two forms
Γ ⊢e : τ
and
Γ ⊢S
where Γ is a typing context, e is a stream expression, τ is a pacing annotation,
and S is a list of annotated equations. The first kind of judgement, Γ ⊢e : τ,
is used to check the pacing of stream expressions e. Judgements Γ ⊢S are used
to check the consistency of sets of equations. In both judgements, the typing
context Γ is a partial map from output variables x ∈Vout to annotations τ,
representing assumptions made on the pacing of some output streams. In the
following, we use the notation convention Γ, x : τ to denote a context where x
maps to τ, and we note (x : τ) ∈Γ when Γ(x) = τ ̸= ⊥.
Typing Equations. The typing rules for equations are processing the stream
equations in a specification S in order of their appearance, extending the typing
context after each processed equation. The Empty rule states that an empty
list of equations is consistent in any context. The Equation rule processes the
first equation of x @ τ := e of a list. For such an equation to be well-typed,
the x should be unbound in Γ (i.e., x /∈dom(Γ)), making sure that there is at
most one stream equation per output variables in the specifications. Further, we
require the stream expression e to be well-typed in Γ for the annotated pacing
(i.e., Γ ⊢e : τ). Finally, the remaining equations should be well-typed in a
context where x is assumed to be τ-paced.

accesses. Each kind of stream access comes associated with two typing rules de-

check that the time points at which the expression must be evaluated according

In all rules, τmust corresponds to the pacing type that the target expression is
expected to have. If the accessed stream is an output stream, τcan is determined
from the typing context. For accesses to input streams, τcan is the stream name
itself. An important remark is that checking τmust |= τcan can be done using a
SAT-solver. Indeed, since pacing annotations are positive boolean formulas, it
suffices to check the validity of the boolean implication τmust →τcan.
Since hold and prev accesses can depend on the value of a default expression
e, their associated typing rules require the default expression to be well-paced.
For example, for x.prev(e) to be τmust paced, e should also be τmust paced. We
note that, contrary to synchronous accesses, hold accesses do not impose pacing
restrictions on their accessed variables: hold accesses x.hold(e) are τ-paced for
any τ (provided the default expression e is also τ-paced). This coincides with
the semantics of hold, which is guaranteed to produce a defined value by either
returning the last defined value of the accessed stream, or a default value.

While the type system presented in Figure 4 is sound, it is also incomplete:

extensions of the type system to mitigate incompleteness.

aware. Concretely, we replace judgements Γ ⊢e : τ by judgements Γ ⊢x e : τ,
where the additional annotation x ∈Vout indicates the name of the stream
containing e as a sub-expression. With this change, the rule for equations is

even when they have models, and therefore do not need to be covered.

Conclusion
In this paper, we formalized the core of RTLola’s pacing annotations, a mecha-
nism for data synchronization in stream-based monitoring. We provided a formal
semantics interpreting annotated stream equations as relations between input
and output streams. We showed that pacing annotations can introduce inconsis-
tencies and addressed this by treating pacing annotations as types. The resulting

type system rejects contradictory annotations, and we proved its soundness with
respect to the formal semantics.
While the presented fragment of RTLola is already practical, extending it to
the whole language remains future work. Another interesting research direction
would be to relate the type system to an operational semantics, establishing not
only the existence of models but also their computability.
