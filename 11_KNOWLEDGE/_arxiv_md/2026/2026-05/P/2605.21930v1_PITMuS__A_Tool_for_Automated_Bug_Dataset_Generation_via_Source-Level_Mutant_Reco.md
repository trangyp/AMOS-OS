Abstract
LLM-based software engineering increasingly depends on exe-
cutable, context-rich bug artifacts: paired correct and buggy
code, methods under test (MUTs), documentation, and meta-
data. These artifacts support the training and evaluation of
automated bug localization and repair techniques, testing and
test oracle generation methods, and documentation-driven
automation. Although curated benchmarks (e.g., Defects4J)
remain valuable, they are static and increasingly vulnerable
to contamination as code models are trained on large pub-
lic corpora. A complementary strategy is to generate fresh,
cutoff-aware datasets by selecting real system versions and
injecting controlled bugs at the source level.
Mutation testing is a natural basis for this strategy: it ap-
plies predefined mutation operators to programs and records
whether the existing test suite detects each injected change.
PIT is a state-of-the-practice mutation testing tool for Java
that performs mutation at the bytecode level. This design
makes mutation testing fast and practical, but PIT reports
mutants primarily through XML, making them difficult to
inspect, replay, or reuse as structured source-level dataset
records. To address this gap, we present PITMuS, which
combines PIT XML metadata with debug information from
compiled Java class files to localize and reconstruct the source
edit corresponding to each mutant. PITMuS then automat-
ically produces structured datasets containing source-level
buggy and fixed code pairs, documentation context, and meta-
data for downstream training and evaluation. Although we
evaluate PITMuS on eight open-source Java systems, it can
be applied to any Java system where PIT can be integrated.

Introduction
Automated and LLM-based software engineering tasks such
as bug localization, program repair, test generation, test or-
acle generation and assessment, and documentation-driven
automation require paired examples of correct and buggy code,
along with methods under test (MUTs), documentation, local-
ization information, and metadata describing the fault. Such
artifacts make it possible to train and evaluate techniques
on concrete source-level changes within their surrounding
program context.
Curated benchmarks such as Defects4J [8] have been central
to software engineering research, but they are fixed by design.
They cover a limited set of systems and bugs, and they typi-
cally do not evolve as new system versions become available or
as the field shifts toward new paradigms such as LLM-based
software engineering. This limitation is especially pressing in
the LLM era because code models are trained on large public
corpora, making widely used benchmarks increasingly vulner-
able to contamination [7, 12, 13]. A complementary strategy
is to generate fresh, cutoff-aware datasets by selecting real
system versions and injecting controlled bugs at the source
level.
Mutation testing is a natural basis for this strategy: it ap-
plies predefined mutation operators to programs and records
whether the existing test suite detects each injected change [2].
In the Java ecosystem, PIT [10] is a state-of-the-practice
mutation testing tool because it is fast, integrates cleanly
with modern build workflows, and has been used in numer-
ous software engineering studies [3–5, 9]. PIT achieves this
practicality by performing mutation at the bytecode level and
reporting each mutant through metadata such as the mutator,
source file, line number, and mutation description.

This design is effective for mutation-score computation, but
it limits the usefulness of PIT mutants as source-level arti-
facts. A PIT report tells users that a mutant exists, where it
occurred, and what mutation operator was applied, but it does
not directly provide the mutated source code. Consequently,
users cannot easily inspect the mutant in an editor, replay it
as a concrete source file, compile it, or reuse it as a structured
dataset record containing the original code, mutated code,
documentation context, and mutation metadata.
Recovering such artifacts is, to the best of our knowledge,
neither readily supported by existing tools nor always straight-
forward. A line number and mutation description may be
ambiguous when a source line contains multiple candidate
operators. For example, a line containing both index + 1 and
length + index has two possible targets for a mutation de-
scribed as “Replaced integer addition with subtraction.” PIT
distinguishes such mutants using bytecode-level information,
but that information must be reconciled with the original
source code to reconstruct the exact edit.
To address this gap, we present PITMuS, a tool for auto-
mated dataset generation via source-level mutant reconstruc-
tion. PITMuS combines PIT XML metadata, debug informa-
tion from compiled Java class files, and javalang [11] parsing
of the original source code to localize and reconstruct the
source edit corresponding to each mutant. PITMuS then pro-
duces reusable source-level artifacts and structured datasets
containing buggy and fixed code pairs, documentation context,
and mutation metadata.
This work makes the following contributions:
∙We introduce PITMuS, which reconstructs source-level
mutants from standard PIT reports without replacing
the underlying mutation engine.
∙We provide two utilities: source-level mutant injection
and replay, and method-level dataset construction with
original methods, mutated methods, Javadoc when avail-
able, and mutation metadata.
∙We evaluate PITMuS on eight open-source Java sys-
tems, where it processes 69,229 PIT mutations and
reconstructs 69,198 aligned mutant-method pairs across
1,913 source files. Although evaluated on these systems,
PITMuS can be applied to any Java system where PIT
can be integrated.

PITMuS Workflow

a PIT XML report, the system’s compiled .class files, and
the original Java source files. The XML report identifies each
reported mutant, while the class files and source files provide
the information needed to map bytecode-level mutations back
to concrete source edits. Figure 2 summarizes the high-level
workflow.

2.1

Dataset generation turns each PIT report entry into a method-
level record. For a Java system 𝑃with PIT report 𝑅𝑃, PIT-

𝒟𝑃= { ⟨orig𝑖, mut𝑖, doc𝑖, meta𝑖⟩| 𝑚𝑖∈𝑅𝑃}.
Each record corresponds to one PIT mutation 𝑚𝑖. Here, orig𝑖

of that method, doc𝑖is the preceding Javadoc when present,

file path, bytecode index, and mutation description.
The main challenge is that a PIT mutation description and
line number do not always identify a unique source token. A
single source line may contain multiple candidate operators.
To resolve this, PITMuS combines the XML report, bytecode
information from the compiled class file, and source parsing
with javalang [11]. It first identifies candidate source tokens,
then uses bytecode information when needed to select the
correct occurrence. After applying the edit, PITMuS extracts
the enclosing method and preceding Javadoc when available.

2.2
Source-Level Mutant Injection
Source-level injection materializes reconstructed mutants as
Java source files. PITMuS copies the original source file,
replaces the target statement with the reconstructed mutated
statement, preserves indentation, and checks the resulting file
using javalang tokenization.

3
Evaluation
We evaluate PITMuS along three dimensions. First, we mea-
sure the scale and diversity of the datasets that PITMuS
can generate from real-world Java projects. Second, we assess
how often PITMuS successfully reconstructs PIT mutants as
source-level original–mutant method pairs. Third, we analyze
the cases in which reconstruction fails in order to identify the
main limitations of the approach.
3.1
Subject Systems
We evaluate PITMuS on eight open-source real-world Java sys-
tems including bcel, commons-beanutils, commons-dbutils,
commons-jexl3, commons-lang3, http-request, joda-time,
and jsoup. These systems were selected to cover a range of
application domains, including bytecode engineering, reflec-
tion utilities, JDBC support, expression-language processing,
general-purpose Java utilities, HTTP clients, date and time
handling, and HTML parsing. They also vary substantially
in size, from http-request, which contains 4 source files, to
commons-lang3, which contains 401 source files.
3.2
Dataset Scale and Documentation Context
Table 1 summarizes the datasets produced by PITMuS. Across
the eight subject systems, PITMuS processes 69,229 PIT
mutations and reconstructs 69,198 aligned original–mutant
method pairs from 1,913 source files, yielding an overall recon-
struction rate of 99.96%. The generated records also retain doc-
umentation context when it is available: 45,913 reconstructed
pairs contain non-empty Javadoc, representing 66.35% of the
final dataset. Among the subject systems, commons-lang3
contributes the largest dataset, with 17,992 reconstructed
pairs from 401 source files, and also has the highest Javadoc
coverage, at 94.01%.
3.3
Preservation by Mutation Operator
Table 2 reports reconstruction rates by mutation operator.
PITMuS achieves complete reconstruction for six operators:
VoidMethodCall, NullReturns, TrueReturns, FalseReturns,
Increments, and InvertNegatives. For the remaining oper-
ators, reconstruction remains consistently high, with every
operator preserving at least 99.69% of its reported PIT muta-
tions.
Overall, only 31 of the 69,229 reported mutations are not re-
constructed. The largest loss occurs for RemoveConditionals,
with 14 unreconstructed mutations out of 35,739, while all
other operators lose at most eight mutations. These results
indicate that PITMuS preserves nearly all PIT STRONGER
mutants as source-level original–mutant method pairs, with
only a small number of operator-specific reconstruction fail-
ures.

3.4
Failure Cases
The unreconstructed mutations are caused by source-position
mismatches between PIT reports and source tokens. We ob-
serve two patterns. First, multiple bytecode-level mutants can
map to the same source-level edit; for example, PIT reports six
mutations for the single - operator in fp = tinter.fp - 1;.
After one reconstruction, the remaining entries would create
duplicates, so PITMuS skips them. Second, some mutations
occur in multi-line expressions where PIT reports a line differ-
ent from the line containing the operator. Because the current
rewriter searches within a single source line, these cases are
not reconstructed. Overall, only 31 of 69,229 mutations are
missed, for a failure rate below 0.05%.
4
Conclusion
Mutation testing tools such as PIT generate valuable mu-
tants, but their reports are not directly structured for source-
level analysis. Researchers and developers often need aligned
original–mutant code pairs, documentation context, and reusable
project-level datasets that can be inspected and analyzed with-
out additional manual processing. PITMuS addresses this
need by converting standard PIT artifacts into source-level
mutant-method pairs.
Our evaluation shows that PITMuS scales to real-world
Java systems, reconstructing 69,198 of 69,229 reported PIT
mutations across eight projects. This result demonstrates
that most bytecode-level PIT mutants can be recovered as
usable source-level examples. By preserving method bodies,
mutant edits, mutation metadata, and Javadoc when available,
PITMuS makes mutation data easier to use in empirical
studies, model training, documentation-aware analysis, and
tool evaluation.
Overall, PITMuS lowers the effort required to build mutation-
based datasets and makes PIT mutants more accessible to
users who need source-level representations rather than report-
level mutation artifacts.
