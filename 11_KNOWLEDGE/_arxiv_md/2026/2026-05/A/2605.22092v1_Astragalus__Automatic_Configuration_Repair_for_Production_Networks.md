Abstract
Network configurations are prone to errors, which can lead
to catastrophic service outages. A tool that can achieve au-
tomatic configuration repair (ACR) is highly desired by op-
erators. Existing tools for ACR follow a semantic-driven ap-
proach: they model network semantics as a set of SMT con-
straints, and solve them for a location or fix of the error. Due
to the complex semantics of networks, constructing and solv-
ing these constraints can be prohibitively expensive, making
these tools neither general nor scalable. Inspired by auto-
matic program repair (APR), we explore another direction,
i.e., a syntax-driven approach, which tries to repair program
bugs by “grafting” some existing code in the same reposi-
tory, without modeling program semantics. Following this
direction, we propose Astragalus, a syntax-driven method
for ACR. It uses multiple iterations of a “localize-fix-validate”
pipeline to search for repairs, and proves quite effective on
configurations of our production network. Specifically, we
show that Astragalus can repair every incident in multiple
sizes of a synthesized network, and 97.5% of the incidents on
a real network, both with 15 types of errors injected, within
an average time of 7.36 seconds. It has also provided valid
repair suggestions in under 6 minutes for 4 recent network
incidents or undesired changes, in a real production network
with O(1,000)∼O(10,000) devices.

Introduction
Network outages frequently make headlines due to mis-
configurations, software bugs, and hardware failures [28].
Among them, misconfiguration is a major source of network
outages [20, 32]. In the network of a large cloud service
provider (CSP, referred to as Provider Alater), misconfigura-
tion account for 35.4% of all incidents in the past 5 years.
To detect network misconfigurations, both the academia
and industry have proposed a lot of network verifiers [1, 8,
11, 12, 16, 31, 33, 34]. These tools can check whether network
forwarding behaviors align with operator intent, and con-
form to properties like loop freedom, and blackhole freedom.
However, network verifiers can only detect issues or re-
duce the impact rather than resolve it, and operators still
need to manually localize the root causes and repair the con-
figurations. Such a manual process can be frustrating and
time-consuming, thereby delaying planned network updates.
Taking Provider A for example, the verification mostly finish
within 3 minutes, while operators take more than 10 minutes
to localize and repair 45.8% of the cases, with the longest
case taking 5 hours.
Similar to the Automatic Program Repair (APR) tools that
greatly facilitate software development [13, 22], a tool that
can achieve Automatic Configuration Repair (ACR) is highly
desired by operators to help them quickly localize the root
causes and resolve the incidents.
Towards ACR, there have been a handful of excellent tools
[2, 14, 15], which can localize configuration errors or gener-
ate repair for misconfigurations. These tools encode network
semantics, forwarding properties, and configurations as a
set of SMT constraints, and solve them with off-the-shelf
solvers, e.g., Z3. However, we find them still limited gen-
erality and scalability. This is mainly due to the network
semantics, especially the distributed routing protocols, is
very complex. As a result, the constraints, even already very
complex, can only cover a subtset of protocol or features,
so may not be general enough to be applied to production
networks. In addition, the complexity of routing protocols
also makes the number of constraints explode with the net-
work size. For example, we find that for a fattree network
of 45 nodes running BGP, the number of SMT constraints is
already as large as 7900. Such a large number of constraints
make it prohibitively expensive for SMT solvers to solve in
a reasonable time.
Before diving into the design of ACR, let us first visit APR
for some inspiration. In APR, there are broadly two classes

of approaches, i.e., the semantics-driven approaches and the
syntax-driven approaches. The semantics-driven approaches,
or correct-by-construction approaches, formally encode the
program repair problem as a set of SMT constraints, and solve
them for a repair [21, 23]. The syntax-driven approaches,
or generate-and-validate approaches, leverage the “plastic
surgery hypothesis” [6]: the code ingredients that can re-
pair the software already exist somewhere in the codebase.
These approaches generate a set of candidate updates, and
validate them to find a repair, Without modeling program
semantics [18, 19, 26].
We can seen that existing ACR methods e.g., [2, 14, 15], fall
within the first category of “semantics-driven” approaches,
and acknowledge the scalability and generality limitations.
In this paper, we explore the other direction, i.e., the
“syntax-based” approach, and find it a quite promising ap-
proach for ACR, due to the following reasons. First, the “plas-
tic surgery hypothesis” also holds for network configura-
tions, since multiple devices often take the same role with
similar configurations, and misconfigured devices can be
repaired based on configuration lines from other devices
of the same role. Second, for syntax-driven approaches in
APR, the validation process often dominates the total repair
time, due to recompiling and rerunning parts or the entire
program [27]. For network, configuration verifiers are al-
ready very fast and it is possible to validate a large number
of candidate fixes for high repair ratio.
Following the direction of syntax-driven approach, we pro-
pose Astragalus, a general and scalable tool that can achieve
ACR for large-scale production networks. Astragalus con-
sists of three steps: (1) Localization. We localize suspicious
configuration lines with techniques from APR, Spectrum-
Based Fault Localization (SBFL)[4, 17]. The intuition for these
techniques is that faulty lines contribute more to property
violations than correct ones. (2) Fix Generation. According
to the suspiciousness of configuration lines, we generate a
set of candidate fixes including remove, insert, and modify,
based on existing configuration in the same network. (3) Val-
idation. We use off-the-shelf configuration verifiers to check
whether the update resolves the violation without any side
effects.
In summary, our contribution includes:
• We motivate a shift from semantics-driven paradigm to a
syntax-driven paradigm for ACR, based on some insights
from program repair.
• We design and implement Astragalus to realize ACR, a
syntax-driven approach that is more scalable and general
than existing methods based on SMT models.
• We test Astragalus on both real faults and synthesized
network configurations with 15 types of injected errors,
and show that it can repair all synthesized errors of O(100)
real devices with an average time of 6.97 seconds.
2
Motivation
In this section, we discuss the hurdle of current configuration
repair approaches to motivate the need for a syntax-driven
approach to ACR. Then, we contrast network configurations
with software code to introduce the challenges of a syntax-
driven approach.
2.1
Semantics-driven repair
Existing work has explored synthesis-based methods for
root-cause diagnosis and automated repair. Synthesis methods
build a formal model of the network control plane, and repair
the configuration with solvers.
AED [2] encodes the intent like (e.g., blackhole-freedom)
and the semantics of routing protocols as a set of SMT con-
straints, and introduces free variables for each line to repre-
sent candidate modifications. An assignment of these free
variables that make the constraints satisfied is a repair. While
this SMT-based approach guaranties correct updates, it is
hard to scale to large networks, due to the vast search space
generated by SMT constraints and free variables. Meanwhile,
the repairs tend to focus on "the most straightforward modi-
fications" that make the constraints satisfiable, which does
not necessarily correspond to a true root-cause repair. For ex-
ample, on our dataset with injected misconfigurations, AED
produced a repair that restores reachability by adding a static
route. Although this kind of “workaround” is functionally
effective, it neither resolves the underlying configuration
error nor provides a clear explanation of the root cause.
CEL [15] extends Minesweeper by decoupling configura-
tion from the control logic and encoding the network model
and intent using SMT constraints. It localizes misconfigu-
rations by solving for a Minimum Correction Set (MCS) of
constraints, which maps back to the root-cause configuration
statements. However, since it is designed for fault localiza-
tion, it can only identify the statements that are most likely
responsible (in most cases), but cannot output an action-
able repair. In addition, its scalability is similarly constrained
by the size of the candidate space, the complexity of the
constraints, and the performance of the solver. When these
factors are combined in a large-scale data center network,
the methods often struggle to maintain stable time/space
consumption.
2.2
Preliminary of APR
In the following, we discuss approaches for automatic pro-
gram repair (APR), which inspires our method in the next
section. APR has been extensively studied, and methods for
APR are broadly classified into two categories: semantics-
driven methods and syntax-driven methods.
Semantics-driven approaches, also known as correct-by-
construction approaches, formally encode the program re-
pair problem as a satisfiability problem, i.e., a set of SMT
constraints, and solve the problem using off-the-shelf SMT

solvers (e.g., Z3, CVC5) [21, 23]. The advantage of such ap-
proaches is that they can guarantee the repair does not intro-
duce side effects. However, scalability is quite limited due to
the fact that the entire problem can have many constraints.
Syntax-driven approaches, also known as generate-and-
validate (G&V) approaches, is another important category
of approaches for APR. Many of G&V approaches are based
on the “plastic surgery hypothesis” [6], that is, the code ingre-
dients that can repair the software already exist somewhere
in the codebase, so we can graft existing configuration lines to
construct the repair.
Automated Program Repair (APR) systems mainly follow
generate-and-validate approaches: they enumerate patch
candidates via syntactic modifications, such as template-
based changes, and use the test suite as the primary cor-
rectness evaluation, rather than relying on a full semantic
specification.
At a high level, these systems (i) generate a set of candi-
date updates and (ii) validate each candidate to identify a
patch that fixes the failing behavior while avoiding regres-
sions [18, 19, 26]. In practice, this approach is often preferred
over semantics-driven repair because it is more scalable: it
sidesteps expensive global semantic reasoning (e.g., solving
large SMT constraints), and more general: it does not require
a precise, program-specific semantic model, but instead lever-
ages readily available tests for validation.
2.3
From APR to ACR
Automated Configuration Repair (ACR) and Automated
Program Repair (APR) share a highly similar problem
structure: both aim to apply smaller, safer changes, starting
from current erroneous behavior and using consistent input
intention without introducing side effects as the criteria to
filter and validate candidate fixes, thereby driving the sys-
tem from an incorrect state to one that satisfies the expected
behavior. In practice, this intent is often expressed as a set
of checkable specifications, such as test cases, configuration
item checks.
Network configuration repair presents unique chal-
lenges compared with general program repair. Network
configurations are typically declarative, with their effec-
tive behavior resulting from the composition and overlay
of multiple rules. Consequently, configuration repair needs
to take into account the system’s global behavior, which
emerges from the combination of multiple configuration
rules through mechanisms such as priority or override, and
configuration items are interconnected through network
topology, protocol states, and other information. Modifica-
tion of a single rule may affect routing, access control, or
service availability across the entire network. Therefore, net-
work configuration repair cannot be accomplished solely
through local syntax checking or single-rule validation.
To the best of our knowledge, all existing methods [2, 14,
15] for network configuration repair fall within the category
of “semantics-driven” approaches. For example, CPR [14] and
AED [2] encode network control plane semantics and oper-
ator intents as a set of SMT constraints, and incrementally
synthesizing configurations by solving the satisfiability prob-
lem. CEL [15] localizes the root cause by solving the minimal
correction set (MCS), a minimal subset of SMT constraints
whose removal makes the remaining constraints satisfied. In
contrast, we explore the other direction, that is, the “syntax-
based” approach for automatic configuration repair.
3
Overview
3.1
Key Ideas
The key idea of this paper is: instead of following the semantic-
driven approach, we explore the syntax-driven approach to
achieve ACR for better scalability and generality. This fea-
sibility of applying syntax-driven approaches is due to the
following two observations.
The “plastic surgery hypothesis” holds true for net-
work configurations. As observed in Provider A’s network,
the devices are organized into availability zones, planes and
pods; each of the zones also has multiple devices with the
same role (i.e. core, aggregation, edge, etc.) to serve the pur-
pose of redundancy. The devices serving as each other’s
backup are often configured similarly; and even the devices
with the same role in different zones share similar configu-
rations to achieve the same functionality[10, 25]. Therefore,
we can repair a device’s configuration by copying the con-
figuration of other devices.
Validation is efficient for network configurations. Net-
work verification is well-developed [33, 34] and can quickly
check configuration correctness for large networks within
seconds. Provider A has an in-house control plane simula-
tor, which can finish the computation of the data plane for
a production network with 2000 nodes, within 5 seconds,
enabling us to efficiently try a lot of candidate fixes. Note
that in APR, the validation process dominates runtime due
to the time required for recompiling and rerunning parts or
the entire program [27]. Thus, the efficiency of validation
implies the efficiency of repair for network configurations.

tools to validate candidate updates. If the validator shows
the network is fully fixed, it returns success. Otherwise, if it
shows the network has fewer errors than before, it localizes
again based on the new configuration (i.e., with the candidate
update) to find new suspicious configurations; if it shows
the network is not improved, it tells the fix generator to try
again by generating a new candidate update and validate it.
The above process iterates for several rounds until a repair
is found, or a maximum number of iterations is reached.
3.3
Merits of Astragalus
The localize-fix-validate framework has three merits, com-
pared with semantic-based approaches.
• Scalability. The search space for fix is relatively small,
as it only involves a small subset of configurations
related to the suspicious one.
• Generality. The framework generalizes to different
protocols and vendors, since it operates upon configu-
ration syntax, rather than semantic.
• Flexibility. the framework allows a flexible choice of
various techniques for each stage. For example, many
SBFL methods can be applied for localization.

Most routing software and network simulators model the
configuration as an abstract syntax tree [12]. Similarly, As-
tragalus also internally represents the configuration files as
an AST. Figure 2(b) is an example of the AST of Figure 2(a).
It organizes the configuration into three nodes: BGP process,
route policies, and prefix lists; and each node is a well-formed
structure containing child nodes, e.g. BGP peers and prefix
list rules. The leaves of the AST are singular parameters: A
string like the import policy, a boolean for permit, and an IP
address for the peer address. To make the AST syntactically
correct, its nodes are well typed; e.g., a route policy node
cannot be a child of a prefix list. We can only remove or add
children to some of the AST nodes, e.g. adding a new rule
to a prefix list is valid, but we cannot create a route policy
with two permit / deny actions.
Astragalus generates syntactically valid candidate updates
on the AST. To meet the restrictions, we hereby define two
terms:
1. A configuration unit is a node in the AST. The term
configuration unit and AST node are used interchange-
ably throughout the rest of this paper.

4.2
Localization
In APR, spectrum-based faults localization (SBFL) is a widely-
used technique which generates suspiciousness scores for
each line of a given program. Specifically, it uses a test suite
[3], and generates an execution profile, which contains:
1. A coverage report: what test cases are executed by each
line of code.
2. An error vector: the pass / fail result for each test case.
Astragalus uses SBFL in the localization step. The follow-
ing section introduces how to construct the test suite, how
to execute the test suite to form the execution profile, and
how to compute suspiciousness of each configuration unit.
Prefixes as the test suite. For APR, the test suite is a set of
inputs to the program. Since the input space of the program
can be huge, and even unlimited, one has to sample some
inputs to form a test suite. By viewing the network control
plane as a program, the inputs are a set of prefixes announced
by some devices inside the network or advertised into the
network by some neighbors. For example, BGP uses com-
mands like bgp network and bgp aggregate 1 to announce
a prefix. Compared to the huge input space of APR, the space
of prefixes for a network’s control plane is often quite limited,
and even fixed in prior. For example, all prefixed announced
inside the network can be easily determined based on the
device configurations. Therefore, Astragalus constructs the
test suite as the set of all prefixes specified by all bgp network.
In case which external routes are also relevant, their prefixes
are included in the test suite as well.

For Astragalus, we implement the coverage test function-
ality as an interface of the in-house simulator. We start an
iteration of data plane computation. The simulator records
the coverage during its simulation process, and outputs the
report to Astragalus.
The execution is initialized by simulating a single iteration
of route advertisement from a converged data plane: each
router sends all of its routes in the main RIB to neighbors.
The insight of starting from a converged data plane is as
follows: (1) the test cases (i.e. the bgp networks’ and external
routes’ prefixes) are propagated to every destination as the
control plane program suggests, so every logic that should
be covered by the test cases is covered; (2) because of the
convergence, route withdrawal in transient states will not
affect the coverage. The converged data plane can be derived
from the validation step of the previous ACR iteration to
avoid duplicate calculation. By aligning Astragalus’s AST
with that of the simulator’s, the coverage report can be used
seamlessly by Astragalus.

4.3
Generating the Fixes
The fix generation step generates candidate repairs for the
suspicious configuration units computed by the localization
step.
How to fix. For each suspicious configuration unit, Astra-
galus can use three change operators to fix the suspicious
configuration unit.
• Remove deletes the node (and its subtree) of the suspi-
cious configuration unit from the AST.
• Insert inserts a node into the suspicious configuration
unit in the AST.
• Modify changes the value of the suspicious configu-
ration unit to other values different from the current
one.
Where to apply Remove / Insert / Modify. As discussed
in §4.1, to maintain the syntactic validity of the AST, only
container configuration units support Insert and Modify
operators. As a result, we restrict Remove / Insert to be appli-
cable to only container configuration units; Modify can be
applied to any configuration unit.
What to Insert / Modify. As the plastic surgery hypothesis
suggests, Astragalus inserts into / modifies the suspicious
configuration unit with nodes that exists elsewhere. At first
glance, it seems there are a large number choices for con-
figuration lines to copy and parameters values to modify.
However, we find that the number of all feasible choices

Deciding the order of fixes. Astragalus generates all possi-

> 0. Then, Astragalus sorts the possible fixes from high to
low based on the suspiciousness of the configuration unit
from which each fix is generated. If multiple configuration
units have the same score, then Remove updates are placed
higher in the list and searched earlier, since there are at most
one removing option per configuration unit, and it is more
likely to yield a successful repair based on our tests; Insert
updates are placed after Remove, and finally Modify, If the
comparison is a tie, their order in the list is determined ran-
domly. The order is decided based on the heuristics of the
data center studied. The list then forms all candidate updates
of the network, as shown in Figure 3(b).
4.4
Validating the Fixes
For each fix, Astragalus first apply the fix to the configura-
tions, thus forming a new control plane consisting of the new
configurations. Then Astragalus computes the data plane,
and validate the fix by testing if all test cases are passed,
using the specification described by §4.2.
The above process of generate-and-validate is repeated for
multiple iterations until a repair is found. In each iteration,
we apply the topmost repair option in the candidate update
list (as shown in Figure 3) to our network, and a new set
of configurations with the repair applied (e.g. the removal
of line 6 in 𝑆2) is produced. By viewing the old and new set
of configurations as two states, each iteration can be seen
as transition from the old state to the new one. Therefore,
Astragalus needs a search strategy to efficiently explore the
state space of configurations.
Currently, Astragalus adopts a depth-first strategy as fol-
lows. After each iteration, if the new configuration state
produces less errors, then we fork a new iteration base on
the new state, and start searching on the state immediately.
To avoid duplicates, we will check whether the state has been
visited before executing the iteration. We also backtrack to
the previous state if the repair option is exhausted.
If we find the state that produce no error, we report a
successful repair, with the path to the final state as the final
repair suggestion.

In this section, we evaluate Astragalus to answer the fol-

the repair / fault localization of network configurations?
(RQ2) Can Astragalus improve the scalability of ACR to

• ACR-SDK is an SDK that provides utilities for Rust-

5.5
(RQ3) Repair Quality
To quantify the repair quality of Astragalus, we evaluate how
many repair suggestions are given by directly removing the
root cause of the problem, i.e. removing the misconfiguration
being injected. we define hit ratio as the frequency of a tool
giving a repair suggestion with the location exactly the same
as the location where the misconfiguration is injected. That
is, if a repair is “add a static route”, it does not count as a hit
since it does not localize the root cause. This metric roughly
estimates the probability that the repair solutions provided
by Astragalus are directly adopted by operators.
For each network to be repaired, CEL gives multiple can-
didate predicates, which can be seen as the possible locations
of misconfigurations. To apply a fix, network engineers also
need to investigate all of the candidate predicates. We calcu-
late the frequency of the root cause as the frequency of the
root cause in all candidate predicates.
Table 4 presents the hit ratio of AED, CEL, and Astragalus.
A key note is that despite CEL’s lower overall hit ratio com-
pared to Astragalus, it includes all root causes within its
candidate predicates, which means network engineers can
still identify the true issue by investigating the full set of
CEL’s suggestions.
For all test cases, AED exclusively proposes adding static
routes, which do not localize the root causes, resulting in a hit
ratio of 0% across all errors. The hit ratio of Astragalus highly
relies on the misconfiguration type and the priority of the
candidate updates. If an easier approach (e.g. changing a
node of route policy from “deny” to “permit”) can fix the
network, Astragalus would not search further for the root
cause, e.g. adding a new route policy. This leads to the vast
difference of the hit ratio: errors with easier root causes tend
to have higher hit ratio.

5.6
(RQ4) Localization quality
Astragalus searches candidate updates guided by the suspi-
ciousness given by SBFL. Without an efficient localization
strategy, Astragalus may end up with randomly searching
and validating in space of all configuration units, which is ex-
tremely time consuming. As a result, the localization quality
directly determines the efficiency and quality of Astragalus.
We define relative root cause location 𝐿𝑟as the ratio of
position of the root cause configuration in the list to the
number of all suspicious configuration units. For example, if
the suspiciousness of the root cause is 0.5, and there are 5
configuration units with suspiciousness higher than 0.5 out
of a total of 100 configuration units, the relative root cause
position is 5/100 = 0.05.
The distribution of 𝐿𝑟indicates how effective the local-
ization is. If we choose the fix randomly from all suspicious
configuration units, 𝐿𝑟should satisfy uniform distribution,
where the root cause should be found anywhere with equal
possibility density; if the localization method is effective, we
should expect more root causes to be found in prior positions.

port policy from the AS12 / AS13) to override the AS path of
the routes sending to another data center. Any routes with
the AS-path containing ASNs from the original data center
will be replaced with ASN 11 repeated several times.
The incident. The operators found that the routes origi-
nated from ASN 12 could not be received by the devices in
ASN 13. The root cause is that the operators overlooked the
vendor-specific behavior (VSB) of the RRs – it not only have
EBGP loop prevention mechanism in BGP standard, it also
have IBGP loop prevention: it would discard a route if it
contains the ASN it belongs to. As 𝑆3 and 𝑆4 rewrited the
AS-path of the route from AS12 to several 11s, 𝑅𝑅1 thought
it contains an IBGP loop. As a result, 𝑅𝑅1 could not learn the
routes from AS12, and all of 𝑅𝑅2, 𝑆7, 𝑆8, 𝑆5 and 𝑆6 could not
receive it.
The repair suggestion given by Astragalus. Astragalus gave
2026 candidate updates for the network fault. Among these
updates, the 23rd most suspicious update is to Modify set
as-path replace to set as-path exclude in the import
policy from 𝑆1 in 𝑆3. Effectively, instead of overriding the AS-
path by its own ASN, it empties the AS-path attribute directly.
Thus, it prevents the IBGP loop prevention mechanism of
𝑅𝑅1 from acting unintentionally, while also serves the pur-
pose of preventing routes drop by EBGP loop prevention in
other data centers.
Astragalus adopted it as the fix successfully restores the
reachability requirement from AS13 (via𝑆3) to AS12. Nonethe-
less, AS12 is still unreachable via 𝑆4, since 𝑆4’s route was still

6.2
Incident B: Route Flips
Compared to Incident A, Incident B features more complex
and obscure phenomenon and root cause.
Network and configurations. The network is larger than
Incident A’s, with 10× more devices and 4× more total lines
of configuration. As shown in Figure 8(b), the devices of AS21
is configured with BGP aggregate address of 20.0.0.0/24
and advertises the route into AS22. They are configured with
an export policy to AS22 that sets the community attribute. In
AS22, the switches sets the BGP routes comming from AS21
to have a lower local preference. Switches in AS23 would
also advertise some prefixes to the network. It does so by
matching community 𝜅, which is set up by the downstream
devices.
The incident. After adding two new switches 𝑆1 and 𝑆2
in AS21, a route flapping happened between 𝑆3, 𝑆4 and 𝑆5.
The root cause was: the configuration of export policy in 𝑆1
and 𝑆2 mistakenly set the community to 𝜅. Considering the
propagation path of 20.0.0.0/24 from 𝑆1 first. The route
propagated normally in 𝑆1 →𝑆3 →𝑆5; but as 𝜅is matched
by the export policy to AS22 in 𝑆5 in AS23, the route is
advertised back to 𝑆4. 𝑆4 also receives the route 20.0.0.0/24
from 𝑆3, but due to the low local preference set by the import
policy from AS21, 𝑆4 now prefers the route sent from 𝑆3,
and the route sent to 𝑆3 is withdrawn. The same problem
also happened on 𝑆3. But as the route sending from 𝑆4 to 𝑆5
withdrawn, it still prefers the route sent from 𝑆1.
The repair suggestion given by Astragalus. In this inci-
dent, however, Astragalus does not repair the network di-
rectly by revealing the root cause. Instead, Astragalus gives
repair suggestions for two locations in 𝑆3 and 𝑆4: First, in the
5th iteration, Astragalus find the candidate update on 𝑆4 to
Modify the import policy from AS23 from allow to deny. As
𝑆4 is no longer able to receive routes from 𝑆5, so the routes
from 𝑆2, despite the low local-preference, is preferred. The
route from 𝑆4, still matches the community 𝜅in 𝑆5 and is
still preferred in 𝑆3. But as it is no longer withdrawn from
𝑆4, the route flapping stopped.
The next step is to fix the incorrect route propagation from
𝑆5 to 𝑆3. In the 15th iteration, Astragalus find the candidate
update on 𝑆3 to Modify the import policy from AS21 to a
policy that sets the local-preference of routes to 200. The
fix is pasted from the import policy of 𝑆3 from a network
controller. As the direct cause of the incident is that 𝑆3 and
𝑆4’s local preference of routes received from AS21 is lower,
the repair candidate removes the condition for 𝑆3 to prefer
routes of 20.0.0.0/24 from 𝑆5. Finally, the route from both
𝑆1 and 𝑆2 is propagated correctly. In total, the repair solution
is found in 315.93 seconds from 15 iterations.
Lessons learned. The repair suggestions generated by As-
tragalus may not be the root cause, but it can be helpful to
find the root cause. In this case, the lower local-preference
of 𝑆3 and 𝑆4 is a direct cause of the route flapping problem.
With the suggestion, network engineers can easily find the
reason of why routes in 𝑆5 are sent back to 𝑆4, further find
the matching condition and the mistakenly set community
value. On the other hand, one might not take the suggestion
as a permanent solution for a network fault, as it might be
not robust and only works for the specification when fixing.
7
Discussion
Using LLMs for fix generation. In this paper, we lever-
aged the “plastic surgery hypothesis” for repair network
configurations. When generating fixes, we used heuristics
to generate fixes from candidates. Recent studies (e.g., [30])
suggests that LLMs can be used to find better fixes. We will
try to apply similar approaches to improve the quality of
fixes in the future.
Repairing data plane misconfigurations. Astragalus cur-
rently repairs only misconfigurations for routing protocols
(e.g., BGP). There are other configurations used for data plane
forwarding (e.g., policy-based routing and NATs), and can
also cause network incidents if there are errors. For data-
plane configuration, the same SBFL approach also works. By
viewing packets as test cases, and test packet forwarding
properties (reachibility, blackhole-freedom, etc.), the local-
ization approach can be also applied on data plane configu-
rations. As the simulator only supports simulation of control
plane. Astragalus currently is unable to fix these configu-
rations. In the future, we will try to implement the ACR
principle on data plane or general network simulators to
enable the repair of data plane configurations.
Repairing wide-area network configurations. In this pa-
per, we design and evaluate Astragalus based on data center
network configurations. For other kinds of networks such
as WANs, we tentatively think the plastic surgery hypoth-
esis also holds, as there are also some level of redundancy
(e.g. multiple border routers peering with the same ASes).
Therefore, we hypothesize Astragalus can be a general tool
for repairing these networks. We leave the evaluation of
Astragalus on WANs as a future work.

8
Conclusion
In this paper, we motivate the need of automatic configura-
tion repair (ACR) with experiences of real-world network
incidents. Inspired by APR, we propose to achieve ACR with
a syntax-driven approach, which is general and scalable.
Specifically, we design and implement Astragalus, and eval-
uate it based on configurations of real production networks.
We show Astragalus can repair over 97.5% of the injected
errors within 5 seconds.
This work does not raise any ethical issues.
