Abstract
Grassroots Logic Programs (GLP) is a concurrent logic program-
ming language in which logic variables are partitioned into paired
readers and writers. An assignment is produced at most once via a
writer and consumed at most once via its paired reader, and may
contain additional readers and/or writers. This enables the concise
expression of rich multidirectional communication modalities.
“Logic Programs as Types for Logic Programs” (LICS’91) defined
types as regular sets of paths over derivable ground atoms. Here, we
define types to be regular sets of moded paths, where a mode cap-
tures directionality of communication—whether a subterm is con-
sumed from or produced to the environment—enabling the typing
of interactive partial computations including those that eventually
deadlock or fail, or never terminate. We provide a syntactic defini-
tion of well-typing and prove that a program is well-typed iff the
path abstraction of its moded-atom semantics satisfies covariance
and contravariance conditions with respect to its type.
The GLP type system was implemented in Dart by AI, starting
from a mathematical specification of Typed GLP (this paper), de-
riving from it an English spec (written by AI), and from the spec
deriving Dart code (by AI). While GLP is naturally untyped, the mo-
tivation for Typed GLP comes from programming with AI: Asking
AI to program complex communication modalities in GLP (and in
general) and hoping for the best is a tenuous strategy. The emerg-
ing discipline we advocate and employ is for the human designer
and AI to jointly develop and agree upon (1) GLP types; (2) GLP
procedure type declarations; (3) informal (English) descriptions of
the procedures; and only then let AI attempt to write (4) GLP code
based on those.

Introduction
Grassroots Logic Programs. Grassroots Logic Programs (GLP) is
a concurrent logic programming language in which logic variables
are partitioned into paired readers and writers, conjuring both linear
logic [14] and futures/promises [1]: an assignment is produced
at most once via the sole occurrence of a writer (promise) and
consumed at most once via the sole occurrence of its paired reader
(future), and may contain additional readers and/or writers.
Hence, GLP provides for the concise expression of rich multidi-
rectional communication modalities, including bidirectional com-
munication and the dynamic expansion and reconfiguration of
communication networks.
GLP’s design eschews unification in favour of simple term match-
ing. Being relational and nondeterministic, GLP—like its predeces-
sor concurrent logic languages [29]—can express nondeterministic
asynchronous concurrent processes such as the fair merging of
streams.
GLP is designed for the implementation of smartphone-based,
serverless, grassroots platforms [31]. A digital platform is grass-
roots [30, 32] if it can have multiple instances that can (1) operate
independently of each other and of any global resource other than
the network, and (2) coalesce into ever larger instances, possibly
resulting in a single global instance. The SRSW restriction is what
makes GLP suitable for grassroots distributed execution: each vari-
able binding has exactly one producer and one consumer, so assign-
ments can be communicated between independent agents without
consensus.
Typing GLP. The challenge of ensuring correctness in concurrent
programs with rich communication modalities motivates a type
system that can express and verify the intended communication
behaviour. “Logic Programs as Types for Logic Programs” [11]
defined types as regular sets of paths over derivable ground atoms.
Here, we define types to be regular sets of moded paths, where a
mode captures directionality of communication—whether a subterm
is consumed from or produced to the environment—enabling the
typing of interactive partial computations including those that
eventually deadlock or fail, or never terminate.
GLP types are thus regular sets of moded paths, naturally speci-
fied using BNF rules with a complementation operator ? that relates
producer and consumer views: a type Stream implicitly defines
its dual Stream?, with modes complemented throughout. Proce-
dure type declarations specify the mode of each argument, e.g.,
merge(Stream?,Stream?,Stream) declares that merge consumes
two streams and produces one.
A GLP program is well-typed if three conditions hold. First, output
conformance: each clause’s head and body must have paths accepted
by the declared types. Second, input coverage: every input path
permitted by the type must be accepted by some clause, ensuring
the program handles all inputs the type promises it will. Third, the
types of a writer 𝑋and its paired reader 𝑋? must be compatible,
meaning that the writer’s type is a subtype of the dual of the reader’s
type [13].
We provide GLP with moded-atom semantics—capturing the
distinction between produced and consumed values, and doing so
even for partial computations—and prove that a program is well-
typed iff the path abstraction of its semantics satisfies covariance
and contravariance conditions [5, 26] with respect to its type: every
output path in the semantics is accepted by some path in the type
(covariance), and every input path in the type accepts some path in
the semantics (contravariance).
Programming with AI. The GLP type system was implemented
in Dart [15] by AI, starting from a mathematical specification of
Typed GLP (this paper), deriving from it an English spec (written
by AI), and from the spec deriving Dart code (by AI), with multiple
bidirectional iterations between the code, the spec, and the paper.
The paper, which underwent multiple major revisions during the
implementation process, may be more detailed than usual so as to
serve as the complete specification of Typed GLP for AI to derive
from it the English spec and in turn the implementation.

While GLP is naturally untyped, the motivation for Typed GLP
comes from programming in GLP with AI: asking AI to program
complex communication modalities in GLP (and in general) and
hoping for the best is a tenuous strategy. A key goal of Typed GLP
is to offer an abstract and precise interface between the human
designer and the AI programmer: moded types serve as a spec-
ification language for data types and communication modalities,
constraining the space of legal programs and helping AI get commu-
nication modes right during programming rather than debugging.
The emerging discipline [3, 9, 24] we advocate and employ is for the
human designer and AI to jointly develop and agree upon (1) GLP
types; (2) GLP procedure type declarations; (3) informal (English)
descriptions of the procedures; and only then let AI attempt to write
(4) GLP code that complies with these formal and informal specs.

Grassroots Logic Programs
Grassroots Logic Programs (GLP) extend LP by (1) adding a paired
reader 𝑋? to every “ordinary” logic variable 𝑋, now called a writer;
(2) restricting variables in goals and clauses to have at most a single
occurrence (SO); and (3) requiring that a variable occurs in a clause
iff its paired variable also occurs in it (single-reader single-writer,
SRSW). The result eschews unification in favour of simple term
matching, is linear-logic-like [14], and is futures/promises-like [10]:
each assignment 𝑋:= 𝑇is produced at most once via the sole
occurrence of a writer (promise) 𝑋, and consumed at most once via
the sole occurrence of its paired reader (future) 𝑋?.

Guards
GLP clauses may include guards—tests that determine clause appli-
cability.
Definition 3.12 (Guarded Clause). A guarded clause has the form
𝐻:- 𝐺| 𝐵, where 𝐻is the head, 𝐺is a conjunction of guard
predicates, and 𝐵is the body. The guard separator “|” distinguishes
guards from the body, and is interpreted logically as a conjunction.
Guard arguments are readers paired to head writers.
Guards have three-valued semantics. Each guard predicate ex-
plicitly defines its success condition. A guard suspends if it does
not succeed but some instance of it under a readers substitution
would succeed. A guard fails if no such instance exists. A guard
conjunction succeeds if all members succeed; it suspends if any

Typed GLP
While GLP is an untyped language, with types being an addition,
we introduce Typed GLP including the notion of types and well-
typing. The GLP type system supports correct programming of
multidirectional communication modalities.
4.1
Type Syntax
4.1.1
Type Declarations. LP types are concerned with the values
logic variables may take. In GLP, we are also concerned whether
these values were produced or consumed during the computation.
Thus, a GLP type also indicates whether a term, or a subterm, is
produced or consumed. By convention, we define types from the
perspective of their producer, which implicitly defines its dual—the
same type but from the perspective of its consumer.
GLP types are naturally specified using BNF rules with the com-
plementation operator ?, with every type definition implicitly defin-
ing also its dual. For example, the stream producer type:
Stream ::= [] ; [_|Stream].
implicitly defines the dual stream consumer type Stream?. If it
were to be specified explicitly, it would be written as:
Stream? ::= []? ; [_?|Stream?]?.
with primitive types _ denoting any produced term and _? any
consumed term.
A type that is not complemented (for example Stream) is an
output type, and its dual (for example Stream?) is an input type. A
type that contains both produced and consumed positions is an
interactive type. An alternative in a type definition may also be a
type name 𝑆, providing type union for types with disjoint top-level
functors.
The primitive types include Integer, Real, Number, String,
Constant, and Exp (arithmetic expressions). Their formal defini-
tions appear in Appendix B.
The formal specification of the type automaton induced by a
typed GLP program appears in Section 5.3.
4.1.2
Procedure Declarations. Typed GLP includes a type decla-
ration for each procedure. For example, the merge program could
include the procedure declaration:
procedure merge(Stream?,Stream?,Stream).
which is a syntactically-pleasing alternative to the formal definition
of a procedure type as a typed term:
Procedure ::= merge(Stream?,Stream?,Stream).
To ease the specification of types, we include parametrised types,
a limited form of type polymorphism. A parametrised type declara-
tion of merge could look like:
Stream(X) ::= [] ; [X|Stream(X)].
procedure merge(Stream(X)?,Stream(X)?,Stream(X)).
Declaration placement. Type declarations may appear anywhere
in a program before they are used. A procedure declaration must
appear immediately before its defining clauses, which must be
contiguous. For example:
Stream ::= [] ; [_|Stream].
procedure merge(Stream?,Stream?,Stream).
merge([X|Xs], Ys, [X?|Zs?]) :- merge(Ys?, Xs?, Zs).
merge(Xs, [Y|Ys], [Y?|Zs?]) :- merge(Xs?, Ys?, Zs).
merge(Xs, [], Xs?).
merge([], Ys, Ys?).
procedure copy(Stream?, Stream).
copy([X|Xs], [X?|Ys?]) :- copy(Xs?, Ys).
copy([], []).
Here, Stream is defined before it is referenced in either procedure
declaration. Each procedure declaration immediately precedes its
contiguous clauses.
4.2
Program Syntax
4.2.1
SRSW Relaxations. The SRSW restriction (Definition 3.3)
may be relaxed under certain conditions. Section 3.4 described
guard-based relaxations; here we describe additional relaxations
available in Typed GLP.
Anonymous variables. An anonymous variable is any variable
whose name begins with _ (e.g., _, _In, _Out). Anonymous vari-
ables may appear anywhere a writer variable may appear. Each
occurrence denotes a fresh writer with no paired reader, providing
a controlled exception to the SRSW restriction. Values assigned to
anonymous variables are discarded. For example:
second([_, X | _], X?).
foo(X) :- bar(_Result, X?).
In the first clause, _ discards the head and tail of the input list. In
the second, _Result discards the first output of bar. Using named
anonymous variables like _Result improves readability while main-
taining the same semantics as _.
The symbols _ and _? in type definitions are primitive type sym-
bols, not variables. They should not be confused with anonymous
variables in program clauses.
Type-based relaxations. If the type of a variable is a constant
type (Number or String), any number of readers of that variable are
permitted in a clause, since constant values contain no writers and
can be safely duplicated. This extends the guard-based relaxation
of Remark 3.2: guards establish groundness dynamically at runtime,
whereas type declarations establish it statically at compile time.
Type checking of guards. For the purpose of type checking,
guards are treated as conjunction with the body: H :- G | B
is type-checked as H :- G, B.

5.4
Subtyping
Definition 5.7 requires that body-body variable pairs have dual
types. This requirement can be relaxed using subtyping: it suffices
that the type of the writer𝑋be a subtype of the dual of the type of its
paired reader 𝑋?. Informally, this means that anything produced by
the writer X can be consumed by the reader X?, with a caveat: when
the direction of communication is inverted between the producer
and consumer, so does the direction of the subtyping obligation
among their corresponding types. We provide a motivating example
and a formal definition of this notion.
Consider a file system monitor that handles read, write, and
delete operations:
FileOp ::= read(Path?,Content)
; write(Path?,Content?)
; delete(Path?).
procedure fs_monitor(Stream(FileOp)?).
A read-only client wishes to interact with this monitor, but only
issues read operations:
ReadOp ::= read(Path?,Content).
procedure ro_client(Stream(ReadOp)).
Connecting these directly violates the strict duality requirement:
the monitor expects Stream(FileOp)? but the client produces
Stream(ReadOp), and ReadOp ≠FileOp. Yet this interaction is safe:
the client produces a subset of what the monitor accepts, and the
monitor’s responses (the Content in read operations) are exactly
what the client expects.
This motivates subtyping on moded types, which captures when
interaction is safe despite the types not being exact duals.
Definition 5.10 (Simple Prefix). A simple prefix of an output type
𝑇is a path in 𝑇’s type automaton starting from 𝑇that contains no
mode inversions. A simple prefix ends when it reaches either:
• The produced primitive _ (which accepts any produced
term), or
• A mode inversion point: any position whose type is marked
with ? (including _?, S? for user-defined 𝑆, or Integer?,
etc.).
Since the type automaton is deterministic, each position along a
simple prefix corresponds to exactly one functor.
Definition 5.11 (Prefix Acceptance). A simple prefix 𝑝of type
𝐴is accepted by type 𝐵if 𝐵has a simple prefix 𝑞with identical
functor/position structure, where endpoints satisfy: _ matches only
_; output type 𝑆matches 𝑆or _; mode inversion 𝑆? matches any
mode inversion at the same position.
Definition 5.12 (Subtyping). Let 𝐴and 𝐵be GLP output types.
We say 𝐴is a subtype of 𝐵, written 𝐴<: 𝐵, if:
(1) Every simple prefix of 𝐴is accepted by 𝐵.
(2) For every mode inversion point in 𝐴reached by a simple
prefix—say, type 𝐴′? at that position—there is a correspond-
ing mode inversion point 𝐵′? in 𝐵at the same position, and
𝐵′ is a subtype of 𝐴′.

6
GLP Semantics and Well-Typing
Similarly to LP, we can derive denotation semantic notions for the
type system to be an abstraction thereof. However, the semantic
objects we employ—moded terms—are richer than in LP, since we
wish them to capture:
(1) Behaviours of partial runs, so that a well-typed program
would well-behave even in runs that eventually fail or dead-
lock, or not terminate.
(2) Interaction with the environment, namely whether val-
ues to variables were produced or consumed during a run.
This would allow the type system to express both output
conformance—all values produced are in the type, and input
coverage—any input within the type may be consumed by
the program.
6.1
Path Projections
We partition moded paths by their root mode, separating what the
program produces from what it consumes.
Definition 6.1 (Path Projections). Given a set 𝑆of moded paths,

Module System
Programs composed of multiple communicating components re-
quire modular structure. This section extends Typed GLP with a
module system that integrates with the moded type system, en-
abling type-safe composition of separately developed modules.
7.1
Design
The module system rests on four principles.
Hierarchy mirrors the file system. A GLP project is a direc-
tory tree. Each .glp file is a module; each directory is a scope. A
distinguished file self.glp in any directory defines types and pro-
cedures shared by all modules in that directory and its descendants,
following FCP’s self.cp convention [? ].
Implicit ancestor scoping. A module sees every type and pro-
cedure definition from every ancestor scope—from its directory’s
self.glp up through the project root—without any import direc-
tive.
Self-contained type checking. Every module declares the full
moded type signature of every cross-module procedure it calls, via
imported procedure declarations. Procedures defined in ancestor
self.glp files are visible without import, just like types. Type
checking is entirely local: the type checker needs only the module’s
own text and its ancestor scope.
Structural type compatibility. Type identity is structural. Two
independently defined types with the same type automaton are
compatible, regardless of their names or defining modules.
Procedure declarations. Every procedure declaration is one of
three kinds:
procedure p(...).
private to the module
exported procedure p(...).
reachable from other modules
imported procedure M#p(...).
declares dependency on module 𝑀
An imported declaration carries the full moded type signature
of the remote procedure. Types referenced in the signature are
resolved against the caller’s type scope (which includes ancestor
types). The type checker verifies calls to M # p(...) against the
local imported declaration, without accessing module 𝑀.
Ancestor scoping. The scope for a module 𝑀at path 𝑝in a project
rooted at 𝑟is constructed by starting with the predefined type envi-
ronment 𝐸0 (built-in types: Integer, String, Constant, etc.), then

7.2
Static Linking
When all modules are available at compile time, project compilation
transforms the module hierarchy into a single flat program. All inter-
module calls become local calls. The output is indistinguishable
from a hand-written single-file program.
The transformation proceeds in four steps. First, the compiler
walks the project directory tree, collecting every .glp file and
constructing the ancestor scope chain for each module. Second,
each module is type-checked independently against its ancestor
scope, exactly as for single-file compilation. Third, after type check-
ing, every procedure 𝑝/𝑛in every .glp file (including self.glp
files) is renamed to 𝑀:𝑝/𝑛, eliminating name collisions—for exam-
ple, both agent.glp and boot.glp may define merge/3, yielding
agent:merge/3 and boot:merge/3 in the output. Fourth, every
goal in every clause body is resolved: a local call to 𝑝in mod-
ule 𝑀becomes 𝑀:𝑝, a cross-module call 𝑀′ # 𝑝becomes 𝑀′:𝑝, a
call matching a procedure in an ancestor self.glp is resolved to
its renamed form by walking the ancestor chain, and calls to root
prelude procedures remain unqualified. Every exported procedure
in every module receives an unqualified alias as an entry point, so
that code loaded on top of the linked program can call any exported
procedure by its original name.
The result is a single program compiled through the standard
pipeline. Renaming is purely syntactic and call resolution maps each
call to the unique procedure that type checking already verified it
against, so the transformation preserves well-typing.
7.3
Dynamic Linking
In FCP, a module is a server process—a monitor—that serves a
stream of procedure-call requests [? ]. The call M # goal(...)
sends a request to module 𝑀’s server. GLP dynamic linking follows
the same architecture, with moded types providing static guarantees
about the interaction.
A dynamically loaded module is represented at runtime by a
monitor process that consumes a stream of call requests. The type
of this stream is determined by the module’s exported declarations:
each exported procedure contributes an alternative to the request
type. For example, a module exporting agent/4 would serve re-
quests of the form agent(Constant?, ...) on its input stream.
The compiler generates a dispatch table that maps each request to
the corresponding exported procedure. At runtime, a body kernel
resolves each incoming request against this table, following FCP’s
activate mechanism [? ].
The caller’s imported declaration describes the type of requests
the caller will send. Type safety requires that the module server
accepts at least the requests the caller may issue. This is precisely
the subtyping condition on the request stream: the callee’s exported
type must be a supertype of the caller’s imported type (contravari-
ance on the consumed stream), and any responses embedded via
hollow messages must satisfy covariance.
For dynamic linking, type automata must be available at load
time. A compiled module carries its type automata alongside its
bytecode, enabling the compatibility check without access to source
code.
7.4
Implementation
The module system has been implemented in Dart as part of the GLP
runtime. Ancestor type scoping, the three procedure declaration
kinds, and cross-module type checking are operational. Both linking
modes are implemented.
Static linking is implemented as an AST-to-AST transformation:
the linker renames every procedure 𝑝/𝑛in every .glp file (includ-
ing self.glp files) to 𝑀:𝑝/𝑛, resolves local calls to their prefixed
names, replaces cross-module calls 𝑀′ # 𝑝with 𝑀′:𝑝, resolves calls
to ancestor self.glp procedures to their renamed form, leaves
root prelude calls unprefixed, and generates entry-point aliases for

fed through the standard compilation pipeline.
Dynamic linking follows the architecture described above: the
compiler generates a _select/1 dispatch table from exported decla-

Parameterized Types
The type system presented in Section 4 uses monomorphic types:
merge is declared over Stream, which carries elements of type _.
This loses information—a merge of integer streams produces an inte-
ger stream, but the type system cannot express this. Parameterized
types recover this precision.
Parameterized types are syntactic sugar. A parameterized type
definition is a template; each use with concrete type arguments is
expanded into a fresh monomorphic type definition before type au-
tomaton construction. After expansion, the existing type checking
and subtype checking machinery apply without modification. Note
that instantiating Stream(_) recovers the original unparameterized
definition Stream ::= [] ; [_ Stream]|, so the parameterized
form strictly generalizes the monomorphic one.

ten as uppercase identifiers in parentheses after the type name:
Stream(X) ::= [] ; [X | Stream(X)].
This defines a type template with one parameter X. An instantia-
tion supplies a concrete type for each parameter:

the type checker reports an error.

8.4
Subtyping
Since parameterized types expand to monomorphic types, subtyp-
ing is handled entirely by the existing DFA-based subtype check
(Section 5.4). No additional subtyping rules are needed.
Example: subtyping through expansion. Suppose:
Msg ::= text(String) ; cmd(String).
Cmd ::= cmd(String).
Then Cmd ≤Msg by the standard subtype check. Expanding
Stream(Cmd) and Stream(Msg) yields:
Stream<Cmd> ::= [] ; [Cmd | Stream<Cmd>].
Stream<Msg> ::= [] ; [Msg | Stream<Msg>].
The DFA-based subtype check determines that Stream<Cmd> ≤
Stream<Msg>, because at each list-cons step, the head type Cmd
is a subtype of Msg. This is the standard covariance result for
output-position parameters, obtained without any explicit variance
annotation—it follows directly from the existing subtype machinery
operating on the expanded types.
Contravariance from modes. For input positions, the mode anno-
tation ? reverses the subtype direction through complementation.
Consider:
Channel(In, Out) ::= ch(In, Out?).
A Channel(Msg, Cmd) expands to ch(Msg, Cmd?). A Channel(Msg, Msg)
expands to ch(Msg, Msg?). Since Cmd ≤Msg, by complementation
Msg? ≤Cmd?. Therefore Channel(Msg, Msg) ≤Channel(Msg, Cmd):
the channel that accepts the wider input type (Msg) is a subtype
of the one that accepts the narrower input type (Cmd). This is the
standard contravariance result, obtained automatically from com-
plementation on the expanded types.
Because parameterized types are expanded before type check-
ing, the system does not require explicit variance annotations.
Variance—covariant, contravariant, or invariant—is determined au-
tomatically by the DFA-based subtype check operating on the ex-
panded monomorphic types.

Interaction with Modules
Parameterized types and modules interact naturally through expan-
sion at the call site.
Imported declarations instantiate parameters. A module that
imports merge instantiates its type parameter to the specific mes-
sage type used locally:
CounterCall ::= inc ; dec ; read(Integer).
imported procedure merge(Stream(CounterCall)?,
Stream(CounterCall)?,
Stream(CounterCall)).
The merge module need not know about CounterCall. Its pa-
rameterized declaration merge(Stream(X)?, Stream(X)?, Stream(X))
is instantiated to Stream(CounterCall) at the importing site. Type
checking of the importing module uses the expanded monomorphic
type.
Structural compatibility across modules. Because type identity
is structural (Section 7.1), independently expanded types are com-
patible if their type automata are equivalent or related by subtyping.
If module A expands Stream(Msg) and module B independently
defines MsgStream ::= [] ; [Msg MsgStream].|, the two types
have identical automata and are fully compatible.
Example: monitor with parameterized merge. Consider a mon-
itor that accepts requests via a merged input stream:
%% counter_monitor.glp
CounterCall ::= inc ; dec ; read(Integer).

confirms they agree.
8.6
Expansion Algorithm
The expansion algorithm runs as a preprocessing step, after parsing
and before type automaton construction.
(1) Collect templates. Scan all type definitions. A definition
whose name is followed by a parenthesized parameter list
is a template; all others are monomorphic. Templates are
recorded but not added to the type environment.
(2) Collect instantiations. Scan all type definitions, procedure
declarations (including imported and exported declara-
tions), and type definition bodies for parameterized type ref-
erences𝑇(𝑆1, . . . ,𝑆𝑘). Each distinct instantiation is recorded.
A type definition body may reference a different parame-
terized type (e.g., a Pair appearing inside Stream); such
cross-references are collected in this step and expanded in
the next.
(3) Expand. For each recorded instantiation, generate a fresh
monomorphic type definition by substituting parameters
and renaming. Recursive references within the template
body are expanded to the same fresh name. Nested instan-
tiations are expanded inside-out.
(4) Replace references. In all type definitions and procedure
declarations, replace every parameterized type reference
𝑇(𝑆1, . . . ,𝑆𝑘) with its expanded name 𝑇⟨𝑆1, . . . ,𝑆𝑘⟩.
(5) Remove templates. Remove parameterized type definitions
from the type environment. Only the expanded monomor-
phic definitions remain.

Related Work
Concurrent Logic Programming. GLP belongs to the family of
concurrent logic programming (CLP) languages that emerged in the
1980s: Concurrent Prolog [28], GHC [35], and PARLOG [7]. These
languages interpret goals as concurrent processes communicating
through shared logical variables, using committed-choice execution
with guarded clauses.
A key evolution was flattening: restricting guards to primitive
tests only. Flat Concurrent Prolog (FCP) [21] and Flat GHC [35]
demonstrated that flat guards suffice for practical parallel program-
ming while dramatically simplifying semantics and implementation.
Shapiro’s comprehensive survey [29] documents this family and
its design space.
GLP can be understood as Flat Concurrent Prolog with the
Single-Reader Single-Writer (SRSW) constraint added. FCP in-
troduced read-only annotations (?) distinguishing readers from
writers of shared variables, enabling dataflow synchronization.
However, read-only unification proved semantically problematic:
Levi and Palamidessi [19] showed it is order-dependent, and Mierowsky
et al. documented non-modularity issues. GHC dispensed with read-
only annotations entirely, relying on guard suspension semantics.
Tick [34] surveyed this evolution as a “deevolution” of concur-
rent logic programming languages, driven by the growing per-
ception that reduced expressiveness is sufficient for practical pro-
gramming. GLP continues this trajectory: the SRSW constraint—
requiring that each variable has exactly one writer and one reader
occurrence—resolves the difficulties of read-only unification by
ensuring that (1) no races occur on variable binding, and (2) term
matching suffices, eschewing unification entirely. The result is a
cleaner semantic foundation while preserving the expressiveness of
FCP, including streams, hollow messages, and meta-programming.
Janus [27] (see also [8]), a concurrent constraint language de-
signed for distributed programming, enforces a two-occurrence
restriction on variables—each variable has exactly one writable
occurrence (teller) and one readable occurrence (asker)—which is
the constraint-programming counterpart of GLP’s SRSW restric-
tion. Lafont’s Interaction Nets [18] enforce linearity through graph
rewriting: each agent has a single principal port, and interaction
rules fire only between agents connected at their principal ports,
ensuring deterministic reduction. Both Janus and Interaction Nets
share with GLP the design principle that restricting the use of
shared resources—whether logic variables, constraint store entries,
or graph ports—to single-reader single-writer disciplines yields
simpler semantics and enables distributed execution.
Modes in Concurrent Logic Programming. Mode systems for
CLP have a rich history. PARLOG used mode declarations at the
predicate level, with input modes enforcing one-way matching
where clause variables can be instantiated but goal variables cannot
be bound.
Ueda’s work on moded Flat GHC [36, 38] is most directly rel-
evant to Typed GLP. His mode system assigns polarity to every
variable occurrence: positive for input/read capability, negative for
output/write capability. The well-modedness property guarantees
each variable is written exactly once—a single-writer constraint
matching half of GLP’s SRSW requirement. Ueda’s subsequent lin-
earity analysis [37] identifies variables read exactly once, enabling
compile-time garbage collection for single-reader structures.
GLP enforces both single-reader and single-writer universally as
a syntactic restriction, whereas Ueda’s system guarantees single-
writer with single-reader as an optional refinement. This stronger
restriction enables GLP’s simpler distributed execution model. Our
contribution is a type system for this discipline, building on LP types
rather than mode inference.
Types for Logic Programs. The type system for GLP builds on the
Frühwirth et al. framework [11], which defines LP types as regular
sets of paths and characterizes well-typing via path abstraction
of the ground-atom semantics. The companion paper [41] estab-
lishes the semantic foundations through tuple-distributive sets. Our
moded types extend this framework by augmenting paths with
mode annotations that capture the distinction between consumed
and produced subterms.
Earlier work on LP types includes Mycroft and O’Keefe’s pre-
scriptive polymorphic type system [25] and Mishra’s foundational
work on tuple-distributivity [23]. Mercury [33] provides a compre-
hensive practical system separating type checking, mode checking,
and determinism inference. Our work differs in integrating modes
directly into the type structure rather than treating them as a sepa-
rate analysis.
Linear Logic, Session Types, and Futures. GLP’s SRSW dis-
cipline is reminiscent of linear logic’s [14] resource sensitivity:
each variable binding is produced at most once and consumed at
most once. A GLP reader/writer pair is operationally a future or
promise [1]: the writer creates a promise for a value, the reader
awaits fulfillment. Unlike futures in mainstream languages, GLP
futures can carry logical terms containing further reader/writer
pairs, enabling recursive communication structures—a capability
shared with channel-passing calculi such as the 𝜋-calculus [22].
Session types [16, 39] use linear logic to type communication
protocols. Since GLP messages may contain variables, they allow
continuation of the session in both directions, ad infinitum: a reader
embedded in a message allows a further message in the same direc-
tion, and a writer allows a message in the opposite direction—each
of which may contain additional readers and writers. Thus a Stream
type is a session: each [X|Xs] message consists of an element X
and continuation Xs, extending the interaction indefinitely. The
CounterCall example (Section 4.3) is richer: read(Integer?) is
a message that embeds a writer that inverts the communication
direction, enabling the monitor to respond—typed precisely by the
mode inversion in the moded type definition. GLP’s moded types
are thus the logic-programming counterpart of session types, with
the mathematical foundations differing in derivation: session types
from linear logic sequents, moded types from regular sets of moded
paths.
Session type theory distinguishes duality from subtyping. Du-
ality [16] is an involution 𝑆↦→𝑆that swaps input and output
modalities; dual endpoints have perfectly matching protocols. Sub-
typing [13] is a preorder for safe substitution: 𝑆<: 𝑇if a channel

Specification-First AI Programming. The development disci-
pline employed in this work—jointly agreeing on types, proce-
dure declarations, and informal descriptions before AI attempts
implementation—synthesizes classical specification-first method-
ologies with recent advances in AI-assisted programming. Design
by Contract [20] prescribes formal interface specifications (precon-
ditions, postconditions, invariants) before implementation. Literate
Programming [17] advocates natural language exposition alongside
code. Type-driven development [4] uses types to guide implemen-
tation, with typed holes allowing incremental refinement. Recent
work extends these ideas to LLM-based code generation: Blinn et
al. [3] demonstrate that typed holes provide crucial semantic con-
text for AI code completion, while Mündler et al. [24] show that
type constraints during generation reduce compilation errors by
over 50%. Our discipline applies these principles at the specification
level: types and procedure declarations serve as a contract between
human designer and AI programmer, constraining the space of valid
implementations before generation begins.

Conclusion
We have developed a type system for Grassroots Logic Programs
(GLP), a concurrent programming language that partitions logic
variables into paired readers and writers, restricts each to a single
occurrence, and eschews unification in favour of term matching.
This design ensures that each variable binding is produced at most
once and consumed at most once.
Our moded types extend LP types [11] with mode annotations
that capture the distinction between values produced by the pro-
gram and values consumed from the environment. Types are regular
sets of moded paths, specified via BNF rules with a complementa-
tion operator (·)? that uniformly relates producer and consumer
views of the same communication channel.
Well-typing is defined to capture both output conformance—all
values produced conform to the type—and input coverage—the
program accepts all inputs permitted by the type. Theorem 6.7
establishes that well-typing is preserved through GLP computation:
if a program and initial goal are well-typed, then all moded-atoms
outcomes and resolvents remain well-typed.
We extended the core type system with two mechanisms for
programming in the large. The module system (Section 7) supports
separate type checking of modules against locally declared inter-
faces, with structural type compatibility ensuring that indepen-
dently developed modules can be composed safely. Static linking
flattens a module hierarchy into a single program via procedure re-
naming; dynamic linking verifies subtype compatibility at load time.
Parameterized types (Section 8) enable generic definitions—merge
over Stream(X) for any X—with variance determining how subtyp-
ing propagates through type parameters. Together with subtyping,
these extensions form a coherent package: modules enable inde-
pendent development, parameterized types enable type-preserving
composition, and subtyping enables flexible substitution.
Future Work. The formal semantics of parameterized type automata—
extending the DFA-based type representation of Section 5.3 to pa-
rameterized families—remains to be developed. The dynamic link-
ing protocol requires a concrete specification of how type automata
are serialized and compared at load time. Finally, the interaction
between parameterized types and subtyping across module bound-
aries deserves further study, particularly for higher-order cases
where type parameters themselves carry mode structure.

GLP provides predefined types, guard predicates, system predi-
cates, and body kernels that are available in every program. The
complete listing—predefined types, guards, arithmetic comparisons,

B.1
Type Aliases
For documentation and readability, type aliases are permitted in
source programs. A simple alias has a single alternative that is a
type reference:
AgentId ::= Constant.
% alias for primitive type
MyStream ::= Stream.
% alias for defined type
ConsumedStream ::= Stream?. % alias for dual of defined type
A union alias has multiple alternatives, each of which is a type
reference:
Msg ::= NetMsg ; UserMsg.
% union of two message types
Union aliases are expanded by collecting all alternatives from the
referenced types. For example, if NetMsg ::= msg(_, _, _). and
UserMsg ::= sent(_, _) ; received(_, _)., then Msg is ex-
panded to Msg ::= msg(_, _, _) ; sent(_, _) ; received(_, _).
The referenced types must be defined (not aliases themselves or
primitives), and the expanded alternatives must satisfy the deter-
minism requirement.
All aliases are fully resolved during preprocessing: every occur-
rence of an alias name is replaced by its expansion before type
automaton construction and well-typing analysis. The well-typing
checker therefore never encounters alias definitions—it operates
only on resolved types. Circular alias chains (e.g., A ::= B. B ::= A.)
are detected and rejected during preprocessing.
B.2
Predefined Parameterized Types
The prelude defines four parameterized type templates, available
in every program:
Stream(X) ::= [] ; [X | Stream(X)].
OpenStream(X) ::= [X | Stream(X)].
DiffList(X) ::= Stream(X) \ Stream(X)?.

Stream(X) is a list of elements of type X, possibly empty. OpenStream(X)
is a non-empty stream (no [] base case). DiffList(X) is a differ-
ence list: a pair of a stream and a hole (reader) for constant-time
concatenation. Channel(In, Out) is a bidirectional communica-
tion channel with read stream In and write stream Out? (the mode
annotation on Out indicates it is consumed by the channel holder).
These templates are expanded at each use site before type au-
tomaton construction (Section 8.2).

C.8
Association List Lookup
This example demonstrates two key aspects of Typed GLP: (1) the importance of matching procedure declaration modes to data flow
semantics, and (2) the SRSW relaxation for constant types.
Typed GLP Program.
Pair ::= pair(String, Integer).
PairList ::= [] ; [Pair | PairList].
procedure lookup(String?, Integer, PairList?, PairList).
lookup(Key, V?, [pair(K, V)|Rest], [pair(K?, V?)|Rest?]) :-
Key? =?= K? | true.
lookup(Key, Val, [pair(K, V)|Rest], [pair(K?, V?)|Rest1?]) :-
otherwise | lookup(Key?, Val?, Rest?, Rest1).
lookup(_, 0, [], []).
Key Design Decisions. Output vs Input for Return Value: The second argument is declared as Integer (output, mode ↑), not Integer?
(input, mode ↓). This is because lookup returns the found value—it does not receive it from the caller. The reader V? in argument position 2
is a “hole” to be filled with the lookup result.
If incorrectly declared as Integer?, the type checker would expect a consume-mode position, but the clause uses V? to produce output,
causing a mode mismatch error.
SRSW Relaxation for Constant Types: The reader V? appears twice in the first clause: once in argument 2 (the return value) and once in
argument 4 (threading through the updated list). This would normally violate the single-reader constraint. However, variable V has type
Integer, which is a constant type. Per Section 4.2.1, constant types permit multiple occurrences of both writer and reader because constant
values contain no internal writers and can be safely duplicated.
