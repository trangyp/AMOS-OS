Abstract
ErgoAI is a high level, multi-paradigm logic programming language and system developed
by Coherent Knowledge Systems as an enhancement of and a successor to the popular
Flora-2 system. ErgoAI is oriented towards scalable knowledge representation and rea-
soning, and can exploit both structured knowledge as well as knowledge derived from
external sources such as vector embeddings. From the start, ErgoAI (and Flora-2 before
it) were designed to exploit the well-founded semantics for reasoning in a multi-paradigm
environment, including object-based logic (F-logic) with non-monotonic inheritance; higher
order syntax in the style of HiLog; defeasibility of rules; semantically clean transactional
updates; extensive use of subgoal delay for handling unsafe queries and for better perfor-
mance; and optional support for bounded rationality at a module level. Although ErgoAI
programs are compiled into XSB and adopt many Prolog features, ErgoAI is altogether a
different language and system.

the resolution method used by Prolog. If negation is not used, SLDNF resolution

Prolog is always left to right.7 SLDNF also supports a type of negation as failure
via the Prolog operator \+ (called \naf, in ErgoAI syntax). However, SLDNF will
not terminate for the query “?- s.” to any of the programs in Figures 1 or 2, all
of which contain positive and/or negative loops.

which is evaluation of WFS via tabled SLG resolution (Chen and Warren 1996;
Chen et al. 1995) extended to provide Reactivity to updates, and – optionally –
Abstractions for bounded rationality. In this section we focus on SLG, which ErgoAI
uses to support WFS as well as to adjoin argumentation theories to a program (Sec-

rationality is discussed in Section 9.

present tabling informally, in order to maintain focus on ErgoAI. SLG resolution
includes three mechanisms necessary to evaluate queries according to WFS: loop
detection, incremental completion for sets of mutually dependent subgoals, and an
adaptive literal selection strategy.9

support incremental completion, XSB’s tabling engine implicitly maintains a de-

which there is an edge from subgoal S1 to subgoal S2: if S1 (directly) depends on

the set of mutually dependent subgoals, p,q,r forms an SCC. A tabling engine with

3 Frame Logic
Frame Logic (abbr. F-logic) (Kifer et al. 1995) offers a number of benefits for repre-
senting knowledge using a style that is both object-oriented and ontology-oriented.
Although ErgoAI can make use of external knowledge represented in nearly any
format, a pure ErgoAI program contains rules and facts formed from a mixture of
HiLog predicates and F-logic frame formulas or frames. In this section we highlight
frames along with classification predicates to denote a hierarchy of classes and in-
stances, and then describe how the two together provide structural and behavioral
inheritance for a program. We should note here that the syntax used in ErgoAI
differs from the original F-logic (Kifer et al. 1995) in many respects. That original
syntax was first improved by the Flora-2 system (Yang et al. 2003; Kifer 2022) and
then further extended in ErgoAI.
Throughout this paper, ErgoAI features are illustrated using a set of examples
motivated by the US DARPA AIDA project.12 In 2021-2022 the AIDA project
constructed sample problems centered around tracking misinformation about the
COVID-19 virus (NIST 2022). To address these problems, various natural language
inputs were analyzed and the results represented as a set of knowledge graphs over
which various types of reasoning and hypothesis generation was performed.13

3.3 Type Checking
A type in ErgoAI can be any class in the classification hierarchy. Remembering
that the class membership (the :/2 relationship), the class hierarchy (the ::/2
relationship), and the properties (the ->/2 relationships) can be defined via logic
rules, it is no wonder that ErgoAI types are powerful and expressive but also that
fully static type-checking is not possible. Dynamic type checking is possible. While
dynamic type checking cannot be guaranteed to terminate and may be slow in
complex cases, it is often a highly useful aid to program development.. To perform
dynamic type checks, one can easily express different type type violation as queries
that return type violations as counterexamples to type correctness.
Although the semantics needed for signatures is sometimes program-specific,
many type inconsistencies are common, including 1) that an object has an at-
tribute value inconsistent with the inferred type for that value; 2) an object has an
attribute that is not in any of its inherited signatures; or 3) the number of values
for a given object and attribute are not consistent with cardinality constraints de-
clared in an inherited signature. Type checking can be particularly important when
complex objects are inserted in a dynamic setting, as will be discussed in Section 8.
Here is an example of type violations expressed as a query that identifies at-
tributes and values for instances that violate properties 1 and 2 above.

3.4 ErgoAI Frame Compilation.
The compilation of ErgoAI frames into Prolog predicates follows the general design
of (Kifer et al. 1995) and consists of two parts: 1) frames are translated into Prolog
predicates; and 2) closure rules are added to support the object-oriented semantics
of frames. In this section, we describe a few aspects of ErgoAI compilation to give

Mary : employee,Mary[age->29],Mary[salary(1998)->100000],
Mary[kids->Tim],Mary[kids->,Leo].

mvd(Mary,age,29).
mvd(Mary,salary(1998),100000).
mvd(Mary,kids,Tim).
mvd(Mary,kids,Leo).

4 HiLog
The previous section showed how complex frames, called frame formulas, can be
constructed and used, but the examples also contained logical terms such as the
object id claim(13344) and the occurrence of py_func/3 in the body of a rule.
ErgoAI fully supports HiLog (Chen et al. 1993) which gives a higher-order syntax to
Prolog-style resolution. The idea behind HiLog can be explained easily. For instance,
the HiLog fact
p(fact(7))(a,f(b,b),[3,?X])
is schematically translated to Prolog as:
apply(apply(p,fact,7),a,apply(f,b,b,[3,?X]).
where every non-list compound term T is translated into a term with functor
apply/n and T as its first argument. By similarly translating a query such as
?- p(?X)(a,f(b,b),[3,foo])
to
?- apply(apply(?X),a,apply(f,b),[3,?X]),
the query can be resolved against the fact with either tabled or non-tabled Prolog-
style resolution. To be more specific a HiLog term is defined as follows and this
semantics is equivalent to the model-theoretic view of HiLog (Chen et al. 1993).

Since variables can appear nearly anywhere in HiLog terms, HiLog is useful for

5 The Module System of ErgoAI
In HiLog and F-logic, the number of unique predicates used for the Prolog trans-
lations is small. As a result, it is easy to write a goal that backtracks through all
clauses in the program, a behavior that can lead to ineﬀiciency. The salting tech-
nique of the previous section prevents unintended resolutions between ErgoAI’s
wrapper predicates and similarly named predicates from other XSB programs that
may be used in conjunction with ErgoAI in the same XSB pprocess. Without salt-
ing there could be name clashes between the mvd and apply wrappers discussed in
previous sections and mvd or apply used in other XSB programs (if XSB predicates
are in the default usermod module). But there is another problem: the separation
of namespaces among the wrappers within the ErgoAI system. Such separation
is necessary to enable component-wise construction of large knowledge bases and
to reduce the chances of inadvertent interactions.As in most languages, ErgoAI’s
module system addresses these and similar issues.
ErgoAI’s module system was designed to be dynamic and to support a num-
ber of other unique features. Modules can be created “on the fly” at runtime, and
rules and data can be loaded into them, inserted, or deleted at run time as well.
Calls from one module to another may also be constructed at run time. At the same
time, any module can prevent unwanted calls by encapsulating itself. Encapsulation
can happen at compile time or dynamically, via the executable export/1 direc-
tive (e.g., export{?[abc ->?], pqr(?)} or even export{?[abc ->?], pqr(?)}
>> module1,module2). Furthermore, modules need not be instantiated within a
goal; for instance one can query the modules and argument values for which p/1 is
true:
?- p(?X)@?M.
Some of the above features exist in various logic programming systems, but others
(variables over modules, support for non-predicate-based languages like HiLog and
F-logic), are unique to ErgoAI.
The implementation of ErgoAI modules elaborates on the idea of salting the wrap-
pers such as apply/n and mvd/3. The goal is to ensure that when these wrappers
are used in different modules they are translated using different salted wrappers.
For example, the statements John[age->11] and Mary[age->12] that appear in
the same module would be related to each other because they would be encoded
using the same set of salted wrappers: like 'salt̂mvd', 'salt̂isa', or 'salt̂apply'.
In contrast, these same statements in different modules would be encoded using
different salted wrappers.

Thus, the basic idea underlying the implementation of ErgoAI modules is that
in the end, all HiLog and F-logic wrapper predicates are translated with respect

5.2 Loading vs. Adding
Normally the user creates a file that includes facts, rules, and queries. Then the user
loads or adds that file to a module (the module may or may not exist at the time),
which causes the file to be compiled for that module and the queries executed. The
user might pose additional queries, load and/or add additional files into new or
already existing modules, or do many other things.
For concreteness, suppose we have a file called myProgram.ergo that contains
the query and the rule just discussed plus some data facts (i.e., bodiless rules). We
can load the file into some explicit module, e.g., mainRules, or into the current
module:
?- [myProgram >> mainRules].
?- [myProgram].
The first form will create the empty module mainRules„ if it did not exist before,
compile myProgram.ergo for the module mainRules causing compiled salted Prolog
rules to appear in XSB’s memory. (If the module existed prior to the command it
is emptied out of its old contents first.) In the second version of the load command,
myProgram.ergo will be compiled for the current module but the rest is the same
as we just explained.
The current module dynamically changes during an ErgoAI session. When ErgoAI
starts up, it automatically creates the module main which is the first current mod-
ule. If either of the above load commands executes next, it executes with main
as the current module. During the compilation of myProgram.ergo using the first
option, the current module will be mainRules rather than main. With the second
version of the load command, the current module will not change, of course, and
will still be main. If myProgram.ergo includes another loading command, like ?-
[myStuff >> miscRules], then when this command is executed, myStuff.ergo
will be compiled with miscRules as the current module.
Loading wipes out any existing contents of the target module, so loading two
different sets of rules into the same module is rarely meaningful unless the first
set of rules and data has become obsolete. Such scenarios arise when dealing with
streaming data, but are unlikely in cases where working knowledge of an application
evolves. For such applications, ErgoAI provides the add command, e.g.,
?- [+myAddlStuff >> mainRules].
?- [+myAddlStuff].

the reasoning system. We first describe the overall effect of defeasibility on ErgoAI’s

the use of GCLP in Program Peneg the defeasibility transformation ensures that

GCLP’s choice of semantics for explicit negation is the same as most of ErgoAI’s
argumentation theories, but it differs from approaches like WFSX (Alferes et al.
1994) in which both A and \neg A would have the truth value undefined. The
fact that GCLP sets their truth value to false makes it arguably more useful for
paraconsistent reasoning based on frame logic with argumentation. If the truth
value of opposing literals were set to undefined then the truth values of literals that
depend on these opposing literals would also be set to undefined.
Although some logics use a four-valued lattice to distinguish unknown from in-
compatible truth values, like those in Peneg, handling inconsistency purely within
WFS requires mapping inconsistency to an existing truth value: true, false, or un-
defined. Viewed in this way, WFSX conflates the inconsistency of a literal with a
literal’s being undefined/unknown (u) while GCLP conflates it with false. In fact,
ErgoAI users have suggested a way to support a four-valued truth lattice semantics
based on an argumentation theory that acts like GCLP except that it has no con-
cept of rebuttal. This argumentation theory, RefuteCLP, is included with ErgoAI.
In RefuteCLP, if one rule refutes another, any inferences made by the second rule
are defeated. However, if two rules rebut (but do not override) each other then no in-
ferences are defeated and it is possible to infer that, in a pair of opposing facts, both
are true. Therefore, if Peneg in Example 1 used RefuteCLP instead of GCLP, both
A and \neg A would have been true. ErgoAI does not provide direct support for the

7 Flexible Search Strategies for Unsafe Subgoals
As mentioned in Section 2 ErgoAI does not require a program to be ground to be
evaluated, a major factor in its scalability. However, this freedom can give rise to
unsafe queries that do not have a required instantiation pattern. Given ErgoAI’s
reliance on well-founded negation within non-monotonic inheritance and argumen-
tation, unsafe negation must be addressed. In addition, ErgoAI’s use of external
knowledge may also give rise to unsafe queries that must be addressed.
ErgoAI’s approach to unsafe queries uses instantiation delay together with the
WFS u truth value. Instantiation delay is different from the SLGR(A) delay pre-
sented in Section 2, although the two mechanisms do bear some resemblance. As
discussed, SLGR(A) delay is invoked on a ground negative literal GT when the
tabling completion operation encounters a loop through negation involving GT . Af-
terwards, GT is never re-evaluated, but instead simplified away when further evalu-
ation of goals upon which GT depends determines it to be true or false. On the other
hand, instantiation delay occurs when a goal GI is not instantiated enough to be
evaluated; afterwards, any time a variable in GI is instantiated, GI is rechecked to
determine whether it satisfies an instantiation property (such as nonvar or ground),
and is evaluated if so.
In this section, we first show how ErgoAI automatically uses instantiation delay
to address unsafe negation, and then how it can be invoked by the user to handle
safety requirements imposed by external knowledge sources, or for other reasons,
such as improving the query time.

7.2 Delay Quantifiers
The delay quantifiers wish/1 and must/1 cause dynamic reordering of subgoals that
do not fulfill argument binding requirements. These quantifiers check conditions on
variables in a subgoal and delay that subgoal if these conditions fail. For example,
the subgoal
must(ground(?X) or nonvar(?Y))^?X[foo->?Y]
contains the delay quantifier must/1, and evaluation of the subgoal delays evalua-
tion of ?X[foo->?Y] until either ?X is ground or ?Y is partially instantiated. If the
desired instantiation is unachievable, a runtime error results. The wish/1 quantifier
delays its subgoal in the same manner as must/1, but the subgoal is executed after
no more delay is possible, and no error is raised.
8 KRR in a Dynamic Setting
Most real-world knowledge changes over time. A Claim object, like that in Figure 3,
may be added or modified. New rules expressing beliefs, like those in Figure 5, may
be designed by a knowledge engineer or learned. Knowledge must also adapt to
changing circumstances. For instance, if polls show that a viral pandemic is not a
high concern of voters, a number of rules may be canceled in the sense of defeasible
logic (Section 6).
In ErgoAI, every rule and fact is treated as dynamic information, so that any rule
or fact may be inserted, deleted, enabled, or disabled.21 The changes made possible
by such flexibility can give rise to different issues. A new claim may need to be
added transactionally so that either all necessary elements must be added or none
may be. Adding or canceling a rule can have complex consequences especially when
argumentation theories are used or when a change is made to a program’s classifi-
cation hierarchy. As a result, assurance may be needed that certain conditions hold
or do not hold after an update. ErgoAI addresses such issues through Transaction
Logic (Bonner and Kifer 1994) extended with integrity constraints.22
Returning to our running example about claims and beliefs, it may be useful to
distinguish between two classes of people who frequently make claims: politicians

9.3 Tripwires
From the viewpoint of ErgoAI, both subgoal abstraction and restraint based on an-
swer abstraction are instances of tripwires. A tripwire allows a developer to specify
that a property of an evaluation should cause some intervention from the system.


## Page 31

31
The intervention may be an automatic change in the resolution method, such as
with call abstraction or restraint; or the intervention could throw an error; or sus-
pend the computation for debugging. ErgoAI also supports a max answers tripwire
that allows a user to set a limit on the number of answers a given subgoal S may
have. If this limit is reached, a new answer AS is added that is a variant of S,
the truth value of AS is set to u and S is completed. Afterwards queries to S will
return all of the derived answers for S, as well as AS. The effect is to change the
closed-world assumption for S from using false as default to using u as default.
Another kind of tripwire is the ability to time out a goal Gcostly that may either
call ErgoAI or an external system. The tripwire can be set either to add an answer
A that is a variant of Gcostly with truth value u, or to throw an exception. Finally,
as mentioned in Section 7, a negative subgoal that cannot be ground via delaying
its execution can be given the truth value u instead of throwing an error.
In each of these types of tripwire a developer can weigh the benefit of a bounded
execution time against the possibility of deriving a set of answers that are informa-
tionally sound but not complete. It is because of such uses that we denote the third
WFS truth value as u, since it can mean as unknown in addition to undefined.26
10 Architectural Summary
Figure 8 illustrates the high-level architecture related to the features presented in
previous sections. ErgoAI is compiled into tabled Prolog code that is executed by the
XSB engine, along with ErgoAI’s runtime libraries. Optionally Janus (Section 3.2)
can load a Python engine into the same process, leading to extremely eﬀicient
calls between the ErgoAI and Python. Direct interfaces to Java, C, SQL databases,
SPARQL, and direct connectors to XML, JSON, and RDF are also available.
More specifically, the ErgoAI compiler performs the HiLog and frame transfor-
mations of Section 4 and compiles them (Section 3) first into GPP macros and then,
at loading time, further into Prolog. The first of these steps is performed by the
ErgoAI compiler and the second by the GPP preprocessor. Most of these macros
provide a convenient way to specify how module-dependent salting is to be done.
Inheritance and other background theories, such as typing, are implemented using
ErgoAI builders of GPP-enhanced Prolog as an intermediate language. In addition,
the compiler performs transformations in support of several aspects of defeasible
reasoning (Section 6.1). This includes handling rule tags and other rule descriptors
as well as adding a defeasibility check to each defeasible rule. The resulting Prolog
code makes use of SLGR(A) tabling (Section 2), attributed variables for instantia-
tion and \naf delay (Section 7) and tripwires for bounded rationality (Section 9).

ErgoAI can access large factual knowledge bases in several ways, including:
• As full HiLog facts, loaded directly into ErgoAI’s internal knowledge store or

• As Prolog facts, loaded into XSB’s internal knowledge store; or
• As Prolog terms, accessed via Python connectors through Janus
As a scalability experiment a KG of 11,847,275 triples from the DARPA AIDA
project (cf. Section 6) was loaded into the knowledge stores of ErgoAI and XSB.
• Loading the KG as ErgoAI HiLog facts. Using ErgoAI’s fastload the KG was
loaded at a rate of about 59,000 facts per second of elapsed time. ErgoAI’s
fastload uses trie indexing (Ramakrishnan et al. 1999).
• Loading the KG directly into Prolog Using XSB’s dynamic loading, the KG
was loaded with full indexing on each fact (7 indexes) at a rate of about
137,000 facts per second of elapsed time.

expressiveness, ease of maintenance, and updatability. Put another way, ErgoAI is
a KRR system with scalability and performance similar to a programming system.
12 Discussion
ErgoAI is a multi-paradigm logic programming system that makes radically differ-
ent choices from virtually all other logic programming systems. We have presented a
few of these features, including frames and inheritance for object-oriented logic pro-
gramming based on a solid semantics; HiLog predicates and terms integrated into
a powerful module system; argumentation theories, the handling of unsafe queries,
logical approach to updates and management of change, along with support for
termination and bounded rationality. We have not covered in detail important fea-
tures such as explanation; non-termination analysis; user-defined functions; quanti-
fied logical formulas in rule bodies and heads; typed variables and type constraints;
and many other features of the ErgoAI language.
ErgoAI is a significant system in itself, but also a testbed for features that may
be suitable for Prologs or other logic programming paradigms. For instance, the im-
plementation of HiLog (Section 4) may extend well to Prologs like SWI, whose just-
in-time indexing can adapt to the extra indexing burden required by the HiLog and
frame transforms (Definition 2). Transaction Logic (Section 8) with non-recursive
update rules can be implemented in Prolog via backtrackable dynamic code with
hooks to call integrity constraints. Indeed the implementation of ErgoAI has shown

that backtrackable updates can be implemented on top of regular assert/1 and

The F-logic frames and classification hierarchies, whose compilation into Prolog was
outlined in Section 3.4 mainly requires compiler and reader extensions rather than
engine modifications, particularly in Prologs with strong tabling and indexing.30
As mentioned in Section 1, ErgoAI has proven useful in domains such as finan-
cial compliance, tax accounting, and legal reasoning. As mentioned above, in the
DARPA CODORD project, ErgoAI code is generated from natural language nar-

ILPs, semantic parsing and other techniques. Our near-term work includes con-
tinued improvements in ErgoAI’s speed and robustness, as well as improvements
in explanation generation. Longer-term objectives include supporting fuzzy and
probabilistic reasoning techniques for HiLog predicates. The approach under de-
sign uses techniques from the PITA (Riguzzi and Swift 2011) system. PITA, which
was originally implemented for XSB, is based on a source-level transformation fol-
lowed by execution that uses tabling and BDDs. A first extension to ErgoAI’s HiLog
predicates requires reimplementing PITA’s source-code transformation within the
ErgoAI compiler.
