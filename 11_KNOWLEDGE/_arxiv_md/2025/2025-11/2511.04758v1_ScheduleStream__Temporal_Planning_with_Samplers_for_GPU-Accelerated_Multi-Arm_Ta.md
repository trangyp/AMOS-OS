ScheduleStream: Temporal Planning with Samplers for
GPU-Accelerated Multi-Arm Task and Motion Planning & Scheduling
Caelan Garrett1 and Fabio Ramos1,2
Abstract— Bimanual and humanoid robots are appealing
because of their human-like ability to leverage multiple arms to
efficiently complete tasks. However, controlling multiple arms
at once is computationally challenging due to the growth in the
hybrid discrete-continuous action space. Task and Motion Plan-
ning (TAMP) algorithms can efficiently plan in hybrid spaces
but generally produce plans, where only one arm is moving at a
time, rather than schedules that allow for parallel arm motion.
In order to extend TAMP to produce schedules, we present
ScheduleStream, the first general-purpose framework for plan-
ning & scheduling with sampling operations. ScheduleStream
models temporal dynamics using hybrid durative actions, which
can be started asynchronously and persist for a duration that’s a
function of their parameters. We propose domain-independent
algorithms that solve ScheduleStream problems without any
application-specific mechanisms. We apply ScheduleStream to
Task and Motion Planning & Scheduling (TAMPAS), where
we use GPU acceleration within samplers to expedite planning.
We compare ScheduleStream algorithms to several ablations in
simulation and find that they produce more efficient solutions.
We demonstrate ScheduleStream on several real-world biman-
ual robot tasks at https://schedulestream.github.io.
I. INTRODUCTION
There’s recently been a spike in demand for bimanual
and humanoid robots to be used to automate tasks in
both industrial and home settings, in place of traditional
manipulators. However, programming these robots to take
full advantage of their multiple arms through simultaneous
manipulation remains challenging. Imitation learning from
human teleoperation demonstrations can be an effective
control approach but requires an enormous amount of data,
and thus human effort, even for narrowly-defined tasks [1]. In
contrast, automated robot planning, such as Task and Motion
Planning (TAMP) [2], is able plan behaviors that generalize
across a broad distribution of tasks through composing a
set of engineered or learned primitive actions. Additionally,
planning can be used to develop imitation learning systems
by serving as automated training data generator [3].
In order to safely and productively control robots, TAMP
algorithms must make discrete decisions, such as which arm
to use to manipulate which object and how, as well as
continuous decisions in the form of the motion and other
parameters that lead to executable robot actions. Consider the
bimanual robot in Figure 1, which is tasked with sorting the
two fruit into the two bins. In order to maximize execution
efficiency, a TAMP algorithm should plan to use both arms
in parallel, but critically, it must identify which arms can
reach which objects by reasoning about reachability.

Most existing TAMP approaches [2] are only able to

using both arms in parallel to minimize schedule makespan,
or duration. The existing work that incorporates multi-arm
parallel manipulation typically is application-specific [4], [5],
[6], addresses a strict subclass of TAMP [7], [8], or has
limitations in its ability to leverage parallelism [9], [10], [11].
In this work, we seek to address full Task and Motion
Planning & Scheduling (TAMPAS), where solutions are
schedules of timed hybrid actions. Unlike all prior work, we
accomplish this by first introducing ScheduleStream, a new
domain-independent framework for planning & scheduling
with samplers. We implement this language in the program-
ming language Python, allowing external procedures such as
GPU-accelerated collision checkers and inverse kinematics
solvers to be flexibly be invoked by ScheduleStream al-
gorithms. We propose domain-independent ScheduleStream
algorithms that alternate between scheduling and sampling
phases, which solve each scheduling subproblem through
planning the start and end of each action. In simulated
experiments, we show that these algorithms have higher suc-

II. RELATED WORK
We build on prior work in single-arm Task and Motion
Planning (TAMP) as well as multi-arm manipulation.
A. Task and Motion Planning
There are a number of existing approaches for traditional
TAMP that can efficiently produce single-arm plans but
are unable to produce multi-arm schedules [2]. Several
approaches apply TAMP to humanoid robots [12], [13];
however, they only address single-arm loco-manipulation
rather than bimanual manipulation. cuTAMP [14] proposed
leveraging GPU parallelization for single-arm sampling and
gradient-based TAMP. The closest to our approach is PDDL-
Stream [15], which also is a domain-independent planning
framework for hybrid systems. Key differences from Sched-
uleStream are that PDDLStream describes domains using
text (i.e. PDDL) instead of code (i.e. Python) and does not
support temporal, functional, or GPU-batched planning.
B. Multi-Arm Manipulation
Several prior works plan for multiple arms in automated
assembly, an application of TAMP that makes various as-
sumptions about task allocations, monotonicity, single object
goals [4], [5], [6]. Many of these approaches also factor dis-
crete and continuous planning into a strict hierarchy and will
fail to solve problems that are not downward refinable [16],
problems where some high-level plans aren’t viable.
Several approaches address synchronous multi-arm ma-
nipulation [9], [17], [10], where each robot takes an action
that starts and ends simultaneously according to a global
clock. Such synchronicity requirements restrict the space
of schedules, limiting opportunities to minimize schedule
makespan. Still, many traditional TAMP systems can im-
plement this strategy by treating the arms collectively as a
single composite robot [18], [19]. However, these strategies
discard factoring and often sparse interaction among robots,
leading to combinatorial growth in their search spaces.
Two approaches investigate multi-arm handover tasks.
Shome et al. [7] extend dRRT* [20], a sampling-based multi-
robot motion planner, and Wei et al [8] combine Linear
Temporal Logic (LTL) and Graph of Convex Sets (GCS)
in a hierarchical manner. However, these planners would
need to be continuously extended to address more general
manipulation tasks, for example, ones where objects aren’t
limited to a pre-determined set of placements.
Hartmann and Toussaint [21] develop a rescheduling al-
gorithm that greedily reschedules an inputted serial plan
subject to conflicts to locally minimize its makespan. The
Decomposable State Space Hypergraph (DaSH) line-of-
work [22], [11] also presents several algorithms that explic-
itly factor problems into separate planning spaces per robot
and later resolve conflicts to produce a schedule. Unlike
ScheduleStream, these algorithms are application-specific
and don’t directly minimize schedule makespan.
III. SCHEDULESTREAM LANGUAGE
We start by introducing ScheduleStream, a new general-
purpose language for planning & scheduling with continuous
sampling operations. We will use a simplified bimanual
manipulation domain as a running example. Figure 2 visual-
izes three cartoon problems in this domain, where there’s a
bimanual robot with two arms, arm1 and arm2, and the
goal in each problem is for arm1 to hold object obj1
and arm2 to hold object arm2. We build ScheduleStream
entirely in the Python programming language, which, unlike
prior works [23], [15], enables direct interfacing between the
declarative and procedural language aspects.
We consider a universe of possibly infinitely-many con-
stants, atomic values. In our bimanual domain, there are
1) discrete constants in the form of first-class objects for
the arms arm1, arm2 and the objects obj1, obj2 and 2)
continuous constants in the form of (PyTorch) tensors for arm
configurations q ∈Rd, object placement poses p ∈SE(3),
and object grasp poses g ∈SE(3).
Similar to Functional STRIPS [24], we describe states and
actions using declarative functions, relations between a tuple
of input constants and a single output constant. This sub-
sumes predicate-based languages, such as STRIPS [25] and
Planning Domain Definition Language (PDDL) [23], which
only consider Boolean functions. Each function Function,
or predicate Predicate, is defined by a string of input
parameters (e.g. "?x1 ... ?xN") and optionally a do-
main condition cond that specifies predicates that the input
parameters are guaranteed to satisfy. For example, let At
be a function from an arm "?arm" parameter that satisfies
typing predicate Arm("?arm") to its current configuration.
And let Conf("?arm ?q") be True if "?q" is a valid
configuration for arm "?arm" in some state.
At = Function("?arm", cond=[Arm("?arm")])
Arm = Predicate("?arm"); Conf = Predicate("?arm ?q")
States are assignments to the functions in the domain. For ex-
ample, the assignment At(arm1)<=q1 declares that func-
tion At(arm1) with argument arm1 currently evaluates to
configuration q1. We make a version of the closed-world
assumption in that any undeclared function and predicate
evaluate to None and False respectively. We can also test
whether a function evaluates to a particular constant using an
equation At(arm1)==q1, which evaluates to either True

A. Instantaneous Actions
In order to describe actions, operations that change the
current state, we adopt a precondition/effect representation
similar to that of STRIPS [25] or PDDL [23]. An action
Action has a string of input parameters params, a list of
equality conditions cond, and a list of assignment effects
eff. In order to apply an action, the conditions must hold
in the current state. After applying an action, the state is
updated according to the effect assignments.
In our running example, we model pick and place as
actions that cause an instantaneous change in the parent of
object "?obj" in the scene graph. The pick action has
parameters for the arm "?arm", pick configuration "?q",
object "?obj", before placement pose "?p", and after
grasp pose "?g". Its conditions are that the parameters
comprise a valid kinematic solution Kin (see Section III-
C), "?obj" isn’t initially attached, "?obj" is initially
at placement pose "?p", "?arm" isn’t initially holding
anything, and "?arm" is currently at configuration "?q".
pick = Action(params="?arm ?q ?obj ?g ?p",
cond=[Kin("?arm ?q ?obj ?g ?p"),
Attached("?obj")==None, Pose("?obj")=="?p",
Holding("?arm")==None, At("?arm")=="?q"],
eff=[Holding("?arm")<="?obj", Pose("?obj")<="?g",
Attached("?obj")<="?arm"])
place is defined similarly, as the reverse of pick.
B. Durative Actions
Existing TAMP frameworks generally only support se-
quential plans [15], where solutions are sequences of actions.
We wish to beyond this to support schedules as solutions,
where actions can asynchronously overlap in time. To do
this, we generalize the concept of an instantaneous action to
a durative action [26] that can be started at a point in time
and ended after a certain duration. Each start and end event
causes a change to the state. In order to correctly execute
durative actions, certain conditions must hold before the start
event, while the action is ongoing, and before the end event.
Formally, a durative action DurativeAction has a
string of input parameters params, a list of start conditions
start cond that must hold prior to starting, a list of start
effects start effects that take effect after starting, a
list of ongoing conditions over cond that must remain
true while the action is ongoing (exclusively), a list of end
conditions end cond that must hold prior to ending, a list
of end effects end effects that take effect after ending,
and a duration duration that specifies the minimum time
elapsed between starting and ending the action.
In our running bimanual domain, the key durative action
is move, which models arm motion where the arm may or
may not be holding an object. The move durative action has
parameters for the arm "?arm", start configuration "?q1",
trajectory "?t", and end configuration "?q2". Its start
conditions are that "?t is a valid Motion (see Section III-
C) that connects "?q1" and "?q2" and that "?arm" starts
at configuration "?q1". Critically, its start effect is that the
"?arm" is no longer at "?q1" but instead is “at” trajectory
"?t", meaning that it is somewhere along the trajectory. The
move action does not have any end conditions, and its end
effect is that the robot is at configuration "?q2". Finally, its
duration is a numeric function of the trajectory "?t". Here,
trajectories "?t" can be both long multi-second paths as
well as short steering segments that are a part of a larger
roadmap and executed via successive move actions.

C. Samplers as Streams
In order to instantiate the pick, place, and move
actions in Sections III-A and III-B, we need to be able
to generate possibly arbitrarily-many continuous parameter
values for them. Additionally, combinations of these param-
eter values must satisfy the static predicates Kin, which
holds if forward kinematics from configuration "?q" times
grasp pose "?g" results in placement pose "?p", and
motion Motion, which holds if trajectory "?t" avoids
collisions with static objects, respects dynamical joint limits,
and connects configurations "?q1" and "?q2.
Grasp = Predicate("?arm ?obj ?g",
cond=[Arm("?arm"), Object("?obj")])
Kin = Predicate("?arm ?q ?obj ?g ?p",
cond=[Conf("?arm ?q"), Placement("?obj ?p"),
Grasp("?arm ?obj ?g")])
Motion = Predicate("?arm ?q1 ?t ?q2",
cond=[Conf("?arm ?q1"), Conf("?arm ?q2")])
We build on the PDDLStream framework [15] by ex-
tending a typical finite action language [23] with streams
Stream, procedural conditional generators that consume
existing constants and generate new ones that satisfy specific
predicates. We can derive a stream from a predicate by
partitioning its arguments into inputs inp and outputs. This
also partitions the predicate’s conditions cond into input
conditions, which the input values must satisfy to call the
stream, and output conditions, which all generated values
are guaranteed to satisfy. For example, the grasps stream
generates grasp poses "?q" for a given arm "?arm"
and object "?obj", the inverse kinematics stream ik_qs
generates configurations "?q" that satisfy kinematics with
input grasp and placement poses "?g", "?p", and the
motion planner stream motions plans trajectories "?t"
that connect configurations "?q1", "?q2". In Section V,
we discuss how these samplers can be GPU accelerated.
grasps = Stream(Grasp, inps="?arm ?obj", gen=...)
ik_qs = Stream(Kin, inps="?arm ?obj ?g ?p", gen=...)
motions = Stream(Motion, inps="?arm ?q1 ?q2", gen=...)
ScheduleStream algorithms can call each stream’s condi-
tional generator gen to enumerate new constants and, in turn,
pass these new constants to other streams and functions. A
typical sequence of operations in our example is as follows,
where the underlined values are generated by streams.
g, = next(grasps.gen(arm1))
q, = next(ik_qs.gen(arm1, obj1, g, p1))
t, = next(motions.gen(arm1, q1, q))
duration = Duration.fn(t)
collision = ObjCollision.test(t,p1)
or ArmCollision.test(t,None,q2,None)

B. Schedule Subroutine
A key subroutine in EAGER-STREAM is SCHEDULE, which
solves a finite planning & scheduling problem defined by
initial state I, goal conditions G, and durative actions A. This
requires not only selecting the action instances a(x) required
but also timing them into a schedule τ, exceeding the
capabilities of classical planning algorithms [27]. Building
on ideas in temporal planning [28], we reduce scheduling
to sequential planning of the start and end of each applied
action instance. To do this, we compile each durative action
a into two instantaneous actions, a start action a.start and an
end action a.end, and solve a sequential planning problem
for a plan π for the order to start and end each action.

Let action a be a durative action. First, we create a
predicate Ongoing that is true if action a is currently being
executed and a function Ongoing that tracks the minimum
time remaining in order to terminate the action. Both have
arguments corresponding to the original action parameters.
We define the start action start_a to inherit the start
conditions and effects of action a, add a condition that a is
not currently ongoing, and add effects that a is now ongoing
and its remaining time is equal to the duration of the action.
Ongoing = Predicate(args=a.params)
Remaining = Function(args=a.params)
start_a = Action(params=a.params,

OverCondition("#s")],

Remaining(a.params)<=a.duration])
The end action end_a similarly inherits the end conditions
and effects of action a, adds a condition that a is currently
ongoing, and an effect that afterward a is no longer ongoing.
The cost of end_a is time remaining, which can be seen
as advancing time forward by this amount. Additionally,
we leverage Python by defining a procedural condition
OverCondition that checks whether the ongoing condi-
tions a2.over cond for each ongoing action a2 are still
satisfied as well as a procedural effect ElapseEffect that
updates the Remaining duration for each ongoing action
a2 by subtracting the remaining duration for a.
OverCondition = Condition(args="#s", fn=...)
ElapseEffect = Effect(args="#s ?d", fn=...)
end_a = Action(params=a.params,
cond=a.end cond + [Ongoing(a.params)==True,
OverCondition("#s")],
eff=a.end eff + [Ongoing(a.params)<=False,
ElapseEffect("#s", Remaining(a.params)),
Remaining(a.params)<=0.],
cost=Remaining(a.params))
Now, we implement SCHEDULE (Algorithm 2) by first
solving a SEARCH problem with start and end actions to
produce a sequential plan π and then extracting a schedule
τ that corresponds to that plan. First, it instantiates the start
and end actions for each durative action. Then, it calls a
generic search algorithm SEARCH to find a sequential plan
π, minimizing total end action cost (i.e. time). We implement
SEARCH with a lazy weighted A∗heuristic search using a
modified version of the Fast-Forward (FF) heuristic [27] that
ignores procedural and nested conditions. If it produces a
plan, we call SEARCH again using just the action instances
in π, with weight w = 1, in order to locally optimize the
plan. For start instance a.start(x) in the plan, it records
the start time as the current time t∗. For end instances
a.start, it computes the remaining time ∆t that must elapse
to terminate the action. It adds this to the current time t∗or
zero if ∆t < 0. Finally, SCHEDULE returns the schedule τ.
C. Lazy Stream Scheduling
Although the EAGER-STREAM algorithm in Section IV-A
will provably solve ScheduleStream problems if a solution
exists, it will often unnecessarily call many streams not
required to solve the problem, and streams for robotics
domains involve, for example, expensive inverse kinematics
operations. Thus, building on prior work [15], we propose
a lazy stream scheduling algorithm that saves time by first
identifying which streams could be useful for calling them.
The key insight is to temporarily replace a stream’s condi-
tional generator s.gen with a version that creates unique
placeholder constants (here denoted as strings with the prefix
"@") and plan with these inexpensive values first. Later,
an algorithm will retrace which placeholder constants are
used and call the streams associated with those constants. In
the running example in Figure 2, the lazy stream calls will

Algorithm 3 gives the pseudocode for the lazy stream
scheduling algorithm LAZY-STREAM. It maintains a set of
identified schedule skeletons P, schedules τ with lazy con-
stants along with stream plans ψ that could bind values for
those constants. On each iteration, LAZY-STREAM replaces
each stream conditional generator s.gen with a version that’s
lazy for stream instances s(x) not on a stream plan ψ in P. It
then calls EAGER-STREAM (Algorithm 1) to identify a new
stream plan ψ′ and schedule skeleton τ. From ψ′, it retraces a
minimal subsequence ψ that’s sufficient for generating values
for the lazy constants on τ. At the end of each iteration,
LAZY-STREAM evaluates each stream instance s(x) on an
identified stream plan ψ, attempting to replace each lazy
output y with a real one y′ in a map of bindings Y . If this
process is successful, it replaces all lazy constants in ψ and
τ with their new values in Y and returns this pair.

V. GPU-ACCELERATED STREAMS
Another challenge of performing temporal instead of se-
quential TAMP is the need to check collisions between pairs
of moving arms instead of a single moving arm against a
stationary one. Moreover, the ArmCollision procedural
predicate in the move action’s conditions (Section III-B)
checks for collisions between all pairs of configurations
along two trajectories in the event that another arm arm
is moving, namely when At(arm) is a trajectory. As an
example, consider the usage of ArmCollision in the
schedule for Example 1 versus Example 2 in Figure 3. In
Example 1, it computes collisions between lazy trajectories
"@t1", "@t2" whereas in Example 2, it computes colli-
sions between trajectory and configuration pairs. Sequential
schedules avoid a quadratic number of collision checks;
however, they have higher makespans than parallel schedules.
To ease this computational burden, we use GPU accelera-
tion to batch together expensive collision checking, forward
kinematics, inverse kinematics, and motion planning stream
calls in Section III-C. Our use of GPU acceleration for multi-
arm planning goes beyond that of cuTAMP [14], which only
considers single-arm TAMP. Specifically, we build on the
cuRobo [29] custom CUDA kernels. We represent each robot
as a union of inflated inscribed spheres derived from its


## Page 7


meshes, which we greedily sample for a given computation
budget [30]. For moving object collisions, we perform asym-
metric sphere-mesh collision checks where we transform the
sampled swept volume of spheres along a arm trajectory into
the frame of an object at a batch of poses. For moving arm
collisions, we cast pairwise arm collisions as a batch sphere-
sphere self-collision check for a two arm composite robot.
VI. RESULTS
We analyzed the performance of ScheduleStream com-
pared to ablations representative of prior works in simulation
(Section VI-A) and tested it in the real-world (Section VI-B).
A. Simulated Experiments
We are interested in evaluating the success rate, runtime,
and solution quality of ScheduleStream algorithms compared
to prior ones. We compared four algorithms that consume the
same ScheduleStream problem formulation.
1) Sequential: an ablation that reduces durative actions
to traditional actions and thus performs sequential
planning. This is representative of traditional TAMP
approaches, namely PDDLStream [15] algorithms.
2) Hierarchical: an ablation that performs schedules once
and attempts to satisfy the schedule in a strict hierarchy
without backtracking. The is representative of multi-
arm task then motion planning approaches [4].
3) Ours: LAZY-STREAM in Algorithm 3.
4) Ours + GPU: LAZY-STREAM with batched instead of
sequential GPU-accelerated samplers in Section V.
We experimented on five tasks (Figure 4), each with
parameter N that specifies the number of objects or robots,
that test how the algorithms scale as N increases.
1) Franka Hold Assigned N: N Franka robots must hold
an assigned one of N objects on separate platforms.
2) Franka Hold Any N: N Franka robots must each hold
any one of N objects on separate platforms. This is
more challenging than “Franka Hold N” as algorithms
must match robots to objects based on reachability.
3) SO100 Hold Any N: N SO100 robots must each hold
any one of N objects on the same cluttered platform.
4) Franka Pack N: 2 Franka robots pack N objects
randomly on the floor into a tight region.
5) Franka Stack N: 2 Franka robots stack N objects
randomly on the floor on top of each other.
We randomly sampled 100 problems per task. We ran each
algorithm in an anytime mode for 60 seconds and recorded
the discovery time and makespan of each identified solution.
Table I lists the success rate (%) and runtime to produce
the first solution (Time) per task. Hierarchal results in low
success rates because sampled problems are not always
downward refinable [16], particularly when only certain arms
can reach certain objects. GPU acceleration clearly improves
the success rate of decreases the runtime of planner. Table II
lists the makespan of the first solution (t1
∗) and the best
solution (t∞
∗) after 60 seconds. Because Hierarchical fails to
solve many of the longer-horizon problems, their makespans
are averaged across only the easier problems, resulting in
a slightly lower average makespan (denoted by *). As
expected, Sequential produces much longer solutions than
Ours because it does not exploit opportunities for parallelism.
B. Real World Demonstration
We validated ScheduleStream through several real-world
demonstrations on the custom bimanual robot in Figure 1,
which has two Kinova Gen3 arms. We deployed Sched-
uleStream using a strategy similar to that of Curtis et
al. [31], where we used GroundingDINO [32] for open-
world object detection and estimated object affordances from
the segmented point cloud corresponding to each detection.
ScheduleStream was indeed able to plan simultaneous mo-
tion that makes use of both arms to efficiently complete real-
world tasks. See the website for videos of the demonstrations.
VII. CONCLUSION
We introduced ScheduleStream, a new framework for
planning & scheduling with samplers that can be used to
efficiently solve Task and Motion Planning & Scheduling
problems. We showed that ScheduleStream algorithms result
in higher success rates and lower makespans than sequential-
only only algorithms and demonstrated ScheduleStream on
several real-world bimanual manipulation tasks.
