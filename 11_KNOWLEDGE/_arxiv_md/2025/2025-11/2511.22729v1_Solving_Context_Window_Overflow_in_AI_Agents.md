Abstract
Large Language Models (LLMs) have become increasingly capable of interacting
with external tools, granting access to specialized knowledge beyond their training
data – critical in dynamic, knowledge-intensive domains such as Chemistry and
Materials Science. However, large tool outputs can overflow the LLMs’ context
window, preventing task completion. Existing solutions such as truncation or
summarization fail to preserve complete outputs, making them unsuitable for
workflows requiring the full data. This work introduces a method that enables
LLMs to process and utilize tool responses of arbitrary length without loss of
information. By shifting the model’s interaction from raw data to memory pointers,
the method preserves tool functionality, allows seamless integration into agentic
workflows, and reduces token usage and execution time. The proposed method is
validated on a real-world Materials Science application that cannot be executed with
conventional workflows, and its effectiveness is demonstrated via a comparative
analysis where both methods succeed. In this experiment, the proposed approach
consumed approximately seven times fewer tokens than the traditional workflow.
1
Introduction
Recent advances in Large Language Models (LLMs) have significantly enhanced their capabilities in
tool usage. This ability is particularly relevant, as it enables the LLMs to be applied/operate effectively
in domains that were either underrepresented or entirely absent during their pretraining phase. By
leveraging domain-specific knowledge through tool outputs, LLMs can overcome limitations in their
original training data. When prompted with a request for which they require auxiliary knowledge to
answer, the LLMs just need to identify the tool that best suits them in the case and call it with the
appropriate arguments. The tool result is subsequently incorporated into the LLM’s context window
(i.e., the information that is in fact considered by the LLM when generating a response), thereby
enabling it to reason over this augmented information – either for directly answering the user request,
or use it for further processing (by another tool, for instance). This capability unlocks their potential
in dynamic and knowledge-intensive fields such as chemistry research and laboratory assistants[1, 2].
Nonetheless, when the tool outputs a large response, the authors of LongFuncEval[3] show that
frontier models’ performance deteriorates drastically (from 7% to about 91%). In more extreme
scenarios, the length of certain tool-generated outputs may even surpass the model’s context window,
thereby limiting their practical applicability in domains characterized by such demands. This
constraint is particularly salient in disciplines such as Materials Science and Chemistry, where
voluminous outputs are frequently encountered.

As solutions to this context window limitation within the scope of tool calling without requiring
architectural changes, works have explored strategies such as summarizing tool descriptions [4] or
selectively including tools in the context [5, 6, 7], tackling the issue of a large tool catalog.
Other methods focus on parsing and truncating tool outputs to manage excessively large responses
[8]. However, none of these approaches is able to deal with large, indivisible outputs. Since all of
them present a loss of some sort of the tool response–such as truncating or summarizing it–they are
unable to preserve and utilize the tool output in its original, complete form as input for subsequent
processing steps, thereby hindering their application to workflows dependent on such outputs for
further processing.
In this work, we introduce a method designed to enable LLMs to process tool responses of arbitrary
length entirely — including those that far exceed the model’s context window — and to subsequently
use them as input for other tools or as output to the user, without any information loss. The agent
accomplishes this by operating on pointers to large data values rather than the raw data itself.
This approach preserves both the functional behavior and input expectations of the original tools,
ensuring full transparency to the agent and seamless integration within any tool or agentic framework.
Additionally, by manipulating pointers instead of raw data, the proposed method reduces token
generation compared to conventional workflows, resulting in lower computational costs and faster
decoding times. Crucially, no architectural modifications or changes to the underlying tools are
necessary.
With our method, we extend the applicability of agent systems to domains and use cases in which
large tool responses are routine, such as Materials Science and Chemistry, without loss of information.
To demonstrate this, we apply the approach in a real-world Materials Science application, which
could not be accomplished by a conventional agentic workflow.
2
Handling large tool responses
In many real-world domains, it is common for tools to receive and generate extensive data. In the
context of Materials Discovery, for instance, an agent might be tasked to generate a molecule structure
and reason about its properties–potentially using these structures as inputs to other functions to filter
out undesirable candidates. Applications like this cannot be solved using a conventional agentic
workflow that presents these tool outputs directly to the language model in its context, as it would
overflow its context window. Proposed techniques of extending the context window of LLMs without
architectural changes also cannot solve the issue, as they circumvent this problem by treating a large
input as divisible, and therefore do not present it in its entirety to the model.
To overcome this limitation, we store large data outside the LLM’s context window, and allow the
model to interact with it using only short identifiers (i.e., pointers). Each tool in the agent’s toolkit–
whether provided by an MCP server or defined locally–is mirrored with a wrapper that enables it
to handle these pointers. A mirrored tool comprises three components: (1) a module that inspects
the input to determine whether it is a pointer or a raw value, (2) the original tool with its unmodified
behavior, and (3) a post-processing module that stores large outputs in memory and returns access
instructions if necessary. A high-level overview of the solution is illustrated by the MCP Mirrored
Tool component in Figure 1.
During agent execution, a runtime memory is maintained to temporarily store large values that exceed
the model’s context window. Each stored value is assigned a unique path, constructed from the name
of the tool that produced the output and a corresponding identifier. In cases in which the tool returns
a dictionary containing multiple key-value pairs, each pair is stored individually under the same
base path, extended with the respective key. This hierarchical naming scheme ensures accurate and
efficient retrieval of stored data during subsequent interactions.
Upon receiving input, a mirrored tool first determines whether the input corresponds to a memory
path and resolves any pointers to their associated values. Once all arguments have been associated
to their actual content, they are forwarded to the original tool for execution. The resulting output is
then stored in the runtime memory under a path that adheres to the established naming convention.
To present final results to the user, a dedicated tool retrieves values from memory when explicitly
needed.

3
Experiments
To illustrate the practical value of the method, a representative use case from the Materials Science
domain was selected: given a molecule, the user requests a set of molecules with similar electronic
grid structures. This scenario exemplifies the type of problem the approach is designed to address.
Importantly, the method must also remain effective when tool outputs are small enough to fit within
the model’s context window. To validate this, a second experiment was conducted in which the agent
processes a Safety Data Sheet (SDS) provided in PDF format and accurately identifies the ingredients
listed within the document.
Both experiments were executed using an agent powered by Llama 4 Maverick 17B-128E-Instruct1
and the BeeAI agentic framework,2 guided by a simple system prompt defining its role as a helpful
scientific assistant. The agent followed the ReAct pattern and was equipped with the relevant MCP
tools for each task.
3.1
Retrieval of molecules with similar electronic grid structures
In this experiment, the agent is equipped with two tools: one that generates the electronic grid
structure of a molecule, and another that retrieves molecules with similar electronic grids. The first
tool takes a molecule’s SMILES string as input and outputs a 3D matrix of dimensions (128, 128,
128), totaling 2,097,152 float32 elements. This output far exceeds the context window of any widely
used LLM. The second tool accepts such an electronic grid as input and returns a list of the top-k
most similar molecules including their similarity scores and SMILES strings.
Although the output of the first tool serves as input to the second, we maintain them as separate tools
to reflect realistic agentic settings, in which outputs may be reused across multiple tools. Presenting
only the relevant tools to the agent simplifies the task, but our goal is not to evaluate tool selection or
planning capabilities–instead, we focus on how the model handles large tool responses.
In this experiment, the user asks the agent to identify the molecules whose electronic grids are similar
to that of the query molecule, specified via the provided SMILES string. The agent should first call
the grid-generation tool with the user-defined SMILES as input, then use the resulting electronic grid
it outputs as input to the similarity-retrieval tool.
Under the conventional workflow, the agent successfully calls the first tool with the appropriate
argument. Nevertheless, as the tool response exceeds (by far) the model’s maximum input length, an
error occurs due to the message’s body size exceeding its given limit, failing at this stage.
In contrast, with the proposed method, the agent is able to complete the entire pipeline. After invoking
the grid generation tool, the agent receives a memory path indicating where the output is stored and

The complete execution using the proposed method took an average of 33.87 seconds and 1,234.04

approach the agent was unable to complete the workflow, we couldn’t measure execution time in that
case. However, we can estimate the token usage up to the point where the context overflow occurred.
By substituting the memory path returned in the successful executions with the actual tool output, we
approximate the number of tokens that would have been consumed using the conventional approach
up to that stage in the workflow. Applying this substitution across all 50 runs yields an average token
consumption of 20,822,181.34 tokens, highlighting the infeasibility of the conventional approach for
handling large tool outputs.
3.2
Extracting ingredients from a safety data sheet
To perform the extraction of ingredient information from Safety Data Sheets (SDS), the agent has
access to two complementary tools: (i) a PDF extractor, which receives the path to a PDF file, extracts
its content, and returns it as a text string; and (ii) an SDS ingredient extractor, which processes the
textual content of the SDS, identifies and returns relevant information regarding the ingredients.
Figure 1 illustrates the workflow execution following our proposed approach. The user provides
a prompt requesting the ingredients contained in a PDF file (e.g., “What are the ingredients of the
product contained in the PDF file at ‘sds.pdf’?”). The agent begins by selecting the PDF extraction
tool and providing ‘sds.pdf’ as input, which returns a memory path referencing the extracted content.
Using this memory path, the agent then runs the SDS ingredient extractor. Within the Mirrored MCP
tool, the memory path retrieves the stored content and executes the tool with its original parameters,
producing another memory path pointing to the extracted ingredients. Finally, the agent calls the
tool to retrieve the final answer and presents the result to the user. A detailed execution trace of this
workflow, illustrating the proposed method, is included in the Appendix B.
The experiment involved executing the workflows 50 times to collect metrics on execution time
and token usage, both using the proposed solution and the traditional approach (i.e., without the
proposed solution). In the traditional approach, an average of 6,411.36 tokens were used, with an
execution time of 43.05 seconds. In contrast, executing the workflow with the proposed solution
required an average of 841.66 tokens and 11.05 seconds. These results demonstrate that the solution,
in addition to enabling tool calls that would exceed an LLM agent’s context window as described in
Experiment 3.1, does not interfere with workflows where the LLM’s context window would otherwise
be sufficient. On the contrary, it serves as an effective mechanism to significantly reduce token usage
–approximately sevenfold in this use case – thereby accelerating workflow execution, since only the
most relevant information from tool outputs is passed to the LLM. Furthermore, the solution provides
cost savings in scenarios where LLMs are deployed in cloud services, as the cost in such contexts is
directly related to the number of tokens processed.
4
Conclusion
In applications such as Accelerated Discovery and Materials Design, tool outputs can exceed the
context window of LLMs, causing overflow and limiting the applicability of agentic workflows. This
work introduces a method that handles large tool responses by shifting the model’s tools domain from
raw data to pointers referencing memory-stored results, preserving tool functionality and enabling
scalability to arbitrarily large inputs. Consequently, agentic systems can tackle previously infeasible
use cases. Furthermore, the proposed method offers additional benefits beyond handling large data.
As demonstrated, it reduces token consumption– which directly translates into cost savings when
using cloud-based LLM services – and improves execution speed even in workflows where tool
outputs fit within the model’s context window. This makes the approach broadly applicable and
efficient across a wide range of scenarios. For future work, the agent should be equipped with a
mechanism to transform the data schema of a memory element. For those cases, we probably need to
