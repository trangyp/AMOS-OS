Dynamically executing specific target methods in Android applications remains a critical and unresolved
challenge. Despite notable advancements in GUI testing, current tools are insufficient for reliably driving
execution toward specific target methods.
To address this challenge, we present GAPS (Graph-based Automated Path Synthesizer), the first system that
leverages static, method-guided call graph reconstruction to guide the dynamic, interaction-driven execution
of an Android app. GAPS performs a lightweight backward traversal of the call graph, guided by data-flow
analysis, to reconstruct paths reaching the target methods. These paths are then translated into instructions
that guide runtime app exploration.
On the AndroTest benchmark, GAPS statically identifies paths towards 88.24% of the target methods,
averaging just 4.27 seconds per app, and reaching 57.44% of them through dynamic analysis. This performance
exceeds the state-of-the-art tools’ one: the model-based GUI tester APE reaches only 12.82%, the hybrid tool
GoalExplorer reaches 9.69%, and the LLM-based Guardian reaches 17.12%. Finally, we applied GAPS to the 50
most downloaded apps from the Google Play Store, achieving an average static analysis time of 278.9 seconds
to reconstruct paths towards 62.03% of the target methods and reaching 59.86% of them through dynamic
analysis.

Introduction
Android dynamic analysis is a methodology that examines an Android app’s behavior during its
runtime execution. It can be used to verify security vulnerabilities, measure performance, and detect
malicious activities. Complementary to static analysis, which inspects the app without executing
it, dynamic analysis involves running the app in a controlled environment, such as a real device,
an emulator, while monitoring its interactions with the system, network, and other components.
Even though some apps, such as the Android Operating System (OS) services, can come without a
Graphical User Interface (GUI), most apps require interaction with the available GUI components
to change their status. Thus, dynamic analysis for Android apps mainly involves GUI testing tools.
This choice already comes with an important limitation: such tools are able to reach only code
within a GUI component and not any code inside an app. In fact, proving the reachability of an app
target method is still an open research question [11, 35, 52].

The evolution of Android GUI testing tools has progressed through various phases, each one
employing an increasingly sophisticated approach. The very first ones were pseudo-random input
generators, such as Monkey [20], which lack an understanding of the app’s semantics and UI hier-
archy, thus being inefficient for deep functional testing, but very useful for finding shallow random
crashes in an app. Then, GUI testers started embedding models, such as finite state machines, to
better reproduce common interaction scenarios and maximize exploration. Notably, APE [21] is
a model-guided GUI testing tool that has been recognized in prior studies for its effectiveness
in improving code coverage and detecting GUI-related bugs [1, 48, 49]. A hybrid solution, Goal-
Explorer [24], builds a Screen Transition Graph (STG) to statically map relationships between
activities and then guides automatic interaction using Stoat [46]. The advent of machine learning
and deep learning techniques paved the way for GUI testers to autonomously discover new test
paths, guided by optimization algorithms [37]. Finally, the introduction of Large Language Models
(LLMs) enabled GUI testers to leverage semantic and contextual information to solve tasks more
closely aligned with those performed by humans. Among recent advancements, Guardian [36]
stands out for leveraging LLMs to guide UI exploration, showing competitive results across task
completion benchmarks. Despite the multiple contributions in the field of Android automatic inter-
action [9, 11, 12, 28, 30, 47], the efforts made so far have been mainly driven by either increasing
the app code coverage or by replacing a real user in the completion of a task (e.g., “add an event to
the calendar app”).
In this paper, we present our solution designed to provide dynamic method-level reachability
through the following intuition: every target method should be reached by traversing a path that
connects an app entry point to it. Such a path can be statically precomputed and then used to guide
the dynamic analysis until the target method is reached.
At first, we evaluated the performance (i.e., the ability to reach a target method) of the best state-
of-the-art tools designed for Android GUI interaction and call graph reconstruction. In particular,
we randomly selected 50 target methods in each app among the 56 open-source ones from the
AndroTest [11] dataset1, a standard benchmark in the field of Android automatic interaction, still
used by current state-of-the-art [1, 9, 11, 12, 28, 30, 47]. We then tested the performance of the
selected tools. We started with the GUI testers, evaluating their ability to dynamically reach the
target methods within a 5-minute timeout for each app, over three runs: on average, Guardian [36]
was able to execute only 17.12% of the target methods, while APE [21] and GoalExplorer [24] just
12.82% and 9.69% respectively, within the same time limit. In terms of call graph reconstruction,
we chose FlowDroid [6], the best static analysis tool for such a purpose [39], and DroidReach [8],
the only available static path reconstruction tool: FlowDroid was able to generate paths towards
58.81% of the target methods, DroidReach towards 9.48% of the methods. Our findings confirm the
lack of both static and dynamic solutions for reaching a target method in an app.
To this end, we design GAPS (Graph-based Automated Path Synthesizer), a framework relying
on static analysis to guide the dynamic execution until a target method is reached in an Android app.
Statically, GAPS performs target-oriented, context-sensitive call graph construction via backward
traversal, rather than whole-program analysis, restricting its analysis to the subset of the program
relevant to a given target method. It uses data-flow analysis techniques, such as points-to-analysis
and constant propagation, to statically reconstruct partial execution paths using backward traversal
from a target method, resolve conditional statements, and identify triggering UI elements. These
results are translated into high-level interaction instructions that dynamically drive the app to
execute the desired behavior.

Background
In this section, we describe the main methodologies used for automatically interacting with an
Android app and for statically reconstructing its call graph.
2.1
GUI-Based Test Input Generators
Dynamic test input generators, often called GUI testers, explore Android apps by interacting with
their GUIs. Their core functionality relies on repeatedly querying the device for the current view
hierarchy, which is retrieved in XML format and lists all the interactable UI elements on the
screen, such as buttons, checkboxes, text fields, and menus. Each GUI tester uses this structured
representation to decide which element to interact with next. This decision process is guided by a
strategy that may be pseudo-random (e.g., Monkey [20]), model-based (e.g., APE [21]), machine-
learning based (e.g., ARES [37]), or semantic (e.g., Guardian [36]).
GUI testers are typically designed to maximize code coverage or detect UI-related bugs. Pseudo-
random strategies rapidly issue events for lightweight testing, while model-based and machine-
learning based tools interact heuristically with the UI, often guided by internal models of app
states or by optimization algorithms, and prioritize breadth and novelty of interactions rather than
triggering specific behaviors.
LLM-based tools follow a different paradigm. These systems are provided with a high-level
task description (e.g., “save a note in the app”) and operate as agents that reason over the app’s
interface to complete the task. Leveraging an LLM, they attempt to interpret screen layouts and
prior interactions to plan and execute the sequence of actions.
Despite these advances, GUI testers, whether coverage-oriented or goal-driven, are fundamentally
limited in their ability to consistently and specifically reach methods within an app, resulting in an

2.2
Call Graph Generation
Call graphs are a core building block of static program analysis, since they capture the method
invocation relationships within an app. In Android, call graph construction is especially chal-
lenging due to the platform’s event-driven architecture, components’ lifecycles, Inter-Component
Communication (ICC), and dynamic behavior such as reflection.
Several tools, such as FlowDroid [6] and Amandroid [50], attempt to build inter-procedural call
graphs using context- and flow-sensitive analysis. These tools are computationally intensive and
face scalability challenges due to their exhaustive exploration of all app edges. For instance, a
previous study [7] reported that even with 730GB of RAM and 24 hours of analysis time, FlowDroid
failed to analyze certain applications. Additionally, Android call graphs are known to suffer from
unsoundness, with missing or incorrect edges caused by unresolved dynamic behavior [39]. More
specifically, many state-changing events for an Android app are not declared in its code, but
are instead part of the Android framework, which implicitly invokes callback methods, such as
onCreate, onClick [9, 10]. In addition, Android apps consist of multiple interacting components
(i.e., Activities, Services, and BroadcastReceivers), each governed by its own lifecycle. Accurately
modeling these lifecycles and their transitions is critical for generating meaningful call graphs;
however, it is also challenging since they involve implicit invocations and asynchronous handlers
that cannot be statically resolved. ICC introduces further complexity, as components interact by
sending Intent messages that dynamically determine the control flow across components. Without
proper modeling of ICC, the resulting call graph is incomplete and may miss valid transitions
altogether [25]. Finally, static analysis must also consider conditional logic: even when a path exists
between an entry point and a method, it may be guarded by a conditional statement.
Altogether, these challenges make it clear that full call graph construction for Android apps is not
only resource-intensive but also fundamentally limited in terms of soundness and precision [39].
Moreover, complete call graph construction is not always necessary or even desirable when the
analysis goal is to verify the reachability of a specific method. A full call graph introduces the risk
of path explosion, particularly in large applications with deeply nested lifecycles, asynchronous
flows, and extensive library usage.
3
Related Work
In this section, we discuss current state-of-the-art research related to GUI testers, call graph
generation, and hybrid analysis.
3.1
GUI Testers
Automated GUI testing for Android has been approached with various techniques, but generally
shares the goals of maximizing code coverage and finding UI bugs. Android’s built-in Monkey
tool [20] is the archetype of random GUI testing. It simply issues pseudo-random UI and system
events with minimal configuration, making it extremely easy to use. Variants like SmartMonkey [22]
and Dynodroid [28] are built on Monkey by adding simple heuristics to reduce wasted inputs.
While random testers are scalable and easy to deploy, their lack of app-state awareness often leads
to shallow coverage and repeated interactions with the same screens.
Model-based approaches construct an explicit GUI model (e.g., a finite state machine or transition
graph) and systematically explore it. Notably, APE [21] extends Monkey-like random testing with
adaptive heuristics to improve coverage and efficiency. However, the models built at runtime are

Reinforcement learning (RL) has been applied to adaptively guide GUI exploration. ARES [37]

3.2
LLM UI Automation
A rising trend in Android UI automation is to rely on LLMs to automatically interact with the device
screen and complete a task specified by the user. GPTDroid [27] supplies the LLM with additional
contextual information from the view hierarchy, along with a functionality-aware memory that
maintains knowledge about past interactions. Autodroid [51] incorporates an initial random UI
interaction to provide contextual information to the LLM, thereby enhancing its performance.
However, this approach is neither exhaustive nor scalable for larger applications. VisionTasker
[42] employs a different approach, utilizing an object detection model to identify UI elements in
screenshots taken from the device. Although this strategy is more resistant to missing or misaligned
elements, it is limited by what is currently shown on the screen and cannot properly process
dynamic screens (e.g., games) or slow-loading apps. Guardian [36] has a replanning strategy that
prevents invalid or repeated selection of GUI elements. This approach, coupled with state restoration,
allows Guardian to favor app exploration. In subsection 4.2, we evaluated Guardian’s effectiveness
in reaching targeted methods within AndroTest applications, achieving an average reachability of
only 17.12% over three runs.
3.3
Call Graph Generation
FlowDroid [6] is a taint analysis tool that generates the app’s call graph to discover privacy and
security leaks between defined sources and sinks. FlowDroid constructs a call graph using Soot
[43] and performs a flow- and context-sensitive analysis. However, FlowDroid did not model ICC
in its initial version, leaving an essential contribution to call graphs unaddressed. This was later
introduced with the integration of IccTA [25]. Similarly, Amandroid [50] is a taint analysis tool that
builds an inter-procedural call graph and computes points-to information for all objects of an app
component. FlowDroid and Amandroid employ data-flow analysis techniques to construct a call
graph using a forward-visit approach, where every branch is visited during the process. In addition,
this approach has proven to be resource-intensive when integrated with the increasing complexity
of apps [7]. GAPS aims for a more scalable approach: we build a partial inter-procedural call graph
backward, starting from a target method invocation, to limit processing overhead. DroidReach [8]
is the only known path reconstruction tool. Its path reconstruction techniques rely on generating a
complete call graph using either the Androguard call graph creation tool [4] or FlowDroid.
In subsection 4.3, we compare GAPS against DroidReach and FlowDroid. In both cases, GAPS’s
static analysis module proved to be faster and more effective in generating paths towards target
methods compared to its counterparts. Additionally, it provides specific app entry points, execu-
tion paths to satisfy conditional statements, and corresponding GUI events to guide automated
interaction.

3.4
Hybrid analysis
Andrubis [26] is a hybrid analysis tool created for detecting Android malware. Andrubis’ static
analysis retrieves meta information (e.g., permissions, components, package name) and examines
the Dalvik bytecode to extract a complete list of Java objects and methods. Subsequently, dynamic
analysis is aided by information previously collected to interact with known entry points and
measure code coverage, but it is not ultimately guided by the data collected during static analysis.
AndroPyTool [31] is another malware detection tool that combines static and dynamic analysis. It
utilizes Androguard to extract essential features (e.g., package name, permissions, opcodes, API
calls), and FlowDroid to perform taint analysis. Samples are run inside a sandbox. However, dynamic
analysis is not assisted by static analysis; instead, they are included as separate contributions in
the output. GAPS aims to use static analysis information to provide path-sensitive instructions
and guide automatic interaction. Evodroid [29] proposes an evolutionary approach to the system
testing of Android apps. It builds a Control Graph Model consisting of code segments used during
GUI exercising to increase coverage. GAPS, instead, proposes a targeted approach to reach a specific
method inside the app. Furthermore, Evodroid bases its static analysis on MoDisco [17], which
requires the source code of the app to be provided; however, this is not always possible for most
apps on the Google Play Store. GAPS can analyze any APK and DEX files as input and does not
require the source code to operate. LetterBomb [19] employs a hybrid approach for automatically
generating exploits for Android apps, specifically targeting Inter-Component Communication
(ICC) vulnerabilities. The methodology combines a path-sensitive symbolic execution-based static
analysis with software instrumentation and test oracles to identify and exploit weaknesses in the
ICC interface. GAPS differs from LetterBomb in that it performs static analysis without relying on
symbolic execution, which is known to be computationally expensive and often impractical for
large, real-world apps. Instead, GAPS uses a lightweight static approach to reconstruct paths to a
target method and then translates them into high-level instructions to guide UI exploration.
GoalExplorer [24] is a hybrid system for automated, goal-driven exploration of Android applica-
tions. Its core idea is to first statically model the app’s UI screens and the transitions between them
by combining results from modified versions of FlowDroid [6] and BackStage [23], creating an STG.
This STG is then used to guide dynamic exploration, allowing the tool to navigate to a specific
target of interest, such as an Android activity, an API call, or a program statement. In subsection 4.2,
we compared GoalExplorer against GAPS, and it only achieved 9.69% of the target methods on
average across three distinct runs.
4
Motivation
To better understand the limitations of existing tools and evaluate the effectiveness of our approach,
we structure our study around four research questions:
• RQ1: How effective are GUI testers at triggering the execution of target methods?
• RQ2: How effective is static analysis in reconstructing a path towards a method?
• RQ3: How does GAPS perform compared to state-of-the-art approaches?
• RQ4: Can GAPS be applied to real-world apps?
4.1

benchmark, for which we collected the apps’ latest version. These apps were instrumented using
AndroLogs [41] to measure method reachability by logging every time a method was executed. For
each app, we randomly selected a consistent set of 50 target methods to be reached during testing,
out of which only 34.39% are located inside an Activity.

4.2
RQ1: GUI testers’ effectiveness for dynamically executing target methods
To evaluate the effectiveness of GUI testers in dynamically executing targeted methods within
Android applications, we selected APE, recognized as one of the best-performing tools in recent
studies [1, 48, 49], and Guardian, an LLM-based UI exploration tool that has outperformed other
task-guided approaches [36]. We also compared against GoalExplorer [24], a hybrid analysis tool
that statically builds an STG to guide the Stoat [46] stochastic GUI testing. The experiment was
conducted using the AndroTest benchmark. Each app was executed for five minutes across three
independent runs. We chose a 5-minute timeout for all competing tools, including GAPS, to ensure
an efficient dynamic analysis. Previous works [38, 40] chose the same threshold. During execution,
logs were collected to verify the dynamic reachability of the target methods. To execute Guardian,
we tasked the LLM model to “interact with the application to maximize exploration”.
Considering the set of 50 target methods for each app, over three runs, GoalExplorer executed
an average of 9.69% methods, APE 12.82%, and Guardian 17.12%. These results demonstrate the
differences in usability among the three techniques: APE can rapidly generate GUI events, but
struggles to consistently build app states that facilitate the discovery of more hidden parts of
the app code. GoalExplorer uses the STG to guide Stoat by flagging activities when a target API
is invoked. However, it faces limitations when the target methods reside in third-party libraries
or when control-flow conditions are involved, as these often require more complex interactions
beyond merely reaching the target activity. Finally, Guardian leverages the LLM’s decision-making
capabilities to systematically interact with UI elements in a goal-oriented manner, enabling it to
uncover more comprehensive execution paths. Despite this, its average capability to execute target
methods remains low, highlighting that semantic planning alone is insufficient without deeper
control-flow awareness.
RQ1: GUI testers effectiveness for dynamically executing target methods
Our evaluation highlights the limitations of dynamic interaction tools in executing target
methods. Both APE and Guardian show low success rates, with GoalExplorer reaching
only 9.69%, APE 12.82%, and Guardian 17.12% of the predefined target methods across
three runs. These findings highlight the need for a hybrid strategy that integrates dynamic
execution with path-sensitive static guidance.
4.3
RQ2: Path reconstruction through static analysis
We evaluated the effectiveness of static analysis tools in identifying paths to target methods using
FlowDroid [6] and DroidReach [8]. FlowDroid is a well-established static analyzer that is actively
maintained and was recently recognized as the best-performing tool for call graph generation [39].
DroidReach, on the other hand, is the only available tool that reconstructs paths by leveraging
call graphs generated via AndroGuard [4], applying graph-search algorithms to assess method
reachability. In our setup, we improved DroidReach by restricting entry points to only exported
components, whereas the original configuration considers all manifest-declared components as
potential entry points. We note that DroidReach also supports FlowDroid-generated call graphs,

Static analysis tools fail to build paths towards a substantial portion of the target methods:
FlowDroid’s generated paths reach only 58.81% of the methods, while DroidReach only
reaches the 9.48%. These findings demonstrate that current call graph generation tools
are ineffective for target-method reachability, underscoring the need for more focused and
goal-driven approaches.

5.4
Backward Generation of the Call Graph
GAPS adopts a goal-directed, demand-driven approach to call graph construction that diverges from
traditional whole-program analyses, such as those used by Flowdroid. Instead of building a complete
call graph upfront, GAPS performs a targeted, backward traversal starting from a specified method
of interest. This traversal is both inter-procedural and context-sensitive, collecting only those
method calls that lie along feasible paths leading to the target. The resulting structure is a partial
call graph slice that is sufficient for reachability purposes but avoids the scalability bottlenecks of
global analyses. GAPS also incorporates data-flow analysis to capture branch conditions and control
dependencies, which are essential for reconstructing realistic execution paths, as well as actionable
entry points and GUI event identifiers. The pseudocode for the partial call graph generation can be
consulted in Algorithm 2.
The process begins with the target method and iteratively traverses backward through its
potential callers. This is implemented using a queue of nodes to process (2 and 3), where the current
node being processed is removed from a queue (6) and all its statically discoverable callers are
identified via find_new_nodes (10). These new nodes are added to the call graph and appended to
the queue (11). When an entry point is encountered, it serves to terminate the backward traversal,
and no further predecessor nodes are added. Then, nodes that are processed are added to the
seen_nodes set (12), to avoid reprocessing and ensure termination (7). This backward expansion
continues until no new nodes are found. At that point, the constructed call graph contains a slice
of the original application call graph that is specifically focused on reaching the target. Once the
partial call graph is complete, GAPS invokes a depth-first traversal (dfs_visit) (14) to extract all
feasible paths from known application entry points to the target method. These paths are further
enriched by resolving conditional branches (16 and 17) and detecting associated GUI elements (18),
which are necessary to trigger the GUI events.

Implementation
In this section, we provide more details about GAPS’ implementation, including call graph genera-
tion and path reconstruction, retrieval of Graphical Elements’ IDs, and the automatic interaction
module.
6.1
Call Graph Generation and Path Reconstruction
At its core, GAPS uses the Androguard [2] Python library to load and analyze the APK or DEX files
in input through the AnalyzeAPK and AnalyzeDex [3] built-in functions. Then, GAPS analyzes the
MethodAnalysis construct for each method to access its basic blocks. Every basic block obtained
is represented by a sequence of smali instructions, an intermediate representation of the app
bytecode. Internally, GAPS uses the networkx [33] Python library to create and model the graph.
Subsequently, we use the all_shortest_paths [32] method from the networkx library to retrieve
the paths connecting the source nodes and the entry points. Since solving implicit flows is still
considered an open research problem [39] that falls out of the scope of this paper, we have added
callback mappings provided by popular works in Android static analyzers, such as EdgeMiner [10]
and Soot [43] through its virtual edges [44]. In this way, we can find the corresponding constructor
or method initializer and partially solve implicit flows. Data-flow analysis is performed following the
smali code representation, which provides a rigorous register-based syntax that we have modeled to
adapt the points-to analysis and constant propagation. For example, to track the transition to a new
activity, when an Intent is constructed, the last argument passed to the constructor corresponds
to the destination activity, which matches the last register in smali syntax. This data-flow-aware
analysis is also essential for linking paths that satisfy conditional statements. Moreover, through
constant propagation, a conditional statement involving primitive-type variables, objects, or method
return values is translated to compare constant values to test its satisfiability.
6.2
Static Output and Dynamic Guidance
GAPS uses Apktool [5] to decompile apps and retrieve GUI resource IDs during static analysis. To
convert them from the smali numerical representation, GAPS consults a file generated by Apktool
called public.xml, where they can be converted into a literal one. GAPS can generate high-level
instructions in JSON files, consisting of actionable entry points and sequences of graphical element
IDs to interact with, along with the Activity name where they reside. Additionally, a call sequence is
also included. These results can be used in two ways. First, they can serve as the standalone output
of the static analysis phase: for each target method, GAPS lists all the paths found during analysis,
together with their reconstructed call sequence and the corresponding high-level interaction plan.
Second, they can directly guide dynamic analysis. In this case, each plan begins with instructions
that can be executed through adb to send an Intent and trigger the correct entry point discovered
during the static analysis. The plan then continues with a sequence of UI element IDs and the
Activity in which they appear, specifying the concrete actions to perform on the app interface in
order to reach the target method. When conditional statements are resolved during the static phase,
the relative call sequences and their associated high-level instructions are prepended to the plan,
ensuring that the conditions are satisfied before continuing with the UI interactions.

7.3
Discussion and Limitations
While GAPS demonstrates significant improvements in targeted method reachability, it comes with
some limitations.
First, its reliance on static bytecode analysis restricts its effectiveness for apps built with frame-
works like Flutter or React Native, where the app’s logic resides outside traditional Dalvik code.
Furthermore, apps with an obfuscated call graph can lead to path explosion and significantly slow
down analysis time, as evidenced by the higher analysis times of real-world apps. Another obstacle
to path reconstruction is dead code located in libraries, which can worsen GAPS’ performance.
Finally, call graph generation is known to suffer from unsoundness [39], caused by untracked
implicit flows. GAPS uses the same callback mappings used by FlowDroid [6] and Soot [43], and
also includes those generated by EdgeMiner [10], but might still suffer from unsoundness when an
unexpected implicit flow is met. The analysis of the Android Framework to identify implicit edges
for static analysis tools is an orthogonal problem that falls outside the scope of this work. Our
current approach does not support Jetpack Compose. Unlike XML-based layouts, Jetpack Compose
defines UI elements directly in Kotlin code and attaches event handlers through lambdas rather
than OnClickListener objects. Furthermore, UI state can change dynamically through recomposi-
tion. These differences make data-flow analysis for Jetpack Compose more complex. Extending
static analysis to reliably extract GUI elements and events from Jetpack Compose remains an open
research problem, and we consider this an important direction for future work.
In some cases, we cannot dynamically execute target methods, even though GAPS has built
a static path. Complex interactions might be required to fully traverse a path: Hot Death and
Yahtzee are games where some of the randomly selected target methods can only be reached upon
winning a game. Finally, most apps have paths with intent filters as an entry point, which can
have permissions or be owned by the system (e.g., BOOT_COMPLETED), or could require data to be
passed along with the Intent. Retrieving the required data parameters and automatically generating
Intents is an orthogonal problem to dynamic analysis, which falls outside the scope of this paper.
Despite these challenges, GAPS’ hybrid approach strikes a balance between precision and
scalability, providing a practical foundation for future enhancements.
8
Conclusions
In this paper, we present GAPS, a framework designed for statically reconstructing paths that
guide the dynamic analysis until the target method is executed. In our evaluation, we show that
GAPS can reconstruct at least one path for 88.24% of the target methods and traverse 57.44% of
such paths in apps belonging to the AndroTest benchmark, with an average analysis time of 4.27
seconds. In contrast, state-of-the-art tools achieve significantly lower performance in static path
reconstruction and dynamic method reachability: GoalExplorer (9.69%), APE (12.82%), Guardian
(17.12%), FlowDroid (58.81%), DroidReach (9.48%), with longer or less targeted analysis phases.
On the other hand, the results on the real-world apps dataset report that GAPS can reconstruct
paths for 62.03% of the target methods, averaging an analysis time of 278.9 seconds per app, and
dynamically executing 59.86% of them.
