With the rapid progress of deep learning and large language models (LLMs), companies now spend enormous
sums executing GPU kernels. These kernels have, therefore, become prime targets for aggressive optimization.
Recent efforts increasingly leverage LLMs to generate GPU kernels, but make no formal guarantees about the
generated kernels. We present the first equivalence checker for GPU kernels and use it to formally verify the
correctness of machine learning (ML) kernels optimized by hand, by LLMs, and by compilers. We show that
our equivalence checker is sound and, for a well-defined class of GPU kernels which includes the programs of
interest, complete. Our implementation, Volta, can verify ML computations such as convolutions, matrix
multiplications, and various attention mechanisms.

Introduction
Given two GPU kernels—a reference implementation and an optimized counterpart—our goal is
to prove their semantic equivalence, i.e., that they produce identical outputs for all valid inputs,
thereby verifying the correctness of the optimized kernel. Although equivalence checking has
been extensively studied for over half a century [42] and recent works have successfully proved
correctness of optimized CPU code [23], GPU programming introduces unique challenges arising
from fine-grained synchronization among a massive number of threads. To date, the literature
proffers no equivalence checker for GPU programs.
With the rapid progress of deep learning and large language models, companies now spend
enormous sums executing GPU kernels. These kernels have thus become prime targets for aggressive
optimization, performed manually [10], fully automatically by agents [5, 50, 64], or even the old-
fashioned way, by compilers [62]. Recent efforts increasingly leverage large language models to
generate GPU kernels. For example, NVIDIA has used DeepSeek-R11, Stanford researchers have
used OpenAI o3 and Gemini 2.5 Pro2, Kevin-32B is a model trained with reinforcement learning for
kernel generation3, Feature Search and Reinforcement combines search with reinforcement learning
to derive kernels [12], Standard Kernel is building AI infrastructure for kernel generation4, and
mako offers an interface for generating GPU kernels with different LLMs5. None of these systems
provides any guarantee of correctness for the optimized kernels beyond their ability to pass a set
of tests. Incorrect kernels may still succeed on test cases but fail in production, potentially causing
costly errors or public setbacks [65].
Given the increasing reliance on aggressively optimized GPU kernels, we believe it would
be beneficial to formally verify their correctness. GPU kernels execute thousands of threads in

concurrency errors that testing alone cannot reliably detect. One major source of such errors is data
races, which may appear only in extremely rare executions or may remain latent when kernels rely
on implicit synchronization that happens only for a specific version of the test runtime or the test
hardware but is not guaranteed to hold in general. For example, a widely cited GPU programming
tutorial [24] relies on warp-level synchronization that was removed after CUDA 9.0 [8]. Testing-
based correctness checking is further complicated by floating-point arithmetic. GPU optimizations
often reorder arithmetic operations, causing small numerical differences between the outputs of
the reference and optimized implementations. Such variations are usually tolerated in tests, yet
similar deviations can arise from genuine semantic bugs. For instance, an unsound optimization
that omits a clipping operation may seem acceptable for some test inputs even though it reduces
overall model accuracy. While compilers rarely introduce such mistakes, they are plausible when
kernels are hand-optimized by human programmers or generated by automated agents.
State-of-the-art equivalence checking supports single-threaded integer programs [23] and high-
level tensor operations [3, 67], but it is not obvious how to decompose the equivalence checking of
GPU kernels into single-threaded sub-tasks. In an optimized kernel, there may be no one-to-one
correspondence between its threads and the threads in the reference implementation. In addition,
existing techniques have no support for synchronization among multiple threads.
Although equivalence checking is undecidable in general and GPUs allow programmers to write
arbitrary code, efficient GPU kernels typically follow structural patterns that make formal reasoning
feasible. We assume that the programs analyzed by our equivalence checker are structured-CTAs, a
subset of kernels that we motivate in Section 3.2 and formally define in Section 4.1. Although it
is easy to construct programs that violate these assumptions (e.g., by writing recursive code) and
make our techniques inapplicable, we and others [32, 38, 57] observe that the assumptions very
often hold in practice (Section 3.2). Our tool checks that its input is a structured-CTA and raises
an exception if it is not. Finally, our work focuses on kernels targeting NVIDIA GPUs due to their
widespread adoption, although the techniques are applicable to other GPU runtimes as well.
The core of our equivalence checker is symbolic evaluation. Consider a tensor computation—a
workload that dominates machine learning. We symbolically execute the reference computation
under an arbitrary, fixed schedule to derive an expression over the mathematical reals that represents
the output tensor as a function of the input tensors. Is it possible that a different scheduling of the
threads could lead to a different expression? Our main technical result, confluence, guarantees that
all symbolic evaluator schedules lead to the same expression. If the kernel contains a deadlock or a
data race, the symbolic evaluator is guaranteed to catch it and produce a diagnostic report. The
same procedure is applied to the optimized computation. Finally, we develop a procedure to decide
equality of the two symbolic expressions and, if they are equal, we conclude that the optimized
kernel is semantically equivalent to the reference kernel over the reals, for all schedules. We are
not aware of a proof in the literature that the symbolic identities we need to decide are, in fact,
decidable (though there is work on related problems, e.g., [41]). We prove that these identities
are decidable in Section 4.4. It is worth noting that optimized kernels are almost never bit-wise
equivalent to the reference implementation in floating point arithmetic, since most optimizations
reorder arithmetic operations when distributing work among GPU threads.

frameworks that check weaker properties such as data race freedom [38]. Our equivalence checker
Volta6 soundly verifies data race freedom of kernels (Theorem 1) and satisfies a true positives

ends. For example, GPU programmers can either write CUDA kernels or CUTLASS templates [17].
NVIDIA’s nvcc compiler translates both into PTX.

3
Background
We begin with necessary background on GPUs. To execute a task on a GPU accelerator, the CPU
host launches a grid of cooperative thread arrays (CTAs), also known as thread-blocks. All CTAs
share access to global memory (HBM), typically sized in gigabytes. Different CTAs in a grid usually
write to disjoint regions of global memory due to its weak consistency model. The GPU hardware
schedules each CTA on a streaming multiprocessor (SM); a modern GPU may contain hundreds of
SMs. The resources assigned to each SM are limited and hence each CTA is tasked to compute only
a tile of the output tensor. Each CTA consists of 128 to 1024 threads, depending on the hardware
generation. Within a CTA, threads are grouped into warps, each consisting of 32 threads. Every
thread maintains its own registers for local storage, while shared memory serves as a software-
managed cache accessible to all threads in the same CTA. To coordinate access to shared memory,
threads must use explicit synchronization operations. Missing synchronization leads to data races
and over synchronization leads to loss of performance. The shared memory available per CTA
ranges from 48 KB to 256 KB, depending on the GPU architecture. In a typical CTA, threads first
load data from global memory into shared memory, perform arithmetic operations while keeping
intermediate values in registers or shared memory, and finally write the results back to global
memory. Writing code for efficient CTAs is challenging because programmers must reason about
massive thread-level parallelism and low-level hardware details. Volta aims to statically identify
incorrect or unsafe optimizations. We next describe the synchronization mechanisms available on
GPUs.

3.1
Synchronization operations
NVIDIA GPUs support independent thread scheduling, meaning that in the absence of explicit
synchronization, each thread executes independently. The fundamental synchronization primitive
is syncthreads, a barrier that spans all threads within a CTA. Threads that reach the barrier earlier
are suspended until all threads in the CTA arrive, at which point execution resumes for all of them.
Another synchronization primitive is syncwarp, which operates on a user-specified subset of
threads within a single warp. This mechanism is commonly used when programming tensor cores,
where CUDA intrinsics such as wmma::mma_sync synchronize all threads in a warp to perform matrix
multiplication. Most prior verification techniques for GPU kernels support only syncthreads and
therefore do not reason about machine learning kernels that rely on warp-level synchronization.
While syncthreads guarantees deadlock freedom, syncwarp can introduce potential deadlocks.
In summary, the synchronization mechanisms we consider are barriers that block subsets of the
available threads. Asynchronous primitives such as arrive and wgmma are beyond the scope of this
work and left for future research.
3.2
Practical considerations
Here, we discuss the assumptions that Volta makes over the input kernels at a high level. These
assumptions are checked: Volta raises an exception if a kernel does not satisfy these requirements
(Section 5). We first state these assumptions and then provide motivation for them.
Volta checks equivalence of two CTAs that operate over tensor tiles whose sizes are statically
known. For each thread of a CTA, given its tid, all branch targets and addresses used in memory ac-
cesses are statically fixed. Later we define structured-CTAs that formally encode these assumptions
(Section 4.1) and prove the completeness of Volta for this class of programs (Section 4.3).
Although these assumptions arise from domain knowledge of machine learning, they also reflect
well-established best practices for achieving high GPU performance. Empirical studies support
these assumptions. A large-scale analysis of GPGPU kernels in the wild found that most memory
accesses are control independent and data independent [38] (59.5% of 2770 programs). Similarly, a
study of the CUDA SDK showed that most programs exhibit access invariance [32], meaning that
threads perform the same memory accesses for all inputs (52 out of 76). Moreover, Weft [57], a race
detector for scientific and cudaDMA kernels, makes all of the above assumptions and confirms that
all 26 scientific computations studied by Weft fall in that class. Next, we provide some background
on ML GPU kernels and motivate why they fall in this class.
We focus on kernels that form the performance bottlenecks in training or inference of machine
learning (ML) models, such as matrix multiplications, convolutions, and multi-head attention. In
these workloads, the structure of the ML model is fixed: tensor entries depend on runtime inputs, but
tensor sizes are statically known. Kernels are therefore specialized for particular tensor dimensions
to achieve maximum performance. Consequently, we assume that the sizes of all arrays accessed
by the kernel are statically known to Volta.
Once array sizes are known, all loop bounds can also be determined, since the bounds in tensor
operations depend on tensor shapes. Volta can therefore unroll these loops statically. We also
require that the targets of conditional branches can be statically resolved; note this restriction
exploits the fact that efficient machine learning kernels do not make truly data dependent runtime
decisions. Under these assumptions, the code executed by each individual thread can be represented
as straight-line, containing no dynamic branches or loops. It is common for threads to branch on
predicates of their thread index; however, such control flow still preserves the straight-line property
for each thread’s execution.

Efficient GPU kernels carefully orchestrate memory transfers by coalescing accesses to global
memory and avoiding shared memory bank conflicts. As a result, GPU programmers typically
define memory access patterns statically, making memory addresses independent of the tensor
contents. Consequently, when a straight-line thread accesses an array element, both the base array
and the exact index can be determined statically. This property allows the symbolic evaluator to
record memory accesses precisely and to detect data races accurately.
The ML kernels launch a grid of CTAs where the code of each CTA is identical and differs
only in the instantiation of free variables blockIdx.x, blockIdx.y, and blockIdx.z. Each CTA is
responsible for computing a fixed-size tile of the output tensor. Many GPU optimization focus on
this CTA-level code. For instance, the CTA code can be modified to use tensor cores. When checking
a reference kernel against an optimized kernel, we focus on proving the equivalence between the
code of a CTA from the reference kernel with the code of the corresponding CTA in the optimized
kernel. Hence, correctness checking of optimizations that change the number of CTAs launched in
a grid is beyond the scope of this work. Since each pair of CTAs can be checked independent of
each other, following prior work [57], our evaluation focuses on checking the equivalence of CTAs
with blockIdx.x = blockIdx.y = blockIdx.z = 0 in the reference and the optimized kernels.
A sound equivalence checker operating over floating-point arithmetic would likely reject many
aggressively optimized kernels. In practice, both developers and domain-specific compilers treat
tensor values as real numbers when applying optimizations. Such transformations, similar in spirit
to the –ffast-math option in gcc, are unsound for floating point arithmetic. Volta follows the
same convention as existing optimizers and models tensor elements as reals.

Algorithm
Our equivalence checker proceeds in two phases. The first phase symbolically executes a pair of
programs, determining whether they are data race free and, if so, expresses their output values
as terms of symbolic input tensors. If both programs are data race free, we proceed to the second
phase, which verifies that, for each output element, the symbolic terms derived for both programs
are equal. For example, when analyzing Listing 1a, the symbolic evaluator starts with environment

Implementation
We implement our techniques in a proof-of-concept tool called Volta. Given a pair of PTX assembly
programs 𝑃, 𝑄to be checked for equivalence, Volta proceeds as follows. First, the implementation
could raise an exception because the given PTX programs are not structured-CTAs. Next, the
symbolic execution could report a deadlock or a data race. If the symbolic execution succeeds,
then for 𝑃,𝑄we obtain the environments (G𝑃, R𝑃), (G𝑄, R𝑄). The verification conditions (VCs)
corresponding to the output tensors are given to the decision procedure that checks for their validity.
If a VC is found to be invalid, then an equivalence bug is reported. If all VCs are provably valid,
then the two programs are declared equivalent, i.e., they are guaranteed to compute semantically
equivalent expressions over reals for all schedules.
At a high level, Volta is comprised of two main components: a simulator that performs symbolic
execution to generate decision problems, and a decision procedure that verifies their validity. For
a program where each thread runs at most 𝑁statements, the simulator’s runtime is linear in 𝑁,
whereas the decision procedure exhibits superlinear complexity in 𝑁. Accordingly, we place greater
emphasis on optimizing the latter. The current simulator implementation, described below, is not
optimized for performance and could benefit from additional engineering. Nevertheless, because
equivalence checking is not typically required in real time, the existing prototype is sufficient to
demonstrate the core contributions of our work.

Volta operates on CTAs written in PTX ISA 9.09. The scheduler also accepts user-provided
annotations that specify parameters such as the number of threads and the arrays designated
as input/output tensors. The PTX file is first parsed into a low-level intermediate representation
consisting of a list of statements. Examples of statements include memory reads and writes, arith-
metic operations, jumps, and labels. Each statement is encoded as a record containing an opcode, a
destination, a list of arguments, and an optional predicate for conditional execution. The parser
currently supports all PTX instructions that appear in our benchmarks, and support for additional
instructions is being added incrementally.
The list of statements corresponding to a thread block is provided to the scheduler. If the
thread block contains threads with identifiers 0, . . . , 𝑁−1, the scheduler maintains a queue of
𝑁program counters along with a single shared copy of the statement list. Initially, the queue is
[(0, 0), (1, 0), . . . , (𝑁−1, 0)], where each pair (𝑡,𝑐) indicates that thread 𝑡currently has program
counter 𝑐. During execution, the scheduler repeatedly dequeues a program counter, symbolically
evaluates the corresponding thread until it becomes blocked while updating the program state
(discussed further below), and then enqueues the updated program counter. This round-robin
scheduling continues until all threads reach return. If the symbolic evaluator detects reads from
undefined registers or uninitialized memory locations then Volta raises an exception. For arrays,
an out of bound memory read or write also cause Volta to raise an exception.
The program state consists of X, G, and R, as introduced in Section 4. It is implemented as a
Python class that uses SymPy10 expressions to uniformly represent both symbolic and concrete
values. Volta leverages SymPy’s built-in simplification capabilities to perform arithmetic operations
during simulation, such as computing array offsets for memory reads and writes or when evalu-
ating branch predicates that determine the next instruction to execute. The state also maintains
information to ensure that all threads expected to reach a synchronization barrier have done so. If
a data race or deadlock is detected then a report is generated.
After the simulation completes, the final G and R are written to a file. Because SymPy expressions
can be large, they are converted into a custom serialization format, and only the symbolic expressions
corresponding to the output tensors are stored. This process is performed for both programs.
For each element of an output tensor, the decision procedure uses the stored files to construct a
verification condition (VC). Since deciding all VCs is an embarrassingly parallel task, our imple-
mentation employs multi-threading to evaluate them concurrently. Given a VC of the form 𝑓= 𝑔,
where 𝑓and 𝑔are symbolic expressions over the input tensors, Volta constructs a SymEngine11
expression representing 𝑓−𝑔and checks whether it canonicalizes to zero. An earlier version of
the decision procedure, implemented in Python with SymPy, did not scale to our benchmarks,
motivating a re-implementation in C++ using SymEngine. Unlike SymPy, which provides a large
set of built-in simplification rules, SymEngine offers a minimal core that enables us to implement
only the simplification rules required for our domain.
Volta traverses each node of the abstract syntax tree (AST) for 𝑓−𝑔exactly once, in a bottom-up
manner, applying a sequence of simplification rules. For internal nodes, SymEngine’s internal
ordering is used to sort child nodes, ensuring a canonical representation. In addition, Volta applies
a collection of rewrite rules when applicable. Examples include max(−∞,𝑥) = 𝑥, max(𝑥,𝑥) = 𝑥,
max(max(𝑎,𝑏),𝑐) = max(𝑎,𝑏,𝑐), 𝐸+ (−𝐸) = 0, and 𝑒𝑎× 𝑒𝑏= 𝑒𝑎+𝑏. The system also distributes
multiplication over addition to find the coefficient of each monomial term. This operation, in
principle, may cause exponential blowup. Since machine learning workloads do not typically have

Evaluation
There are three main ways to create efficient GPU kernels for machine learning workloads: manual
optimization (Section 6.1), generation by LLMs (Section 6.2), and compilation by domain-specific
compilers (Section 6.3). Since our equivalence checker operates as a black box and makes no
assumptions about the optimization process, it can verify the correctness of optimized kernels
produced by all three approaches. We evaluate on reductions, matrix multiplications, convolutions,
and various attention mechanisms. We report the time to solve the verification conditions (VCs)
on a machine with a 24-core 2.64 GHz AMD EPYC 7413 processor and 220 GB of RAM. We show
that Volta scales to realistic machine learning workloads and effectively identifies correctness
issues when they exist. In particular, Volta detects data races that have been previously reported
in open-source GitHub repositories (Section 6.4).

In a recent blog post, Stanford researchers demonstrated how LLMs can generate optimized GPU
kernels for 2D convolution [50]. We verify the equivalence of the final LLM-generated kernel after

cores significantly increases the code size of the optimized kernel compared to the reference. The
reference has no synchronization operations whereas the final version has 6.4k CTA-wide and 3.1k
warp-level barriers.

Data races
FaialAA is the state-of-the-art data race checker for GPU programs [38]. Its canonical failure case,
as described by the authors, is the following pattern:
1. M[tid] = tid;
2. x = M[tid];
3. M[x] = ...;
Static analyses like FaialAA cannot track the concrete value of x at line 2 and model it as non-
deterministic. Subsequently, line 3 is reported as a (spurious) data race. Since we use symbolic
evaluation, we don’t generate a report and declare the write in line 3 correctly as data race free.
FaialAA evaluates on GitHub commits that fix data races. These programs come from well-used
open source repositories OpenMM12 and NVIDIA’s MegaTron13. Empirically, on the programs
where FaialAA successfully detects data races, Volta succeeds as well, i.e., the data races are caught
by the symbolic evaluation. The details of these programs are shown in Table 6 for completeness.

Related Work
Prior work on equivalence checking does not support GPU parallelism or synchronization [6, 13,
23, 28, 39, 43, 44, 54–56, 58, 59, 61]. Alive [40] symbolically evaluates straight-line single-threaded
programs over bit-vectors to generate decision problems for equivalence checking that can be
handed over to SMT solvers. Volta can be seen as generalizing this mechanism to many threads
running in parallel that synchronize with each other to perform computations over the reals.
Treating floating point operations as uninterpreted functions renders standard GPU optimizations
unsound [4, 16], while fully modeling IEEE-754 semantics is known to cause equivalence checking
failures for such optimizations [31].
Several existing approaches bound the worst-case numerical error in floating point implementa-
tions [20, 29, 30, 51, 60]. However, the worst-case errors when arithmetic operations are reordered
in tensor computations (as in GPU optimization) are huge for contrived inputs and do not provide
useful insights. For ensuring memory safety in floating point programs, enforcing non-interference
between floating point and non-floating point values has proven useful [22].
During its operation, the equivalence checker also establishes well-synchronization, guaranteeing
both deadlock freedom and the absence of data races. There is a rich body of work that focuses
exclusively on data race detection in GPU programs. Traditional data race analyses consider only
where memory accesses occur, ignoring what data is being accessed, whereas an equivalence
checker must reason about both. FaialAA [38] represents the state of the art in sound data race
freedom checking, but, like most prior work, supports only basic synchronization primitives
such as syncthreads and does not support syncwarp. A notable exception is Weft [57], which
addresses producer-consumer synchronization that lies outside the scope of our work. Volta
achieves higher precision than FaialAA; for example, it does not report the spurious data race
identified by FaialAA in its Alarm 4, Figure 1 [38] (Section 6.4). However, FaialAA provides sound
analysis for GPU kernels beyond structured-CTAs. Other approaches either suffer from exponential
blowup [35, 37], fail to detect certain data races [21, 25, 26, 36, 52, 53, 66, 68, 69], or exhibit high
false positive rates [9, 27]. Several analyses rely on reductions [7, 14, 15, 33, 34, 38] that are sound
only when the synchronization primitive is a barrier across all threads. In these methods, the kernel
analysis can be partitioned into barrier intervals, defined as code segments between two consecutive
executions of syncthreads. However, in the presence of syncwarp and tensor core operations,
which synchronize only subsets of threads, the barrier interval assumption no longer holds. Finally,
test amplification [32] can be seen as a special case of Volta’s data race checking, where all threads
run identical commands and synchronize exclusively with barriers across all threads.

Conclusion and future work
We have presented Volta, the first equivalence checker for GPU ML kernels. We formally prove
that Volta is sound and complete for structured-CTAs. Volta scales to realistic ML benchmarks. In
