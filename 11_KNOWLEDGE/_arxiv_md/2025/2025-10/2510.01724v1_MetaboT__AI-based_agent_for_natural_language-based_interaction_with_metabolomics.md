Abstract
Mass spectrometry metabolomics generates complex data that overwhelms traditional analysis
approaches. MetaboT, a multi-agent Large Language Model (LLM)-based framework, converts natural-
language questions into needed SPARQL queries, enabling effective knowledge graph navigation
(https://holobiomicslab.github.io/MetaboT/). We validate MetaboT’s performance on a large plant
dataset with 50 representative queries. MetaboT's modular design facilitates advanced data mining,
biological interpretation, and the discovery of novel compounds without specialized programming
expertise.
Introduction
Contemporary mass spectrometry-based metabolomics approaches generate unprecedented volumes
of spectral data that are becoming increasingly challenging to process manually, creating a significant
bottleneck in the discovery pipeline for life and environmental sciences. Laboratories are producing more
data than can be feasibly annotated by experts, thereby slowing the pace of discovery for molecular
interactions, metabolic pathways, and novel drug candidates1. Over the past decade, the community has
developed several open-source frameworks that streamline spectral data processing and annotation2–5,
yet the considerable complexity and volume of metabolomics data necessitates advanced expertise in
statistical analysis, programming, data science, engineering, and visualisation, ultimately constraining
researchers' ability to extract deeper biological insights6.
Over the past decade, molecular networking has democratized mass spectra exploration—enabling
researchers from diverse backgrounds to intuitively map structural relationships among metabolites
through graph‑based comparison of their fragmentation spectra.3 More recently, knowledge graphs have
emerged as the next frontier in the field—semantically integrating metabolites, pathways and biological
entities into an interoperable framework7–9. These graphs rely on domain-specific ontologies that
provide standardised vocabularies, including concepts and relation hierarchies, essential for consistent
data integration and interpretation across different experimental platforms. Despite their potential, both
knowledge graphs and their underlying ontologies remain underutilised due to the steep learning curve
associated with representation languages like Resource Description Framework (RDF) and query
languages like SPARQL, as well as the complexity of mastering domain-specific ontological frameworks.
These technical barriers require an in-depth understanding of the data graph model, its query syntax, and
the underlying schema that defines its structure, constraints, and semantics—significantly limiting
accessibility for many researchers10,11. Although recent advances in generative AI using Large Language
Models (LLMs) have shown promising results in automating SPARQL query generation10,12–14 and in
enabling knowledge graph creation through tools like BioCypher15, LLMs still suffer from critical
limitations. In particular, they are prone to hallucinations, where models generate incorrect identifiers or
properties, leading to errors in query construction14. Furthermore, LLMs’ performance is heavily
dependent on access to detailed, substantial schema information and precise entity identifiers, which

has so far limited their standalone applicability in complex metabolomics contexts. While supplementing
LLMs with tools—such as retrieval‑augmented generation (RAG) pipelines, schema parsers, specialized
entity‑resolution modules, or integrated frameworks like BioChatter and ExpasyGPT13,16, can reduce LLM
dependency on schema details, these approaches still demand complex, schema-specific integration
and may face challenges, such as occasional hallucination of entity identifiers due to limited
orchestration. Emerging evidence shows that SPARQL generation improves with chain-of-thought
prompting17, and role-based specialized-agent orchestration18.
To overcome these hurdles—and harness the power of chain-of-thought prompting and role-based agent
orchestration—we created MetaboT, a multi-agent LLM framework that decomposes complex
metabolomics knowledge graph queries into discrete subtasks, routes each to a specialist agent, and
thereby delivers precise entity resolution, schema-aware SPARQL generation, and markedly fewer
hallucinations than single-LLM baselines. MetaboT enables researchers to query a metabolomics
knowledge graph through an intuitive conversational interface (Fig. 1a). MetaboT resolves entity
identifiers through orchestrated resolution steps to prevent hallucinations, leverages knowledge graph
schemas, and translates natural-language questions into SPARQL queries adapted to the specific
schema of the knowledge graph.
The architecture of MetaboT consists of a flexible pipeline that manages entity resolution, query
processing, and iterative refinement (Fig. 1b). When a user submits a natural-language question (e.g.,
"What bioactive compounds are found in Tabernaemontana coffeoides?"), the Entry Agent first
determines whether the question is new or a follow-up to previous interactions. New questions are
forwarded to the Validator Agent, a single LLM prompted with relevant details of the knowledge graph
schema, which checks the question's scope to ensure relevance (e.g., confirming that bioactive
compounds and plant species are valid entity types in the schema). For plant-specific questions, the
PlantDatabaseChecker Tool confirms the presence of the plant in a curated database (e.g., verifying that
“Tabernaemontana coffeoides” exists in the plant database).
Then, for questions requiring chemical conversions or standardised identifiers, the Supervisor Agent
delegates tasks to the KG (knowledge graph) Agent. In our demonstration, we used the Experimental
Natural Products Knowledge Graph (ENPKG)9, a comprehensive semantic graph that integrates mass
spectrometry data with taxonomic information, chemical structures, and biological activities of natural
products from plant sources. To use this knowledge graph, the KG Agent first extracts entities mentioned
in the user's question and resolves them to their Internationalised Resource Identifiers (IRIs) or
molecular representations. To do so, the KG Agent queries specialized databases (like Wikidata19 for
taxonomy or ChEMBL20 for biological targets) by calling specialized tools—including ChemicalResolver,
SMILESResolver, TargetResolver, and TaxonResolver. For example, when "Tabernaemontana coffeoides"
is mentioned, the TaxonResolver tool is called by KG Agent to retrieve its Wikidata IRI, while for chemical
classes like "flavonoids" the ChemicalResolver tool retrieves the appropriate chemical class (NPCClass)
IRI. Similarly, when a SMILES string, such as "C1 = CC = C2C(= C1)C = CN2" is provided, the

SMILESResolver converts it to a standardized InChIKey, and when a biological target like
"acetylcholinesterase" is referenced, the TargetResolver obtains its IRI from ChEMBL20, a comprehensive
database of bioactive molecules. These tools leverage either external application programming
interfaces (APIs) or carry out retrieval augmented generation (RAG) on local documents, significantly
reducing hallucinations by accurately resolving each entity and relation type against authoritative
sources. Finally, the KG Agent verifies the returned matches against contextual information and selects
the correct standardized identifiers.
Once entities and knowledge graph schema details are collated, the SPARQL Query Runner Agent
contextualizes the user's question with aligned identifiers and schema information to build a rich,
structured prompt for the GraphSparqlQAChain tool. This tool leverages an API call to an LLM to
generate a SPARQL query from the prompt, executes it on the knowledge graph endpoint, and retrieves
the corresponding answer. A particularly noteworthy aspect of MetaboT is its ability to distinguish
between query construction errors and genuine data absence when no results are returned,
implementing an iterative refinement loop that reduces manual debugging and enhances user
confidence. For detected errors, the system automatically reformulates the query by adjusting
predicates, relaxing constraints, or correcting entity references, then re-executes it. If this second query
attempt also returns no results, the system concludes the process and informs the user that the
requested data does not appear to exist in the knowledge graph.
Figure 2 presents two representative interactions; we further illustrate the full process with the following
question: “Which lab extracts have bioassay results with inhibition percentages above 50% against
Leishmania donovani?” Upon submission, this question is first classified by the Entry Agent and
validated by the Validator Agent to confirm its relevance to the knowledge graph schema. The Supervisor
Agent identifies that the question includes a biological target—Leishmania donovani—which requires
resolution into a standardized identifier. To accomplish this, the Supervisor Agent invokes the KG Agent,
which uses the TargetResolver tool to retrieve the corresponding ChEMBL target IRI. The resolved IRI,
along with the original question and schema information, is then passed to the SPARQL Query Runner
Agent. This agent leverages the GraphSparqlQAChain tool to construct and execute a SPARQL query
against the ENPKG endpoint. The final results, representing lab extracts that meet the specified criteria,
are retrieved and stored in CSV format. If further interpretation of the results is needed, the Supervisor
Agent calls the Interpreter Agent, which opens the CSV file with the results and summarizes the output
or provides visualizations, such as a bar chart or diagram. This example highlights the coordinated
functioning of the agents and tools in transforming a high-level natural-language query into a precise
semantic search over the knowledge graph.
We evaluated MetaboT to measure the accuracy of the SPARQL generation task, and identify limitations.
Our assessment used 50 representative questions available at https://zenodo.org/records/15236256
crafted to span multiple ontology classes within ENPKG, each question being paired with a reference,
manually crafted SPARQL query. Three configurations were compared: GPT-4o in a single-shot mode
without orchestration, a multi-agent system using GPT-4o mini, and a multi-agent system using GPT-4o.

The results demonstrated that while GPT-4o operating in isolation struggled with complex queries
(8.16% accuracy), GPT-4o mini, when integrated into the multi-agent framework, achieved an accuracy of
12.24%. In contrast, GPT-4o's integration into the multi-agent framework yielded a significantly higher
accuracy of 83.67%. This synergistic effect confirms that our multi-agent architecture successfully
mitigates the limitations of standalone LLMs for metabolomics knowledge graph exploration. Moreover,
the substantial performance gap between GPT-4o mini and GPT-4o within the same architecture
highlights the importance of model capacity for tasks requiring precise semantic understanding and
structured output generation.
MetaboT is accessible via a web application, deliberately designed to prioritize usability for researchers.
It captures natural-language questions and displays results, while the processing is managed by the
backend LLM multi-agent framework. Current features—including file uploads, visualizations, and the
SpectrumPlotter module that integrates Metabolomics USIs21 by constructing a URL to render spectrum
plots22—are implemented as proofs-of-concept that demonstrate the system’s extensibility toward other
functionalities. Outputs are presented as concise summaries that can be supplemented with optional
plots for visual interpretation of complex datasets. MetaboT’s design ensures accessibility for
researchers without extensive computer science expertise while providing robust data querying
capabilities through its interactive query interface, automated SPARQL generation, and built-in error
handling.
A critical strength of MetaboT lies in its scalability and adaptability. Although our current demonstration
focuses on ENPKG, the modular design supports straightforward extension to other mass spectrometry-
based knowledge graphs with minimal reconfiguration. Additionally, the system can interface with
different LLM models, which is beneficial given the rapidly evolving LLM landscape. As models advance,
the multi-agent architecture allows for seamless integration of new capabilities without requiring
extensive modifications, translating directly into improved query precision and reduced processing
times23,24.
Despite these promising results, several limitations remain. In its current state, MetaboT requires high-
performance LLMs for optimal accuracy in complex cases, as demonstrated by questions 17, 20, and 48
in our evaluation—complex queries involving multiple entity types and relationship constraints—where
GPT-4o significantly outperformed smaller models. While LLM costs are decreasing as performance
improves, this expense still presents an adoption barrier for some research communities14. Additionally,
our agent prompts were developed for specific LLM models and may require adaptation to function
properly with other models. We postulate that overall efficiency and cost-effectiveness could be
improved by implementing a hybrid approach that combines multiple models with varying capabilities
alongside automated prompt optimisation strategies.
A notable limitation is MetaboT's restriction to single-graph querying. Currently, researchers must
manually connect knowledge graph data with external resources (e.g. subsets of ChEMBL20, Wikidata19
and LOTUS25), as the system cannot generate federated SPARQL queries that would simultaneously

retrieve information from multiple knowledge graphs. While this is addressed through the incorporation
of critical external data directly into the ENPKG knowledge graph employed here, developing true

Building upon these foundations, a dedicated federated-query module could then execute SERVICE

relationships among metabolites, pathways, and phenotypes while leveraging MetaboT's modular
architecture.
Looking ahead, we envision MetaboT evolving into a comprehensive toolbox for mass spectrometry data
analysis by integrating agents and specialized components for commonly used computational
metabolomics approaches. Future developments will focus on automated benchmarking, expanded
interoperability with metabolomics tools, and integrating emerging AI capabilities for cheminformatics
and biomedical hypothesis generation.16,27 The framework empowers domain scientists to analyze
complex spectral datasets without extensive computer science expertise, bridging the gap between
specialized SPARQL query writing and intuitive conversational interactions. By streamlining data
querying and analysis through natural language interaction, MetaboT can accelerate metabolomics
discoveries—enabling a broader research community to uncover patterns, generate evidence-based
hypotheses, and advance from spectral data to chemical and biological insight.
Online Methods
Schema and IRI Provision
To accurately generate SPARQL queries from natural language inputs, the LLM needs to be provided with
the specific ontology schema and IRIs pertinent to the knowledge graph, as the schema defines the
relationships between the nodes1 and IRIs uniquely identify the entities and properties used in querying2.
Since LLMs are trained on broad datasets that may not include these specific IRIs, the models may lack
specific identifiers required for the entities mentioned in user queries3,4. Furthermore, even when relevant
IRIs are present in the training data, LLMs are not guaranteed to retrieve them correctly or incorporate
them appropriately into SPARQL queries, limiting their effectiveness for precise identifier-based tasks.
Consequently, these IRIs must be supplied externally to the LLM alongside the ontology schema to
ensure the correct construction of the SPARQL query. This requires dedicated tools and agents within
the system that can provide the appropriate IRIs, enabling the LLM to incorporate them accurately into
the generated SPARQL query. This approach is supported by the findings of Meyer et al.3 and Avila et al.5
who demonstrated that providing LLMs with explicit schema information and IRIs significantly enhances

the accuracy and reliability of SPARQL query generation. Therefore, integrating mechanisms to supply
schema and IRI information to the LLM is crucial for the optimal performance of a system like MetaboT.
System Architecture
MetaboT employs a multi-agent architecture that systematically decomposes complex tasks into
discrete subtasks managed by specialised agents (Extended Data Fig. 1). The system is constructed
using the LangChain6 (version 0.1.11) and LangGraph7 (version 0.0.26) libraries, which facilitate the
integration of LLMs with external tools and resources. LangChain provides a flexible framework for
developing LLM-based applications, incorporating essential components such as:
LLM: Models underpinning the core processing capabilities, including translating natural language
queries into SPARQL.
Prompts: Instructions guiding LLMs to achieve targeted outcomes.
Chains: Integrations of prompts and LLMs to produce coherent outputs.
Agents: Units combining LLM chains with tools, where LLMs act as reasoning engines to determine
appropriate actions.
LangGraph builds on LangChain to structure the workflow as a directed graph, where each node
represents a discrete computational step and edges represent message passing between agents. This
stateful graph enables dynamic state evolution as each agent completes its task, allowing for adaptive
interactions throughout the query processing pipeline.
Each agent in MetaboT's workflow is represented as a tuple Ai=(Li,Pi,Ti)8, where:
Li is the language model guiding the agent's decision-making.
Pi is the prompt customised for the agent's purpose.
Ti is the specific function or tool the agent utilises to fulfil its task.
The system was developed and tested using OpenAI's9 GPT-4o model, with GPT-4o mini employed for
comparative evaluation. All code and configuration files are available at
https://github.com/HolobiomicsLab/MetaboT/.
Agent Framework
MetaboT implements six primary agents with distinct roles in processing user queries. Each agent is
designed to address specific challenges in translating natural language questions into SPARQL queries:
Entry Agent

Tools Integration
MetaboT employs nine specialised tools for entity resolution and query processing, each addressing
specific challenges in knowledge graph interrogation:
1. PlantDatabaseChecker
Objective: Verify the presence of plant names within a pre-existing database to filter queries based on
data availability.
Input: Plant name string provided by user query.
Process: Loads a CSV file containing plant names considered in the ENPKG analysis and searches for
exact matches of the input name in the designated column.
Output: Returns confirmation of the plant's presence or absence, with appropriate error handling for file
access issues.
2. ChemicalResolver


## Page 13


Page 13/29
Objective: Resolve chemical names to standardised chemical class identifiers (NPCClass URIs).
Input: Chemical name string extracted from user query.
Process : Matches chemical names to NPCClass URIs using a Facebook AI Similarity Search14 (FAISS)
database with OpenAI embeddings15. This involves loading a precompiled CSV file extracted from the
knowledge graph and containing NPCClass data, processing it into searchable chunks, creating
embedding vectors, and generating a retriever object.
Output: Returns NPCClass URI with type information.
3. SMILESResolver
Objective: Convert SMILES (Simplified Molecular Input Line Entry System)16 molecular representations to
standardised InChIKeys17 for chemical interoperability.
Input: SMILES string representing molecular structure.
Process: Sends SMILES strings to the Global Natural Products Social Molecular Networking (GNPS) API
to retrieve corresponding InChIKeys.
Output: Returns standardised InChIKey with logging of process status.
Error Handling: Implements robust logging for API request issues and exception handling for system
notification.
4. TargetResolver
Objective: Map biological target names to standardised ChEMBL Target IRIs12.
Input: Biological target name string.
Process: Queries the ChEMBL API to locate matches based on target names, parsing XML responses to
extract and format ChEMBL target IDs as IRIs.
Output: Returns formatted ChEMBL Target IRI for the biological target.
Error Handling: Provides logging for successful and unsuccessful API calls, with suggestions for refining
target names when no matches are found.
5. TaxonResolver
Objective: Resolve taxonomic names to their corresponding Wikidata IRIs.


## Page 14


Page 14/29
Input: Taxonomic name string.
Process: Constructs and executes SPARQL queries on the Wikidata endpoint to retrieve unique IRIs
associated with taxon names.
Output: Returns Wikidata IRI for the taxonomic entity.
Error Management: Implements robust error handling for unexpected formats and connectivity issues,
with clear logging of outcomes.
6. FileAnalyzer
Objective: Analyse user-provided files and generate content summaries.
Input: User-uploaded files and session identifier.
Process: Initialises session-specific directories, identifies file types, and applies tailored analysis
methods:
For spreadsheets: Extracts rows, columns, headers, and sample data using pandas18
For MGF files: Counts the number of spectra feature IDs
For text files: Provides line counts for identifying the number of features present.
Output: Produces structured summaries with file paths, sizes, and content-specific details for
downstream processing.
7. GraphSparqlQAChain
Objective: Generate and execute SPARQL queries aligned with the knowledge graph's schema.
Input: User question, schema information in Turtle19 format, and resolved entity identifiers.
Process - Query Generation: Uses LLMs with structured prompts combining in-context learning, chain-of-
thought reasoning20, and one-shot examples to create schema-compliant queries.
Process - Query Refinement: When initial queries yield no results, identifies schema nodes related to the
original query and leverages similar queries from a FAISS database to regenerate more accurate
commands.
Process - Result Processing: Executes queries on the knowledge graph endpoint and saves outputs to
temporary CSV files.
Output: Returns query results with contextual information and file paths for downstream processing.

Error Handling: Removes extraneous elements from generated queries and ensures compliance with the
knowledge graph's schema. Manages token limits and optimises results for the LLM's context window.
8. WikidataStructureSearch
Objective: Retrieve compound annotations associated with a taxon (e.g., plant genus) using its Wikidata
ID.
Input: A string representing the Wikidata ID of a taxon.
Process: Constructs and executes a SPARQL query on the Wikidata endpoint to retrieve the Wikidata IRIs
of chemical compounds annotated to species within the genus of the given taxon. The results are saved
in a temporary CSV file.
Output: Path to a CSV file containing the list of compound Wikidata IRIs, or None if no results are found.
9. OutputMerger
Objective: Identify overlapping Wikidata compound annotations between results from two different
SPARQL endpoints.

SPARQL Query Generation and Execution
The GraphSparqlQAChain tool implements a sophisticated process for translating natural language
questions into executable SPARQL queries:
Initial Query Generation: The tool combines the user's question with schema information (in Turtle
format) and resolved entity identifiers to generate a SPARQL SELECT query25. For example, a user
question about "bioactive compounds in Tabernaemontana coffeoides" would be combined with the
Wikidata IRI for Tabernaemontana coffeoides (Q15376858) and schema properties to construct a query.
The generation prompt ensures adherence to content clarity, proper prefix usage, schema alignment, and
validation requirements. By combining in-context learning, chain-of-thought prompting, and one-shot
examples, the prompt guides the LLM to produce well-structured, syntactically correct queries.
Query Execution and Result Analysis: Generated queries are executed on the knowledge graph endpoint,
with results analysed for completeness and relevance. If a query yields no results or errors, the tool
initiates a refinement process.
Query Refinement: For unsuccessful queries, the tool identifies schema nodes related to the initial query
and retrieves one similar query from a stored database. Using these insights, it prompts the LLM to
regenerate a more accurate, schema-compliant query. This refinement is performed only once, guided by
concise schema information, step-by-step reasoning, and validation criteria.
Result Processing: Successfully executed query results are saved to a temporary CSV file for
downstream analysis. Token usage is monitored to ensure compatibility with the LLM's context window,
with results truncated if necessary. If the combined tokens from the generated SPARQL query, the user's


## Page 17


Page 17/29
question, and the output from the knowledge graph exceed a specified limit (6000 tokens), the full
results are not passed to the LLM; instead, users can retrieve the complete output from the generated
CSV file.
An important component of the refinement workflow is the tool’s ability to distinguish between errors in
query construction and the actual absence of relevant data in the knowledge graph. For example, if a
query about "terpenes in Tabernaemontana coffeoides" returns no results, the system first assesses
whether the query might be improperly constructed. It then attempts to regenerate the query—if the
regenerated query yields results, this confirms that the initial failure was due to construction errors.
However, if the regenerated query still fails, this may either indicate that the knowledge graph truly lacks
data on the topic or that errors persist in the query formulation. This distinction enables targeted
refinement strategies that enhance overall system reliability.
Interaction Between Agents
Agent interaction is orchestrated through a directed graph structure (Extended Data Fig. 2), with
messages passing along edges from one agent to the next. The output of each agent becomes the input
for subsequent agents, enabling seamless information flow and decision-making throughout the system.
For instance, after the Entry Agent determines a query's nature, it passes relevant data to the Validator
Agent via their connecting edge.
This structured communication ensures that each agent operates with the most current and relevant
information, enhancing system efficiency and accuracy. To monitor and analyse these interactions
during development and evaluation, we utilised LangSmith26 (version 0.1.22), a platform for developing,
testing, and evaluating LLM-based applications. Through LangSmith, we systematically evaluated each
agent's performance, tracked interactions, and identified refinement opportunities within the multi-agent
system.
Evaluation Procedure
Assessing MetaboT's performance presented unique challenges due to its capacity to handle diverse
and complex tasks. We implemented an automated evaluation process using LangSmith's evaluation
workflow27, with LLM-based evaluators assessing outputs against criteria including correctness,
accuracy, and SPARQL query similarity to reference standards. In addition to these automated
evaluators, we conducted manual evaluations to validate the performance of the LLM evaluators,
acknowledging that they can occasionally hallucinate28.
For comprehensive MetaboT evaluation, we created a synthetic dataset comprising 50 questions across
different ontology classes within ENPKG, each paired with a reference SPARQL query. The questions
were crafted with the help of domain experts, considering the classes and properties present in the


## Page 18


Page 18/29
schema of the knowledge graph. These questions were then submitted to MetaboT, which generated
initial SPARQL queries. We manually reviewed and corrected these queries based on the knowledge
graph schema to ensure semantic correctness and full alignment with the intent of each question.
These questions were categorised by complexity:
Low complexity (11 questions): Simple entity retrieval (e.g., "List all compounds found in Lovoa
trichilioides")
Medium complexity (19 questions): Multi-step operations (e.g., "Find all plant species containing
flavonoids with molecular weight > 300")
High complexity (20 questions): Complex relationships and filtering (e.g., "Which compounds in Acer
species have been reported to interact with human kinase targets and show molecular similarity
(cosine score) > 0.7 to known anti-inflammatory compounds?")
We first conducted a baseline evaluation to determine whether GPT-4o alone, without the multi-agent
system, could generate accurate SPARQL queries. Questions were submitted directly to GPT-4o
alongside the schema in Turtle format, using a prompt analogous to that of the Query Generation chain
from GraphSPARQLQAChain. Results showed that standalone GPT-4o produced inaccurate queries with
property mismatches and incorrect entity identifiers, highlighting the necessity for our structured multi-
agent approach.
Building on this baseline, we evaluated three configurations to compare standalone performance with
the multi-agent system, and to assess the effect of different underlying LLMs:
1. GPT-4o in a single-shot mode without orchestration
2. MetaboT using GPT-4o mini as the underlying LLM
3. MetaboT using GPT-4o within the full multi-agent framework
The evaluation setup isolated individual components to identify performance bottlenecks. Each
configuration processed identical queries under controlled conditions, with consistent hardware and
network environments to ensure comparable results. It is important to note that this evaluation was
performed only up to the point of SPARQL query generation; it did not include the Interpreter Agent, and
therefore, the interpretation of query results was not evaluated. The goal was to ensure that all
components leading to the generation of SPARQL queries were functioning correctly.
Average query processing time was 10.04 seconds for the single-shot GPT-4o approach, 36.28 seconds
for the GPT-4o mini configuration, and 80.45 seconds for the GPT-4o multi-agent system. For the single-
shot GPT-4o approach, processing time was measured from the moment the prompt was submitted until
the SPARQL query was generated. For the GPT-4o mini configuration, the average time was computed
only for those questions in which all agents were invoked; in many cases, the Validator Agent
hallucinated, halting the workflow before it reached the SPARQL Query Runner Agent. Finally, for


## Page 19


Page 19/29
MetaboT using GPT-4o within the multi-agent system, the processing time was measured for all
questions, from initial submission until the final agent completed its task.
Our LLM-based evaluators compared system-generated outputs with reference outputs, providing
detailed feedback on discrepancies. This evaluation process occurred iteratively across three rounds,
with prompt refinements between rounds addressing identified issues. In addition to evaluator feedback,
a manual evaluation was performed to further assess the outputs, considering the potential for LLMs to
hallucinate.
For 3 out of the 50 questions, the SPARQL refinement chain regenerated queries by using formulations
identical to the correct reference queries for those questions; however, this approach proved beneficial
for only 1 question, and consequently, that question was removed from the overall accuracy count. In the
other 2 cases, the core issue was that the Supervisor did not invoke the KG agent to retrieve the
necessary entities.
The results (Supplementary Table 1) demonstrated that while GPT-4o operating in isolation struggled
with complex queries (achieving only 8.16% overall accuracy), its integration into the multi-agent
framework achieved an 83.67% accuracy rate—a substantial improvement over both the standalone
model and the GPT-4o mini-based system (12.24% accuracy). This performance difference was
particularly pronounced for high-complexity queries, where the multi-agent GPT-4o configuration
maintained 78.95% accuracy while the standalone GPT-4o failed completely (0% accuracy). Interestingly,
the GPT-4o mini-based MetaboT system performed better on high-complexity questions than on low-
complexity ones. This counterintuitive result likely stems from the fact that low-complexity questions
often omit explicit entity mentions, making them harder for the Validator Agent—powered by a weaker
LLM—to validate.
Error analysis revealed four primary error types:
Type 1 –Validator misclassifying questions as invalid (e.g., rejecting valid queries about plant
metabolites)
Type 2 –Incorrect SPARQL queries generated (e.g., using incompatible properties or malformed syntax)
Type 3 – Supervisor failing to call the Knowledge Graph agent when needed (e.g., for queries requiring
entity resolution)
Type 4 – Knowledge Graph agent selecting inappropriate tools (e.g., using TaxonResolver for chemical
entities)
These findings informed subsequent system refinements and highlighted the synergistic benefits of our
multi-agent architecture for metabolomics knowledge graph exploration.

Limitations and Future Directions
Despite its effectiveness, MetaboT exhibits several limitations that warrant acknowledgement:
Hallucinations: LLMs occasionally generate incorrect objects or properties, leading to errors in query
construction. For instance, the model might confuse properties of "InChIKey" with "InChIKey2D" or apply
properties to incompatible classes. These hallucinations can also cause agents to invoke inappropriate
tools, such as using TaxonResolver for queries about biological targets.
Non-determinism: The inherent variability in LLM outputs means that identical queries may yield slightly
different SPARQL commands, potentially reducing user confidence. While this variability occasionally
benefits exploration, it can create inconsistency in system performance.
Computational Cost: MetaboT's multi-agent architecture requires multiple LLM API calls for each user
question, resulting in corresponding computational expenses. A typical query incurs 5-8 API calls
depending on complexity. Additionally, providing detailed schema information and examples in prompts
increases token counts and overall operational costs. On average, each complete query processing cycle
consumes approximately 22,240tokens (including both prompt and completion tokens), translating to an
average cost of $0.06 per question. The maximum cost observed was $0.092, corresponding to a high-
complexity question, while the minimum cost was $0.041, corresponding to a low-complexity question.
To mitigate these issues, MetaboT incorporates deterministic functions as tools, reducing reliance on
the language model alone and enhancing accuracy. Extensive prompt engineering guides LLMs toward
more consistent and contextually accurate outputs. By refining prompts and incorporating stable,


## Page 21


Page 21/29
reliable functions, MetaboT aims to minimise the effects of hallucinations, non-determinism, and token-
related costs.

with complementary metabolomics tools to create a comprehensive ecosystem for mass spectrometry
