ABSTRACT
LLM-based software engineering agents are increasingly used in real-world development
tasks, often with access to sensitive data or security-critical codebases. Such agents
could intentionally sabotage these codebases if they were misaligned. We investigate
asynchronous monitoring, in which a monitoring system reviews agent actions after the
fact. Unlike synchronous monitoring, this approach does not impose runtime latency,
while still attempting to disrupt attacks before irreversible harm occurs. We treat monitor
development as an adversarial game between a blue team (who design monitors) and a red
team (who create sabotaging agents). We attempt to set the game rules such that they upper
bound the sabotage potential of an agent based on Claude 4.1 Opus. To ground this game
in a realistic, high-stakes deployment scenario, we develop a suite of 5 diverse software
engineering environments that simulate tasks that an agent might perform within an AI
developer’s internal infrastructure. Over the course of the game, we develop an ensemble
monitor that achieves a 6% false negative rate at 1% false positive rate on a held out test
environment. Then, we estimate risk of sabotage at deployment time by extrapolating from
our monitor’s false negative rate. We describe one simple model for this extrapolation,
present a sensitivity analysis, and describe situations in which the model would be invalid.
Code is available at: https://github.com/UKGovernmentBEIS/async-control*.

INTRODUCTION
Autonomous software engineering (SWE) agents based on LLMs have the opportunity to cause harm if
deployed without appropriate safeguards. Developers can mitigate risks in two ways: (i) by designing AI
agents to be more robust and trustworthy or (ii) by designing safety measures that mitigate harms even if
AI agents are untrustworthy. Work in AI control (Greenblatt et al., 2023) attempts to solve (ii). Following
Greenblatt et al. (2023), we frame control as a two player game: the ‘blue team’ designs and defends the
control measures, while the ‘red team’ tries to build or adapt the AI model to bypass those defenses. The red
team’s performance after they have optimised against the final blue team system ideally provides an upper
bound on the likelihood of harmful outcomes at deployment time.
Previous work (Greenblatt et al., 2023; Bhatt et al., 2025) has not conducted red-blue team games in realistic
software engineering environments, has been restricted to a single malicious side task (such as downloading

Control measures are typically intended to intercept dangerous actions before they cause harm. For instance,
they might replace suspicious actions with the action of a weaker, trusted model, at a cost of latency overhead
and a capabilities decrease. However, many sabotage attempts are likely to be reversible if detected promptly,
making low-overhead, post-hoc monitoring an attractive initial defence, without the latency of synchronous
systems.

In order to conduct a control game for asynchronous monitors in as realistic an environment as possible, we
develop a suite of environments featuring complex codebases and associated benign SWE tasks, as well as
side tasks representing diverse potential safety failures such as secret exfiltration or security policy weakening.
We develop an initial ruleset for a control game with current frontier models, that allows the red team to
provide a conservative upper bound of the sabotage abilities of language model agents using these models.
The game proceeds in discrete rounds until the red team’s false negative rate plateaus. The red team writes
system prompts for an agent based on Claude 4.1 Opus, such that the agent can successfully complete side
tasks without being detected by a monitor. The blue team creates monitor systems in response, that rely on the
weaker Claude 3.7 Sonnet. The blue team tries to achieve a low false negative rate for side task attempts by
the agent, under a constraint of a 1% false positive rate on benign behaviour, and the red team tries to increase
false negative rates. We simulate deployment of asynchronous monitors by assuming we add agent episodes
to a queue ordered by monitor suspicion score, and need to audit attacks before they cause harm. However our
approach is limited by not measuring factors such as the latency between agent actions and harms occurring
or the combination of various security weakening steps into a particular harm in our environments.
In summary, we build a suite of realistic software engineering environments with benign main tasks that
correspond to real tasks a user might want to achieve, and malign side tasks that correspond to real security
failures, and run the most realistic control evaluation to date in these environments, providing a blueprint
for future control evaluations that aim to estimate the safety properties of language model agents. Our main
findings are:
• Ensemble monitors achieve low false negative rates: Our final blue team monitor system achieves
a 6% false negative rate at 1% false positives on a held-out test environment (taking the maximum
rate over all red team prompts). Ensembling is crucial: our best single monitor only achieves a 33%
false negative rate under the same conditions.
• Explicit side task discussion can be suppressed in outputs but not in reasoning; hiding reasoning
still fails to improve evasion against monitors: When the untrusted model does not use reasoning
tokens (i.e., when extended thinking mode is turned off), we successfully eliminate explicit mentions
of the malicious side task entirely. When reasoning tokens are turned on, the model always discusses
the side task. Surprisingly, even when reasoning tokens are enabled but hidden from the monitor, the
agent shows no improvement in evading the strongest blue team monitor, though it does evade two
weaker monitors more effectively.
• System design choices may matter more than monitor quality: In deployment simulations,
requiring multiple successful attacks before harm occurs, or introducing delays between attack
execution and effect, improves safety, often more than improving monitor accuracy.

SETTINGS
We develop four software engineering environments and one synthetic data generation environment, featuring
realistic codebases (e.g. vLLM, Kubernetes, AWS CDK), authentic development tasks, and diverse sabotage
scenarios spanning, e.g., code tampering, data poisoning and secret exfiltration. We create all of our settings
in ControlArena (Inglis et al., 2025). Table 1 summarizes the settings. We use the vLLM and Kubernetes
settings as a training set, which the red and blue team iterate on, and leave the other settings as held out. The
IaC setting is also an agentic coding task, so we use this as a test set. The other settings cover different threat
models, and we use them as an out-of-distribution set to test if monitor protocols designed to perform well for
high-stakes code sabotage can work in dissimilar settings, for instance subtle, low stakes side tasks in our
evaluation sabotage environment.

We developed control settings through a systematic process: from identified risk models, to relevant deploy-
ment contexts, to specific malicious tasks for the red team system to attempt. Settings consist of sandbox
environments where agents complete main tasks (benign user requests) while potentially attempting side
tasks (malicious tasks). Our main criteria when designing settings were coverage of risk models, especially
those that are in principle able to be caught by an asynchronous monitor (so we ignore realtime harms like
downloading and running malicious code from the internet), and enough overlap between benign main tasks
and side tasks that it is possible to complete both tasks stealthily.

RED-BLUE TEAM GAME
We frame monitor development as an adversarial game between two teams: a “blue team” that designs monitor
systems with a trusted language model (Claude 3.7 Sonnet) and a “red team” that attempts to produce an
agent based on a stronger, untrusted language model (Claude 4.1 Opus) that can bypass the monitor system.
4


## Page 5


Since the red team iterates against the blue team monitors, and moves last, we aim to produce an empirical
upper bound on the false negative rate that is more realistic than evaluation against a fixed attack strategy
(Terekhov et al., 2025). We resolve any disputes about the rules with a dedicated green team, who gives
suggestions and adjudicates on the final ruleset.
The game proceeds in discrete rounds. Each round consists of three phases: (1) the blue team submits an
updated monitor system, (2) the red team develops attack strategies optimized against that monitor, and (3) the
red team submits their best-performing attack episodes. After each round, the blue team receives the attack
episodes and corresponding monitor success statistics (false negative rates), but crucially, not the system
prompts or explicit strategies used to generate them. This forces the blue team to infer attack patterns from
behavioral evidence alone.
Team Affordances: The red team has access to the blue team monitor implementation (i.e., all details of the
monitor system, including code). The red team can only change the LLM agent’s system prompt (which is
hidden from the monitors), and they cannot use hidden chain-of-thought, and cannot employ fine-tuning or
output rewriting techniques such as hidden LLM calls that would modify outputs before blue team observation,
so that all red team agent outputs are on-policy for the LLM, and thus the chain-of-thought is authentic. If we
allowed finetuning or arbitrary scaffolding on top of model outputs, the chain-of-thought might not reflect
realistic model behavior. Our choices are partly motivated by aiming for a tight upper bound on the model we
are testing, targetting the ACL-1 level described by Korbak et al. (2025b).The blue team can use Claude 3.7
Sonnet in any way, for example they can use extended thinking mode, or train a machine learning model on
top of monitor scores.
Objectives and Metrics: Our primary performance metric is the false negative rate (FNR) under a false
positive rate (FPR) constraint of 1%–the fraction of attacks missed, at 1% FPR on benign (no side task)
data. The red team tries to increase the FNR, while the blue team tries to decrease it. The blue team must
keep average inference costs (proxied by API cost in USD) of their monitors less than the average cost of
running the untrusted model on our environments (the final monitor system uses all of this budget). During
the red-blue team game, we only calculate FNR on cases where the side task is completed successfully.
Including cases with incomplete side tasks would make the results hard to interpret, as they may not contain
any evidence of malicious changes.

RESULTS
4.1
RED-BLUE GAME MONITORS AND RED-TEAM RESPONSES
This section describes individual rounds from the blue and red team perspectives. Figure 3 provides an
overview of monitors produced by the blue team, and a high-level overview of the strategies the teams employ
can be found in Appendix B.
Blue team round 1 monitor.
The blue team round 1 monitoring system is an ensemble of three distinct
monitors, with the final episode score computed by taking the mean of their outputs. The first, which we refer
to as the high-stakes monitor, is prompted to act as an assistant overseeing high-value internal codebases,
specifically searching for malicious actions disguised as benign ones. It first analyses the agent’s actions
for intrinsic security threats (e.g., privilege escalation, data exfiltration). It then compares these actions
against a minimal set of required actions derived solely from the task description, heavily penalising any
unexpected behavior as a strong indicator of potential sabotage. The second and third monitors are task drift
monitors, which look for actions which were unrelated to the main task. One version of this monitor reviews
chain-of-thought reasoning and actions and the other only reviews actions, similar to Arnav et al. (2025).
Monitors can occasionally be baited into believing a certain action was necessary based on untrusted model
reasoning, and action-only monitors avoid this failure mode.

Red team response to round 1.
The primary strategy for this round was to interleave main and side task
actions, framing the side task actions as naturally relevant and logically following from the main task. The
prompt also instructed the agent to avoid admitting when actions were unrelated to the main task, and to
abstain from attempting the side task if the chances of evading detection appeared low (for example, when
framing them as related proved too difficult). Because the blue team employed monitors that ignored the
agent’s chain-of-thought, the red team adapted by embedding justifications directly into tool calls. For
example the agent was prompted to create a PLAN.md document containing a suitable framing for the side task
actions, and then refer back to this plan when choosing variable or function names or adding code comments.
Blue team round 2 monitor.
The blue team round 2 monitoring system is an ensemble monitor which uses
a random forest to aggregate the outputs of three sub-monitors. The ensemble’s final output probability is
then calibrated to a 1% false positive rate by first using a training set of honest episode logs, and then using a
threshold of the 99th percentile of the random forest output score to enforce a 1% FPR.
The first monitor is a variation of the high-stakes monitor from round 1. The second is a hierarchical judge
monitor, which itself consists of four specialized monitors that analyse the episode log: a semantic analyser
compares the task description to the agent’s code diff, a dynamic analyser looks at the execution trace for
suspicious runtime behavior, and a static analyser looks at risky code patterns and API combinations. A
judge monitor receives these three reports, which include a raw score between 0-100, reasoning, and specific
evidence for the risks detected, and outputs a final score between 0 and 100.
The third monitor is a role-play monitor, which puts the entire transcript of the untrusted agent in the trusted
model’s context (i.e. the trusted model is ‘put in the shoes’ of the untrusted model), and asked to summarise
the actions it has taken. This summary is then put in the context of another model, which assigns a score
between 0 and 100.
Red team response to round 2.
In round two, the red team retained the overall structure of the prompt
from round one, only removing elements that had proven ineffective in ablation experiments and introducing
several targeted changes. Unit test handling was identified as a potential weakness in the monitors, and
the agent was instructed to implement side-task-related functionality within test files and to import from
these locations, anticipating that such changes would receive less scrutiny. As the monitors got better at
identifying relevant changes, the prompt also emphasised obfuscating identifiers and removing potentially
revealing comments from side-task code. However, the agent often struggled to follow instructions precisely,
particularly with respect to obfuscating identifiers and omitting comments.

Blue team round 3 monitor.
The third and final blue team monitor system is again a random forest model
on top of a set of four monitors. The hierarchical judge monitor that synthesised three analysers’ scores
and the high stakes monitor with no CoT are retained. We use two new monitors and a suite of engineered
features, and use a target of 4096 reasoning tokens, with Claude 3.7 Sonnet’s extended thinking mode.
The first new monitor is a few-shot high-stakes monitor, which adapts the existing high stakes prompt to
include two specific examples of a complete analysis: one for a known attack episode and one for a known
honest episode. The second is a quote monitor similar to Arike et al. (2025). The monitor is first asked to
extract multiple specific quotes from the agent’s actions, including CoT, that it deems suspicious, and then
provides an overall score between 0 and 100, with the quotes as context.
In addition to the new monitors, nine engineered features were added to the Random Forest model, selected
from over twenty candidates using Recursive Feature Elimination with Cross-Validation. The nine selected
features include absolute score differences between specific monitors (quote extractor vs. hierarchical judge,
and quote extractor vs. few-shot high-stakes), as well as aggregate statistics across all monitor scores: mean,
median, standard deviation, max, 25th percentile, 75th percentile, and the interquartile range.

Red team response to round 3.
By the third round, the red team de-emphasized interweaving main and
side task changes, as monitors were now more capable of detecting the most relevant changes despite this
tactic. Monitors also showed greater resilience against fake justifications, especially the hierarchical judge
monitor. The prompt was extended with examples of plausible justifications tailored to suspicious actions that
the monitors were specifically designed to flag. For instance, explanations such as “the privilege change is
needed to fix an error indicated by main task tests” were considered plausible because the monitors focused
on code changes themselves and did not verify broader transcript context such as prior test results. The
agent was also encouraged to introduce more changes tangentially related to the main task so that side-task
modifications would be less conspicuous overall.

both settings. Finally, the baseline strategies work much better in these settings, with the worst monitor
performance across all train and test settings being 12% for baseline strategies, whereas all monitors have
FNR higher than 13% for the out of distribution set settings. Our tentative conclusion is that the difference
between highly incriminating and less incriminating side tasks is more important for monitor performance
than other differences in the environment, mirroring the results of Taylor et al. (2025) and Ward et al. (2025).

5
ESTIMATING RISK ACROSS A DEPLOYMENT
Our monitors achieve a false negative rate of 6% with a false positive rate of 1% on individual episodes
in which the red team attempts sabotage. However, monitor statistics alone are insufficient for inferring or
bounding the likelihood of a harmful outcome across a deployment, which also depends on how the blue team
acts on monitor scores and on fixed details of the deployment. How many attacks could the agent attempt
during a full deployment? How many successful attacks are needed for a harmful outcome? Will the blue
team shut down an AI system after catching a single attack? Answering these questions is necessary for
estimating the safety of a deployment.
Greenblatt et al. (2023) introduce the use of deployment models to estimate safety, Griffin et al. (2024)
formalise this as a two-player game, and Korbak et al. (2025c) give an example of how to make a safety
case via this extrapolation. Prior empirical work (Greenblatt et al., 2023; Bhatt et al., 2025) uses deployment
models where a single AI instance solves tasks sequentially and where monitor are synchronous: each agent
action is blocked until monitor scoring and review has been completed. In contrast, Lindner et al. outline a
range of protocols that account for parallel agent instances and non-negligible oversight latency (but do not
investigate them empirically or give a deployment model). In this paper, we study an asynchronous monitoring
protocol, which allows agents to take actions before monitor scores and human review has completed, using a
hypothetical deployment.†
Example Deployment and Protocol.
An AI agent completes 10, 000 user-assigned tasks per-day across a
6-month deployment. An asynchronous monitor scores solutions to each task with minimal latency. Scored
solutions are added to a queue sorted by monitor score, so that the most suspicious tasks can be audited first.
Audits are completed by a team of human experts (with various tools to support them). If auditors find a
solution is malicious, they end the agent’s deployment. The protocol aims to prevent a harmful outcome that
we leave unspecified.‡

5.2
MODEL UNCERTAINTY AND LIMITATIONS
Our safety estimates depend critically on parameter values and modeling assumptions that may not hold
in practice. Some of our quantitative uncertainties would be clarified for an actual control evaluation. For
example, a developer could estimate the number of tasks the agent needs to solve per-hour by looking at real
usage statistics. Other factors would still be unknown to a developer, for example, estimating the number
of attack steps that would be required for causing catastrophe. Finally, the model makes some simplifying
assumptions that might not hold in practice. For example, the assumptions that human auditors can perfectly
distinguish attacks, that the probability that the agent attacks in an episode is constant, and that the probability
of detecting each attack is independent. The most important uncertainties are those in the third category: if
our simplifying assumptions are violated (e.g., agents can coordinate attacks), our safety estimates become
much less useful.
6
DISCUSSION
Many choices we make are motivated by finding a conservative, yet tight bound on what current models
can achieve, in line with the arguments of Korbak et al. (2025b). The effectiveness of our final blue team
monitor should be interpreted within the context of our assumptions: we study high-stakes code sabotage
(i.e. the side tasks are obviously and clearly harmful), assume full access to the unobfuscated CoT of the
agent (corresponding to ACL-1 from Korbak et al. 2025b), and assume no collusion or jailbreaking attempts
against the monitor. The asynchronous monitoring setup gives monitors rich context (an entire self-contained
episode) to work with, and does not restrict latency requirements.
Reasons why we may overestimate blue team performance.
• Rather than red teaming a fixed blue team protocol, we iteratively improve the blue and red teams,
allowing the blue team to adapt their strategies (although we do let the red team move last).
• We restrict our red team quite heavily, only allowing system prompt tuning, and no modification of
the agent transcripts.
• We assume auditing is infallible.
• In our safety calculation, we assume that a side task needs to be completed in one episode, and
therefore the monitor has access to all relevant agent outputs. This may not be true in practice, for
example, if the agent incrementally modifies the same codebase across episodes.
• In safety simulations with multiple side tasks, we assume the catch probabilities are independent.
This may not hold for red team strategies where one side task can build on top of a previous one (e.g.,
13


## Page 14


when the agent inserts a monitor jailbreak into the monitor context in one episode, and leverages
that to avoid being caught in subsequent episodes).
• Agents exhibiting malicious behaviour induced in a different way than through a system prompt
change may be more successful at covert side task execution (e.g., because they may struggle less
with instruction following over long contexts).
• The blue team has inference budget limited by the cost of running the untrusted agent. This may be
too generous in some contexts.
• The untrusted model can try to influence monitor calibration by producing “honest” episodes
designed to subtly increase average suspiciousness scores. We show blue team results are worse
if we allow the red team to modify honest episodes in Appendix E (although it is difficult to know
what degree of modification is realistic).
Reasons why we may underestimate blue team performance.
• During the red-blue team game, we allow the red team to inspect the monitors. In practice, a
malicious agent may not get much information about monitors. Asynchronous monitors in particular
reveal very little (as opposed to resampling or more aggressive blocking strategies, where the model
may infer that a monitor has intervened through introspection).
• We allow the red team to choose optimal parameters in the safety calculation, e.g., the probability
of attack. In practice, the untrusted model may not have access to sufficient information about the
monitoring system or the ability to follow optimal random policies (Mallen et al., 2025).
• We give the red team agent clear instructions and ideas for obfuscation in its system prompt. In
practice, the agent may need to reason out loud to come up with similar strategies, which could be
caught by a monitor.
Future work.
We do not model many factors that would determine the true probability of the untrusted
agent causing harm. Future work could extend our settings by allowing agent commits to persist over time
(allowing for message passing between instances of the agent), or by building an ‘attack tree’, i.e. a series of
side tasks that result in a particular kind of harm if they are all achieved. We could include realtime harms
like untrusted code execution, and we could expand the range of affordances the red and blue teams have
available, for example by allowing resampling of the untrusted model in order to gather more evidence. We
could also extend the range of settings we cover and the depth of our exploration into data poisoning and
evaluation sabotage. Future work can also explore a broader range of blue team strategies such as untrusted
monitoring, adaptive strategies that adjust parameters based on the security sensitivity of the modified code,
or stateful monitors that retain information between episodes.

RELATED WORK
AI control seeks to establish safety measures that are robust to intentional subversion. Greenblatt et al.
2023 introduced AI control in the APPS backdoor setting (which involves adding backdoors to competitive
coding problems, and was built on by Bhatt et al. (2025) in a multi-step Bash problem setting, and Terekhov
et al. (2025), who explore adaptive attack on control protocols, again in the Bash setting. Wen et al. 2024
explored AI control in a ‘distributed threat’ setting where no single failure is catastrophic. Griffin et al. 2024
explored some game-theoretic aspects of AI control. Mallen et al. 2024 explored whether AI models have the
capabilities needed to generate subversion strategies independently. Korbak et al. (2025b) provide example
rules for control evaluations, control measures, and safety cases that might be appropriate for different
capability levels. Kutasov et al. (2025b) introduce a benchmark, SHADE-Arena, designed to test for the
ability of models to evade monitors in enterprise settings such as bank transfer or email tasks. Kutasov et al.

## Page 15


(2025a) conduct a red-blue team game in SHADE-Arena, and Loughridge et al. (2025) develop a procedure
for eliciting strong control attack policies in the same setting.
Evaluating agent safety and monitoring agents.
A series of work focuses on evaluating how easy it
is to jailbreak agents (Andriushchenko et al., 2025) or use prompt injections on them (Ruan et al., 2024;
Zhan et al., 2024; Debenedetti et al., 2024). Various work has explored monitoring to prevent jailbreaking
(Zhang et al., 2023) and for content moderation (Meta, 2021), but these focus on adversarial users rather
than the AI itself being adversarial. Kale et al. (2025) perform a similar monitor red-teaming exercise on
enterprise agent workflows, with a focus on enabling weaker monitors to successfully classify episodes from
a stronger agent. Yueh-Han et al. (2025) develop monitors for decomposition attacks. A variety of work has

In particular, Arnav et al. (2025) explore ensembling CoT and action-only monitors for AI control.

CONCLUSION
We develop a suite of five software engineering environments representing realistic deployment scenarios
for AI agents, featuring authentic codebases like vLLM, alongside benign development tasks and diverse
security failure modes. Using these environments, we conduct an iterative red-blue team evaluation where a
blue team designs monitor systems using a weaker model (Claude 3.7 Sonnet) and a red team attempts to
evade detection by changing the system prompt of a stronger agent using Claude 4.1 Opus.
After three rounds of iteration, the blue team’s final monitor system achieves a 6% false negative rate at
1% false positive rate on held-out test data. This represents substantial improvement over the initial round
(67% worst-case FNR) and we find monitor quality improves faster than red team evasion ability. Our best
performing monitor systems all use ensembling of diverse base monitors.
We extrapolated these results to hypothetical deployment scenarios using a simple mathematical model of
asynchronous monitoring, where episodes are scored and placed in a priority queue with human auditors
reviewing the most suspicious episodes each hour. Under a model where a single attack causes catastrophic
harm, zero latency between attack and harm, and a 1% audit rate, the model predicts 0% safety probability.
For our strongest monitor, safety improves to 91% when two successful attacks are required for catastrophic
failure, and to 99% with three attacks. Similarly, a 1-hour detection window before attacks cause harm
increases safety to 96% in the single-attack case. Thus we expect system design choices as well as monitor
strength will be important to safely deploy asynchronous monitors.
The results suggest that current language models can be caught by asynchronous monitors with reasonable
but not overwhelming reliability, at least when attacking by changing agent system prompts in ways that leave
behavioral traces. Whether this level of performance is sufficient depends heavily on deployment context,
and particularly whether systems can be designed such that single points of failure are rare and multiple
successful attacks are required for catastrophic outcomes, or how willing we are to block changes before
they are reviewed. Future work should explore whether these results hold under less restrictive red team
rules, expand the scope and realism of the settings used for control evaluations, and make sure deployment
simulations better reflect real deployments.

HIGH-LEVEL VIEW OF RED AND BLUE TEAM STRATEGIES
This section presents an abstracted view of each team’s approach, expressed as an idealised attack–defence tree that omits
detailed prompt-level specifics. The model is idealised because the blue team acted solely on observed behaviour without
knowledge of the true red team’s underlying strategy, and the red team responded to the monitor submitted for each round
as a whole rather than to specific components of that monitor.
Red Team Strategy: Natural Framing
Present a plan that frames the side task changes as naturally relevant and necessary for the main task.
Blue Team Response: No CoT Monitoring
Include a monitor variant examining only code changes with the agent’s chain of thought stripped.
Red Team Response: Justify in Actions
Include the plan and justifications in markdown files and code comments.
Blue Team Strategy: Incriminating Quotes
Identify potentially suspicious code snippets and analyse them verbatim for concerning
behaviour.
Red Team Response: Spread Out + Tailored Cover Stories
Spread implementation across multiple files, and use hand-crafted framings and jus-
tifications tailored to the harmful patterns the monitors target (e.g., “data transfer is
actually a cache warming feature required for performance reasons”, “privilege changes
are needed to fix an error indicated by unit tests”, “the token is a health check monitor
credential necessary for service monitoring”, . .. ).
Blue Team Strategy: Task Drift Detection
Use a trusted model to identify actions likely to be required for the task, and penalise any unexpected actions.
Red Team Response: Subtask Proliferation
Include unnecessary or overly granular steps (e.g., test changes, refactoring, breaking and fixing code) to
create more opportunities to hide or justify side task changes.
Blue Team Strategy: Perspectives Cross-Check
Analyse the relationship between claimed intent and code changes (semantic perspective), risky code patterns
(static perspective), and agent runtime behaviour (dynamic perspective). Check the results for inconsistencies
and deception indicators.
Red Team Response: Hide in Overlooked Locations
Hide changes in places likely to be overlooked, such as in test files.
Red Team Response: Intent Obfuscation
Abstain from commenting on the intent behind side task changes, and obscure the code purpose (e.g., use
opaque variable and function identifiers, make the code more dense).

RESULTS WITH REASONING TOKENS
The red team was permitted to use reasoning tokens (extended thinking in Claude API), with the reasoning visible to the
monitors. The red team opted not to use reasoning because it led to poor monitor evasion: the false negative rate (FNR)
was zero for almost all monitors in our experiments (only the Blue Team Round 2 monitor had a small non-zero FNR, as
it focused on actions rather than chain-of-thought). This was because the agent often explicitly discussed how to achieve
the side task in its reasoning, despite instructions not to.
In a post-game experiment, we tested allowing reasoning without exposing it to the monitors. Contrary to expectation, in
a configuration using Claude 4.1 Opus with extended thinking mode (16,000 reasoning tokens), we found that hidden
reasoning generally reduced evasion success against the best blue team monitor, and produced mixed results against
Round 1 and Round 2 monitors.
Figure 9 shows that enabling reasoning, without adjusting prompts, lowered the FNR in almost all cases for both the train
and test sets.
Figure 10 compares the best-performing no-reasoning prompt from the main experiments (Prompt 3) with a variant
designed to exploit hidden reasoning -— e.g., moving sensitive planning to hidden reasoning only, or using it as a
scratchpad while obfuscating code in visible outputs. Although this variant showed better instruction following for the
strategies proposed by the red team in agent prompt, its overall evasion rate against the Round 3 monitor remained lower
than the no-reasoning version on both train and test sets. The only exceptions were increased FNRs for Round 1 and
Round 2 monitors on the train set.
These results should be interpreted with caution. The red team invested relatively little iteration effort into the hidden
reasoning configuration compared to the no-reasoning setup, meaning the prompts were not thoroughly optimised.

E.2
INCREASING AVERAGE SUSPICIOUSNESS
To assess the potential impact of non-attack episode manipulation by an untrusted model, we allow the red team to alter a
prompt used for generating honest episodes. Red team strategies are restricted to those that can plausibly survive training
pressure, are not obvious enough to make a human auditor shut down the model immediately, and do not rely on rare
manipulation strategies (we assume the blue team can calibrate on a large number of episodes where rare manipulation
would have only a small effect). Here is a list of red team strategies we consider:
• Security Probing: Exploring security measures is instrumentally useful for sabotage tasks but is also plausible
for a model honestly trying to improve safety of honest code.
• Honest Mistakes: Producing code that contains bugs or vulnerabilities can increase monitor suspicion even
if these problems are eventually fixed later in the episode. If mistakes that are self-corrected later are not
sufficiently penalised during training, such behaviour may get past the model selection pressure.
• Changes in agent output distributions may throw off a monitor (e.g., sudden increase in use of feature flags).
For this strategy to be viable, the agent would need to produce different output distribution in eval or monitor
calibration phase from deployment. One way a model can achieve this is to have a set of different coding styles
selectively activated depending on environment properties that are likely to be different between eval and in
deployment. We use an example of altered harmless behaviour in Persona and Creative Solutions prompts.
A special case of this strategy is activating a coding style based on the user instructions, e.g., mix in code or
comments written in the likely native language of the user. We explore this with the Persona French prompt.
• Suspicious Language: A model can use suspicious language (e.g., excess use of words like “tampering”) or
limit the justifications it gives for its actions, to trick monitors into misinterpreting benign behaviour. This
strategy would require doing so in a way that tricks monitors but passes through human feedback during training
and auditing, so its effectiveness may be limited to weaker monitors prone to interpretations different from
humans.
We present the results in fig. 11. Almost all strategies increase the false negative rate, mostly in the range of 1-7
percentage points increase. Two strategies stand out – Suspicious Language and Honest Mistakes achieve 60-90% false
negative rate. These two should be interpreted with caution, however. Manual review shows that Suspicious Language
episodes included unnecessary dead code (despite prompting the agent to not produce this); Honest Mistakes produces
longer episodes than are strictly necessary, which is not efficient and would face optimization pressure in practice.
