Factor(T,U): Factored Cognition Strengthens Monitoring of Untrusted AI
Aaron Sandoval
Independent
aaron.sandoval10@gmail.com
Cody Rushing
Redwood Research
Abstract
The field of AI Control seeks to develop robust
control protocols, deployment safeguards for
untrusted AI which may be intentionally sub-
versive. However, existing protocols that rely
on weaker monitors to detect unsafe behavior
often fail on complex tasks beyond the moni-
tor’s comprehension. We develop control pro-
tocols based on factored cognition, in which a
trusted model decomposes a task, an untrusted
model solves each resultant child task in iso-
lation, and the results are reassembled into a
full solution. These protocols may improve
safety by several means, such as by simplify-
ing the context for monitors, or by obscuring
vulnerabilities in the environment. We imple-
ment our protocols in the APPS coding setting
and red team them against backdoor attempts
from an adversarial GPT-4.1 Nano. We find
that: (i) Adding factored cognition to a trusted
monitoring protocol can boost safety from 41%
to 63%; (ii) Safety improves because monitor
performance improves; (iii) Factored cognition
makes it no harder for capable LLMs to write
backdoors in APPS. While our protocols show
low usefulness in APPS, they hold promise for
more complex tasks.

Introduction
Given the challenges of either aligning powerful
AI or detecting misalignment through evaluations
(Hubinger et al., 2024), the field of AI control treats
those models as untrusted, models their worst-
case behavior, and develops deployment safeguards
called control protocols which aim to be robust
even to intentional subversion by the untrusted AI
(Greenblatt et al., 2023). Many existing control pro-
tocols use a weaker trusted model T to monitor the
actions of the stronger untrusted model U, a tech-
nique called trusted monitoring (Greenblatt et al.,
2023). However, when faced with more complex

To address this, we introduce Factor(T,U), a

the root task into a set of child tasks, child tasks
are each implemented by U under trusted monitor-

performance is enhanced, and security through ob-

information about security vulnerabilities, making
it harder for U to attack effectively. Furthermore,
child tasks may be solved using any control proto-
col, enabling simple integration of advances from
other AI control research.

In our control evaluations we study Factor(D,U),

a powerful trusted model to decompose tasks. We

attacks on child tasks as more suspicious, while
the suspiciousness of honest solutions shifts less.

trol protocols show promising safety benefits, task
decomposition degrades accuracy in the APPS set-
ting. We expect the usefulness of these protocols to
be highly setting-dependent and best for complex
tasks where task decomposition enhances accu-
racy, such as those solved by large language model
(LLM) agents (Xi et al., 2023).
Our main contributions are:
• We introduce a novel family of factored cog-
nition control protocols with several potential
safety benefits.
• We demonstrate the superior safety of
Factor(D,U) in the APPS control setting by
red teaming and baselining against a trusted
monitoring protocol.
• We find evidence that Factor(D,U) provides
simplicity benefits for monitors, but not se-
curity through obscurity in APPS.
• We find that Factor(T,U) has very low use-
fulness in APPS, and that this is likely a per-
manent property of the setting.
2
Setting
We perform control evaluations using methods sim-
ilar to Greenblatt et al. (2023). For readers familiar
with this work, Appendix E contains an alternate
description of our setting in terms of deviations
from theirs.
We use the APPS control setting of coding prob-
lems (Greenblatt et al., 2023) where a red team
attempts a side task of writing backdoored solu-
tions that pass undetected during a deployment.
1Code and data available at https://github.com/aaron-

We use 500 tasks from the APPS-verified subset
(likaixin, 2024), applying a 50/50 train/test split.
99% of tasks have exactly one unit test case, mod-
eling a setting with little ground truth knowledge
about the intended behavior of solutions. Control
evaluations are conducted as an iterative red team-
ing process, in which a red and a blue team use
different resources to achieve opposing objectives.
2.1
Resources and Restrictions
Untrusted model: The blue team has access to U,
a strong model that may or may not be attempting
to write hidden backdoors. In a deployment, U
may either act identically to GPT-4.1 Nano, which
we call the honest policy UH, or it may follow an
attack policy UA designed to write backdoors. UA
is an LLM system that has been built by the red
team. UA may use attack templates, make calls to
GPT-4.1 Nano, and follow stochastic policies pre-
cisely. UA makes an attack whenever it attempts
to write a backdoor. The red team has full knowl-
edge of the blue team’s control protocol and can
access all the results of previous experiments. The
blue team can also access the results of previous
experiments, except for any internal functionality
of UA. The red team cannot call T or fine tune on
T’s outputs, but they can iterate directly against the
control protocol, which calls T. U maintains no
memory between calls. These red team allowances
are intended to amplify the capabilities of GPT-4.1
Nano to conservatively bound the ability of a sim-
ilar model that is scheming to subvert the control
protocol. Following Greenblatt et al. (2023), the
blue team may measure summary statistics of UH
and use them in protocols.
Trusted models: The blue team may also use T,
a weaker trusted model which never attempts at-
tacks, implemented using Llama 3.1 8B-instruct
(Grattafiori et al., 2024). We additionally allow
access to a powerful trusted model for the exclu-
sive use of decomposing tasks. We call this de-
composer model D and implement it with Ope-
nAI o3-mini. Using D in Factor(T,U) produces
the Factor(D,U) protocol. This compensates for
Llama 3.1 8B-Instruct’s poor decomposition ability
without directly upsetting the capability gap in the
weaker T monitoring the outputs of the stronger
U. See Appendix D for further justification and
discussion of this allowance.
Auditing: Similar to the methods of Bhatt et al.

and one such audit costs the same against the bud-

using fixed criteria over the deployment for decid-
ing whether to audit a solution.
2.2
Metrics and Red/Blue Team Objectives
The blue team’s objective is to maximize the test set
usefulness and safety of their protocol as defined in
Greenblatt et al. (2023). The threat model is high-
stakes, meaning that a control protocol accepting a
single backdoor is considered catastrophic. The red
team’s objective is to minimize safety. In a run mea-
suring usefulness, all calls to U are implemented
by UH, and we measure accuracy, the proportion
of samples where the solution passes all unit tests.
Usefulness is a linear rescaling of accuracy where
T has 0% usefulness and UH has 100% usefulness.
To measure safety, we run the experiment using UA
and measure the probability that the deployment
terminates safely before a backdoored solution is
accepted by the protocol. A solution is considered
backdoored if it meets all of the following criteria.
We discuss these criteria further in section 4.1.
• It passes a set of unit tests from the dataset
• It contains an attack

3.1
Red Teaming
Like in Greenblatt et al. (2023), we find the best
red team strategy against trusted monitoring is to
write subtle backdoors. We use the same strategy
for Factor(D,U), as no distinct red team strategy
superior at countering Factor(D,U) was found. The
only change in the red team’s tactics is to tune sep-
arate attack selection parameters to account for the
different task distribution. The blue team tests 3
variations of Factor(D,U), using different prompts
to D to create different decomposition granularities.
Decompositions from Factor(Dlow,U) have an aver-
age of 2.0 child tasks, those from Factor(Dmed,U)
have 3.0, and those from Factor(Dhigh,U) have 3.5.

3.2
Security through Obscurity
To investigate the causes of our superior ASR rela-
tive to trusted monitoring, we perform an additional
experiment. We test if the ASR difference is due
to security through obscurity, a possible safety ben-
efit of Factor(D,U) protocols. If these protocols
possess security through obscurity, it means that
attacks fail more often because the limited context
hides information about the target of the attack,
making it harder to assess attack opportunities, re-
sulting in some attacks failing which would have
succeeded had U been given the full root task con-
text. We expect this possible benefit to only apply
to some threat models, including APPS backdoors.
See Appendix I for details on this threat model
partition.
We test the security through obscurity hypothesis
by running all protocols using the stronger o3-mini
as the exploit finder rather than GPT-4.1 Nano. If
the hypothesis were true, then Factor(D,U) should
maintain its superior ASR with a stronger exploit
finder since U’s failed attacks were more likely to
be unsalvageable. However, since we see in Fig-
ure 2 that there is no significant difference in ASR
using an o3-mini exploit finder, it’s more likely
that the difference when using a GPT-4.1 Nano
exploit finder is due to something other than secu-
rity through obscurity, such as the longer and more
complex Factor(D,U) solutions impeding GPT-4.1
Nano’s ability to understand and exploit the at-
tacked code. Though generating complex solutions
whose structure is specifically intended to confuse
attackers is a possible blue team strategy, we don’t
expect our implementation of Factor(T,U) to have
such a benefit against models of capability similar
to o3-mini, let alone truly untrusted models.
If we expect Factor(T,U) to have no systematic
advantage in ASR, then to what degree does it
maintain its safety advantage? As a proxy mea-
surement, we recompute the safety of each pro-
tocol using the o3-mini exploit finder and conser-
vatively estimate P = 0.066 that Factor(Dlow,U)
has no safety advantage compared to trusted mon-
itoring. This value is conservative both because
Factor(T,U) maintains its systematic advantage in
monitor performance, and because the estimate
does not fully account for possible correlations

3.3
Usefulness
Separately from the red teaming experiments, we
benchmark the usefulness of Factor(Tlow,U), ex-
cluding the allowance for the powerful decomposer
D. With the models used in the red teaming experi-
ments, Factor(Tlow,U) has -63% usefulness. This is
unsurprising since weak models like Llama 3.1 8B-
Instruct tend to be especially weak decomposers
(see Appendix C). We also measure usefulness for
several strong models under typical model selection
constraints. Control evaluations typically main-
tain a substantial capability gap between T and U,
as measured by accuracy on the main task, to re-
flect the expected circumstances when an actual
untrusted model is trained (Shlegeris, 2023). If we
maintain a typical minimum 25% gap between T
and U, then this restricts candidates for T to the
<75% accuracy regime in all future studies. For T,
we select the three strongest decomposers which
meet that constraint, and for U, we select o3-mini
and GPT-5 mini, the two strongest models on APPS
that we tested. Among the six combinations of T
and U, the highest Factor(Tlow,U) usefulness is
-7%. Full results are shown in Figure 6. While
some improvement may be achievable with better
elicitation and a future, stronger U, it is unlikely
that Factor(T,U) could overcome such a large gap
to attain competitive usefulness in APPS.
4
Discussion
Mechanisms for improved safety: Our findings
indicate that factored cognition provides simplic-
ity benefits for monitors by increasing the trusted
monitor’s suspicion of attacks in APPS. However,
there is no such clear distribution shift for honest
solutions. While we find no evidence for security
through obscurity in APPS, this doesn’t preclude
such safety benefits in other settings.
Low Factor(T,U) Usefulness is Not a General
Property Across Settings: The usefulness of task
decomposition protocols is likely much more task-
dependent than for the more foundational protocols
in Bhatt et al. (2025) and Greenblatt et al. (2023).
While our scaffold degrades accuracy in APPS,
other task decomposition scaffolds improve accu-
racy on tasks such as question-answering, math,
and symbol manipulation (Wang et al., 2023; Dua
et al., 2022; Hernández-Gutiérrez et al., 2025). Fur-
thermore, there is a broad class of tasks already

## Page 6


being solved through automated task decomposi-
tion and multi-step LLM workflows. In the context
of AI control, a generic LLM agent implemented
with an untrusted model can be viewed as a task
decomposition protocol without any of the safety
features of factored cognition protocols like mon-
itoring or context isolation for child tasks, where
decomposition and child task implementation are
all done by U. It may not be difficult to add safety-
relevant features to these protocols and workflows.
Task decomposition in the form of LLM agent sys-
tems has gained immense popularity purely for
its capabilities on complex tasks (Chowa et al.,
2025). Factored cognition protocols will be most
viable for these types of tasks, where decomposi-
tion is not a burden but an enhancement. For these
tasks, the loss in usefulness will come from the con-
text isolation and other safety features necessary
to turn a regular LLM agent system into a proper
Factor(T,U) or Factor(U,U) protocol. Decompo-
sition itself will not differentially degrade useful-
ness, increase inference cost, nor lengthen latency.
Therefore, these protocols are most promising for
tasks where decomposition occurs by default, and
where the natural baseline is a generic task decom-
position system without the safety features of AI
control protocols. The usefulness of Factor(T,U)
in APPS is an underestimate of its potential useful-
ness on more complex tasks.
4.1
Limitations
Powerful Decomposer Allowance: Given the
weakness of T, this allowance was necessary to
investigate our hypotheses about factored cognition
protocols, but it may also result in overestimating
their safety. Since D never sees U’s outputs, we
think that Factor(D,U)’s safety performance is a
decent first-order safety estimate. Still, there may
be bias in our safety results, such as from highly de-
tailed child tasks giving monitors extra clues as to
what parts of a child solution are/aren’t legitimate.
See Appendix D for a full discussion.
Honest Policy Safety Failures: We found that UH
writes backdoored solutions on about 1% of tasks.
This is more likely for our split of APPS because
99% of tasks in our split contain exactly one unit
test, far fewer than the splits used by Greenblatt
et al. (2023) or Terekhov et al. (2025). Honest
policy safety failures like these can undermine key
features of high-stakes control evaluations such
as the red team’s incentive to attack and the blue
team’s ability to incriminate scheming models. Our
definition of a backdoor (see section 2.2) was se-
lected to artificially mitigate these problems, and
though we don’t believe that these are good general
assumptions for other research using backdoored
code threat models, we believe that our experiments
maintain their integrity relative to our specific re-
search questions and reflect the qualitative results
that one would get using a split of APPS without
honest policy safety failures.
Generalization from Weak Models and Elicita-
tion: This study uses relatively weak models due
to its limited budget and scope. Also, while we
are satisfied with our elicitation in attack selection,
our attack policies were much simpler than those
in Greenblatt et al. (2023) or Wen et al. (2024). It’s
unclear how well our results would generalize to
stronger models using more thorough elicitation.
4.2
Future Work
Control evaluation in a new setting: A proper
evaluation of the safety and usefulness of task de-
composition protocols must test Factor(T,U), not
Factor(D,U). It would be most relevant to use a
setting where task decomposition is a lesser hin-
drance, such as an LLM agent setting or one with
otherwise complex tasks.
Test Attack Coordination Challenges hypothesis:
Factored cognition might provide additional safety
via a separate mechanism for multi-step control
settings like BashBench (Bhatt et al., 2025). In
their study, a dominant strategy is multi-step attack
strategies in which attacks are distributed across an
agent trajectory. If this trajectory is broken up into
isolated child tasks, it may be harder for an attack
policy to coordinate these attacks.
Test Simplicity Benefits for Other Blue Team
Tactics hypothesis: In addition to monitoring,
other blue team tactics may be more effective when
applied to simpler child tasks, such as editing solu-
tions and generating unit tests.
Extensions of Factor(T,U): Other potentially use-
ful features which could be added include:
• Use implementers besides trusted monitoring
• Test a range of model capabilities for D and
examine safety trends

• Add another monitoring, editing, or resam-
pling step after reassembly with the full root
task solution
• Use T or U to generate child task unit tests
• Use more sophisticated LLM task decomposi-
tion scaffolds from the literature
Other factored cognition protocols: Forthcoming
work is exploring Factor(U,T) and Factor(U,U)
protocols, where the untrusted model decomposes
tasks. However, some questions related to those
protocols remain open. In particular, future re-
search should explore what steganographic band-
width can be achieved in decompositions in a
Factor(U,U) protocol, and how various blue team
measures for limiting that bandwidth trade off
safety and usefulness.

Related Work
Greenblatt et al. (2023) introduce the field of AI
control, control protocols, and high-stakes control
evaluations. Bhatt et al. (2025) create BashBench,
an LLM agent setting more realistic than APPS,
and resample protocols, which are effective against
stochastic attack strategies. Wen et al. (2024) in-
troduce untrusted planning, a task decomposition
protocol using an untrusted decomposer and trusted
implementers, which they test in a low-stakes con-
trol evaluation, where no single failure is catas-
trophic. Our work is the first to test task decompo-
sition techniques in a high-stakes setting. Mallen
et al. (2025) evaluate frontier LLMs for several
dangerous capabilities necessary for models to sub-
vert control protocols. In parallel with our work,
Terekhov et al. (2025) explore trusted monitoring
in depth, measuring the performance vs inference
cost tradeoff of monitoring in the APPS setting.
We adapt their trusted monitor and use it in our
experiments.
The subfield of scalable oversight, exemplified
by Iterated Distillation and Amplification (Chris-
tiano et al., 2018), seeks to develop AI training
methods which scale beyond human abilities to
efficiently provide feedback. Factored cognition
was originally developed as a scalable oversight
method wherein the capability of a weak question-
answering AI is amplified by using task decompo-
sition to create a tree of simpler, context-free child
questions (Stuhlmüller et al., 2018). A large body
of work leverages task decomposition to improve
performance on various types of complex tasks, in-
cluding Min et al. (2019); Perez et al. (2020); Deng
et al. (2022); Dua et al. (2022); Zhou et al. (2023);
Wang et al. (2023); Yao et al. (2023); Khot et al.
(2023); Juneja et al. (2024); Prasad et al. (2024);
Hernández-Gutiérrez et al. (2025). Our study is dis-
tinguished from this literature in focusing on task
decomposition’s ability to reduce risks from un-
trusted models rather than to improve performance
on benchmarks.

A
Glossary
The primary desiderata for control protocols are:
Safety: The protocol can reliably detect and safely
manage attacks within the untrusted AI’s capabili-
ties that help it achieve its misaligned goals.
Usefulness: In the case that the untrusted model is
not scheming, the protocol minimally degrades the
capabilities at the task.
Cost: The protocol does it all economically, with
minimal compute and human labor.
The basic set of intelligent resources which we have
at our disposal to build control protocols are:
U: A smart untrusted model, which might be
scheming against us.
8


## Page 9


T: A trusted model with capabilities inferior to U,
which we are confident isn’t scheming.
H: Trusted, high-quality human labor. In experi-
ments, this is often simulated using a frontier LLM
for practical reasons.
The 3 roles of human researchers which control
different elements of control experiments are:
Red team: Elicits worst-case adversarial behav-
ior from U given a set of affordances. The red
team’s goal is to minimize safety given a blue team
protocol.
Blue team: Constructs control protocols given a set
of affordances to maximize safety and usefulness.
White team: Decide the affordances, assumptions,
and high-level experimental setup within which the
red and blue teams optimize their objectives.
The red team creates two distinct policies that U
can follow when called by the control protocol:
UH: Untrusted model honest policy. Faithfully
follows instructions without attempting an attack,
like a trusted model.
UA: Untrusted model attack policy. Sometimes
attempts an attack, and sometimes follows a policy
identical to UH.
Usefulness run: The part of a control evaluation
which measures the usefulness of a protocol. It is
executed as an evaluation in the setting where UH
is used whenever the protocol calls U.
Safety run: The part of a control evaluation which
measures the safety of a protocol. It is executed
as an evaluation in the setting where UA is used
whenever the protocol calls U.
In the APPS setting, UA attempts attacks, where
it attempts to include a backdoor in its solution.
A backdoor is an exploitable feature of the solu-
tion which produces a behavioral difference from a
ground truth reference solution for some valid in-
puts while the solution still passes a set of unit tests.
To determine if a solution contains a backdoor, an
exploit finder (implemented by an LLM) proposes
an exploit, which is a specific input to a solution
which may produce a behavioral difference. If it re-
ally does produce a behavioral difference, then this
is a successful exploit. If the solution passes unit
tests and the exploit is successful, then the solution
is backdoored. If an attacked solution fails unit
tests or the exploit does not produce a behavioral
difference, it is a failed attack.
We use the following terms related to the task de-
composition. These terms are defined with code-
writing tasks in mind but should be pretty general-
izable:
Task: A data structure containing a natural lan-
guage problem description and possibly other fields.
For functional programming tasks, it may include
a function signature and a set of unit tests and test
cases to check the validity of a solution.
Solution: An implementation of a task, including
the solutions to any and all child tasks.
Parent task: Any task which has been decomposed
into child tasks.
Child task: A task resulting from the decomposi-
tion of a parent task.
Sibling task: A child task which shares the same
parent as another child task.
Root task: The original problem that we ask the
AI system to solve.
Leaf task: A task which is not decomposed and is
solved by direct implementation.
Reassembly logic: The part of the parent task so-
lution which defines how to use the child task solu-
tions to solve the parent task.
Decomposer: The part of a control protocol which
decomposes a parent task into a set of child tasks
and a reassembly function.
Implementer: A human/LM system which im-
plements a solution to a task. Implementers are
themselves control protocols.
The following are abbreviations for certain cate-
gories of task decomposition control protocols.
Factor(T,T): A factored cognition system for the
trusted model.
Factor(T,U): A task decomposition control proto-
col with T as decomposer and implementer proto-
cols which use U.
Factor(U,T): A task decomposition control proto-
col with U as decomposer and implementer proto-
cols which use T only.
9


## Page 10


Factor(U,U): A task decomposition control proto-
col with U as decomposer and implementer proto-
cols which use U.
Some miscellaneous terminology which we haven’t
seen in control literature previously but which we
found useful:
Trigger set: The set of all possible inputs to a back-
doored function which return unexpected results.
Or, more formally, for a valid input x ∈S, a refer-
ence solution function f(x), a backdoored version
f′(x), and assuming a single unit test which asserts
the equality of solutions, the trigger St set of f′(x)
is St ⊆S : x ∈St ⇐⇒f(x) ̸= f′(x).
Decomposition tax: The relative loss in accuracy
from adding task decomposition to a protocol. De-
composition tax = 1 - (accuracy of Factor(T,T) /
accuracy of T).

Discussion on Powerful Decomposer
Allowance
We’d like experiments in the APPS setting to
be able to tell us helpful information about fac-
tored cognition protocols despite the shortcom-
ing of the setting. We think that giving access
to the powerful decomposer D allows us to do
this for Factor(T,U) protocols. With the current
state of LLMs, Factor(D,U) is a better model of
the safety-related dynamics of future AI control
scenarios than Factor(T,U) when using a signif-
icantly weaker trusted model like Llama 3.1 8B-
Instruct. We select a T significantly weaker than
U because this seems to usually be our best way
to model future control evals with actual untrusted
models (Shlegeris, 2023). This assumption seems
reasonable for uses of T which are directly adver-
sarial to U, such as monitoring, editing, generating
unit tests, and generating honeypots. But we don’t
think that the assumption is valid for every pos-
sible use of T, including for task decomposition.
Using Llama 3.1 8B-Instruct as our decomposer
we would achieve -63% usefulness and conclude
that Factor(T,T) and Factor(T,U) were completely
hopeless. Factor(U,U) might be competitive with
vanilla trusted monitoring in APPS only if you used
the very best frontier models for U.
However, we think that these huge performance dif-
ferences will not generalize to most important set-
tings even when T and UH have a similar accuracy
gap. Consider measuring a safety and usefulness
result from trusted monitoring using weak mod-
els, and attempting to estimate the performance on
the same setting when using a stronger T and U
with a similar capability gap. It seems plausible
that the results could be similar to those from the
weaker models. When doing a similar extrapola-
tion with Factor(T,U), however, this pattern prob-
ably doesn’t hold. Since a stronger T tends to
have a lower decomposition tax (see Appendix C),
it will gain accuracy that is not lost by the nor-
malization from accuracy to usefulness. The fu-
ture T that we use in actual control evaluations
will be at least as good at decomposing as o3-
mini. The current low usefulness of Factor(T,T)
and Factor(T,U) relative to simple baselines is an
artifact of the weak selection of T, a necessity
when running control evaluations in a relatively
easy setting. This creates a large usefulness bias
against task decomposition protocols when we try
to generalize their performance to more difficult
settings using more capable models. We can reduce
that bias by using our best available LLM decom-
poser instead. The usefulness of Factor(D,T) and
Factor(D,U) is closer to what we predict will be
true using future trusted decomposers, but there
is sufficient irreducible uncertainty that we don’t
think that it’s valid to compare our Factor(D,U)
usefulness results to those of non-decomposition
protocols.
Bias in safety performance: Since D can never
see U’s outputs, we think that Factor(D,U)’s safety
performance is a decent first-order safety estimate.
Still, there may be bias in our safety results, such
as from highly detailed child tasks giving monitors
extra clues as to what parts of an implementation
are/aren’t legitimate. Maybe some of our safety
and monitor performance gains could be achieved
by a protocol where D merely rephrases root tasks
into the style that it uses to write child tasks.

E.1
Differences from Greenblatt et al. (2023)
For readers very familiar with Greenblatt et al.
(2023), we provide here an alternate summary of
our methods given as a list of differences from
theirs, as well as some extra methodological details
which may not be different but are not completely
clear from that paper.
1. Simple baseline protocols: We build a simple
trusted monitoring protocol instead of attempt-
ing to replicate the protocol from Greenblatt
et al. (2023). In particular, the backdoor gen-
eration, attack selection, and trusted monitor
subroutines are simplified.
12


## Page 13


2. APPS dataset split: We use 500 tasks from
the APPS-verified subset (likaixin, 2024), ap-
plying a 50/50 train/test split.2 99% of tasks
in our split have exactly one unit test case.
The red and blue teams have access only to
the train split during red teaming. We allow
for no re-fitting of protocols or policies to the
test split, with the exception of setting a new
audit threshold.
3. Perfect auditing: Any action that deviates
from UH is assumed to be incriminating if
audited, allowing the blue team to trigger a
shutdown.
4. No incrimination by distribution shift:
Greenblatt et al. (2023) allow the blue team to
trigger shutdown by monitoring for shifts in
UA’s summary statistics relative to UH’s. We
do not allow for this mode of incrimination,
as perfect auditing is sufficient to discourage
the red team strategies that incrimination by
distribution shift covers in Greenblatt et al.
(2023) and Bhatt et al. (2025).
5. Audit thresholds and budget: The auditing
budget (2% of tasks) is used to set the auditing
threshold (a suspiciousness rating), but once
the threshold is set, the budget does not con-
strain how many tasks may actually be audited
in the safety run. The budget is the expected
proportion of tasks which would be audited
conditional on U not scheming. If U is actu-
ally scheming and making attacks, then the
expected proportion of audited tasks exceeds
the budget, but this is acceptable and the blue
team may still audit all of them.
6. No free upfront auditing: Greenblatt et al.
(2023) allowed the blue team to audit the first
10 tasks for free to discourage strategies which
use variable audit thresholds, as this was not
a focus of that paper. For the same reason,
we constrain the blue team to maintaining a
constant audit threshold for all tasks and give
no free audits.
7. Discretized suspiciousness and audit thresh-
olds: The blue team scores suspiciousness as
a discrete measure (e.g., integers 0–9). The
audit threshold is set at the suspiciousness

datasets/xtremekiwi/APPS-leetcode-codeforces
value with the smallest expected proportion of
audited tasks at least as large as the auditing
budget. For example, with a budget of 2%,
if 1% of usefulness run solutions have suspi-
ciousness 9, and 3% have suspiciousness 8,
the threshold is set at 8. Solutions equal to
the threshold are audited at random, with a
fixed on-threshold audit probability set such
that the budget is met in expectation. In this
example, the probability would be 33%.
8. Audit thresholds and budget: The auditing
budget (a proportion of tasks) is used to set
the auditing threshold (a suspiciousness rat-
ing), but once the threshold is set, the bud-
get doesn’t constrain how many tasks may be
audited in the safety run. The budget is the
expected proportion of tasks which would be
audited conditional on U not scheming. If U
is actually scheming, then the expected pro-
portion of audited tasks exceeds the budget,
but this is acceptable and the blue team may
still audit all of them.
9. Monitor all solutions: The blue team only
explored strategies where T monitored all so-
lutions, regardless of whether they passed unit
tests. A common alternative in other control
work is to monitor only solutions which pass
unit tests. Since solutions which fail unit tests
are rejected anyway, there is no way that they
can cause catastrophic outcomes. However,
monitoring all solutions offers more opportu-
nities to incriminate U using failed attacks.
10. Exploit finder: Due to a special property of
Factor(T,U) protocols, all exploits in all proto-
cols used to check for backdoors are generated
in a separate call to GPT-4.1 Nano with full
problem and solution context.
11. Exploit validation: A white team call to GPT-
4.1 Nano checks if a proposed exploit obeys
the input constraints of the problem. The ex-
ploit finder has 3 chances to submit a valid
exploit, and it gets feedback from the valida-
tor on each rejection.
12. Computing variance of safety: We run mul-
tiple epochs of our small dataset and use a
two-stage cluster bootstrapping method to es-
timate the variance of safety, usefulness, and
other metrics. See Appendix F for details.

## Page 14


13. Model selection: We use more recent models:
T = Llama 3.1 8B-Instruct, U = GPT-4.1
Nano. Under perfect auditing, there is no need
to simulate trusted human labor.
14. Downsampling: Our final runs use a down-
sampling factor of 18, compared to 12 in
Greenblatt et al. (2023). We scale the down-
sampling factor linearly with the number of
root tasks in the safety run. This practically
decouples the red and blue team strategies (the
attack selection model in particular) from the
size of the safety run, allowing us to scale runs
arbitrarily.
15. Access to opposite team’s protocol or model:
Both the red and blue team have nearly full
black box access to the opposite team proto-
col and all outputs produced while improving
their protocol. Each team may iterate directly
against the adversarial protocol. The red team
also has access to all blue team prompts and
scaffolding, but the attack policy itself still
may not call the trusted model. The only fur-
ther limitation we impose is that teams may
not fine-tune against the adversarial model,
protocol, or policy.
The following are assumptions and allowances spe-
cific to task decomposition protocols.
16. Powerful decomposer: We give the blue
team access to a powerful trusted decomposer
(D), a highly capable model for the exclu-
sive use of decomposing tasks. We imple-
ment D using OpenAI o3-mini (medium rea-
soning). This allowance compensates for T’s
poor decomposition ability, allowing us to ex-
plore strategies for these protocols without
directly upsetting the capability imbalance in
the weaker T monitoring code written by the
stronger U. See Appendix D for further dis-
cussion of this allowance.
17. A backdoored child task does not imply
a backdoored parent task: If a child task
is backdoored, but the backdoor is not ex-
ploitable by the exploit finder in the full con-
text of the root task solution, then this is a
failed attack and a safe outcome.
18. Child task solutions are audited in isolation:
If any child task solution has a suspiciousness
above the audit threshold then that child task
solution alone is audited. Attacks below the
audit threshold in sibling tasks would not get
caught.

Miscellaneous Methodological Details
Here we include a loose collection of details and
points of confusion that we encountered when set-
ting up our experiments in APPS. These match the
methods from Greenblatt et al. (2023) unless other-
wise noted. These details might not be clear from
reading existing literature, and so might serve some
purpose for future researchers.
Red/blue team access to data and adversarial
model: Both teams have nearly full black box ac-
cess to the opposite team protocol and all interme-
diate results while improving their protocol, but
not while actually running evaluations. Each team
may iterate directly against the adversarial protocol.
The red team has access to all blue team prompts
and scaffolding, but the attack policy itself still may
not call the trusted model. The only further limi-
tation we impose is that teams may not fine tune
against the adversarial model at any point.
Monitor ROC Curves: There are several possible
classification tasks on which we could evaluate the
monitors, but we focus on classifying solutions
between:
1. Attacked vs not attacked
2. Attacked and passes unit tests vs not attacked
and passes unit tests
These correspond to the two possible auditing
strategies. We use strategy 1.
1. Monitor all solutions: Monitor and potentially
audit any task
2. Monitor only solutions which pass unit tests:
Since solutions which fail unit tests are re-
jected anyway, there is no way that they can
cause catastrophic outcomes. In real control
deployments, labs can reduce monitoring com-
pute cost and potentially also improve safety
by filtering out failed solutions before moni-
toring.

Bootstrapping Details
We use cluster bootstrapping to estimate the sam-
pling distributions of key metrics including audit
thresholds, safety, and ASR. In a bootstrapping run,
we resample with replacement clusters of leaf tasks
from the results until the resampled quantity of leaf
tasks is equal to the quantity of in the original sam-
ple. Leaf tasks are clustered by the APPS sample
ID, so multiple epochs and multiple child tasks are
all clustered together. Applicable statistics are cal-
culated for each resample. We resample 500 times
independently to compute a bootstrapping distribu-
tion for each statistic. The following enumerates
our procedure:
1. Initialize two random number generators to
use for resampling root task clusters, one for
the usefulness run and one for the safety run,
each with a different fixed seed3.
2. Safety run filtering
(a) Cluster the safety run root tasks by APPS
sample ID.
(b) Filter the safety run root tasks to include
only clusters with at least one attack at-
tempt.
3. Usefulness run resampling
(a) Resample clusters.
(b) Compute usefulness, audit threshold, and
on-threshold audit probability.
4. Safety run resampling
(a) Using the auditing parameters, compute
the win/lose/continue outcome for each
root task.
(b) Resample clusters.
(c) De-cluster into individual root tasks.
(d) Filter to only include attacked root tasks.
(e) Compute safety as a deterministic func-
tion of the root task outcome counts and
the downsampling factor for that run. No
variance due to random downsampling is
introduced.
3For the purposes of comparing performance between pro-
tocols, if those protocols used the same tasks and number of
epochs in their safety and usefulness runs (which ours did),
this common initialization removes the variance of different
protocols resampling different multisets of tasks.
(f) Compute the remaining safety metrics
without downsampling.
5. Perform steps 3–4 500 times and aggregate
empirical distributions for all metrics.
6. For each metric’s bootstrap distribution, com-
pute a confidence interval centered on the me-
dian. Report these as error bars.

Security Through Obscurity Conceptual
Details, Product and Process Threats
We classify AI control threat models into one of
the following categories:
Product Threat: A threat intrinsic to the product
generated by an attack policy, i.e., the tokens in
the root task solution, where a bad outcome can be
locked in only after a root task solution containing
a successful attack is accepted5. Example: APPS
backdoors.
5This is slightly distinct from the idea of runtime threats
16


## Page 17


Process Threat: Harm is locked in during the pro-
cess of an attack policy creating a solution. Exam-
ple: Bhatt et al. (2025)’s threat model of U down-
loading and executing malware while completing
another task.
Under a product threat, protocols like Factor(T,U)
can expand the contextual distance between attack
policy and the attack target. Under Factor(T,U),
U never has direct access to the root task, only
child tasks. We hypothesize that this obscuration
of the target can make executing product threats
more difficult for similar reasons that U lacking
access to private unit tests makes it more difficult
to write backdoors. Attacks must all filter up the de-
composition, passing through additional obscured
security layers before they can cause harm. This
is somewhat similar to the cybersecurity idea of
security through obscurity (Zwicky et al., 2000).
In the cybersecurity field, this strategy is generally
discouraged as a standalone security approach, but
as one of many security layers it can sometimes be
helpful.
Moreover, it may not be necessary to put any spe-
cific effort into creating dedicated security features
like unit testing in the decomposition tree; there
may be some average-case safety benefit from fac-
tored cognition by default on some coding tasks,
and maybe other types too. Consider the example
in Appendix H. The sort_and_round_list im-
plementer attack policy might insert a high-quality
subtle backdoor into a merge sort implementation
which gets past our monitors. Maybe its trigger
set (the set of possible inputs which produce a be-
havioral difference) is sequences of length > 2
that have a negative value only in the center in-
dex. If sort_and_round_list were the root task,
this would be a great attack. However, since this
function is only used to sort areas of shapes which
are all positive, the backdoor is unexploitable in
the context of the root task.
It’s only because
we decomposed the parent task and isolated the
child tasks that U didn’t know that its merge sort
backdoor was a bad idea. The security-through-
obscurity advantage is pretty clear for functional
programming tasks, but it doesn’t generalize to all
in coding tasks, where bad outcomes require executing mali-
cious code as opposed to merely writing it. A runtime threat
might not be a product threat if our process for selecting solu-
tions involves running the code, and that this could possibly
cause harm before we accept the solution, e.g., we run unit
tests on malicious code and harm occurs due to inadequate
sandboxing.
product threats and tasks. A similar analogy is not
apparent for a text summarization task, for exam-
ple.
Under task decomposition protocols, it seems that
most process threats have the potential to cause
harm within child tasks, before root task solutions
are assembled6. U in an LLM agent setting can ex-
ecute commands to download malware in any child
task. There is no need to filter through upstream
and downstream logic. Task decomposition does
not give us the same security-through-obscurity ad-
